| **결정자** | 프로젝트 소유자 |

| **명료화** | [ADR-0005](0005-pin-scoped-changes.md)의 "비교는 커밋 하나(첫 부모 → 그 커밋)"라는 전제: 변경 보기는 두 커밋 사이도 비교하고, 핀 단위 보기는 커밋 하나에만 남는다 |

## 맥락

변경 보기는 최근 12개 커밋 가운데 하나를 골라 그 커밋의 첫 부모와 비교했다. "지난 투고판부터 지금까지"처럼 여러 커밋에 걸친 누적 변경은 볼 수 없었고, 한 주만 지나도 그 시작 커밋이 목록에서 사라졌다. 커밋 고르기는 제목·날짜·해시를 한 줄에 자른 `<select>` 하나라 작성자도, 전후 관계도 보이지 않았다.

비교 PDF의 캐시 키와 상태 응답에는 이미 `base`·`head` 두 SHA가 있다. 그러나 HTTP API는 고른 커밋 하나만 받고, 읽을 수 있는 커밋을 최근 12개로 막아 임의의 Git 객체와 다른 문서의 이력을 보이지 않는다. [ADR-0005](0005-pin-scoped-changes.md)의 핀 단위 보기도 한 커밋의 줄 번호에 묶여 있다.

이 변경은 HTTP API에 선택 필드와 오류 코드를 더하므로 에이전트 계약의 HARD-GATE 대상이다([architecture.md](../handbook/architecture.md) §멈춤 신호).

## 결정

### 1. API — 선택 필드 `base` 하나

- `GET /api/revision-diff`, `POST`·`GET /api/revision-build`, `GET /api/revision-pdf`가 `commit` 옆에 선택 `base`를 받는다. `commit`은 비교의 새 쪽이고, `base`는 옛 쪽이다. 이름은 상태 응답에 이미 있는 `base`를 그대로 쓴다.
- `base`가 없는 요청은 0.4.18에서 성공하던 요청이면 같은 답(diff·상태·PDF 바이트)을 받는다. 빈 쿼리 `base=`는 없는 것과 같다. 본문의 `base`는 적으면 언제나 범위라, `null`·`""`는 `400 bad_commit`이다. `base` 없이 바뀐 것은 셋이다. 고를 수 있는 커밋이 넓어져 13–500번째 커밋의 거절(`404`)이 답으로 바뀌었다. 쪽 매개변수 없는 목록과 `close_ref`를 찾는 12개가 날짜 순서 대신 이력 창의 첫 12행(조상 관계 순서)이다. 목록 행에 필드가 더해졌다. 모두 더하기거나 거절이 답으로 바뀐 것이고, 표는 [api.md](../handbook/api.md) §두 커밋 사이에 있다.
- 범위의 소스 diff는 `base`(실제로 쓴 옛 쪽)·`merge_base`(병합 기준을 썼을 때만)·`commits`(범위의 이 문서 커밋 수)·`commit_ids`(그 커밋들, 최대 500개)·`files`(`[{path,old_path?,add,del}]`)를 더한다. 이름 바꾸기는 범위에서만 `-M`으로 짝짓는다. 단일 커밋 diff는 그대로 `--no-renames`다.
- `GET /api/revisions`의 행은 `author`·`time`(ISO 8601 커밋 시각)·`parents`(전체 SHA)를 더한다. 선택 `?before=<SHA>&limit=<1..50>`으로 쪽을 나누고, 쪽 답에는 `more`가 붙는다. 쪽 매개변수가 없으면 지금처럼 최근 12개, 두 키다.

### 2. 고를 수 있는 커밋 — 문서 이력 창 500개

- 요청이 이름 붙일 수 있는 커밋은 이 문서의 경로 한정 이력 가운데 최근 500개(`REVISION_HISTORY_MAX`)다. 이 창은 조상 관계 순서(`--topo-order`)의 한 목록이고, 목록·쪽 답·검증·`close_ref` 찾기·뷰어의 핀 커밋 고르기가 모두 이것을 읽는다. 순서나 집합이 둘이면 목록에 보인 커밋이 거절되거나 핀이 다른 커밋을 고른다(PR #204 리뷰). 서버는 이 창을 HEAD마다 한 번 읽는다. 뷰어는 30개씩 받는다. 임의 SHA는 받지 않는다.
- `base`는 이 창의 커밋이거나 창의 커밋의 첫 부모다. "이 커밋부터"는 그 커밋의 첫 부모를 `base`로 보내는데, 그 부모가 원고를 건드리지 않았으면 창에 없기 때문이다. 그 밖은 `404 commit_not_recent`다. `base`가 이 문서의 커밋인데 창보다 오래됐으면 `404 base_too_old`다. 뷰어는 이것으로 오래된 "마지막으로 본 자리"를 사라진 것과 가르고 지운다고 보지 않는다.
- 핀의 `close_ref`는 해시면 창 전체에서, PR 번호면 창의 첫 12행에서 찾는다. 해시는 커밋 하나를 가리키기 때문이다. 뷰어의 핀 커밋 고르기도 같은 규칙이고, 줄로 고르는 마지막 단계만 첫 12행이다.

### 3. 검증과 경계

| 경우 | 규칙 |
| --- | --- |
| `base`가 `commit`의 자손 | `422 base_after_head`. 서버는 두 끝을 뒤집지 않는다 |
| `base`가 `commit`의 조상이 아님 | `git merge-base`를 옛 쪽으로 쓰고 `merge_base`에 적는다. 공통 조상이 없으면 `422 no_merge_base` |
| `base == commit` | 소스 diff는 빈 diff(`commits:0`, `files:[]`), 비교 PDF는 `422 empty_range` |
| `pin`과 `base`를 함께 | `400 pin_with_base`. 1단계에서 핀 단위 보기는 커밋 하나에만 쓴다 |
| `base`가 이 문서의 커밋인데 창보다 오래됨 | `404 base_too_old`. 창 밖의 다른 SHA는 `404 commit_not_recent` |

범위의 거절 넷은 `revisions/answer.py`의 `RANGE_REJECTIONS` 한 표가 상태·문장·`reason`을 정한다.

### 4. 비교 PDF와 캐시

- 비교 PDF는 범위가 넓어도 스냅숏 둘, latexdiff 한 번, latexmk 한 번이다. 다만 넓은 범위는 실패할 가능성이 커서, 뷰어는 범위를 고르면 소스 diff를 먼저 열고 [변경 PDF]를 누를 때만 만든다.
- 캐시 키 모양은 그대로다. `base` 자리에 실제 옛 쪽 SHA가 들어갈 뿐이라, 옛 쪽이 그 커밋의 첫 부모인 범위는 단일 커밋 비교와 같은 캐시를 쓴다. 그 밖의 범위는 표시 파일 `ranged`를 두고 따로 세며 넷까지 둔다(`REVISION_RANGED_KEEP`). `REVISION_CACHE_VERSION`은 올리지 않는다.
- `merge_base`는 요청마다의 필드라 공유 상태 파일에 저장하지 않는다.

### 5. 뷰어 — 빠른 범위와 늘 보이는 목록

- 머리에 분절 `[마지막으로 본 뒤 N | 이 커밋부터 | 이 커밋만]`을 두고, 커밋 목록을 늘 보인다(데스크톱은 변경 왼쪽 304px, 휴대폰은 위에 5행 + [더 보기]).
- 행을 누르면 "이 커밋부터"·"마지막으로 본 뒤"에서는 그 커밋부터 지금까지, 이어서 더 새 행을 누르면 끝이 그 커밋이다. "이 커밋만"에서는 그 커밋 하나다. 목록이 조상 관계 순서라 목록에서 기준이 대상보다 새로운 범위는 생기지 않지만, 두 커밋이 늘 조상 관계인 것은 아니다(다른 줄기면 공통 조상부터). 그래서 칠하는 행과 "마지막으로 본 뒤 N"은 목록의 자리가 아니라 서버 답(`commit_ids`·`commits`)을 따른다.
- "마지막으로 본 자리"는 브라우저의 `localStorage`에 문서별로 둔다. 서버에 새 저장 파일을 만들지 않는다. 기록이 없으면 그 칸을 숨기고 "이 커밋만"으로 시작한다. 기록은 서버가 그 커밋에 답한 뒤에만 바꾼다. 서버가 찾지 못하면 칸이 그렇게 적는다.
- 그림 문서의 겹쳐 보기는 커밋이 아니라 빌드 둘을 비교하므로 바꾸지 않는다. 범위는 그림 문서의 [소스 diff]에만 걸린다.

## Trade-off

**장점:**
- 더하기만 한다. `base`·쪽 매개변수를 모르는 에이전트와 옛 요청 가운데 전에 성공하던 것은 같은 답을 받는다. 바뀌는 것은 거절이 답으로 바뀐 요청과, 날짜가 앞뒤로 섞인 병합 이력에서 목록 12개의 순서·집합뿐이다(§1).
- 노출 규칙의 성격은 그대로다. 문서의 경로 한정 이력과 그 첫 부모만 읽고, 임의 객체는 읽지 않는다.
- 범위가 첫 부모에서 시작하면 단일 커밋 비교의 캐시를 그대로 쓴다. 범위는 따로 세어 단일 커밋·핀 단위 비교를 밀어내지 않는다.
- 흔한 경우("마지막으로 본 뒤")는 누를 것이 없다.

**단점·포기한 것:**
- 매 요청이 경로 한정 `git log -500` 한 번을 더 읽는다(수 ms). 비교 PDF 상태 폴링도 같다.
- 마지막으로 본 자리는 브라우저마다 다르다. 다른 기기에서는 처음 보는 것처럼 시작한다.
- 핀 단위 보기와 범위를 함께 쓸 수 없다. 범위 위의 핀 보기(2층 추정만 쓰기)는 따로 정한다.
- 이력 창보다 오래된 커밋, 머지되지 않은 브랜치의 커밋은 여전히 볼 수 없다.

## 대안

| 대안 | 선택하지 않은 이유 |
| --- | --- |
| 최근 12개 유지 | 한 주만 지나도 "지난 투고판부터"를 고를 수 없다 |
| 임의 조상 SHA를 붙여 넣기 | 다른 문서·다른 경로의 객체를 열게 되어 지금의 노출 규칙과 맞지 않다 |
| 서버가 두 끝을 날짜로 정렬해 뒤집기 | 조상 관계와 날짜가 어긋나는 이력에서 다른 범위를 조용히 보인다. 거절한다. 뷰어 목록은 조상 관계 순서라 목록에서는 이 거절이 생기지 않는다 |
| 목록만 조상 관계 순서, 검증·`close_ref`는 날짜 순서 | 처음 구현이 그랬다. 500개를 넘는 이력에서 목록에 보인 커밋이 거절되고, 병합 이력에서 핀의 [변경 보기]가 서버와 다른 커밋을 골랐다(PR #204 리뷰). 한 목록으로 모았다 |
| `close_ref`를 첫 12행에서만 찾기(해시도) | 날짜가 오래된 곁가지가 늦게 병합되면 조상 관계 순서의 첫 12행을 그 곁가지가 채운다. 해시로 닫은 더 오래된 trunk 커밋을 찾지 못해 핀이 `inferred`로 떨어졌다(PR #204 재리뷰). 해시는 창 전체에서 찾는다. PR 번호는 깊은 곳의 같은 번호가 다른 PR일 수 있어 12행에 남긴다 |
| 범위의 비교 PDF를 바로 만들기 | 넓은 범위는 latexdiff 시간 초과나 `compile_failed`가 잦다. 소스 diff를 먼저 보이고 누를 때 만든다 |
| 뷰어 A안(타임라인 시트)·B안(기준·대상 두 칸) | A는 목록이 닫혀 있어 무엇을 보는지 버튼 한 줄로만 안다. B는 매번 두 칸을 정하고 순서가 틀린 쌍을 만들 수 있다 |
| 마지막으로 본 자리를 서버에 저장 | 사람별 새 저장 파일이 생겨 저장 형식 멈춤 신호에 걸린다. 브라우저 저장으로 충분하다 |

## 결과

- 판단은 `revisions/core.py`(`revision_window`·`window_base`·`resolve_range`·`range_diff`·`range_spec`)가 거절 값으로 내리고, `revisions/answer.py`의 `RANGE_REJECTIONS`가 HTTP 답으로 바꾼다. 입력은 `revisions/input.py`가 파싱한다.
- `base`가 없는 답의 바이트는 `tests/data/revision_snapshot.json`(이 변경 전 코드로 기록)과 대조한다.
- [api.md](../handbook/api.md) §변경 보기와 비교 PDF·§비교 PDF 실행과 캐시·§오류 응답, [viewer.md](../handbook/viewer.md) §변경 보기가 현재 규칙을 적는다.
- SKILL은 바뀌지 않는다. 에이전트의 핀 처리 흐름은 범위를 쓰지 않는다.
