# ADR-0033: 보고 있는 사람에게 새 소식을 알리되, 이미 있는 읽기로 말하고 계약을 더하지 않는다

| | |
| --- | --- |
| **번호** | ADR-0033 |
| **제목** | 보고 있는 사람에게 새 소식을 알리되, 이미 있는 읽기로 말하고 계약을 더하지 않는다 |
| **상태** | 제안 |
| **결정일** | — |
| **결정자** | Limn 소유자(승인 대기) |
| **출처** | [설계(제안)](../superpowers/specs/2026-11-05-update-notices.md), PoC 브랜치 `poc/update-notices` |

## 맥락

뷰어는 문서의 새 빌드, 원문의 변화, 공저자와 에이전트의 일을 대부분 조용히 반영한다. 알리는 것도 6초 뒤 사라지거나([viewer.md](../handbook/viewer.md) §알림 자리), 브라우저 알림 스위치를 켠 기기에만 온다([viewer.md](../handbook/viewer.md) §브라우저 알림). Limn이 업데이트돼 열린 탭이 옛 화면으로 새 서버와 말하는 상태는 아무도 말하지 않는다.

알릴 재료는 대부분 이미 있다. 라이트 meta의 `sync` 와 빌드의 `pull`([build-sync.md](../handbook/build-sync.md) §재빌드 전 원격 main 당겨오기 (`--git-pull`)), 문서별 커밋 목록과 범위 diff([api.md](../handbook/api.md) §두 커밋 사이), 원문 줄([api.md](../handbook/api.md) §화면·PDF·정적 파일의 `/api/source`), 나에게 온 이벤트의 커서([api.md](../handbook/api.md) §브라우저 알림 커서), 설치 버전(`/api/version`, [api.md](../handbook/api.md) §버전·상태·사람)이다. 남은 질문은 이것을 화면이 어떻게 모아 말하느냐와, 그러려고 계약을 더해야 하느냐다.

## 결정

| # | 결정 | 상태 |
| --- | --- | --- |
| D1 | 에이전트 계약(HTTP 경로·필드·이벤트 종류, `pins.md`)과 저장 형식을 더하지 않는다. 문서의 변경은 빌드·`sync`·`/api/revisions`·`/api/source` 로, 남의 새 핀은 핀 목록 비교로, Limn 업데이트는 `/api/version` 으로 화면이 계산한다. GET은 여전히 아무것도 쓰지 않는다([ADR-0027](0027-get-write-guard.md)) | 제안 |
| D2 | "본 것"은 브라우저마다 둔다(`localStorage` 의 `limnSeen`: 문서별 마지막으로 본 판과 그때의 최신 커밋, 알린 가장 큰 핀 번호). 문서 변경 메시지는 사람이 [x]나 그 동작을 누를 때 본 것이 된다. 처음 온 기기는 지금 것을 본 것으로 하고 아무것도 말하지 않는다 | 제안 |
| D3 | 나와 관계된 이벤트(부름, 검토 대기, 답글, 다시 열림, 담당, 삭제)는 브라우저 알림 스위치와 무관하게 사람의 탭이 `ev=` 로 묻고 상태 줄에 말한다. 스위치는 탭이 앞에 없을 때 시스템 알림을 띄울지만 정한다 | 제안 |
| D4 | 같은 종류의 사건은 상태 줄의 한 메시지로 모은다(묶음 열쇠). 마지막 답 뒤 2분이 지나 돌아오면 그사이 온 것을 한 줄로 말한다. 오류와 되돌리기는 모으지 않는다 | 제안 |
| D5 | 화면의 버전과 서버의 버전이 다르면 상태 줄의 상태 항목이 새로 고칠 때까지 [새로 고침]을 권한다. 자동으로 새로 고치지 않는다 | 제안 |

## Trade-off

- **"본 것"이 기기를 따라가지 않는다.** 노트북에서 본 변경을 태블릿이 다시 말한다. 서버에 사람별 기록을 두면 이어지지만 쓰기 경로와 저장 형식이 새로 필요하다. 다시 말하는 쪽이 놓치는 쪽보다 싸다고 보았다.
- **탭이 닫힌 사람에게는 문서 변경과 남의 새 핀이 시스템 알림으로 가지 않는다.** 돌아와서 한 줄로 듣는다. 시스템 알림까지 보내려면 이벤트 종류를 더해야 한다(대안 B).
- **사람의 탭이 늘 이벤트를 묻는다.** 스위치를 켠 기기만 하던 `events.jsonl` 조회가 모든 사람의 5초 폴링에 붙는다. 조회는 파일 서명으로 캐시되고 쓰지 않으므로 비용은 작다.
- **1분마다 `/api/version` 을 한 번 더 묻는다.** 라이트 meta에 필드를 더하면 없앨 수 있는 요청이다(대안 A).
- **PR 번호는 커밋 제목에서 읽는다.** squash 머지의 `(#12)` 와 머지 커밋의 `Merge pull request #12` 만 안다. 경로로 거른 이력에서는 머지 커밋이 빠질 수 있어, 머지 커밋으로 합친 PR은 번호 없이 그 PR의 커밋 제목으로 보인다.

## 대안

- **대안 A — 라이트 meta에 `version` 을 더한다.** 요청이 하나 줄고 폴링 한 번에 알 수 있다. 계약 변경이라 승인과 스냅숏 갱신이 필요하고, `/api/version` 이 이미 같은 값을 준다.
- **대안 B — 이벤트에 `created`·`updated`(새 핀, 문서 변경)를 더한다.** 탭이 닫힌 사람에게도 시스템 알림을 줄 수 있다. 공저자의 모든 핀이 모든 사람에게 가는 이벤트가 되어 `events.jsonl` 의 5000건 창이 빨리 차고, 에이전트가 읽는 이벤트 계약이 넓어진다.
- **대안 C — "본 것"을 서버에 사람별로 둔다.** 기기를 바꿔도 이어진다. 본 것을 적는 POST 경로와 상태 파일이 새로 필요하다.
- **대안 D — 지금처럼 6초 메시지와 스위치를 켠 기기만.** 읽는 사람이 변경과 자기를 부른 것을 놓친다.

## 결과

- 서버 코드와 계약 스냅숏은 바뀌지 않는다. 바뀌는 것은 뷰어(`js/updates.js` 와 알림 저장소의 묶음·모으기)와 [viewer.md](../handbook/viewer.md) §알림 자리·§브라우저 알림이다.
- 승인되면 [viewer.md](../handbook/viewer.md)에 새 절 §새 소식이 현재 규칙으로 들어가고, 이 ADR은 `승인됨` 이 된다.
- 대안 A·B는 쓰임을 본 뒤 따로 정한다. 그때는 이 ADR을 부분 대체하는 새 ADR을 쓴다.
