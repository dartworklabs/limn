## 맥락

핀을 삭제하면 `pins.dropped.jsonl`에 복구 가능한 사본을 쓴 뒤 `pins.jsonl`에서 원본을 뺀다. 복원은 반대로 `pins.jsonl`에 먼저 쓰고 휴지통 사본을 뺀다. 각 파일은 임시 파일과 `os.replace`로 개별 교체하지만 두 파일을 함께 교체할 수는 없다. 현재 삭제는 `PinStore.transact()`의 변경 함수 안에서 휴지통을 교체하고, 그 함수가 돌아온 뒤 `write_pins()`가 `pins.md`를 메모리에서 렌더하고 원본 파일과 Markdown을 차례로 교체한다. 렌더 오류나 원본 쓰기 오류가 나면 휴지통만 바뀐 채 원본도 남는다. 프로세스가 중간에 끝나도 같은 상태가 남을 수 있다. 복원에서는 원본 쓰기 뒤 휴지통 쓰기가 실패할 때 같은 중복이 생긴다.

중복은 두 파일 모두 없는 상태보다 안전하지만 현재 해석이 일치하지 않는다. `GET /api/pins/dropped`는 휴지통 파일만 잠금 없이 읽어 살아 있는 핀도 삭제된 것으로 보일 수 있다. 복원은 그 번호가 원본에도 있으면 `AlreadyLive`를 반환하고 휴지통 사본을 남긴다. 삭제를 다시 시도하면 휴지통에 같은 번호를 한 번 더 덧붙일 수 있다. 오래된 중복 사본을 영구 삭제하는 동작도 원본의 상태와 어긋난다.

`pins.jsonl`에서 한 번호가 있는지는 검증된 레코드로 판단한다. 읽을 수 없는 줄이나 번호가 잘못된 줄은 기존처럼 건너뛰고 처음 다시 쓸 때 원본 바이트를 `.corrupt-*.bak`에 남긴다. 알 수 없는 번호를 추측해 삭제하지 않는다. 이 결정은 저장 형식, HTTP 필드·상태 이름, `pins.md` 형식을 바꾸지 않는다.

## 결정

**두 파일에 검증된 같은 핀 번호가 있으면 `pins.jsonl`의 핀을 정본으로 본다. 휴지통 사본은 복구 가능한 잔여물로 취급해 조회에서 숨기고 안전할 때 정리한다.** 이 규칙은 삭제와 복원 양쪽의 부분 실패에 적용한다.

1. **쓰기 순서.** 삭제는 휴지통 사본을 먼저 교체하고 원본을 뺀다. 복원은 원본을 먼저 교체하고 휴지통 사본을 뺀다. 어느 방향에서도 두 파일 모두에 핀이 없는 실패를 만들지 않는다. 가능한 렌더·직렬화 오류는 첫 파일 교체 전에 발견하도록 준비하되, 준비가 파일 간 원자성을 제공한다고 가정하지 않는다. 모든 읽기·수정·정리는 기존 프로세스 핀 잠금 아래 수행하고, 파일 쓰기는 `PinStore`가 소유한다.
2. **읽기.** 휴지통 목록을 만들 때 잠금 아래 원본과 휴지통의 쓰기 없는 스냅샷을 함께 읽고, 원본에 검증된 같은 번호가 있는 사본은 제외한다. `GET /api/pins/dropped`는 계속 파일을 고치지 않는다. 원본 목록과 `pins.md`는 현재처럼 원본 파일을 따른다. 이 조회 규칙은 정리 쓰기가 실패하거나 서버가 부분 실패 직후 계속 돌아도 유효하다.
3. **정리.** 기동 때 기존 만료 정리와 함께 검증된 중복 번호의 휴지통 사본을 제거한다. 휴지통에 읽을 수 없는 줄이 있으면 기존 백업 규칙을 지킨다. 정리에 실패하면 경고를 남기고 중복을 보존한다. 조회 필터가 계속 유효하므로 정리 성공을 서버 기동 조건으로 삼지 않는다. 원본 줄을 읽을 수 없거나 번호를 확신할 수 없으면 그 휴지통 사본을 지우지 않는다. 복원이 원본 쓰기까지 성공하고 휴지통 정리에서 실패한 경우도 같은 규칙으로 회복한다.
4. **재시도와 영구 삭제.** 삭제를 다시 시도할 때 같은 번호의 오래된 휴지통 사본을 먼저 대체해 번호별 사본이 늘어나지 않게 한다. 이미 원본에서 빠진 삭제를 재시도하면 기존 `PinNotFound` 응답 계약을 유지한다. 현재 상태를 알려면 목록을 다시 읽는다. 원본에 살아 있는 번호의 휴지통 사본은 영구 삭제 대상으로 내보내지 않으며, 직접 `purge`를 호출해도 원본은 건드리지 않고 휴지통에 없는 번호로 답한다. 복원은 원본이 이미 있으면 현재처럼 `AlreadyLive`로 거절한다. 정리 뒤 같은 재시도는 휴지통에도 없으므로 `NotInTrash`일 수 있다. 두 결과 모두 원본을 보존한다.
5. **보상 쓰기.** 첫 파일 교체 뒤 예외가 났다는 이유만으로 휴지통을 되돌리지 않는다. `pins.jsonl` 교체는 성공했지만 뒤따른 `pins.md` 쓰기만 실패했을 수 있기 때문이다. 이때 휴지통까지 되돌리면 핀이 두 파일에서 사라진다. 보상은 원본에 해당 번호가 확실히 살아 있음을 다시 확인했을 때만 가능한 최선의 정리이며, 정확성은 보상 성공에 의존하지 않는다. 확인할 수 없으면 휴지통 사본을 보존한다.

### 실패 창과 판정

| 중단 지점 | 디스크에 남는 상태 | 재시도·복구 |
| --- | --- | --- |
| 첫 교체 전: 파싱·줄 맞춤·렌더 준비 실패 | 원본만 있음 | 오류를 전파한다. 다시 시도해도 같은 핀을 대상으로 한다 |
| 삭제의 휴지통 교체 뒤, 원본 교체 전: 원본 렌더·쓰기 실패 또는 프로세스 종료 | 원본과 휴지통 양쪽에 있음 | 원본이 정본이다. 휴지통 조회는 숨기고, 기동 정리는 사본을 제거한다. 삭제 재시도는 사본을 대체한다 |
| 삭제의 원본 교체 뒤, `pins.md` 교체 전: Markdown 쓰기 실패 또는 프로세스 종료 | 휴지통만 있음, `pins.md`는 낡을 수 있음 | 삭제는 저장상 완료다. 기동의 기존 Markdown 재생성과 다음 정상적인 핀 쓰기로 복구한다. 실패 응답을 받은 호출자는 목록으로 상태를 확인한다 |
| 복원의 원본 교체 뒤, 휴지통 교체 전: 휴지통 쓰기 실패 또는 프로세스 종료 | 원본과 휴지통 양쪽에 있음 | 원본이 정본이다. 같은 조회·기동 정리 규칙을 적용한다. 복원 재시도는 `AlreadyLive` 또는 정리 뒤 `NotInTrash`이다 |
| 두 파일의 교체 뒤, 알림·감사 기록 전에 실패 | 파일은 의도한 상태 | 상태를 다시 쓰지 않는다. 알림 전달의 정확히 한 번 보장은 이 결정의 범위 밖이다 |

`atomic_write()`는 각 파일의 임시 파일을 `fsync`한 뒤 `os.replace`한다. 이 결정은 프로세스 중단과 개별 쓰기 실패에 대한 판정이다. 디렉터리 메타데이터의 전원 차단 내구성이나 여러 서버 프로세스가 한 상태 디렉터리를 동시에 쓰는 구성까지 보장한다고 주장하지 않는다.

## Trade-off

**장점:** 파일과 레코드 형식을 그대로 두고 데이터 손실 없는 쓰기 순서를 유지한다. 성공하지 못한 정리나 서버 재시작 전에도 두 목록이 같은 번호를 서로 다른 상태로 보여 주지 않는다. 실패 후 정본을 한 규칙으로 판정할 수 있다.

**비용·한계:** 휴지통 조회가 원본 파일도 읽고 잠금을 잡는다. 기동 정리와 삭제 재시도에 번호별 중복 검사가 추가된다. 두 파일의 동시 원자 커밋은 여전히 없고, 원본 파일이 이미 바뀐 뒤 `pins.md` 또는 알림 쓰기가 실패하면 HTTP 오류와 저장 결과가 다를 수 있다. 클라이언트는 오류 뒤 목록으로 상태를 확인해야 한다.

## 대안

| 대안 | 선택하지 않은 이유 |
| --- | --- |
| 삭제에서 원본을 먼저 빼고 휴지통을 쓴다 | 두 교체 사이에 실패하면 두 파일에 핀이 없어져 복구할 원본을 잃는다 |
| 예외가 나면 항상 휴지통을 이전 바이트로 되돌린다 | 원본 교체가 이미 성공하고 `pins.md`만 실패한 경우 핀을 잃는다. 보상 쓰기도 실패하거나 프로세스 종료로 건너뛸 수 있다 |
| 조회는 그대로 두고 기동 정리만 한다 | 프로세스가 계속 실행되는 부분 실패 뒤나 정리 쓰기가 실패한 동안 두 목록이 충돌한다 |
| 새 저널·세대 파일·manifest로 두 파일의 커밋을 관리한다 | 더 강한 응답·재시도 원자성이 가능하지만 새 저장 파일과 복구 프로토콜이 필요하다. 현재 파일 계약과 되돌리기 호환을 바꾸므로 별도 설계 판단이 필요하다 |

## 검증과 결과

- 휴지통·원본·Markdown의 각 교체 전후에 실패를 주입한다. 특히 렌더 실패, 원본 교체 전 실패, 원본 교체 후 Markdown 실패, 복원 뒤 휴지통 실패, 정리 쓰기 실패와 프로세스 재시작을 구분한다. 매번 두 파일 모두에 핀이 없는 경우가 없고, 조회 결과가 원본 우선 규칙을 따르는지 확인한다.
- 중복 상태를 직접 만들어 삭제 재시도의 휴지통 항목 수·최신 삭제 기록, 복원 재시도, 직접 `purge`, 기동 정리와 만료 정리, 손상 줄의 원본 백업을 확인한다. 잠금 아래 일관된 조회와 `GET /api/pins/dropped`의 쓰기 없는 성질을 확인한다.
- HTTP의 기존 경로·필드·정상 응답, `pins.md`의 문자열·필드 순서, 구버전과 같은 두 JSONL 파일 형식을 유지한다. 기존 상태 디렉터리를 읽기 위해 쓰기 마이그레이션은 하지 않는다. 기동 정리는 부분 실패 사본을 제거하는 운영 정리이며, 오래된 유효 핀의 필드를 채우는 이관이 아니다. 구버전으로 되돌리면 같은 파일을 읽을 수 있지만, 아직 남은 중복 사본을 구버전이 조회에서 숨기지는 못한다.
- 구현이 현재 상태를 바꾼 뒤 [domain.md](../handbook/domain.md) §저장소 안전성과 [api.md](../handbook/api.md) §휴지통의 현재형 설명, 필요하면 [architecture.md](../handbook/architecture.md) 불변식 4의 조회 잠금 설명을 같은 변경에서 갱신한다. 이 제안 문서만으로 현재 동작이 바뀌지는 않는다.
