# ADR-0045: LaTeX 핀의 상자는 드래그한 자리가 아니라 줄 범위를 그린다

| | |
| --- | --- |
| **번호** | ADR-0045 |
| **제목** | LaTeX 핀의 상자는 드래그한 자리가 아니라 줄 범위를 그린다 |
| **상태** | 제안 |
| **결정일** | 2026-11-17 |
| **결정자** | Limn 소유자. 문제 제기와 목적("에이전트의 범위 인식과 사람의 인식을 일치시키고 싶음"), 상자 모양, 여백 규칙, float 핀 포함을 PoC를 보고 골랐다. 구현 방식(정방향 SyncTeX, 계산 필드, 호출 수 줄이기)은 이 변경이 측정으로 정했다 |
| **출처** | 2026-11-17 임시 원고 세 벌로 잰 정방향 SyncTeX의 출력 모양·비용, 직접 파싱과 CLI의 대조, 글 크기별 행간 측정. 설계는 [spec](../superpowers/specs/2026-11-17-pin-mark-snap-to-range.md) |
| **부분 대체** | 없음. [ADR-0011](0011-figure-documents.md)이 그림 문서에 둔 요소 상자 스냅과 읽을 때 계산하는 `mark`의 방식을 LaTeX 문서로 넓히며, 그 결정의 어느 조항도 바꾸지 않는다 |

## 맥락

LaTeX 문서에서 사람이 PDF를 드래그하면 두 가지가 서로 다른 넓이를 가리킨다.

- 에이전트가 받는 것은 `pick`이 답한 기본 단계의 줄 범위다. 기본 단계는 `para`(문단 전체)이고, `--float-envs` 환경 안이면 그 환경 전체다. 한 줄의 일부만 긁어도 저장되는 `lo`~`hi`는 문단 전체다.
- 사람이 보는 것은 드래그한 사각형이다. 핀의 `frac`이 그 사각형이고, 뷰어는 그것을 2px 테두리와 8% 바탕으로 그린다.

그래서 사람은 자기가 긁은 몇 낱말이 핀의 대상이라고 믿고, 에이전트는 문단 전체를 받는다. 그림 문서에는 이 어긋남이 없다 — 요소를 고르면 상자가 그 요소로 옮겨 붙고, 서버가 `mark`를 계산 필드로 붙인다([ADR-0011](0011-figure-documents.md)).

## 결정

| | | |
| --- | --- | --- |
| D1 | **LaTeX 줄 핀의 상자는 그 핀의 줄 범위가 PDF에서 차지하는 영역이다.** 핀 마크와 작성 중인 '새 핀' 상자 모두 그렇다. float 환경 안의 핀도 대상이다. 드래그한 `frac`은 그대로 저장하되 그리지 않는다 | 제안 |
| D2 | **영역은 정방향 SyncTeX(`synctex view`)로 구한다.** 에이전트가 받는 `lo`~`hi`와 같은 출처에서 뽑아야 둘이 어긋나지 않는다. `pdftotext -bbox`로 범위의 낱말을 PDF 단어와 맞추는 근사는 쓰지 않는다 — 수식·표에서 틀어지고, 어긋난 일치는 불일치보다 나쁘다 | 제안 |
| D3 | **`.synctex.gz`를 직접 파싱하지 않는다.** 파일을 통째로 읽는 비용은 2ms로 subprocess보다 싸지만, 직접 파싱한 박스는 CLI의 답과 같지 않다. 실측에서 좌표가 약 1.2pt 어긋났고(원점 보정), 박스가 없는 줄에서 CLI는 조상을 찾아 84개를 답하는데 직접 파싱은 0개였다. 그 탐색 규칙을 재현하면 엔진·판마다 역변환(`synctex edit`)이 쓰는 기준과 갈릴 수 있다 | 제안 |
| D4 | **호출 수를 줄여 비용을 맞춘다.** 비용은 호출 수에 비례하고 문서가 커지면 호출 하나가 비싸진다(35쪽 문서에서 13ms, 문단 5줄 64ms, 사다리 40줄 513ms). `pick`은 기본 단계만 계산하고, 다른 단계와 손으로 고친 범위는 뷰어가 이미 부르는 `GET /api/snippet`이 답한다 | 제안 |
| D5 | **상자는 저장하지 않고 읽을 때 계산한다.** 저장하면 재빌드로 쪽이 바뀔 때 상자가 낡는다. 줄 범위는 `anchor`로 따라가지만 좌표는 따라가지 않는다. 계약에는 `boxes`(`[{page, frac}]`)를 **더하기만** 하고 저장 필드 화이트리스트는 바꾸지 않는다 | 제안 |
| D6 | **여백은 그 범위의 행간에서 정한다.** 여백 = (글줄 `v` 차이의 중앙값 − 글줄 높이 평균) ÷ 2. 글줄이 하나뿐이면 글줄 높이 × 0.175. 고정값은 쓰지 않는다 — 같은 문서 안에서도 필요한 값이 0.50pt(`\Large`)에서 6.33pt(줄간격 1.8)까지 갈리고, 10pt 본문에 맞춘 1.5pt는 `\Large`에서 빈 틈 1.00pt를 넘어 이웃 글줄을 침범한다 | 제안 |
| D7 | **낡은 빌드에서는 엉뚱한 자리를 덮지 않는다.** `pick`은 SyncTeX가 답한 빌드 줄 범위를 그대로 정방향에 넣는다. 핀 목록과 snippet은 핀의 범위가 빌드가 읽은 줄에 그대로 서 있을 때만 상자를 내고, 아니면 내지 않는다 | 제안 |
| D8 | **구하지 못하면 드래그한 `frac`으로 떨어진다.** 거절하지 않고, 폴백을 화면에 따로 표시하지 않는다 | 제안 |

## Trade-off

- **핀 목록 응답이 커지고 계산이 붙는다.** 캐시가 선택이 아니라 요건이다. `/api/pins`가 느려지면 같은 프로세스의 다른 GET까지 밀린다.
- **상자가 커져 서로 더 겹친다.** 한 문단에 핀이 여럿이면 지금보다 겹쳐 보인다.
- **상자의 뜻이 폴백에서 조용히 바뀐다.** 영역을 구하지 못한 핀은 드래그한 자리를 그리는데 사람은 구별할 수 없다. 폴백이 얼마나 흔한지 보고 표시 여부를 다시 정한다(D8).
- **float의 조각 규칙이 문단과 다르다.** 표는 칸마다 박스가 흩어지고 캡션과 본체가 떨어질 수 있다. 그 규칙과 조각 한도는 실제 원고 PoC에서 정하고, 서지 않으면 float만 폴백으로 끝낼 수 있다.

## 대안

- **드래그 자리를 두고 문단을 옅게 비추기.** 화면에 경계가 둘이라 "어느 게 핀의 범위냐"가 여전히 모호하다. 목적을 절반만 이룬다.
- **뷰어에서 드래그를 PDF 글줄에 스냅.** 가장 싸고 서버를 안 고치지만, PDF 글줄과 소스 문단은 다른 단위라 에이전트가 받는 범위와 맞지 않는다.
- **고정 여백.** 구현과 시험이 가장 단순하지만 D6의 측정이 보여 주듯 큰 글에서 이웃을 침범한다.
- **지금 그대로 두기.** 에이전트 쪽 동작은 이미 맞으므로 기능이 망가진 상태는 아니다. 화면의 상자만 좋은 뜻을 못 가리킨다.

## 결과

- 사람이 보는 상자와 에이전트가 받는 범위가 같은 출처에서 나온다. 핀에 "이 문장"이라고 적어도 범위가 무엇인지 화면이 말해 준다.
- `pick`·`snippet`·`pins`에 `boxes`가 붙는다. 모르는 클라이언트는 지나친다. 저장 형식과 기존 필드는 그대로라 옛 서버로 되돌려도 핀이 상하지 않는다.
- 정방향 SyncTeX가 Limn의 두 번째 SyncTeX 사용처가 된다. 빌드는 이미 `-synctex=1`로 돌고 쪽 폴더에 `.synctex.gz` 사본을 둔다.
- 뷰어의 마크가 단수에서 복수(조각)로 바뀐다. 배지·되돌리기 칩·[보기]·팝오버의 기준은 첫 조각이다.
