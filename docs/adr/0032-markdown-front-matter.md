## 맥락

HTML 문서 화면 설계의 이후 단계 3은 원문 위치를 지키는 렌더러가 있는 다른 줄 단위 형식이다. 이 머신의 저장소 11개를 세어 보니 후보 형식(`.qmd`·`.Rmd`·`.ipynb`·`.adoc`·`.org`·`.rst`·`.mdx`)의 파일은 하나도 없었다. Typst는 53개 있지만 제안서 보관본·CV·서식이고, 2026-08 뒤에 바뀐 제안서 Typst는 없다. 연구실은 Markdown(1,281개)과 LaTeX로 쓴다(설계 §이 연구실이 쓰는 문서).

수요는 Markdown 안에 있다. 71개 파일이 YAML 머리 정보로 시작한다(논문 노트, 에이전트 규칙과 스킬 등). 지금 뷰어는 그 첫 줄 `---` 를 구분선으로, YAML을 문단이나 setext 제목으로 그린다. 스킬 파일의 `name:`·`description:` 은 h2 제목이 되어 목차와 절 사다리에 든다. 줄 번호는 맞지만 보이는 글과 문서 구조가 원문과 다르다.

이 변경은 핀 `kind` 값을 하나 더하므로 에이전트 계약을 넓힌다([architecture.md](../handbook/architecture.md) §멈춤 신호의 에이전트 계약 변경). 그래서 소유자 승인이 필요하다. 번들·저장 형식·페이지 정책·서버 코드는 바꾸지 않는다.

## 결정

| # | 결정 | 상태 |
| --- | --- | --- |
| D1 | Markdown 종류 안에서 문서 맨 앞의 YAML 머리 정보를 제 블록으로 그린다. 새 문서 종류와 새 접미사는 없다 | 제안 |
| D2 | 머리 정보는 첫 줄이 `---`(바이트 순서 표시와 끝 공백은 허용, 들여쓰기와 `----` 는 아님)이고, 둘째 줄이 비지 않고 YAML 매핑을 열며(키와 쌍점, 또는 `#` 주석), 뒤의 한 줄이 `---` 나 `...` 일 때만이다. Pandoc `yaml_metadata_block` 의 시작·끝 규칙에 둘째 줄 검사를 더했다. 문서 중간의 블록은 받지 않는다. 어긋나면 다른 규칙이 지금처럼 읽는다 | 제안 |
| D3 | 상자 하나가 두 `---` 줄까지 블록 범위를 가지고, 머리 줄(화면 언어로 `머리 정보 · YAML N줄`) 아래 안쪽 줄을 서버의 줄 그대로 줄마다 하나씩 보인다. YAML은 파싱하지 않으므로 링크·그림·마크업이 없다. 긴 값은 상자 안에서 접는다. 블록을 누른 핀의 `quote` 는 안쪽 줄의 글만이다. 펼쳐 둔다. 제목이 아니므로 목차·절 표시줄·절 단계에 들지 않는다 | 제안 |
| D4 | 블록 종류 `front` 를 더한다. 핀 `kind` 는 `md:front`, `scope` 는 `block` 이다. 사다리는 `고른 줄` → `머리 정보` 이고, 누르면 블록이 기본이다. 서버는 바꾸지 않는다 | 제안 |
| D5 | 규칙은 파싱 worker 안의 Limn 자체 블록 규칙(`mdFrontMatter`)이다. 라이브러리를 번들하지 않는다 | 제안 |

### D2를 고른 근거

Pandoc의 규칙("The initial line `---` must not be followed by a blank line", 끝은 `---` 나 `...`)은 Quarto·R Markdown·Jekyll류 머리 정보가 따르는 공통분모다. 둘째 줄 검사는 `---` 로 시작하는 평범한 Markdown(구분선 뒤 문단과 또 하나의 구분선)을 머리 정보로 잘못 읽지 않으려는 것이다. YAML을 파싱하지 않고도 고를 수 있는 가장 좁은 조건이다. 연구실의 머리 정보 71개는 모두 이 규칙에 든다. 규칙이 받지 않은 문서는 지금과 똑같이 그려지므로, 규칙이 틀려도 줄을 잘못 매기지는 않는다.

### D3을 고른 근거

줄 핀에는 원문 줄이 가장 정확하다. GitHub처럼 표로 그리면 칸에서 어느 줄을 골랐는지 말할 수 없고, YAML 파서(번들, 앵커 폭탄 같은 한도)가 필요하다. 머리 정보는 짧고(중앙값 4줄, 최대 38줄) 핀이 바로 그 줄(제목, 날짜, 태그)에 붙으므로 접지 않는다.

### D4를 고른 근거

머리 정보는 문단도 코드 블록도 아니다. `md:code` 를 받은 에이전트는 코드 블록을 찾는다. `md:front` 는 문서의 메타데이터를 고친다는 것을 값만으로 알린다. 레코드 검사는 `kind` 가 문자열인지만 보고, `pins.md` 범위 칸은 `md:` 로 시작하는 값을 그대로 적는다. 그래서 직전 릴리스도 이 핀을 지우지 않고 `md:front` 로 적는다.

## Trade-off

- 문서 중간의 메타데이터 블록, TOML 머리 정보(`+++`)는 받지 않는다. 연구실 파일에는 둘 다 없다.
- 머리 정보는 표가 아니라 원문 줄로 보인다. 키와 값이 길면 읽기가 GitHub보다 덜 편하다.
- 옛 뷰어는 같은 문서를 지금처럼(구분선과 문단) 그린다. 핀의 줄은 같아 되돌리기에 설정을 바꿀 일은 없다.
- `---` 로 시작하고 둘째 줄이 키처럼 생긴 평범한 문서는 머리 정보로 보인다. Pandoc·GitHub도 그렇게 읽는다.

## 대안

- **markdown-it-front-matter(MIT)를 번들한다.** 3.6 KB를 위해 판 고정·sha256·고지 절차가 하나 늘고, Pandoc 규칙과 둘째 줄 검사를 위해 결국 고쳐야 해서 기각했다.
- **YAML을 파싱해 표로 그린다.** 번들과 한도가 늘고 줄 핀이 흐려져 기각했다.
- **머리 정보를 숨기거나 접는다.** 핀이 붙을 줄을 감추므로 기각했다.
- **새 형식부터 받는다(Quarto·R Markdown 접미사, AsciiDoc, Org, reStructuredText, Jupyter, Typst).** 연구실에 검토할 파일이 없어 지금은 열지 않는다. 여는 조건은 설계 §결정 5에 있다. Org의 uniorg는 GPL-3.0-or-later라 [CLA](../../CLA.md)의 재허락 조항과도 맞지 않는다.

## 결과

- 에이전트 계약에 값 하나(핀 `kind` `md:front`)가 더해진다. 새 경로·필드·저장 형식은 없다.
- 다음 단계로 TeX 수식을 글자로 지키는 설계를 따로 쓴다(설계 §제안).

### 현재 상태 투영

- **영향받는 현재 권위:** 파싱 worker(`viewer/md-parse.mjs`), Markdown 화면(`viewer/js/md-surface.js`, `viewer/css/md-surface.css`), 에이전트 계약(`api.md`, SKILL).
- **갱신할 Handbook role/path:** `docs/handbook/api.md`(§Markdown 문서의 핀 값 목록, 핀 필드 표의 `kind`), `docs/handbook/viewer.md`(§Markdown 화면의 §그리기, §고르기와 범위 사다리), `skill/SKILL.md`·`skill/SKILL.ko.md`.
- **효력 형태:** 승인 뒤 한 번에. PoC 브랜치에 문서와 계약 시험을 더한 구현 브랜치 하나가 모두 넣는다.
- **완료 증거:** 순수 시험이 규칙의 열두 경우와 뒤 블록의 줄을 지킨다. 브라우저 시험이 상자·목차·사다리·저장한 `md:front` 핀·`pins.md` 를 본다. 직전 릴리스가 `md:front` 핀을 지우지 않는다. 네 기기군 실측이 있다.
