# ADR-0053: 원고 수정 시각은 감시가 재 두고, 문서 요약은 그 값을 읽는다

| **상태** | 승인됨 |

## 맥락

뷰어는 탭이 보이는 동안 5초마다 가벼운 폴링을 보낸다. 폴링이 하는 파일 시스템 호출은 하나하나가 요청 스레드에게서 인터프리터를 내놓게 하고, 다른 스레드가 계산 중이면 되찾는 데 전환 간격(5 ms)까지 걸린다. ADR-0052 뒤에 남은 호출의 대부분은 원고 폴더 훑기였다. 원고 수정 시각은 문서마다 2초만 기억하는데 뷰어 하나의 폴링은 5초 간격이라, 그 뷰어의 폴링은 올 때마다 인스턴스의 모든 LaTeX 문서의 빌드 루트를 훑었다.

훑기의 값을 조각으로 쟀다. 파일마다 `stat` 한 번, 폴더마다 목록 읽기 약 네 번이고 `is_dir`·`is_file`은 값이 없다. 파일 내용만 고치면 폴더의 mtime은 그대로라 파일의 `stat`은 뺄 수 없다. 기억 없이 훑기를 싸게 만들 길은 없었다.

인스턴스를 운영하는 기기에서 LaTeX 문서가 있는 인스턴스 18개 가운데 5개는 폴링 한 번에 파일 405~894개(폴더 239~715개)를 본다. LaTeX 문서가 8~12개인 인스턴스다. 시험 원고에서 무거운 읽기 둘 뒤의 폴링 중앙값은 파일 300개에서 180~219 ms, 문서 12개·파일 882개에서 579~595 ms였다.

## 결정

| | | |
| --- | --- | --- |
| D1 | **빌드 기능의 원고 감시 스레드가 원본에서 빌드하는 문서의 원고 수정 시각을 재 두고, 문서 요약은 그 값을 읽는다.** 감시의 측정은 요청이 하던 측정과 같다(화면 빌드 기준, 같은 파일 목록, 같은 `.fls` 규칙, 같은 기억 칸, 같은 세대 규칙). 바퀴의 시작 사이는 1초 이상이고, 한 바퀴가 그보다 길면 바로 다음 바퀴를 돈다 | 승인됨 |
| D2 | **감시는 답을 빠르게 할 뿐 답의 근거가 아니다.** 요약은 감시가 그 문서를 다 잰 지 10초 안일 때만 그 값을 답한다. 넘었거나 감시가 그 문서를 재지 않으면 전처럼 2초 기억을 보고, 없으면 직접 잰다. 쪽 교체는 전처럼 기억을 비우고 감시가 잰 시각도 지운다 | 승인됨 |
| D3 | **문서 요약이 15초 안에 묻지 않은 문서는 감시가 놓는다.** 재지 않고, 감시가 잰 시각을 지운다. 지우지 않으면 놓은 뒤 10초 동안 아무도 갱신하지 않는 값을 요약이 믿는다 | 승인됨 |
| D4 | **빌드의 기준과 pick의 낡음 판정은 감시의 값을 쓰지 않는다.** 빌드 시작 때의 기준, `built_src_mtime.txt`와 이력에 적는 값, 기동 때의 등록은 그 자리에서 잰다. pick의 `stale`은 2초 규칙 그대로다 | 승인됨 |
| D5 | **문서 하나의 측정은 한 번에 하나만 돈다.** 훑는 쪽이 문서마다의 측정 잠금을 쥔다. 기억이 빗나간 요청은 도는 측정을 기다린 뒤 기억을 다시 보고, 빌드의 기준은 기다린 뒤 직접 재고, 감시는 기다리지 않고 건너뛴다 | 승인됨 |
| D6 | **GET은 문서마다 "물은 시각" 숫자 하나를 메모리에 적을 뿐이고, 그 숫자를 보고 일하는 감시는 기동이 시작한 스레드이며 읽기만 한다.** 요청은 스레드를 시작하지 않고 파일을 쓰지 않는다. 불변식 10이 막는 것은 GET이 상태 폴더와 원고 트리를 바꾸거나 그런 작업을 예약하는 일이다 | 승인됨 |
| D7 | **감시는 새 스레드 하나이고, 이미 도는 감시에 얹지 않는다.** 실행마다 하나를 다른 감시와 같은 길로 시작하고 멈춘다. `--doc` 없는 실행에도 있다 | 승인됨 |

## Trade-off

- **얻은 것.** 감시가 재고 있는 문서의 폴링은 원고 폴더를 훑지 않는다. 시제품으로 `main`과 번갈아 잰 폴링의 중앙값은 무거운 읽기 둘 뒤에서 파일 300개 180~219 → 30 ms, 문서 12개·파일 882개 579~595 → 43 ms이고, 계산만 하는 스레드 하나 뒤에서 2,301~2,468 → 151 ms, 7,212~7,276 → 528 ms다. 폴링 한 번의 파일 시스템 호출은 983 → 24번, 2,960 → 87번이다. 뷰어가 늘어도 훑기는 바퀴마다 한 번이고, 동시에 빗나간 요청들 가운데 하나만 훑는다.
- **감수한 것.** 원고를 고친 사실(`src_mtime`·`stale_build`·`src_age_s`·`src_sig`, "원고 수정됨" 배지)이 응답에 보이는 시점이 평소 최대 1초 남짓 늦는다. 감시가 부하로 밀리면 그 한 바퀴만큼 늦는다. 감시가 그 문서를 다 잰 지 10초가 지난 값은 답하지 않는데, 한도를 측정이 끝난 시각부터 세므로 훑기 도중 먼저 본 파일은 그 훑기에 걸린 시간만큼 더 낡았을 수 있다. 실행마다 스레드가 하나 늘고, 누가 보는 동안 초마다 훑기가 한 번 돈다. 문서마다 숫자 둘과 잠금 하나가 는다. 기억이 빗나간 요청은 도는 측정을 기다린다.
- **한도가 지켜 주지 못하는 부하.** 감시의 한 바퀴가 10초를 넘으면 문서마다 그 바퀴의 일부 동안 한도를 넘겨 있고, 그동안 온 요청은 그 문서를 직접 잰다. 측정한 가장 긴 한 바퀴는 문서 12개 시험 원고에서 계산만 하는 스레드 하나 뒤의 약 7초다.
- **주지 않는 것.** 15초 넘게 아무도 보지 않다가 온 첫 폴링은 전처럼 훑는다. 문서 수를 따르는 읽기(문서마다 쪽 포인터·빌드 이력·폴더 확인)는 그대로다. 문서 12개에서 훑기를 없앤 뒤에도 폴링 한 번이 87번 호출한다. 원본에서 빌드하지 않는 문서의 주 파일 `stat` 하나도 그대로다.

## 대안

- **기억을 길게 둔다(2초 → N초).** 스레드가 없지만 N초마다 한 번은 요청이 훑는다. 5초로 잰 p90이 `main`과 같았고(278·698 ms), 배지와 pick의 낡음 판정이 부하와 무관하게 늘 N초까지 늦는다.
- **"2초 안에 잰 값만 답한다"를 그대로 둔다.** 응답의 규칙이 글자 그대로 전과 같다. 감시의 한 바퀴가 2초를 넘는 부하에서 요청이 다시 훑는다(문서 12개, 계산만 하는 스레드 뒤 4,823~4,876 ms).
- **감시가 살아 있으면 한 바퀴가 얼마나 길든 믿는다.** 폴링이 어떤 부하에서도 훑지 않는다. 값이 낡을 수 있는 한도가 상수가 아니라 한 바퀴의 길이가 된다. 소유자가 상수로 된 약속을 골랐다.
- **누가 보든 말든 늘 잰다.** 돌아온 첫 폴링도 빠르고 "물은 시각"이 없어진다. 보는 사람이 없는 인스턴스마다 초마다 훑기가 계속 돈다.
- **기억 없이 훑기를 싸게.** 값이 파일마다의 `stat`이라 줄지 않는다. 폴더 목록을 폴더의 stat으로 기억하는 길은 목록 읽기만 줄이고, [ADR-0050](0050-kept-pin-lines.md) D2가 기각한 종류의 조건(굵은 시계의 한 눈금 안의 두 변화)을 들인다.
- **빌드 루트가 같은 문서의 훑기를 합친다.** 운영 인스턴스 18개 가운데 2개에만 닿는다.
- **OS의 파일 변화 알림.** 표준 라이브러리에 Linux의 것이 없다.
- **이미 도는 감시에 얹는다.** 파일 문서 감시는 `--doc`가 있을 때만 있고 한 바퀴가 지도와 PDF를 읽느라 길어질 수 있다. 핀 유지 감시는 핀 기능의 것이다.

## 결과

- 규칙의 본문은 [build-sync.md](../handbook/build-sync.md) §원고 변화 감지와 §폴링 한 번이 읽는 것에, 감시의 자리와 GET과의 관계는 [architecture.md](../handbook/architecture.md) §의존 방향과 §HTTP 읽기 능력과 유지 실행에, 응답의 시점과 메모리 예외는 [api.md](../handbook/api.md) §버전·상태·사람과 §GET의 영속 무효과에, 시험은 [verification.md](../handbook/verification.md) §불안정한 테스트에 있다.
- 문서 요약이 아닌 곳에서 감시의 값을 쓰려는 코드는 D4를 다시 다뤄야 한다. 빌드의 기준이 낡으면 화면의 PDF가 본 원고를 잘못 적는다.
- 문서 수를 따르는 읽기를 줄이는 일은 이 결정의 범위 밖이고, 따로 설계한다.
