# ADR-0042: 뷰어 JS를 ES 모듈로 나누고 번들러로 지은 한 파일을 저장소에 둔다

| | |
| --- | --- |
| **번호** | ADR-0042 |
| **제목** | 뷰어 JS를 ES 모듈로 나누고 번들러로 지은 한 파일을 저장소에 둔다 |
| **상태** | 승인됨 |
| **결정일** | 2026-11-16 |
| **결정자** | Limn 소유자(CTO)가 2026-11-16 대화에서 지시 |
| **출처** | 지시에 든 측정(아래 맥락), 이 변경의 변환 도구가 잰 값, 전체 브라우저 검사 |
| **부분 대체** | [ADR-0001](0001-blueprint.md)의 기각 목록 중 "프론트엔드 빌드 도구 도입(번들러, 프레임워크)"의 번들러 부분. 프레임워크 기각은 그대로다. [architecture.md](../handbook/architecture.md) 불변식 2의 문구("뷰어의 CSS·JS가 여러 조각 파일이어도 번들러나 모듈 로더를 들이지 않는다") |

## 맥락

뷰어는 JS 파일 57개(15.4k줄)를 서버가 `parts.txt` 순서대로 이어 붙인 인라인 고전 스크립트 하나였다. 모듈 체계가 없어 모든 최상위 이름이 한 전역 범위를 나눠 썼다. 지시가 든 측정은 이렇다: 최상위 이름 1,976개 중 893개가 파일을 건너 쓰이고, 변하는 전역 107개 중 21개를 다른 파일이 다시 대입하며, 파일 하나가 평균 15개(`events.js`는 48개) 파일에 기댄다. 10월 이후 `fix` 커밋 288개 중 225개가 `viewer` 범위였다. 백엔드에는 import 경계 검사(`tools/check_boundaries.py`)가 있지만 뷰어에는 검사할 import 그래프 자체가 없었다.

이 변경의 변환 도구가 같은 코드를 스코프 분석기(eslint-scope)로 다시 잰 값은 정의가 조금 다르다: 최상위 바인딩 2,097개(함수 선언 포함), 파일을 건너 쓰이는 이름 870개, 다른 파일이 다시 대입하는 이름 50개(대입 자리 108곳), 파일당 평균 12.8개 파일에 기댐. 모듈로 나눈 뒤의 import 그래프는 57개 중 54개가 한 강결합 요소(SCC)에 든다.

## 결정

| | | |
| --- | --- | --- |
| D1 | **뷰어 JS는 ES 모듈이다.** 각 파일은 다른 파일의 이름을 명시한 `import`로만 쓰고, 다른 파일이 쓰는 이름만 `export` 한다. 다른 모듈의 `let`은 다시 대입하지 않는다 — 상태는 선언한 모듈이 소유하고 그 모듈이 내보낸 함수로만 바뀐다. 처음 변환에서는 다른 파일이 대입하던 이름 50개마다 소유 모듈에 설정 함수(`setPins` 등)를 두었다 | 승인됨 |
| D2 | **번들러는 Rollup이고, 지은 파일 `src/limn/viewer/dist/viewer.js`를 저장소에 커밋한다.** 판은 `package.json`·`package-lock.json`에 정확히 고정하고, `npm ci --ignore-scripts`로 설치가 끝난다. 빌드(`tools/build_viewer.mjs`)는 결정적이다: 트리 셰이킹·압축·이름 바꾸기 없이 모듈 글을 그대로 잇고 `import`·`export` 문만 걷어 낸다. CI가 다시 지어 커밋된 바이트와 다르면 실패한다(`npm run build:check`). 설치와 배포는 그대로다 — `dependencies = []`이고, 인스턴스는 Node가 없는 기계에서 `uv tool install git+…@<태그>`로 설치한다. 휠에는 지은 파일이 들어간다 | 승인됨 |
| D3 | **모듈이 도는 순서는 `parts.txt`의 `__APP_JS__` 목록 순서다.** 빌드가 각 모듈 앞에 목록의 바로 앞 모듈을 가리키는 맨 `import`를 넣는다. ES 모듈 평가는 import의 깊이 우선 후위 순서라 서로 기대는(순환) 모듈 사이에서는 순서가 모듈 그래프에 따라 달라지는데, 이 사슬이 있으면 어느 모듈이든 그 위의 모듈이 모두 먼저 돈다. 그래서 최상위 코드(리스너 등록, `let`·`const` 초기값, 바로 부르는 함수)는 고전 스크립트 때와 같은 순서로 돈다. 빌드는 이은 순서가 목록과 다르면 실패한다 | 승인됨 |
| D4 | **지은 파일은 같은 출처의 고전 스크립트로 내보낸다(`GET /viewer.js?v=<내용 키>`).** 맨 앞에 `'use strict'`가 있고(모듈은 엄격 모드다), 서버가 시작할 때 자리표시(아이콘 표, 영어 메시지 표, PDF.js·KaTeX 판)를 채운다. `?v=`는 채운 글의 SHA-256 앞 16자리다. 최상위 이름은 전처럼 한 스크립트 범위에 있다 — 브라우저 시험이 그 이름으로 상태를 읽고 바꾼다. 모듈 경계는 원본과 검사가 지킨다 | 승인됨 |
| D5 | **페이지 정책은 넓히지 않는다.** `'unsafe-inline'`·`'unsafe-eval'`·nonce·`blob:`·`data:`·다른 출처는 없다. 지은 파일은 `script-src 'self'`가 허용하고, 남은 인라인 스크립트(테마, 언어)는 전처럼 해시로 허용한다. `limn/web/csp.py`는 속성이 붙은 스크립트 요소 중 `<script src="/경로"></script>` 한 꼴만 받아들이고(해시할 글이 없다) 나머지는 전처럼 거부한다. worker는 같은 출처 파일 그대로다. `GET /viewer.js`는 아무것도 쓰지 않는다(불변식 10). 서비스 워커는 이 파일을 다른 같은 출처 정적 파일처럼 주소째 사본으로 두고, [오프라인으로 받기]는 페이지가 불러온 자원 목록에서 이 주소를 읽는다 — 끊긴 채 다시 연 탭은 페이지와 그 페이지가 가리키는 판의 스크립트를 함께 사본에서 받는다 | 승인됨 |
| D6 | **UI 프레임워크는 들이지 않는다.** Svelte·React 같은 프레임워크는 일부 도입도 하지 않는다 | 승인됨 |
| D7 | **뷰어 코드는 백엔드 수준으로 검사한다.** TypeScript `strict` 전체(JS 원본에 `checkJs`, 타입은 JSDoc), 타입 정보를 쓰는 ESLint(`any` 금지, 타입 단언·비널 단언 같은 탈출구 금지, 닫힌 합집합의 `switch`는 `default` 없이 빠짐없이, 암묵 전역 금지, 다른 모듈의 상태 직접 변경 금지), 모듈 그래프의 import 경계 검사(허용 의존을 이유와 함께 나열, 순환 거부, 파일의 기능·역할을 읽음). 지금 코드가 아직 지키지 못하는 규칙은 파일마다 줄기만 하는 기준선(`tools/strict-baseline.json`)으로 둔다: 새 위반은 실패하고, 줄었는데 기준선을 낮추지 않아도 실패한다 | 승인됨 |
| D8 | **역할과 경계 어휘.** 파일의 자리는 `js/<기능>/<역할>[-<주제>].js`이고, 공용 장치는 `js/platform/<이름>.js`, 입구는 `js/main.js`다. 역할은 `rules`(순수 판단)·`state`(상태와 그 변경 함수)·`api`(서버 읽기·쓰기)·`view`(DOM 그리기)·`input`(입력 처리)·`flow`(기능 안의 흐름)·`lib`(공용 장치)·`main`(입구)이다. 지금의 평평한 파일 57개는 경계 검사의 `LEGACY` 표가 기능과 역할을 대신 말하고, 각각 "제자리에 없음"으로 기준선에 든다. 기능 폴더로 옮기는 일은 2단계다 | 승인됨 |

## Trade-off

- **얻는 것.** 파일이 무엇에 기대는지 import 줄이 말하고, 검사가 그 그래프를 읽는다. 다른 모듈의 상태를 바꾸는 길이 그 모듈의 함수 하나로 모인다. 타입·린트·경계 위반은 파일마다 세어 늘지 못하게 막는다. 화면과 동작은 바뀌지 않는다 — 지은 파일은 예전에 페이지에 들어가던 스크립트와 글이 같고, 다른 것은 걷어 낸 `import`·`export` 문, 설정 함수와 그 호출, 모듈 사이 빈 줄, `else` 뒤 공백(Rollup의 출력 형식)뿐이다.
- **감수하는 것.**
  - 지은 파일(약 1.5 MB)을 저장소에 커밋한다. 뷰어를 고친 PR이 동시에 둘이면 이 파일이 충돌한다 — 원본을 합친 뒤 `npm run build`로 다시 지으면 풀린다.
  - 뷰어를 고치는 사람은 Node와 `npm ci --ignore-scripts`가 필요하다(설치·배포에는 필요 없다). 개발 의존성(Rollup, ESLint, typescript-eslint, TypeScript 6.0 — typescript-eslint가 읽는 판)은 정확한 판으로 고정하고, 설치 스크립트를 돌리지 않는다.
  - 페이지를 열 때 요청이 하나 는다(`GET /viewer.js`). 전에는 같은 바이트가 매번 다시 받는 페이지 안에 있었으므로 받는 양은 같다.
  - 설정 함수는 소유를 형식으로만 옮긴다. 상태 대부분은 아직 `core.js`에 모여 있고, 쓰는 모듈이 하나뿐인 상태는 그 모듈로 옮기는 편이 맞다(2단계).
  - 지은 파일은 여전히 한 스크립트 범위라 런타임에서는 최상위 이름이 전역이다. 브라우저 시험이 시험용 출입구로 옮겨 가면 즉시 실행 함수로 감쌀 수 있다.
  - 모듈 그래프의 거의 전부가 하나의 순환이다. 기준선이 그것을 줄기만 하게 붙잡을 뿐, 이 변경이 줄이지는 않는다.

## 대안

- **esbuild.** 더 빠르고 널리 쓰이지만 코드를 다시 찍어 내며(따옴표·공백·주석), 묶을 때 최상위 `const`·`let`을 `var`로 바꿀 수 있어 순서 오류가 소리 없이 `undefined`가 된다. 지은 파일과 원본의 글이 달라 시험과 디버깅이 원본을 그대로 읽지 못한다. 채택하지 않는다.
- **최상위 부수효과를 모듈마다 `start()`로 모으고 입구가 순서대로 부른다.** 순서를 코드로 드러내지만, 지금은 `let`·`const` 초기값과 부수효과가 파일 순서로 섞여 돌므로 그 순서를 바꾸는 변경이 된다. 동작을 그대로 두는 1단계에는 맞지 않는다. 기능 폴더로 옮길 때 모듈마다 검토한다.
- **사슬 `import`를 원본에 쓴다.** 순서가 각 파일에 보이지만 모든 파일 첫 줄이 순서 정보로 덮이고, 경계 검사가 그 줄을 따로 빼야 한다. 순서의 정본은 지금처럼 `parts.txt` 한 곳에 두고 빌드가 넣는다.
- **번들을 인라인 스크립트로 두고 해시한다.** 정책은 그대로지만 1.5 MB 글의 해시가 실행마다 바뀌는 페이지에 묶이고, 같은 출처 파일이 더 단순하다는 지시와 맞지 않는다. 채택하지 않는다.
- **`.ts` 원본.** 타입 문법이 원본에 들어가면 지은 파일이 원본과 글이 달라지고 변환 단계가 하나 는다. 이미 JSDoc으로 타입을 단 JS를 `checkJs`로 `strict`까지 검사하면 같은 검사를 얻는다. 채택하지 않는다.
- **지은 파일을 커밋하지 않고 설치 때 짓는다.** 인스턴스 기계에 Node가 필요해진다. 채택하지 않는다(D2).

## 결과

- 현재 규칙은 Handbook에 있다: [viewer.md](../handbook/viewer.md) §뷰어 규칙을 바꿀 때·§페이지 정책·§타입 검사, [architecture.md](../handbook/architecture.md) 불변식 2·9와 멈춤 신호, [verification.md](../handbook/verification.md), [api.md](../handbook/api.md)의 `GET /viewer.js` 행.
- 2단계(제안 순서): 쓰는 모듈이 하나뿐인 상태를 그 모듈로 옮기기 → `core.js`를 닫힌 값 표(`platform`)와 기능별 상태로 나누기 → 기능 하나씩 `js/<기능>/<역할>.js`로 옮기며 그 기능의 역순 의존을 없애기(기준선 감소) → 브라우저 시험을 시험용 출입구로 옮긴 뒤 지은 파일을 즉시 실행 함수로 감싸기.
- 되돌릴 조건: 지은 파일 때문에 배포가 깨지면 이전 태그로 업데이트한다(`limn update --ref <태그>`). 상태·저장 형식·API는 바뀌지 않았으므로 되돌려도 남는 것이 없다.
