## 맥락

Markdown 문서의 변경 보기는 소스 diff 하나다. 표·목록·그림이 바뀐 커밋도 원문 기호로만 보이고, 낱말 몇 개를 고친 문단은 줄 전체가 지운 줄과 더한 줄로, 옮긴 절은 지운 줄 수십 개와 더한 줄 수십 개로 보인다. LaTeX 문서에는 latexdiff 비교 PDF가 있다.

서버는 그 커밋의 diff만 주고(256 KiB까지) 원문 전체를 주는 경로가 없다. 뷰어가 지금 원문에 diff를 거꾸로 적용하면 고른 커밋이 HEAD가 아니거나 미커밋 수정이 있을 때 틀린 판이 나온다. 그래서 두 판을 그리려면 에이전트 계약에 읽기 경로가 하나 더해지고, 소유자 승인을 받는다([workflow.md](../handbook/workflow.md) §기본 경로).

## 결정

| # | 결정 | 상태 |
| --- | --- | --- |
| D1 | 새 읽기 경로 `GET /api/revision-source?doc=&commit=[&base=]` 가 브라우저가 그리는 문서(Markdown·텍스트)의 파일 하나를 소스 diff와 같은 두 쪽(첫 부모 → 커밋, 범위는 옛 쪽 → 커밋, 곁가지는 병합 기준)에서 `{id, base, merge_base?, path, old, new}` 로 준다. 쪽은 `{lines, git_line_starts?}` 다. `lines` 는 `GET /api/source` 와 같은 줄 규칙(`str.splitlines()`, 화면 줄)이고, `git_line_starts` 는 git이 세는 줄(LF만)과 화면 줄이 다른 쪽에만 붙는 `[git 줄, 화면 줄]` 쌍 목록이다(첫 쌍 `[1, 1]`, 쌍 `[g0, s0]` 부터 git 줄 `g` 는 화면 줄 `s0 + (g − g0)` 에서 시작, 마지막 git 줄이 화면 줄 여럿이면 끝 쌍 `[git 줄 수 + 1, 화면 줄 수 + 1]`). hunk 머리의 git 줄 번호를 화면 줄로 옮기는 데 쓴다. 파일이 없으면 `null`, 그릴 수 없으면 `{reason}`(`source_too_large`·`source_not_utf8`·`not_a_file`·`source_unreadable`)다. 경로 매개변수는 없다. `path` 는 문서를 등록한 경로(시작할 때 링크를 푼 저장소 기준 경로)이고 이력 창이 커밋을 고른 그 경로이며, 요청마다 다시 풀지 않는다. 이력 창 안의 커밋만 읽는다. 다른 문서는 `404 commit_not_recent`, 범위의 거절은 [api.md](../handbook/api.md) §두 커밋 사이 그대로다 | 승인됨 |
| D2 | 한 쪽은 1 MiB까지(git이 알려 준 크기로 먼저 거른다), git 호출마다 30초. 아무것도 쓰지 않고 캐시도 없다([ADR-0027](0027-get-write-guard.md) 결정 1) | 승인됨 |
| D3 | 뷰어가 두 판을 Markdown 화면의 렌더러로 그려 블록(문단·제목·목록 항목의 제 글·표 행·코드 블록·구분선·HTML 자리표시) 단위로 맞댄다. 블록의 열쇠는 보이는 모든 것(글, 인라인 구조와 그림의 대체 글, 놓인 인용·목록과 번호 목록의 시작 번호, 그림 경로, 링크 대상, 코드 블록은 언어와 줄 그대로)이라, 같은 낱말의 구조만 바뀐 블록도 바뀐 블록이고 무엇이 바뀌었는지 적는다. 같은 틈의 같은 종류·같은 그림 경로·낱말 40% 넘게 겹치는 쌍은 고친 블록(낱말 단위 표시, 낱말은 놓인 인라인 요소까지 비교), 다른 곳의 똑같은 블록은 옮긴 블록이다. 대응과 짝짓기는 비교 한 번에 800만 걸음까지이고, 넘으면 남은 블록을 짝짓지 않고 더함·뺌으로 바로 그리며 그렇게 적는다 | 승인됨 |
| D4 | Markdown 문서의 변경 보기는 [그린 비교] 탭으로 열고, [소스 diff]는 옆 탭에 남는다. 배치는 한 단(뺀 블록을 제자리에 줄 그어 넣는다)이고 옆으로 넘기지 않는다. 핀의 [변경 보기]가 무엇을 보이는지는 D6이다 | 승인됨 |
| D5 | 핀 레코드·`pins.md`·SKILL·저장 형식은 바꾸지 않는다. 에이전트 계약에는 읽기 경로 하나와 쪽의 오류 이름 넷, 쪽의 `git_line_starts` 가 더해진다 | 승인됨 |
| D6 | 핀의 [변경 보기]가 보이는 것(아래 §D6. 핀의 [변경 보기]가 보이는 것). 목표는 B(핀 단위 합성 판: 옛 판에 그 핀의 hunk만 적용한 판, [ADR-0005](0005-pin-scoped-changes.md) §5)다. B를 구현하기 전까지는 C다. 핀의 [변경 보기]는 ADR-0005 §4의 소스 diff로 열고, [그린 비교]는 그 옆 탭으로 커밋 전체 비교와 핀의 블록 테두리를 보인다 | 승인됨 |
| D7 | 비교 화면의 링크: 다른 출처의 웹 링크와 `mailto` 는 새 탭, 트리 파일로 가는 링크는 새 탭에서 지금 트리의 그 파일. 문서 안 `#제목` 과 다른 등록 문서로 가는 링크는 따라가지 않는 글자다(팁이 그렇다고 말한다). 따라가면 변경 보기를 떠나 보던 비교를 잃는다 | 승인됨 |
| D8 | 옛 판의 그림: 두 쪽 모두 지금 원고 트리의 파일을 `GET /api/asset` 으로 그린다. 옛 판의 그림 파일은 읽지 않는다. 그래서 그 커밋 뒤에 같은 경로의 그림 파일이 바뀌었으면 옛 판에도 새 그림이 보이고, 트리에서 지운 그림은 옛 판에서 `그림: <대체 글>` 이다. 그림 파일만 바꾼 커밋은 이 문서의 이력에 없다. 어느 쪽에든 트리 그림이 있으면 비교 위에 그렇다는 줄을 화면 낭독기도 읽게 적는다 | 승인됨 |

## Trade-off

- 읽기 경로가 하나 는다. 이력 창·범위 규칙·크기 한도·쓰기 없음을 시험이 지켜야 한다. 이미 소스 diff가 같은 커밋의 같은 파일을 줄 단위로 내놓으므로 새로 닿는 정보는 없다.
- 렌더러를 두 번 더 돌린다. 700 KB 문서의 두 판이 Chromium에서 약 0.2초다(설계 §결정 2의 잰 값). 1 MiB를 넘는 쪽은 그리지 않고 소스 diff로 보낸다.
- 옛 판의 그림은 지금 트리의 파일이다(D8). 같은 경로의 그림 파일이 그사이 바뀌었으면 옛 판에도 새 그림이 보인다. 비교 위의 줄이 그렇다고 말한다.
- 블록 대응은 짐작이다. 문단을 둘로 나누면 고친 블록 하나와 더한 블록 하나로 보일 수 있다. 정확한 줄은 [소스 diff]에 남는다.
- 낱말은 글자·숫자의 이어진 묶음이라, 띄어쓰기 없는 글(중국어·일본어, 붙여 쓴 한국어)은 묶음 전체가 한 낱말로 표시되고 그런 문단은 고친 블록으로 짝지어지지 않을 수 있다.
- 블록 단위 표시는 한 문단 안의 핀 여럿의 수정을 가르지 못한다. 그래서 핀의 [변경 보기]는 B가 들어오기 전까지 소스 diff로 연다(D6).

## 대안

- **`/api/revision-diff` 에 두 쪽 필드를 더한다.** 경로를 아끼지만 소스 diff만 볼 때도 1 MiB 두 쪽을 읽는다. 기각한다.
- **뷰어가 diff를 거꾸로 적용한다.** 경로가 없지만 HEAD가 아닌 커밋·미커밋 수정·잘린 diff·git과 다른 줄 끝에서 틀린다. 기각한다.
- **원문 줄 diff를 그린 블록에 비춘다.** 낱말 표시도 옮김도 없다. 기각한다.
- **두 단.** 패널을 편 1440 데스크톱에서 비교 칸이 536px라 서지 못한다. PoC의 후보 B(`?cmp=split`)로 보였다.
- **옛 판의 그림을 그 커밋에서 읽는 경로.** 정확하지만 경로가 하나 더 늘고 이력 전체의 트리 그림을 읽게 된다. 다음 단계로 둔다.

## D6. 핀의 [변경 보기]가 보이는 것

[ADR-0005](0005-pin-scoped-changes.md)는 핀의 [변경 보기]를 핀 단위로 정했다. 소스 diff는 그 핀의 hunk만 보이고 나머지를 접으며(§4), 비교 PDF는 옛 판에 그 핀의 hunk만 넣은 합성 판과 견준다(§5). 에이전트가 핀 10여 건을 한 스쿼시 커밋으로 고치는 일이 흔하기 때문이다. PoC는 Markdown 문서에서 이 보기를 커밋 전체 비교와 핀의 블록 테두리로 바꿨다.

| 안 | 보이는 것 | 잃는 것·드는 것 | ADR-0005 |
| --- | --- | --- | --- |
| A. 커밋 전체 비교 + 핀의 블록 테두리(PoC) | 커밋 전체, 핀의 hunk에 걸친 블록에 보라 테두리 | 다른 핀의 수정이 같은 화면에 표시되고 §4의 접기가 없다. 핀 여럿의 수정이 든 한 문단은 블록 전체가 테두리이고 표시 낱말이 섞인다 | Markdown 문서에서 핀 단위 약속을 거두므로 고쳐 쓴다 |
| B. 핀 단위 합성 판 | 옛 판에 그 핀의 hunk만 적용한 판을 새 쪽으로 그린다(`scope.mode` 가 `pin` 일 때). `[커밋 전체 비교]` 토글로 A와 오간다 | 서버가 §5의 합성을 파일 하나의 글에 쓰고, `GET /api/revision-source` 가 선택 `pin` 을 받는다(계약에 더하기, `revision-build` 의 `pin` 과 같은 규칙) | §5를 그린 비교로 넓힌다. 덧붙임 하나 |
| C. 소스 diff를 핀의 기본으로 | 핀의 [변경 보기]는 §4의 소스 diff, [그린 비교]는 옆 탭(A) | 핀을 볼 때 그린 문서까지 한 번 더 누른다. 새 계약은 없다 | 그대로 |

**결정: B가 목표이고, B를 구현하기 전까지 C.** 소유자가 추천대로 정했다. 핀 단위로 가르는 것이 [변경 보기]의 까닭이고, 그린 비교에서 그것을 지키는 길은 비교 PDF가 이미 쓰는 합성뿐이다. C는 ADR-0005를 그대로 두고 새 계약이 없다. PoC의 A(커밋 전체 비교와 핀의 블록 테두리)는 C에서 [그린 비교] 탭 뒤로 간다. 커밋이나 범위를 목록에서 고를 때의 기본 탭(그린 비교, D4)은 이 결정과 따로다.

## 결과

- 이 변경이 PoC를 구현으로 이어 쓴다. 렌더러는 문맥 객체를 받아(줄·요소 수·제목·숨은 문자 셈) 비교가 제 문맥으로 두 판을 지으며 2,000 단위마다 차례를 넘기고, D6은 C로 들어간다. [viewer.md](../handbook/viewer.md) §변경 보기, [api.md](../handbook/api.md) §변경 보기와 비교 PDF·§두 커밋 사이, [verification.md](../handbook/verification.md)와 CHANGELOG가 현재 규칙을 적는다.
- **열림: D6의 B.** 핀 단위 합성 판(서버가 ADR-0005 §5의 합성을 파일 하나의 글에 쓰고, `GET /api/revision-source` 가 선택 `pin` 을 받는다)은 다음 단계다. 에이전트 계약에 더하는 일이라 그 변경이 api.md와 ADR-0005의 덧붙임을 함께 고친다. 그때 핀의 [변경 보기]의 기본이 그린 비교로 바뀐다.
- 되돌리기는 이전 태그로의 업데이트다. 상태 폴더에 남는 것이 없다.
