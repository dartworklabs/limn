# ADR-0011: 벡터 그래픽을 세 번째 문서 종류로 받는다

| | |
|---|---|
| **번호** | ADR-0011 |
| **제목** | 벡터 그래픽을 세 번째 문서 종류로 받는다 |
| **상태** | 확정. D1·D5는 소유자가 정했다. D2–D4·D6·D7과 오류 문장 증가는 소유자가 결정을 위임해 진단으로 확정했다. D6의 값은 첫 실측 전까지 잠정이다 |

## 맥락

Limn은 LaTeX 원고 PDF에서 드래그한 영역을 `.tex` 파일·줄로 되돌려 주고 핀으로 처리한다. 논문 그림은 점점 코드가 그린다. 파이썬 스크립트가 공통 부품을 불러 SVG·PDF를 쓴다. 그런데 그림의 수정 요청은 아직 위치를 되찾을 길이 없다.

- **스크린샷 방식.** 스크린샷에 박스를 그려 대화로 전하면, 요청이 수명 주기 없이 흩어진다.
- **디자인 도구 댓글 방식.** 도구의 댓글은 SVG를 가져온 사본 노드에 붙는다. 그래서 원본 코드로 돌아가지 못하고, 다시 올리면 떨어진다.

Limn에는 이미 두 번째 문서 종류인 보기 전용 PDF가 있다. 빌드 대신 파일 감시로 쪽을 다시 그리고, 줄 대신 쪽·영역으로 핀을 찍는다. 코드를 조사해 보니 그림은 이 경로를 거의 그대로 쓸 수 있다. 다만 문서 종류가 참·거짓 값 `is_pdf` 하나로 약 25곳에서 갈리고 있었다. 또 핀 잠금이 프로세스 안의 잠금이라, 별도 앱이 같은 핀 파일을 쓰면 쓰기를 잃는다.

## 결정

| # | 결정 | 상태 |
| --- | --- | --- |
| D1 | 지원 범위를 **"LaTeX 원고와 벡터 그래픽"**으로 넓힌다. 벡터 그래픽은 PDF 한 쪽에 그림 한 장으로 받는다. 코드로 그린 그림이 첫 사용처다 | 확정 |
| D2 | 그림 문서는 `DOCS=` 항목이 `.limnmap.json` 지도 파일을 가리켜 등록한다. 확장자로 종류를 정하는 지금 규칙을 따르고, 옆 파일 자동 탐지는 쓰지 않는다 | 확정 |
| D3 | 렌더는 그림 저장소가 한다. Limn은 PDF와 지도를 가져오기만 하고, 외부 코드나 외부 API를 실행하지 않는다 | 확정 |
| D4 | 그림 핀은 생성 스크립트의 줄 핀이다. 선택 필드 `el` 하나를 더한다. 렌더를 건넌 위치(`mark`·`el_sync`)는 저장하지 않고 읽을 때 계산한다 | 확정 |
| D5 | 에이전트 계약의 **값 목록을 늘린다**(A안). 늘어나는 값은 다음과 같다. SKILL의 재빌드 규칙은 같은 변경에서 문서 종류 `tex` 기준으로 고친다 | 확정 |
| D6 | pick 임계값은 `cover ≥ 0.6`, `fill ≥ 0.5`로 시작한다. 지도를 내는 첫 그림 도구로 재어 조정한다 | 잠정 확정 |
| D7 | 코드 줄이 없는 벡터 그래픽도 범위에 든다. 서버 밖 내보내기 도구가 PDF와 지도를 쓰고, 지도의 `src`는 생략한다. 그 핀은 영역 모양에 `el`을 붙인다. 내보내기 도구는 P4다 | 확정 |

D5로 늘어나는 값 목록은 넷이다.

| 필드 | 늘어나는 값 |
| --- | --- |
| 문서 `kind` | `figure` |
| `scope`, `levels[].level` | `el`, `el2`…`el8`, `fig` |
| 핀 `kind` | `el:<부품>`, `figure` |
| `via` | `map` |

**D5를 A로 정한 근거.** 값 목록을 늘려도 저장과 되돌리기가 안전하다는 것을 코드로 확인했다.

- 레코드 검사는 `kind`·`via`·`scope`가 문자열인지만 본다.
- 저장소는 모르는 필드를 바이트 그대로 되쓴다.
- `pins.md`의 범위 칸은 모르는 `scope`면 `kind`를 그대로 싣는다.

위험은 목록이 전부라고 가정한 소비자에게 있다. 대표적인 예가 "보기 전용이 아니면 재빌드"라는 SKILL 규칙이다. 이 규칙은 같은 변경에서 고친다.

## Trade-off

**장점.**

- 주소·핀 번호·사람·토큰·`pins.md`·SKILL이 하나로 유지된다. 원고와 그림을 한 인스턴스에서 오가며 리뷰한다.
- PDF.js 뷰어, 보기 전용 감시, 쪽 버전, 줄 anchor를 다시 쓰므로 새 코드는 지도 해석과 pick, 읽을 때 계산하는 위치에 한정된다.
- 새 값은 뜻을 그대로 드러낸다. 새 에이전트가 그림 핀을 LaTeX 환경이나 보기 전용 PDF로 오해하지 않는다.

**비용.**

- 목적 문장이 넓어진다. 문서 종류마다 능력이 달라, 분기를 능력 값으로 먼저 정리하는 구조 이동(P0)이 필요하다.
- 계약 값 목록이 네 개 늘어난다. 옛 에이전트는 그림 문서에 재빌드를 요청하고 `400`을 받는 헛걸음을 할 수 있다. 데이터 손상은 없다.
- 그림 저장소는 지도를 내야 하고, 요소 id를 렌더마다 같게 유지해야 한다.

## 대안

| 대안 | 선택하지 않은 이유 |
| --- | --- |
| 핀 파일을 함께 쓰는 별도 앱 | 핀 잠금이 프로세스 안의 잠금이라 두 프로세스의 쓰기가 서로를 덮는다(불변식 4). 번호 발급과 `pins.md` 렌더도 쓰는 쪽을 하나로 가정한다 |
| 핀 파일까지 따로 둔 별도 앱 | 인증·사람·수명 주기·뷰어를 복제하고, 주소와 번호 공간이 갈린다. "앱 이름은 Limn 하나" 불변식과 부딪힌다 |
| 값 목록은 그대로 두고 필드만 더함(D5의 B안) | 그림 문서가 "보기 전용 PDF인데 줄 핀이 있다"는 모순된 모양이 된다. 그림의 상위 요소가 LaTeX 환경 이름으로 실려 새 소비자까지 헷갈린다 |
| 그림을 PNG로 받음 | 뷰어의 PDF.js 경로, 쪽 수 검사, 목차를 끄는 분기가 뷰어 곳곳에 들어간다 |
| 서버가 생성기를 실행하거나 디자인 도구 API를 부름 | 새 실행 경로와 외부 자격증명이 생기고, 렌더 도구가 런타임 의존성이 된다 |

## 결과

- 구현은 [계획 색인](../superpowers/plans/2026-09-30-figure-documents.md)의 P0 → P1a → P1b → P1c 순서로 한다. 한 단계는 PR 하나다. 0.4.0은 P1c까지 `main`에 들어간 뒤 낸다.
- `bad_scope`·`bad_via`의 오류 문장은 늘어난 값 목록을 나열한다. `reason` 코드는 바뀌지 않는다. 에이전트는 문장이 아니라 `reason`으로 판단하므로, 허용 값을 나열하는 문장이 옛 목록을 말하면 오히려 에이전트를 틀리게 이끈다.
- 결정을 바꿔야 하면 이 ADR의 상태 칸과 결정 표를 먼저 고친 뒤 계획을 고친다.

### 현재 상태 투영

- **영향받는 현재 권위**
  - `src/limn/documents.py`의 문서 종류
  - 빌드 가져오기(`features/builds`)와 pick(`features/pins/location`)
  - 핀 레코드 검사(`pins/record.py`)
  - 에이전트 계약(`api.md`, `pins.md`, SKILL)
  - 뷰어
- **갱신할 Handbook role/path**
  - purpose `docs/handbook/purpose.md`(지원 범위)
  - domain `docs/handbook/domain.md`(여러 문서, 지도 pick, 요소 따라가기)
  - build-sync `docs/handbook/build-sync.md`(그림 가져오기)
  - api `docs/handbook/api.md`(값 목록, `el`, 읽기 필드)
  - viewer `docs/handbook/viewer.md`
  - instances `docs/handbook/instances.md`(`DOCS=`)
  - `docs/handbook/index.md` 파일 지도
- **효력 형태:** 단계적 migration(P0–P1c)
- **완료 증거**
  - 각 단계 PR의 게이트가 녹색이다.
  - 계약 스냅숏에 그림 흐름이 있다.
  - 그림 핀이 있는 상태 폴더를 직전 릴리스가 읽을 때 핀이 지워지지 않는다.
  - 실제 그림 세트로 화면을 실측했다.
