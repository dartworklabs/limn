# ADR-0009: 백엔드를 기능별 세로 슬라이스로 이행

| | |
|---|---|
| **번호** | ADR-0009 |
| **제목** | 백엔드를 기능별 세로 슬라이스로 이행 |
| **상태** | 제안 |
| **결정일** | 2026-09-28 |
| **결정자** | 프로젝트 소유자 |
| **부분 대체** | ADR-0001의 축 1(1차 구조축): 책임별 모듈을 기본 분할 단위로 삼고 VSA를 제외한 결정 |
| **출처** | [백엔드 VSA 점진 이행 설계](../superpowers/specs/2026-09-28-backend-vsa-migration-design.md) |

## 맥락

Limn의 백엔드는 단일 서버 파일에서 책임별 모듈로 이동했다. 실행별 설정·자원 소유권과 순수 규칙·부수효과·HTTP 경계는 명시됐지만, 한 사용자 동작의 입력·판단·저장·응답이 여러 가로 모듈과 `ServerApplication`의 전달 메서드에 흩어져 있다. 프로젝트 소유자는 이 구조의 논리적 불협화음과 동작을 이해할 때의 인지부하를 줄이고, 백엔드 전체를 작은 변경으로 VSA까지 옮기기로 했다.

`ADR-0001`은 웹 SaaS용 VSA를 제외하고 핀 도메인·역변환·저장·빌드·HTTP의 책임별 모듈을 채택했다. 당시의 단일 파일 분리에는 적절한 경계였으나, 이제 평면 `App` 계약과 조립 지점의 기능별 전달 표면이 커졌다. 단일 배포와 실행별 자원, 핀의 상태 타입·저장 잠금, 에이전트 계약의 호환은 계속 유효하다.

## 결정

백엔드 사용자 동작의 **1차 코드 소유 단위를 기능별 세로 슬라이스**로 바꾼다. HTTP 입구·파싱·응답, 해당 동작의 순수 판단과 부수효과를 같은 기능 패키지에 둔다. 공통 요청 보안 가드, 핀 저장 트랜잭션, 실행별 자원 수명, 여러 슬라이스가 실제로 함께 쓰는 타입·파일·문서 규칙은 한 곳에서 유지한다. 슬라이스 안에서도 순수 판단은 파일·HTTP를 모르고, 실행별 협력자는 명시적 인자로 받는다.

전체 백엔드를 한 번에 다시 쓰지 않는다. 완성된 사용자 동작 경로마다 기존 소유자를 제거하고, 동일한 응답과 저장 바이트를 확인하며 점진적으로 이행한다. 끝에는 공통 HTTP 처리기와 조립 지점에 기능별 분기·전달 메서드가 남지 않게 한다. 첫 대상은 핀 닫기·다시 열기·확인이다. 세부 단계와 전체 완료 조건은 출처 설계에 있다.

## Trade-off

**장점:** 한 동작을 바꿀 때 관련 입력·판단·부수효과·응답의 소유자를 한 기능 패키지에서 찾는다. `ServerApplication`과 평면 `App` 계약의 기능별 전달 표면을 제거하고, 이행 과정에서 각 동작의 결정권을 드러낸다.

**비용:** 파서·응답·순수 규칙을 옮기는 동안 import 경로와 테스트의 내부 교체 지점이 바뀐다. 슬라이스마다 같은 전송·보안·저장 규칙을 복사하지 않도록 공통 핵심의 경계를 계속 검토해야 한다. 중간에는 옛 책임별 모듈과 새 슬라이스가 공존하지만, **같은 동작의 이중 소유권은 허용하지 않는다.**

## 대안

| 대안 | 선택하지 않은 이유 |
| --- | --- |
| 현재 책임별 모듈을 유지하고 `ServerApplication`만 더 나눈다 | 전달 메서드를 다른 객체로 옮길 수는 있지만, 사용자 동작을 이해하는 경로와 평면 HTTP 계약의 부담이 남는다. |
| 백엔드를 한 PR에서 전면 VSA로 재작성한다 | 요청 보안 순서, 핀 저장 바이트, 실행별 자원 수명의 회귀를 작은 차등 비교로 분리하기 어렵다. |
| 경로 하나마다 독립 슬라이스와 저장소를 만든다 | 공통 핀 상태·잠금·권한이 복제되거나 서로 다른 결정을 내릴 수 있다. 동작의 변경 이유로 묶고 공통 불변식은 한 곳에 둔다. |

## 결과

- `ADR-0001`의 축 1 중 **책임별 모듈을 1차 분할 단위로 채택하고 VSA를 제외한 부분만** 이 결정이 대체한다. 단일 배포, 실용적 함수형 설계, 검수·에이전트 계약·시간축 호환에 관한 나머지 조항은 유지한다.
- 승인된 목표와 현재 실재를 구분한다. 각 슬라이스가 실제로 옮겨질 때 `architecture.md`와 `index.md`의 현재 구조·파일 지도를 같은 변경에서 갱신한다. 이행이 끝나면 채택한 1차 구조가 코드와 일치한다.
- API·`pins.md`·저장 형식·보안 경계·런타임 의존성은 이 결정으로 변경되지 않는다. 그런 변경이 필요해지면 별도 설계 판단을 받는다.

### 현재 상태 투영

- **영향받는 현재 권위:** `src/limn/`의 백엔드 구조와 이를 검증하는 테스트. 기능별 이행이 끝날 때까지 현재 코드는 책임별 모듈 구조다.
- **갱신할 Handbook role/path:** architecture `docs/handbook/architecture.md`, purpose의 정본 안내 `docs/handbook/purpose.md`(위치가 바뀔 때), 관련 일반 topic과 `docs/handbook/index.md` 파일 지도, verification `docs/handbook/verification.md`(게이트가 바뀔 때).
- **효력 형태:** 단계적 migration.
- **완료 증거:** 모든 백엔드 동작의 슬라이스 소유권, 평면 앱 전달 표면 제거, 요청·저장 차등 비교, 적용 게이트 통과, Handbook의 현재 구조와 코드 일치.
