## 맥락

검토 대기는 에이전트가 닫은 결과를 사람이 봤다는 기록이다(domain.md §전이와 할 수 있는 쪽). 지금은 카드 한 장마다 [확인]을 누르고, 누를 때마다 6초 되돌리기 줄이 선다. 에이전트가 한 번에 스무 건 넘게 닫으면 사람은 같은 일을 스무 번 넘게 한다. 실제 인스턴스에 검토 대기가 22건 쌓인 일이 이슈 #453의 계기다.

여러 건을 한 번에 확인하게 하면 "사람이 결과를 봤다"는 뜻이 흐려질 수 있다. 카드는 스레드와 닫을 때 남긴 답을 보이고, 사람은 카드 한 장을 보고 [확인]을 누른다. 목록에서 여러 건을 함께 누르면 사람이 무엇을 보고 눌렀는지가 기록의 뜻을 정한다.

## 결정

| # | 결정 |
| --- | --- |
| D1 | 검토 대기 구획에 [골라서 확인]을 둔다. 누르면 카드가 **결과 줄**로 바뀐다. 줄마다 고를 상자, `#N`과 위치, 판정·제안 수정 배지, 요청(메모 첫 줄), 에이전트의 답(`close_reply`), 참조(`close_ref`), 바뀐 줄(`changes`)이 있고 [변경 보기]가 있다. 사람은 고른 줄만 [N건 확인]으로 함께 확인한다. 하나씩 빼고 확인할 수 있다 |
| D2 | 결과를 보이지 못하는 줄은 고를 수 없다. 답도 바뀐 줄도 없이 닫힌 핀이 그렇다. 이런 핀은 카드에서 하나씩 확인한다. 판정 핀과 제안 수정 핀은 고를 수 있다 |
| D3 | 줄을 고르는 순간 그 줄이 보인 닫기의 `done_at`을 함께 기억하고, 확인 요청은 그 값을 보낸다. 고른 뒤 핀이 다시 닫히면 서버가 `409 conflict`로 거절하고(ADR-0013), 뷰어는 그 핀을 다시 닫혔다고 알린다. 결과 줄을 보고 고른 것을 사람이 본 닫기로 친다 |
| D4 | 새 경로를 만들지 않는다. 뷰어는 한 번의 되돌리기 줄(6초)이 끝나면 고른 핀마다 `POST /api/pins/{id}/confirm`을 한꺼번에 시작하고 각 답을 따로 받는다. 거절된 핀은 이유와 함께 한 배너로 알리고, 서버에 닿지 않은 핀만 [다시 시도]로 다시 보낸다. HTTP API·`pins.md`·저장 형식·SKILL은 그대로다 |
| D5 | 확인은 지금처럼 사람만 한다. [골라서 확인]은 확인할 수 있는 사람의 화면에만 있고, 서버는 에이전트의 요청을 핀마다 `403`으로 막는다 |

## Trade-off

**장점:**
- 결과를 줄로 모아 훑고 고르므로, 여러 건을 확인해도 사람이 무엇을 보고 눌렀는지가 줄에 남는다.
- 에이전트 계약과 저장 형식이 그대로라 다른 저장소의 에이전트와 옛 뷰어 탭이 영향받지 않는다.
- 핀마다 따로 확인하므로 한 핀의 충돌이 다른 핀의 확인을 막지 않는다.

**단점·포기한 것:**
- 원자적이지 않다. 22건 가운데 몇 건만 확인되고 나머지가 거절될 수 있다. 각 확인은 원래 서로 독립이라 받아들인다. 배너가 무엇이 왜 빠졌는지 말한다.
- 요청이 핀 수만큼 나간다. 시험 인스턴스에서 확인 한 건은 약 16 ms였고 22건을 차례로 보내도 1초 안팎이었다. 한꺼번에 시작하므로 탭을 닫는 순간에도 브라우저가 `keepalive`로 모두 보낸다.
- 답도 바뀐 줄도 없는 핀은 여전히 카드에서 하나씩 확인해야 한다.

## 대안

| 대안 | 선택하지 않은 이유 |
| --- | --- |
| 구획 머리의 [모두 확인 N] 한 버튼(후보 B) | 빠르지만 하나씩 뺄 수 없고, 사람이 줄을 보지 않고도 누를 수 있어 "결과를 봤다"는 뜻이 약해진다 |
| 일괄 확인 경로(`POST /api/pins/confirm` 같은 것)를 새로 둔다 | 요청이 한 번이라 탭을 닫을 때 더 확실하지만, HTTP API에 경로를 더하는 계약 변경이라 설계 승인·계약 시험·SKILL 설명이 따른다. 핀마다 판단이 다른 응답 모양도 새로 정해야 한다. 지금의 단건 경로로 충분히 빠르다 |
| 결과 줄 없이 카드에 고를 상자만 단다 | 카드가 길어 22건을 한눈에 볼 수 없고, 고른 것을 훑어 다시 보기 어렵다 |
