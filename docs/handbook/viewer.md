# 뷰어 — 화면 규칙과 근거

이 문서는 브라우저 뷰어가 어떻게 보이고 어떻게 움직여야 하는지를 정한다. 레이아웃, 컴포넌트, 디자인 토큰, 화면에 드러나는 상태, 입력과 렌더링 규칙을 다루고 규칙마다 왜 그렇게 정했는지를 함께 적는다. 뷰어 화면이나 입력 동작을 바꾸기 전, 그리고 사용자 지적·QA로 화면 규칙이 바뀐 뒤에 읽고 고친다. 서버 API·핀 형식은 [api.md](api.md), 역변환·범위 사다리·앵커·저장소 같은 핀의 뜻은 [domain.md](domain.md)가 맡는다. 이 문서의 규칙은 대부분 "서버 API·핀 형식은 그대로이고 뷰어만 바뀐다"는 조건에서 정해졌다.

> **한눈에**
>
> - 고치기 전에 볼 곳과 가드: §뷰어 규칙을 바꿀 때
> - 화면 폭에 따른 배치: §레이아웃 (모바일 레이아웃, 펼친 화면 레이아웃)
> - 오른쪽 패널·시트·목록: §패널과 목록 (패널 정리, 패널 폭과 시트 높이, 보관함)
> - 알림·상태 점·배지·링크 모양: §상태와 표시
> - 스레드·검토·변경 보기·@태그·담당·브라우저 알림: §협업 UI
> - 한 뷰어에서 문서 여러 개 전환: §여러 문서 전환
> - 색·radius·글자·간격 토큰, 컴포넌트, 아이콘, Limn 마크·파비콘: §디자인 토큰과 컴포넌트
> - PDF.js 벡터 렌더링과 PDF 영역 확대: §렌더링과 확대
> - 재지 못한 것과 화면·입력의 한계: §알려진 제약

## 뷰어 규칙을 바꿀 때

뷰어는 별도 프런트엔드 프로젝트가 아니다. [`src/limn/viewer/`](../../src/limn/viewer/parts.txt)의 파일 — 마크업 `index.html`, 스타일 조각 `css/*.css`, 스크립트 조각 `js/*.js`, 조각의 순서를 적은 `parts.txt` — 이 전부이고, 빌드 단계·번들러·모듈 로더·CDN이 없다. 서버는 시작할 때 `parts.txt`에 적힌 순서대로 조각을 바이트 그대로 이어 붙여 `index.html`의 `__APP_CSS__`·`__APP_JS__` 자리에 끼우고(`limn/viewer/assemble.py`의 `load_viewer_html()`), 그렇게 만든 한 장의 HTML에 버전·아이콘·영어 표 자리 표시자를 채운다(`viewer_html()`, 입력은 모두 인자다). `server.py`는 그 결과를 `HTML`로 두고, 실행 인자가 정해지면 라벨·색 자리 표시자를 채워(`build_html()`) 내보낸다. 그래서 페이지에는 `<style>` 하나와 주 `<script>` 하나가 있고, 화면 규칙을 바꾸는 일은 곧 이 파일들을 고치는 일이다. 표식은 `index.html`에 한 번씩만 있어야 하고, 어기면 서버가 시작하지 않는다 (`tests/test_viewer_files.py`).

**조각은 책임별로 나누고, 순서는 `parts.txt` 하나가 정한다.** 2026-09-26 한 파일이던 `app.js`(2,985줄)와 `app.css`(902줄)를 변경 이유가 다른 조각 45개로 나눴다([code-style-roadmap.md](code-style-roadmap.md) R6). 나눈 자리는 원래 파일의 구역 배너와 같고, 나눌 때는 조각을 목록 순서대로 이으면 원래 파일과 바이트 단위로 같았다. 그래서 나누기 전후 `HTML`과 `build_html()` 결과의 sha256이 같았다. 조각마다 맡은 일은 `parts.txt`의 각 줄에 적혀 있고, 흐름은 이렇다.

- 스타일(`css/`, 10개): 토큰(`tokens.css`) → 화면 틀 → 변경 보기 → 패널 틀·도구 막대 → 컴포넌트 → 작성 패널 → 카드 → 목록 → 떠 있는 층(알림·툴팁·대화상자) → 폭별 배치(`responsive.css`).
- 스크립트(`js/`, 35개): 공용 바탕(`core.js`: DOM 도우미·아이콘·공유 상태) → 화면 언어(`i18n.js`)·설정 → `api()`와 알림 → 툴팁 → 여러 문서·변경 보기·문서 전환 → 시작(`boot.js`)·폴링·브라우저 알림·빌드 칩 → 패널 크기·쪽·PDF.js(`pdf-open.js` 열기, `outline.js` 목차, `pdf-draw.js` 그리기)·확대 → 배치·제스처 → 선택·범위 사다리·작성 패널·초안·저장 → 카드·목록·핀 조작 → @태그·답글·편집·위치 다시 잡기·재빌드 → 이벤트 위임과 `boot()` 호출(`events.js`).

> **주의**
>
> 조각은 모듈이 아니다. JS 조각은 모두 예전 `app.js`처럼 고전 스크립트 하나의 범위를 나눠 쓴다. 함수 선언은 어느 조각에서나 보이지만, 최상위 코드(`let`·`const`, 리스너 등록, 바로 부르는 함수)는 목록 순서대로 실행된다. 그래서 위쪽 조각의 `let`·`const`만 쓸 수 있고, 순서를 바꾸면 페이지가 시작하다 멈출 수 있다. 새 코드는 맡은 일이 같은 조각에 넣고, 새 조각을 만들면 `parts.txt`에 줄을 더한다.

조각은 마지막 줄바꿈으로 끝나야 한다. 그래야 이어 붙일 때 앞 조각의 끝 줄이 다음 조각의 첫 줄과 붙지 않는다. `css/`·`js/`에 있는데 목록에 없는 파일, 목록에 두 번 나온 파일, 형식에 맞지 않는 목록 줄은 테스트나 서버 시작에서 실패한다. 분리는 바이트를 그대로 두려고 구역 배너 주석을 고치지 않아서, 한 구역이 여러 조각으로 갈린 곳은 첫 조각이 구역 전체의 배너를 달고 있었다. 그 뒤 배너만 고쳐 조각마다 제 내용을 가리키게 했다. `i18n.js`는 'UI language', `card-parts.js`는 'Pin card parts', `doc-tabs.js`는 'list/tabs/links' 배너로 시작하고, 원래 배너 'Preferences'·'Pin list'와 문서 전환 배너는 그 내용이 있는 `prefs.js`·`list.js`·`doc-switch.js` 첫 줄로 옮겼다. 주석만 바뀌었고 코드는 그대로다.

> **핵심**
>
> 화면 규칙을 바꾸면 세 곳을 같은 diff에서 맞춘다: `src/limn/viewer/`의 파일, `tests/test_server.py`의 `Frontend*` 가드, 그리고 이 문서의 해당 절.

**CSS는 조각 여러 개지만, 페이지에는 인라인 `<style>` 하나로 들어간다.** 그 맨 앞, 첫 조각 `css/tokens.css`에 토큰 블록 세 개가 있다. 다크 테마 `:root`, 라이트 테마 `:root[data-theme=light]`, 테마와 무관한 척도 `:root`이다. 색 리터럴은 앞의 두 블록 안 변수 정의에만 둘 수 있다. 나머지 규칙은 모두 `var(--…)`를 쓴다(§토큰).

**UI 문자열은 한국어가 원본이고, 영어는 메시지 표로 바꾼다.** 템플릿과 JS에 적힌 한국어 문자열이 정본이다. 영어 화면에서는 [`src/limn/ui_en.json`](../../src/limn/ui_en.json)의 "한국어 → 영어" 표를 찾아 바꾼다. 동작 방식은 이렇다.

- `server.py`를 읽어 들일 때 `load_ui_messages()`(`limn/viewer/assemble.py`)가 표를 읽어 `UI_EN`에 두고, `viewer_html()`이 `__UI_EN_JSON__` 자리를 JS 객체 `I18N_EN`으로 채운다. 거부된 첫 화면도 같은 `UI_EN`을 읽는다.
- 영어 모드에서 `tr()`·`trMsg()`가 표를 찾는다. `trMsg()`는 문자열 전체가 표에 없으면 ` — ` 또는 ` · `로 나눈 조각마다 다시 찾는다. 그래서 조합한 문구도 조각 단위로 번역된다.
- `MutationObserver`가 새로 그려지는 글자 노드와 UI 속성(`data-tip`·`aria-label`·`title`·`placeholder`)을 번역한다. 알림(`toast`)도 `trMsg`를 거친다.
- 실행 중에 조합하는 문구는 `tl('<한국어 틀>', {값})`으로 만든다. 틀 안의 `{name}` 자리에 값을 넣는다(예: `tl('{n}쪽', {n: 3})`). 영어 값은 `{"one": ..., "other": ...}` 복수형일 수 있고, `n`으로 고른다. 문서 탭 이름·메모·답글·원고처럼 사용자가 쓴 글은 번역하지 않는다.
- 표에 없는 문자열은 한국어로 남는다.
- 화면 언어는 `?lang=` 쿼리 → 저장한 선택(localStorage `limnLang`) → 브라우저 언어(`navigator.language`가 `ko`로 시작하면 한국어, 아니면 영어) 순으로 정한다. [더보기]의 `#m-lang`으로 바꾼다.
- pins.md와 API는 번역하지 않는다. 에이전트가 읽는, 언어가 고정된 계약이기 때문이다.
- API 오류는 `errText()` 한 함수를 거친다. 한국어 화면은 서버의 `error` 문장을 그대로 보인다. 영어 화면은 오류 본문의 `reason` 코드로 표의 `reason:<코드>` 영어 문장을 찾고, 없으면 서버 문장을 표로 옮긴다(`trMsg`). 알림(`api()`), 작성 패널과 위치 다시 잡기 배너의 pick 오류, 편집 카드의 원문 칸, 비교 PDF 상태 줄이 이 함수를 쓴다. 코드 목록은 [api.md](api.md) §오류 응답에 있다. 영어 문장은 거절을 가르는 값(한도·줄 수)을 싣지 않는다. 그 값은 한국어 `error` 문장에만 있다.
- pick의 `warn`(작성 패널의 경고 한 줄, 오류 본문이 아니다)은 서버가 문장 한두 개를 공백으로 이어 보낸다. 영어 화면에서는 `warnText()` 가 문장마다 `PICK_WARNS` 의 한국어 틀(숫자 자리 `{x}`)과 맞춰 `tl()` 로 옮긴다. 한국어 화면은 서버 글 그대로다. 서버에 새 경고 문장을 더하면 `PICK_WARNS` 와 표에도 더한다(`test_i18n.PickWarnings` 가 `pick()`·`_pick_region()` 의 문장과 틀을 대조한다).

[`tests/test_i18n.py`](../../tests/test_i18n.py)가 이 연결을 지킨다. 정적 마크업(`<body>`부터 첫 `<script>`까지)의 한국어 글자와 UI 속성은 전부 표에 있어야 한다. `trMsg()`처럼 ` — `·` · ` 조각 단위로 찾아도 된다. 표의 값에는 한글이 없어야 하고, 키에는 `__` 자리표가 없어야 한다. 0.1.1부터는 `tl()` 틀에 번역이 없으면 실패하고, 실제 뷰어를 영어로 띄워 사용자 글 밖에 한글이 남으면 실패하는 브라우저 테스트(데스크톱·폴더블·휴대폰)도 있다. 0.3.4부터 같은 브라우저 테스트가 흔한 거절(`403` 보기 권한, `409` `base_rev` 충돌, `400` 입력 검사, `404` 없는 핀, `422` 핀 단위 비교)의 오류 알림도 본다. 영어에서는 `reason` 의 영어 문장이고 한글이 없어야 하며, 한국어에서는 서버 문장 그대로여야 한다. [`tests/test_errors.py`](../../tests/test_errors.py)는 서버가 내는 코드마다 영어 문장이 있는지 본다. 그래도 `tl()`·`tr()`을 거치지 않은 JS 문구는 잡히지 않을 수 있으니, 새 문구는 늘 이 함수들을 거치고 `ui_en.json`에 추가한다.

**가드는 `tests/test_server.py`의 `Frontend*` 클래스다.** 대부분은 배포되는 `ps.HTML` 문자열에서 고친 패턴이 있고 옛 버그 패턴이 없는지를 본다. `...Logic` 클래스는 JS 함수를 node로 떼어 실행하며, node가 없으면 건너뛴다. `FrontendResponsiveBrowser`는 실제 Chromium으로 레이아웃·키보드 회귀를 잰다. `$LIMN_CHROMIUM` → 시스템 Chrome/Chromium → Playwright 번들 Chromium 순으로 찾고, 못 띄우면 건너뛴다(`LIMN_TEST_REQUIRE_BROWSER=1`인 CI에서는 실패). 조각과 조립은 [`tests/test_viewer_files.py`](../../tests/test_viewer_files.py)가 지킨다. 목록과 파일이 맞는지, 조립한 페이지가 조각을 이은 것과 같은지 본다. 내보내는 페이지(`build_html()`)의 인라인 스크립트마다 `node --check`를 돌려, 문법 오류를 조각 파일과 줄(예: `js/cards.js:41`)로 알린다. node가 없으면 건너뛰고, `LIMN_TEST_REQUIRE_NODE=1`인 CI에서는 실패한다.

| `wide` | 1100px 이상 | 오른쪽 패널, 기본 348px, 폭 조절, 손잡이로 접기(§패널 폭과 시트 높이) | 왼쪽 고정 패널; 접힘·폭 저장값 유지 |
| `mid` | 701–1099px, 입력 장치와 무관 | 기본 330px. 701–900px은 처음에 접힌 오버레이, 901–1099px은 처음에 열린 문서 옆 패널. 위 탐색 줄과 아래 동작 줄 사이에서만 펴고 접는다(§펼친 화면 레이아웃) | 처음에는 접힘. 펼치면 문서 위 오버레이; 핀 패널과 하나씩 연다 |
| `narrow` | 700px 이하 | 하단 시트, 기본은 접힘; 윗가장자리 손잡이로 높이 조절 | 기존 모바일 문서 전환 유지 |

**레이아웃 고르기.** JS가 `innerWidth`로 레이아웃을 고른다(`layoutFor`). `pointer:coarse`는 터치 버튼 크기와 선택 입력만 정한다. 접기·펴기로 폭이 바뀌면 `resize`·`ResizeObserver`가 다음 프레임에 레이아웃을 다시 고른다. 이때 보던 자리(`topAnchor`)를 지킨 채 쪽 폭을 다시 맞춘다. 마크와 선택 상자는 쪽 안 % 좌표라 따로 옮기지 않는다.

**목차 토글은 하나다.** 문서 탐색 줄 맨 왼쪽의 `#nav-toc-toggle`이 열릴 때도 닫힐 때도 같은 위치를 지킨다.

- aria-expanded와 동작 이름을 갱신하고 Enter/Space로 누를 수 있다.
- 중간 폭의 목차는 Escape 또는 장·절 선택으로 닫고, 초점을 토글로 돌린다.
- 목차를 여닫기 전의 쪽과 쪽 안 비율도 복원한다.
- 중간 폭에서 목차를 펴고 핀 패널을 접어도 데스크톱 목차 저장값은 바꾸지 않는다.

**지금 절 표시.** 목차 항목은 쪽 번호와 함께 그 쪽 안의 세로 위치(`frac`, PDF XYZ 목적지의 위쪽 좌표를 쪽 높이로 나눈 값, 없으면 0)를 가진다(`destFrac`). 절 표시줄 `#section-current`와 목차 강조는 화면 위에서 조금 내려온 읽는 선(보이는 높이의 1/4, 최대 160px)보다 위에서 시작한 마지막 제목을 고른다(`outlineIndexAt`). 첫 제목보다 위(제목 쪽, 1쪽 맨 위)에서는 첫 절을 보인다. 0.2.0은 쪽 번호만 봐서 1·1.1·1.2가 모두 1쪽에서 시작하면 1쪽 맨 위에서 `1.2`를 보였다. 목차에서 고른 항목은 그 쪽을 벗어날 때까지 그대로 강조한다.

**번호와 인쇄 쪽 번호.** PDF outline에는 절 번호(`1.1`)와 인쇄 쪽 번호(`iv`)가 없다. 그래서 뷰어는 `GET /api/outline-labels`로 같은 빌드가 PDF와 함께 남긴 `.aux`의 목차 줄을 받아, 제목·계층·순서가 맞는 항목에만 붙인다(`mergeOutlineLabels`). 서버 쪽은 `.aux`를 읽는 일(`limn/meta.py`의 `outline_labels`)과 목차 줄을 해석하는 순수 파서(`limn/outline.py`)로 나뉜다. 응답 형식은 [api.md](api.md)에 있다.

**중간 폭의 패널 기억.** 중간 폭에서 사용자가 [핀]·손잡이·Esc·밀어 닫기·Ctrl+\로 직접 여닫으면 `pinPrefs.midClosed`에 기억하고, 폭이 바뀌어도 유지한다. 저장한 선택이 없으면 900px 경계를 넘을 때 위 표의 기본값을 적용한다. 작성·편집 중인 메모가 있으면 패널을 열어 둔다.

**상단 공간.** 문서 링크는 한 줄을 유지하며 필요하면 그 줄 안에서 가로로 스크롤된다. 중간 폭은 이름표를 [더보기]에 두고, 보기 전환과 목차 버튼은 줄어들지 않는다. 탐색 줄 높이는 마우스 44px, 터치 48px이다. 첫 안내는 `wide`에서는 탐색 줄 아래에, `mid`에서는 동작 줄 바로 위 왼쪽([선택] 위)에 뜬다. 안내 글은 클릭을 가로채지 않고 닫기 버튼만 입력을 받는다.

**compact에서 쪽 폭은 저장하지 않는다.** compact(`mid`·`narrow`)에서는 쪽 폭을 늘 화면에 맞추고 저장하지 않는다. −/＋를 누르면 그 레이아웃 동안만 유지한다. 접은 화면의 폭이 데스크톱 설정을 덮지 않게 하려는 것이다.

**도구 줄에는 넷만 남긴다.** `[핀 N]`(패널·시트 토글, 열린 핀 수), `[선택]`(터치에서만), `[PDF 재빌드]`, `[더보기]`다. 나머지는 `[더보기]` 대화상자로 옮긴다. 옮긴 것은 핀 다시 읽기, 쪽 이동, 축소, 확대, 폭 맞춤, 테마, 도움말, 닫힌 핀, 휴지통이고, 파일·쪽 수·커밋·빌드 시각·작성자 줄도 거기 있다. 원고 수정됨·빌드 진행·연결 끊김·빌드 오류 칩은 접힌 상태에서도 도구 줄 위에 남는다. `mid`에서는 동작 줄 바로 위 오른쪽에 뜬 카드로 보인다.

**대화상자는 바깥을 누르면 닫힌다.** [더보기]·도움말·문서 목록·휴지통이 모두 같다(바깥 = 대화상자 상자 밖의 배경). 예전에는 도움말과 문서 목록만 닫히지 않았다(입력 점검 2026-09-26).

**핀 카드는 아코디언이다.** 접힌 카드는 머리 한 줄(번호·줄 범위·쪽 ··· 담당·답글 수·접기)과 그 아래 메모 미리보기 두 줄(`.sum`)만 보인다. 누르면 태그·메모·버튼이 펼쳐진다.

- 예전에는 미리보기가 머리 한 줄의 남은 폭만 받아 '[C…' 한 조각만 보였다. 이를 고쳤다(QA 2026-09-24).
- 검토 대기 카드는 미리보기 앞에 '내 확인 차례 · '를 붙이지 않는다. 보라 점이 이미 상태를 말한다.
- 마크 배지를 누르면 패널을 펴고 그 카드를 펼친다.
- `wide`는 예전 카드 그대로다.

**선택 입력은 Pointer Events 한 경로다.** 입력 장치마다 동작이 다르다.

- 마우스는 모드와 무관하게 예전처럼 끌어서 고른다.
- 터치·펜은 **선택 모드**를 켰을 때만 한 손가락 끌기가 사각형이 된다. 이때 쪽에 `touch-action:none`을 준다. 두 손가락은 §PDF 영역 전용 확대가 받는다. 선택 모드에서 탭은 **빠른 선택**이다.
- 선택 모드가 아니면 스크롤·확대가 평소대로 되고, **길게 누르기(450ms)** 가 빠른 선택이다.
- 빠른 선택은 누른 점 둘레의 작은 상자(쪽 폭 ±7%, 높이 ±0.6%)로 기존 `/api/pick`을 부른다. 서버의 기본 단계가 본문에서는 '문단', 그림·표에서는 '환경'이라 그대로 쓰고, 범위 사다리로 넓힌다([domain.md](domain.md) §범위 사다리).
- 저장하거나 취소하면 선택 모드는 저절로 꺼진다. 다시 스크롤되게 하려는 것이다.
- 두 번째 손가락이 닿으면 그리던 상자를 버린다.

**좌표.** 좌표는 `clientX/Y`를 `getBoundingClientRect`로 나눈 쪽 안 비율이다. 둘은 같은 레이아웃 뷰포트 기준이라 브라우저 핀치 확대 중에도 맞는다. Playwright에서 scale 5로 확대한 뒤 끌어 오차 1e-8을 확인했다. 지금은 PDF 영역의 브라우저 핀치를 막고 앱 확대로 바꾼다(§PDF 영역 전용 확대).

**툴팁과 포커스.** 터치 직후의 흉내 `mouseover`·`focusin`으로는 툴팁을 띄우지 않는다. 설명은 버튼을 길게 누르면 뜨고, 그때 손을 뗀 click은 삼켜서 버튼이 눌리지 않게 한다. 터치로 고른 뒤에는 메모 칸에 자동 포커스하지 않는다. 가상 키보드가 범위 사다리를 덮었기 때문이다.

**유령 클릭.** 터치를 뗀 뒤 브라우저가 보내는 click은 그 사이 손가락 밑으로 온 요소에 떨어진다. 손가락 밑의 화면을 바꾸는 동작 뒤에는 그 click 한 번을 삼킨다(`SWALLOW_CLICK`, 400ms). 그 사이 터치가 흉내 내는 `mousedown`도 막아 초점이 옮겨 가지 않는다. 대상은 손잡이 탭(폭 순환·시트 높이 순환), 길게 누르기와 [선택] 모드 탭의 빠른 선택(패널·시트가 손가락 밑에 펴진다), 손잡이 끌어 접기, 도구 줄을 끈 시트 드래그다. 예전에는 이 click이 편집을 열거나 종류를 바꾸거나 메모 칸에 초점을 줘 키보드를 띄웠다(입력 점검 2026-09-26, `s07_ghost`·`s12_seltap`).

**두 번 탭.** 선택 모드가 아닐 때 PDF를 두 번 탭하면(300ms·24px 안, `isDoubleTap`) 폭 맞춤 ↔ 2배를 오간다. 누른 자리를 기준으로 삼아 그 글자가 손가락 밑에 남는다(`doubleTapWidth`: 폭 맞춤의 ±5% 안이면 2배, 그 밖이면 폭 맞춤). 브라우저의 두 번 탭 확대는 PDF 영역에서 원래 꺼져 있다(`touch-action: pan-x pan-y`).

**가로 밀기.** `html`·`body`는 `overscroll-behavior-x: none`이다. 폴드·폰에서 오른쪽으로 밀면 브라우저가 뒤로 가기로 받아 Limn을 떠났고 쓰던 메모가 사라졌다(`s05e_nav`). 패널(`#right`)은 `touch-action: pan-y pinch-zoom`이다. 가로 끌기가 포인터 이벤트로 남아 겹친 패널을 밀어 닫을 수 있고(§펼친 화면 레이아웃), 패널 위 두 손가락 확대는 여전히 브라우저 확대다(§PDF 영역 전용 확대). 점검안은 `pan-y`였지만, 그러면 패널 위 핀치 확대까지 꺼진다. 접근성을 앞세워 `pinch-zoom`을 남겼다(소유자 결정 2026-09-26). 밀어 닫기와 뒤로 가기 막기는 어느 쪽이든 같다.

**뒤로 가기 제스처.** 터치 기기에서 시트(`narrow`), 겹친 패널(701–900px), 중간 폭 목차가 열려 있으면 시스템 뒤로 가기가 그 층을 먼저 닫는다(`backLayer`). `CloseWatcher`가 있으면(안드로이드 크롬) 그것 하나를, 없으면 history 항목 하나를 둔다. 다른 방법으로 닫으면 그 항목도 거둬, 뒤로 가기가 헛도는 일이 없다. 문서 전환은 해시를 바꿔 쓰므로(replaceState) 항목을 늘리지 않고, 뒤로 가기로 층을 닫아도 보던 문서의 해시를 지킨다. 모달 대화상자는 브라우저가 스스로 닫는다(history 대체 경로에서는 시트 위에 열린 대화상자를 먼저 닫는다). 시스템 뒤로 가기가 없는 마우스 기기에는 등록하지 않는다. 예전에는 시트를 연 채 뒤로 가기를 누르면 Limn을 떠났다.

**가상 키보드.** viewport meta의 `interactive-widget=resizes-content`(크롬 안드로이드)로 레이아웃 자체를 줄인다. 그 값을 모르는 브라우저에서는 `visualViewport`로 잰 높이(`--kb`)만큼 화면을 올린다. 핀치 확대로 줄어든 visualViewport는 `scale`을 곱해 되돌려, 키보드로 치지 않는다.

**터치 기기 크기.** 터치 기기(`pointer:coarse`)에서는 버튼·입력 칸이 44px 이상이고 입력 글자는 16px이다. 16px은 포커스 때 자동 확대를 막는다. 안전 영역(`env(safe-area-inset-*)`, `viewport-fit=cover`)은 비운다. compact에서 알림은 탐색 줄 바로 아래 위쪽으로 옮긴다(`narrow`는 화면 위, `mid`는 본문 왼쪽 위). 아래 도구 줄·첫 안내와 겹치지 않게 하려는 것이다.

### 펼친 화면 레이아웃

폴드 7 사용자가 두 가지를 지적했다(2026-09-24).

- 편 화면에서 `[핀 N]`으로 패널을 접고 펴면 버튼이 오른쪽 위(패널 머리)와 오른쪽 아래(떠 있는 도구 줄) 사이를 뛰었다. 842×758에서 y 56 ↔ 693, 884×1104에서 y 56 ↔ 1039로 쟀다.
- 문서 옆 패널(901–1099px)이 문서 탐색 줄을 패널 폭만큼 잘랐다. 968px에서 탐색 줄이 630px만 남았다.

그래서 `mid`는 화면을 세 층으로 고정한다. `wide`·`narrow`는 그대로다.

| 층 | 자리 | 담는 것 |
| --- | --- | --- |
| 위 | 탐색 줄 `#doc-nav`, 화면 전체 폭, `position:fixed` | 목차 토글 · 문서 링크 · `원고`/`변경사항`. 패널이 자르지 않는다 |
| 가운데 | 본문(`#main`)과 패널(`#right`) | 패널은 탐색 줄 아래에서 동작 줄 위까지만 편다(701–900px는 문서 위 오버레이, 901–1099px는 문서 옆) |
| 아래 | 동작 줄 `#bar1`, 화면 전체 폭, `position:fixed` | `[선택]` ···· `[PDF 재빌드] [⋯] [핀 N]` |

**손의 흐름.** 편 폴드와 태블릿은 대개 두 손으로 쥐고, 엄지가 아래 양 끝에 닿는다. 그래서 자주 쓰는 동작을 아래로 모았다.

- `[선택]`은 왼쪽 아래 끝이다. PDF 위에서 쓰는 도구라 문서 쪽 엄지에 둔다.
- 패널 토글 `[핀 N]`은 패널이 나오는 오른쪽 아래 끝이고, 그 옆이 `[⋯]`와 `[PDF 재빌드]`다.
- 작성 패널의 `[취소] [핀 저장]`(`#c-actions`)은 패널 바닥, 곧 동작 줄 바로 위라 오른손 엄지 거리다.
- 드문 동작(쪽 이동·확대·테마·도움말)은 예전처럼 `[⋯]` 안이다.

아래 고정은 `narrow`의 아래 시트와도 방향이 같다.

**자리가 움직이지 않는다.** 동작 줄은 패널을 따라다니지 않으므로 `[핀 N]`은 패널을 펴도 접어도 같은 자리다. 842×758·968×842·884×1104·820×1180에서 ±0px로 쟀다. 폭도 최소 88px로 잡아, 핀 수가 늘어 글자가 길어져도 오른쪽 끝이 그대로다. 펴진 상태는 버튼 바탕(`--accent`), 화살표(`›` 펴짐 / `‹` 접힘), `aria-expanded="true"`로 보인다.

**구현.** 도구 줄은 DOM으로는 `#right` 안에 그대로 두고 `position:fixed`로 뺀다. `narrow` 시트가 같은 마크업을 손잡이 아래 sticky로 쓰기 때문이다.

> **주의**
>
> `mid`의 `#right`에는 `transform`·`filter`·`opacity`·`contain`을 주지 않는다. 이 속성이 붙으면 fixed 자식의 기준 상자가 바뀌어 동작 줄이 패널과 함께 움직인다.

버튼 순서는 CSS `order`로만 바꾼다. 키보드 초점 순서는 DOM 순서 `[핀]→[선택]→[재빌드]→[⋯]` 그대로다. 본문·패널은 `body`의 위아래 여백 사이에만 그린다. 위 여백 `--mid-top`은 탐색 줄 + 위 안전 영역이고, 아래 여백 `--mbar-h`는 도구 높이 + 16px + 테두리 + 아래 안전 영역이다. 동작 줄 높이는 터치 60px(44px 버튼), 마우스 44px(28px 버튼)다.

**접힌 패널.** `#right`는 보이지 않는 틀로 남고 입력을 받지 않는다. 상태 칩 줄(`#bar2`)과 위치 다시 잡기 배너(`#banner`)만 동작 줄 바로 위 오른쪽에 카드로 띄운다.

**여닫는 움직임.** 오버레이(701–900px)는 패널이 오른쪽에서 0.18초 밀려 들어오고, 접을 때([핀]·Esc·손잡이·Ctrl+\) 같은 길로 0.18초 밀려 나간다. 위 주의 때문에 `right`만 움직인다. 밀려 나가는 동안에는 `body`에 `side-open`을 남겨 틀이 흔들리지 않게 한다. 문서 옆 패널(901–1099px)은 폭이 바뀌면 PDF 쪽 폭을 다시 맞춰야 해서 움직임 없이 바로 바뀐다. `prefers-reduced-motion: reduce`이면 움직임이 없다(전역 규칙). 문턱과 미리 보기는 그대로다.

**밀어서 닫기(701–900px, 터치).** 겹친 패널은 오른쪽으로 밀어 닫는다. 10px 움직인 뒤 방향을 정한다(`swipeAxis`). `|dx| > 1.5|dy|`이고 오른쪽이면 가로 끌기이고, 아니면 스크롤이다. 패널은 손가락을 따라 `right: -dx`로 움직인다(`--swipe-x`, transform이 아니다 — 위 주의). 손을 떼면 `dismissOutcome`이 정한다. 패널 폭의 35% 이상 밀었거나, 24px 넘게 0.5px/ms 이상으로 튕기면 0.18초에 밀려 나가 닫히고 [핀]처럼 기억한다. 아니면 0.18초에 제자리로 돌아온다.

- 작성·편집·답글·위치 다시 잡기 중에는 닫지 않는다. 고무줄처럼 `dx × 0.25`(최대 24px)만 따라오고 돌아온다(`swipeFollow`).
- 분절 컨트롤(`.seg`), 줄바꿈 끈 원문(`pre.nowrap`), 입력 칸, 손잡이, 도구 줄에서 시작한 끌기는 밀기가 아니다. 그 요소가 가로 스크롤을 쓴다. 450ms 넘게 가만히 누른 뒤의 끌기도 밀기가 아니다(글자 선택).
- 밀던 중에 두 번째 손가락이 닿으면 제자리로 돌아간다.
- 바깥을 눌러 닫지 않는다. 오버레이는 모달이 아니고, 패널을 연 채 PDF를 길게 눌러 다시 고르는 흐름과 부딪히기 때문이다.
- 문서 옆 패널(901–1099px)은 밀어 닫지 않는다. 손잡이 규칙만 따른다.

**Esc.** 오버레이가 열려 있으면 Esc가 패널을 접는다. 고르는 중이면 첫 Esc는 예전처럼 선택을 취소한다.

**고르는 중 가리지 않기.** 오버레이에서 작성 중이면(`body.composing`) `#left`에 패널 폭만큼 `padding-right`를 준다. 변경사항 보기가 이미 쓰는 방식이다. 쪽 폭이 남은 자리에 다시 맞춰져, 오른쪽 단을 길게 눌러 고른 상자가 패널 밑에 숨지 않는다(`s10_fold_cover`). 확대해 둔 쪽은 그 자리까지 가로로 밀어 볼 수 있다.

**문서 링크가 넘칠 때.** 줄 안에서 가로로 밀리고, 스크롤바 대신 넘친 쪽 끝을 흐리게 한다(`.fade-l`·`.fade-r`, `docLinksFade`). 문서가 바뀌면 지금 문서 링크를 보이는 자리로 끌어온다. 폴링으로 다시 그릴 때는 사용자가 민 자리를 둔다.

**첫 안내.** 탐색 줄·패널을 가리지 않게 동작 줄 바로 위 왼쪽에 작은 칩으로 뜬다. 곧 안내가 가리키는 `[선택]` 위다. 알림은 탐색 줄 바로 아래 왼쪽 위라 첫 안내와 겹치지 않는다.

## 패널과 목록

### 패널 정리

편 폴더블(880×790)에서 작성 패널이 어지럽다는 지적(2026-09-23)으로 정리했다. 서버 API·핀 형식은 그대로다.

**한 간격 체계.** 8px 격자를 쓰고, 같은 줄의 버튼은 같은 높이다(터치 44px, 동작 줄 48px). 강조 색(`--primary`, `.btn-default`)은 주요 동작 [핀 저장] 하나에만 칠한다. 카드의 [완료]는 옅은 파랑(`.btn-soft`, 저자 지정 2026-09-23)이고, [삭제]는 옅은 위험 색(`.btn-destructive`)이다. 나머지는 테두리만 있는 outline이다(§디자인 토큰과 컴포넌트).

**도구 줄(compact).** 접은 폴드·폰 시트는 자주 쓰는 순서로 `[핀 N] [선택] [문서] ··· [재빌드] [⋯]`이다(QA 2026-09-24).

- 검토 대기 수는 [핀 N] 안의 알약이다. 예전에는 버튼 모서리에 반쯤 걸쳐 떠 있었다.
- [선택]은 PDF 위 점선 상자와 같은 `square-dashed` 아이콘을 앞에 둔다.
- [PDF 재빌드]는 드물게 쓰므로 아이콘만 둔다. 이름은 aria-label과 길게 누르기로 본다. [⋯]와 함께 테두리 없는 ghost다.
- 모두 같은 높이 한 줄로 잇고, 틈은 4px(`--space-1`)이다.
- 폭이 모자라면 이름표 칩이 먼저 줄어든다(`flex-shrink: 50`, 최소 28px, 전체 이름은 설명에). 예전에는 버튼 글자가 잘려 'DF 재빌드'처럼 보였다.
- 데스크톱 도구 줄은 패널을 좁히면 두 줄로 접힌다.

접은 폴드(`narrow`, 344px 실측)에서는 이름표 칩을 도구 줄에서 빼고 [더보기] 첫 줄(`#more-label`)에 둔다. 대화상자 이름은 `더보기 · <이름표>`가 된다. 줄어든 칩이 'C…'만 남겨 읽을 수 없었고, 맨 위 이름표 색 띠가 이미 인스턴스를 가르기 때문이다. 그 자리에서 [문서] 버튼은 줄어들지 않고 짧은 문서 이름(본문·답변서·커버레터, 5자 안팎)을 다 보인다. `커버레터`로도 실측했고 도구 줄은 한 줄, 잘림 없음이었다.

**도구 줄 높이.** 버튼과 쪽 칸은 한 높이(`--tb-h`: 데스크톱 28px, 터치 44px)이고 아이콘 버튼은 정사각형이다.

- 쪽 칸은 54×28px·`--text-base`·왼쪽 정렬 자리표시 '쪽 이동'이다. 터치에서는 84×44px·`--text-xl` 16px이다(iOS 확대 방지).
- '쪽' 한 글자 칸과 '폭' 글자 버튼은 버튼처럼, 암호처럼 읽혔다(QA 2026-09-24). 그래서 폭 맞춤은 `move-horizontal` 아이콘 버튼이다.
- 기본 348px 패널에서 마우스 도구 줄은 `[PDF 재빌드] [쪽 이동] [−] [＋] [↔] [알림] [테마] [?]`가 한 줄에 든다.
- 위계: 쪽·축소·확대·폭 맞춤은 테두리 있는 탐색 컨트롤, 알림·테마·도움말은 테두리 없는 유틸리티 아이콘, [PDF 재빌드]는 흐린 ghost 글자다. 원고가 PDF보다 새로우면 [PDF 재빌드]가 `.btn-default`로 올라온다.
- 터치 화면과 사용자가 좁힌 패널은 필요하면 줄을 접는다.
- [핀 다시 읽기]는 열린 핀 목록 머리의 [다시 읽기]에 있고, compact에서는 [더보기] 안에 있다.

**위치 한 줄.** `파일 L159` + 쪽 + (낮을 때만) '위치 불확실' 배지 + [복사]다. 예전에는 같은 정보를 세 번 되풀이했다. 파일·줄 줄, 찾은 방법 배지, '1쪽 · 문단 · 1줄 · 드래그한 줄' 줄이다. 지금 범위 종류와 줄 수는 분절 컨트롤의 고른 칸에 이미 보이고, 드래그한 줄은 쪽 표시의 설명에 둔다. 한 줄 버튼으로 직접 맞춰 어느 칸에도 안 맞으면 쪽 옆에 '줄 직접 지정'이 붙는다.

**범위 사다리.** 한 줄 분절 컨트롤이다. 칸 이름은 짧게 쓴다(`문단 · 1줄`, `abstract · 19줄`, `frontmatter · 73줄`). 같은 환경 이름이 겹칠 때만 '(바깥)'을 남긴다. 줄 범위는 칸 설명과 aria-label로 옮겼다. 넘치면 가로 스크롤하고 고른 칸이 보이게 맞춘다. 미세 조정은 붙은 스테퍼 하나(`위 [+][−] 아래 [+][−]`)로 한다.

**원문.** 기본 4줄로 접고, 넘치면 흐리게 끊는다. 원문 바로 밑 한 줄에 왼쪽 [줄바꿈] 토글과 오른쪽 [원문 펼치기]가 있다. [줄바꿈]은 `text-wrap` 아이콘이고, 켜지면 변경사항 [줄바꿈]처럼 채운 면이 된다. 예전에는 [줄바꿈]이 스테퍼 줄 끝에 있어 폴드(330px 패널)에서 혼자 다음 줄로 떨어졌다(QA 2026-09-25). 둘 다 원문을 어떻게 보이느냐를 바꾸므로 원문 밑에 모았다. 긴 한 줄이 여러 줄로 접히는 원고가 흔해, 넘침은 줄 수가 아니라 그린 높이로 잰다.

**동작 줄.** `[취소] [핀 저장]`을 1:2로 나눠 패널 바닥에 고정한다(`#c-actions`, 작성 패널 밖·목록 뒤). wide는 패널 flex 열의 바닥, compact는 스크롤 상자(`#right`)의 sticky 바닥이다. 그래서 목록을 내려도, 키보드가 올라와도(레이아웃이 줄어듦 / `--kb`) 보인다. narrow 시트에서는 메모 칸을 원문보다 위로 올려, 메모 칸이 동작 줄 밑에 숨지 않게 한다.

**선택 버리기와 되돌리기.** 메모를 쓴 선택을 Esc나 [취소]로 버리면 선택은 바로 사라지고 `선택 취소됨 · [되돌리기]` 알림이 6초 뜬다. [되돌리기]는 선택(`CUR`)·메모(@태그 힌트 포함)·종류·담당·점선 상자를 그대로 되살린다(`restoreSelection`). 예전에는 쓴 메모가 되돌릴 길 없이 사라졌다. 확인 대화상자는 두지 않는다(결정 단계는 적게, 되돌리기로 받친다). 메모가 비었거나 위치를 아직 찾는 중이었으면 알림이 없다. 그사이 새 선택을 시작했으면 되살리지 않는다(새 것이 이긴다). 같은 문서·같은 빌드가 아니면 메모만 돌아오고, 자리를 다시 골라야 한다고 알린다.

핀을 저장한 직후의 [되돌리기]도 같다. 핀을 지우면서 같은 선택과 메모로 작성 패널을 다시 연다. 저장 뒤에 고칠 곳이 보였을 때 처음부터 다시 고르지 않게 하려는 것이다.

**쓰던 초안은 탭에 남는다.** 작성 중인 초안(선택·점선 상자·메모·@태그 힌트·종류·담당, 또는 다음 선택을 기다리는 메모)은 고칠 때마다 `sessionStorage`에 적는다(300ms 모아서, 페이지가 숨겨지면 바로). 열쇠는 인스턴스 이름표와 문서마다 하나다(`draftKey`). 새로고침하거나, 뒤로 가기로 시트를 닫은 뒤 한 번 더 눌러 Limn을 떠났다가 돌아오면, 이 탭의 다음 부팅이 초안을 되살리고 `작성 중이던 메모를 되살렸습니다 · [버리기]`를 띄운다. 확인 대화상자 없이 되살리고 되돌리기로 받친다(소유자 결정 2026-09-26).

- 같은 빌드에서 그린 상자면 선택·상자·메모를 모두 되살리고, 접힌 패널이나 시트를 편다(기억하지 않는다). 빌드가 바뀌었으면 상자의 좌표가 틀리므로 메모만 메모 칸에 되살려 다음 선택에 쓰게 하고, 알림이 그렇게 말한다(`draftRestore`).
- [버리기]는 보통의 버리기와 같다. 선택이 있던 초안이면 `선택 취소됨 · [되돌리기]`가 뜬다.
- 저장하면 초안을 지운다. 버린 초안은 되돌리기 알림이 떠 있는 동안 남아 있다가(그사이 페이지를 떠나도 돌아오면 되살아난다) 알림이 사라질 때 지운다.
- 이 탭에서만 보인다. 다른 탭·기기와 나누지 않고, 탭을 닫으면 사라진다.

**드래그 직후 저장.** 드래그 → SyncTeX `/api/pick` 역변환은 약 1.1초 걸린다(`#c-spin`). 그 사이에도 [핀 저장]은 눌린다. 예전에는 `CUR`이 아직 없어 `savePin()`이 조용히 아무 일도 하지 않았고 메모가 사라졌다. ⌘/Ctrl+Enter도 같은 경로였다. 지금은 이렇게 한다.

- pick이 끝나기 전에 저장을 누르면 요청을 큐에 담고(`PEND_SAVE`), 버튼이 "위치 찾는 중… 저장 대기"(스피너)로 바뀐다.
- 메모 글은 스냅샷하지 않는다. pick이 풀려 실제로 저장하는 그 순간 `#note`를 다시 읽는다. 대기하는 동안 고친 글자까지 반영하려는 선택이다.
- pick이 성공하면 저장을 자동으로 이어 실행한다. 실패하면(`d.error`·네트워크 오류) 큐를 비우고 저장하지 않은 채 기존 오류 패널만 보인다.
- 버튼을 다시 누르거나 [취소]를 누르면 대기를 취소한다(토글). Ctrl+Enter도 버튼과 같은 경로라 동작이 같다.

**고르는 중.** 고르는 중에는 첫 화면 안내 문단(`#empty`)을 숨긴다.

**핀 카드.** 머리 왼쪽에 번호·줄 범위·쪽, 오른쪽에 묶음 `.h-meta`(담당 칩·답글 수·작성자)와 접기가 있고, 배지는 그 아래 한 줄이다. 자리가 모자라면 `.h-meta`가 묶음째 다음 줄 오른쪽으로 내려간다. 예전에는 한 줄에 우겨 넣어, 담당 칩이 있으면 작성자 이름이 'W' 한 글자로 잘렸다(QA 2026-09-24). 묶음 안에서는 담당 칩 이름이 먼저 말줄임되고(`담당 @Sa…`), 작성자 이름이 그다음이다. 동작은 같은 폭 격자 `[보기] [수정] [삭제] [완료]`이고, 처리 중이면 [풀기]가 붙는다.

| 항목 | 펼친 화면(`mid`) | 데스크톱(`wide`) |
| --- | --- | --- |
| 최소 | 300px — 터치 도구 줄이 한 줄에 들어가는 폭 | 280px(예전 그대로) |
| 최대 | 701–900px: 440px 오버레이(화면 − 240px가 더 작으면 그 값). 901–1099px: 화면 − 488px(본문 480px + 손잡이 8px) | `min(80%, 화면 − 486px)` |
| 기본 | 330px | 348px |
| 단계(좁게·보통·넓게) | 300 · 330 · 50%(한계 안으로 제한) | 300 · 348 · 42%(한계 안으로 제한) |
| 기억 | `pinPrefs.sideMid`, 접힘은 `pinPrefs.midClosed` | `pinPrefs.side`(예전 키 그대로), 접힘은 `pinPrefs.sideClosed` |
| 접는 문턱 T | 150px | 140px |

**손잡이.** 손잡이(`#grip`, `role=separator`)는 wide·mid 공통의 Pointer Events 구현 하나다. 데스크톱의 옛 `mousedown` 구현을 대신했다.

- 보이는 막대는 6–8px이다. 잡는 영역은 `::after`로 넓혀 터치 24px, 마우스 12px이다. 마우스를 좁게 둔 것은 본문 스크롤바를 덮지 않기 위해서다.
- 손잡이는 `touch-action:none`이라 끄는 동안 스크롤과 다투지 않는다. `setPointerCapture`로 손잡이 밖까지 따라간다.
- mid에서는 가운데에 잡는 막대를 그린다.

**끄는 동안.** 누르는 순간 손잡이의 설명(툴팁)을 닫는다. 예전에는 끄는 내내 PDF 위에 남았다. 패널 폭만 바꾸고, `body.resizing` 동안에는 ResizeObserver가 다시 맞추지 않는다. 손을 떼면 한 번 `relayout`해 쪽 폭을 다시 맞춘다. 마크·선택 상자는 쪽 안 % 좌표라 저절로 제자리다(실측 오차 0.02px 이하). 보던 자리는 `topAnchor`로 지킨다.

**접기.** 손잡이를 오른쪽으로 끌어 패널을 접는다(`snapSide`). `wRaw`는 끌기 시작 폭 + (시작 x − 지금 x)이고 한계로 자르지 않는다. 문턱 T는 최소 폭의 절반(내림)이다.

| `wRaw` | 끄는 동안 | 손을 떼면 |
| --- | --- | --- |
| 최소 폭 이상 | 폭이 따라온다(최대까지) | 그 폭 |
| T 이상, 최소 폭 미만 | 폭은 최소에 멈추고 손잡이 막대가 주 색(`--primary`)이 된다 | 최소 폭 |
| T 미만 | 미리 보기: 패널 **내용**이 40% 불투명도(패널 상자가 아니다 — mid에서는 `#bar1`·`#sheet-grip`을 뺀 자식만), 커서 `w-resize`. T 위로 되돌리면 바로 풀린다 | 0.18초에 밀려 나가 접힌다. 저장 폭은 끌기 시작 폭 그대로라 다시 펴면 그 폭이다 |
| T 미만, 작성·편집·답글·위치 다시 잡기 중 | 접는 구역이 없다. 최소에 멈추고 커서 `not-allowed` | 최소 폭, 알림 없음 |

`pointercancel`이면 끌기 전 폭과 상태로 돌아간다. 끌어 접은 뒤에는 뒤따르는 click을 삼킨다(§모바일 레이아웃 유령 클릭). [핀]을 누르는 것은 분명한 뜻이라 작성 중에도 접힌다. 그때 [핀 N]에 작성 중 점(`.c-dot`, 주 색)이 붙고 이름에 '작성 중'이 붙는다. 메모는 숨었을 뿐 사라지지 않았다는 표시다(`draftOpen`).

**접힌 넓은 패널(`wide`).** 예전에는 넓은 화면에서 패널을 닫을 수 없었다(`#btn-side`를 숨기고 `setSide()`가 바로 돌아갔다). 지금은 접을 수 있고, 접으면 이렇게 된다.

- 손잡이가 오른쪽 가장자리의 6px 레일로 남는다. `#left` 옆의 flex 항목이라 본문 스크롤바를 덮지 않는다. 레일을 왼쪽으로 T 넘게 끌면 최소 폭으로 펴지고 그 뒤로는 따라온다. 두 번 클릭(터치는 탭)하면 저장 폭으로 편다.
- 문서 탐색 줄 오른쪽 끝에 `[핀 N ‹]`(`#nav-side`)가 뜬다. 도구 줄의 [핀 N]과 같은 부품이다(열린 핀 수, 보라 검토 대기 알약, 작성 중 점, `aria-expanded`).
- 상태 칩 줄(`#bar2`)은 mid처럼 PDF 영역 오른쪽 아래에 카드로 뜨고, 알림도 그 위 PDF 영역 오른쪽 아래에 뜬다. 도구 줄(`#bar1`)은 패널과 함께 숨는다. 확대는 Ctrl+휠·Ctrl±·Ctrl+0으로 계속 된다. [PDF 재빌드]는 탐색 줄에 올리지 않는다(소유자 결정 2026-09-26).
- 새 선택, 마크 배지, 알림·`#pin=` 링크, 검토 대기, 글 속 `#N`은 접힌 패널을 편다. 이렇게 편 것은 기억하지 않는다.
- 처음 끌어 접으면 한 번만 안내가 뜬다: '핀 패널은 오른쪽 위 [핀 N] 또는 Ctrl+\ 로 다시 엽니다'.
- 접힘은 기기마다 `pinPrefs.sideClosed`에 기억하고, 폭 저장값(`pinPrefs.side`)은 건드리지 않는다. 부팅할 때 `#pin=` 링크나 쓰던 초안이 있으면 접힌 패널을 편다.

**버튼과 키보드.** 터치는 손잡이를 **탭**하면 좁게 → 보통 → 넓게로 순환한다. 마우스는 **두 번 클릭**해야 순환한다. 한 번 클릭으로 폭이 튀지 않게 하려는 것이다. [더보기] 안에도 '패널 폭' 분절 컨트롤이 있다.

키보드는 WAI-ARIA Window Splitter를 따른다(`gripKey`). 패널이 주 창이고 `aria-valuenow`가 그 폭이다.

| 키 | 펴져 있을 때 | 접혀 있을 때 |
| --- | --- | --- |
| Enter | 접는다 | 저장 폭으로 편다 |
| Space | 좁게 → 보통 → 넓게 순환 | 저장 폭으로 편다 |
| Home / End | 최소 / 최대 폭(예전에는 거꾸로였다) | 최소 / 최대 폭으로 편다 |
| ← / → | 16px 넓히기 / 좁히기(최소 아래로는 접지 않는다) | ←는 최소 폭으로 편다 |

접히면 `aria-valuenow=0`, 이름은 '패널 폭 · 접힘'이다. **Ctrl/⌘+\**는 모든 폭에서 패널(`narrow`는 시트)을 펴고 접는다. 입력 칸 안에서는 받지 않는다. 초점이 패널 안에 있을 때 접으면 초점을 [핀 N]으로 옮긴다.

**화면 폭이 바뀔 때.** 접기·펴기로 화면 폭이 바뀌면 저장값은 두고 보이는 폭만 지금 한계 안으로 맞춘다. 다시 넓은 화면으로 가면 저장한 폭이 돌아온다.

**시트 높이(narrow).** 윗가장자리 손잡이(`#sheet-grip`)나 도구 줄(`#bar1`) 전체를 끌면 높이가 바뀐다. 도구 줄의 버튼 위에서 세로로 8px 넘게 움직이면 시트 끌기가 되고 그 버튼의 click은 삼킨다(`#bar1`은 `touch-action: none`). 목록이 맨 위(`scrollTop` 0)일 때 내용을 아래로 끌면 시트가 내려간다(중첩 스크롤 넘기기, `pullDown`). 포인터 스트림은 브라우저가 스크롤을 시작하면 끊기므로 이 경로는 터치 이벤트로 받는다. 끄는 중에 두 번째 손가락이 닿으면 원래 높이로 돌아간다.

손을 떼면 `sheetRelease`가 정한다.

- 화면 25% 아래로 내려놓거나 아래로 튕기면(24px 넘게, 0.5px/ms 이상) 접힌다. 작성·편집·답글 중이면 접지 않고 30%(`SHEET_MIN_F`)에 멈춘다. 예전에는 작성 중에도 접혀 메모가 숨었다(`phone_05`).
- 위로 튕기면 다음 높이 단계로 간다.
- 그 밖에는 놓은 높이에 머문다.
- 접힌 시트에서 위로 끌거나 탭하면 펴진다.
- 펴진 시트를 탭하면 낮게(45%) → 보통(64%) → 높게(화면 − 48px)로 순환한다. [더보기]에서는 '시트 높이'로 고른다.
- 높이는 화면 높이 비율(`pinPrefs.sheetF`)로 기억한다. 키보드가 올라오면 CSS가 보이는 높이 안으로 줄인다.

### 목록 구획

닫힌 핀을 펼치면 열린 카드와 모양이 같아, 어디서부터 닫힌 핀인지 경계가 모호했다(저자 지적 2026-09-23). 그래서 목록을 구획(`section`)으로 나눈다. 0.2.2부터 구획은 **열린 핀 · 검토 대기 · 완료** 셋이고, 셋이 같은 머리 컴포넌트를 쓴다([ADR-0004](../adr/0004-one-reply-trash-sections.md)). 삭제한 핀은 목록에 없고 휴지통에 있다(§휴지통).

**구획 머리.** 폭 전체를 쓰는 한 줄(`.sec-head`)이다. 맨 앞이 접기 버튼(`button.sec-tg`)이고, 그 안에 꺾쇠(`chevron-down`/`chevron-right`) · 이름 · 수 배지가 있다. 예: `⌄ 열린 핀 3`, `› 완료 18`. 열린 핀 머리에는 버튼 뒤에 [다시 읽기]·[나를 부른 핀]·[모든 문서]가 붙는다.

- 접힌 구획 안의 카드로 가야 하면(PDF 표시 누르기, 알림, 글 속 `#N`, [검토 대기 N]) 그 구획을 먼저 펴고, 그 상태도 기억한다.
- `새 N`의 기준(`SEC_SEEN`)은 창마다의 기억이다. 새로고침하면 그때의 목록이 기준이 된다.
- 휴지통을 다른 문서의 핀 행으로 열면 휴지통만 모든 문서를 보인다. 목록의 문서 필터([모든 문서])는 건드리지 않는다.
- 네이티브 버튼이라 클릭·Enter·Space가 같고 `aria-expanded`·`aria-controls`(구획 몸통)를 가진다. 이름 요소(`#list-h`·`#review-h`·`#done-h`)는 이름과 수를 함께 담아, 구획의 `aria-labelledby`가 `열린 핀 3`처럼 읽힌다.
- 접힘 상태는 기기마다 `pinPrefs.sec`에 기억한다. 기본은 열린 핀·검토 대기가 펼침, 완료가 접힘이다. [⋯]의 [닫힌 핀 N 보기]도 같은 상태를 바꾼다.
- **접힌 구획의 `새 N`.** 구획마다 본 적 있는 핀 번호(`SEC_SEEN`)를 든다. 첫 목록을 읽을 때의 번호와, 펼쳐져 있는 동안 그 구획에 있던 번호(모든 문서)다. 접힌 동안 그 밖의 번호가 목록에 오면 머리에 `새 N`(주 색 옅은 배지)이 붙고, 펼치면 사라진다. 모든 문서의 번호를 보므로 문서를 바꿔도 `새`로 치지 않는다. 내가 방금 저장한 핀도 치지 않는다.
- 머리는 `position:sticky`라 스크롤해도 위에 붙어, 지금 어느 구획인지 늘 보인다. 다음 구획이 오면 앞 머리를 밀어낸다. 구획마다 `section`으로 감싼 덕이다.
- compact에서는 `#right`가 스크롤 상자이고 도구 줄이 먼저 위에 붙어 있다. 그래서 JS가 그 높이를 `--stick-top`으로 잰다. 머리와 접기 버튼의 `scroll-margin-top`도 같은 값이다.
- 검토 대기·완료 구획은 비면 머리째 숨긴다. 열린 핀 구획은 늘 있다.

실측(2026-09-25, 헤드리스 Chromium, 밝게·어둡게 × 한국어·영어): 접기 버튼 높이 데스크톱(1400×850) 22px·머리 31px, 폴드(842×758 터치)·폰(384×832 터치) 44px·머리 52px. 답글 칸의 결과 한 줄과 토글은 데스크톱 23px, 터치 44px로 [보내기]와 같은 높이다. 휴지통 행은 데스크톱 510×62px(한 줄), 폰 318×152px(버튼 묶음이 다음 줄). 전후 스크린샷은 PR #11에 적은 경로에 있다.

### 보관함

**완료 행은 카드가 아니다.** 테두리·바탕·띠 없이 구분선 하나로 나뉘는 납작한 행이고 글자가 흐리다. 상태는 앞머리 아이콘으로 보인다. 휴지통의 행도 같은 모양이다.

- 첫 줄: 아이콘(완료 `check`, 삭제 `trash-2`) · `#번호` · 줄 범위 · 참조(`close_ref`, 예: PR 번호) · 시각(`MM-DD HH:MM`, 닫은 사람은 설명) · [답글] / [되살리기].
- 완료 행의 [답글]은 카드와 같은 답글 칸을 스레드 안에 연다(§스레드와 검토). 사람이 단 답글은 규칙에 따라 핀을 다시 연다. 0.2.1까지 있던 [다시 열기]는 없앴다.
- 둘째 줄(완료): 에이전트 답(`close_reply`) 한 줄이다. 넘치면 말줄임하고 누르면 펼친다. 답이 없으면 '설명 없이 닫힘'이다. 원래 요청 메모는 [원래 요청]을 눌러야 펼쳐진다.
- 둘째 줄(삭제): 그 핀의 메모 한 줄이다. 답이 없으니 그것이 알아볼 단서다.
- 펼친 줄은 자동 동기화로 다시 그려도 남는다.

문서 탭과 '모든 문서' 토글은 열린 목록과 같은 목록 함수(`listDone`·`listDropped`)를 쓴다. 모든 문서를 보면 행에 문서 칩이 붙는다.

### 휴지통

삭제한 핀이 목록 아래 구획으로 남아 목록을 늘렸다. 되살릴 일은 드물다. 그래서 0.2.2부터 삭제한 핀은 휴지통 대화상자(`#trash`)에 있다([ADR-0004](../adr/0004-one-reply-trash-sections.md)).

- **여는 곳.** compact는 [⋯] → `휴지통 N`(`#m-trash`), 데스크톱은 [⋯]가 없어 목록 맨 아래의 흐린 링크 `휴지통 N`(`#trash-link`, 비면 숨김)이다. 글 속 `#12`가 휴지통의 핀이면 그 행으로 연다. 브라우저 알림 `dropped`를 눌러도 연다.
- **행.** 보관함 행과 같다. 첫 줄에 시각 · 지운 사람(`Bob Park 삭제`) · 남은 날(`N일 뒤 지워짐`)이 `·`로 나뉘어 있고, [되살리기]가 있으며, 소유자에게만 [영구 삭제](위험 색)가 붙는다. 폰 폭에서는 두 버튼(`.arc-acts`)이 묶음째 다음 줄로 내려간다. 예전에는 한 줄에 우겨 넣어 [영구 삭제]가 잘렸다(2026-09-25 폰 384px 실측).
- **삭제는 확인 없이 바로.** [삭제]를 누르면 카드가 그 자리에서 목록에서 빠지고(서버 응답을 기다리지 않는다), `핀 #N 삭제됨 · 휴지통에 30일 보관 · [되돌리기]` 알림이 뜬다. 요청이 실패하면 카드를 되돌린다.
- **영구 삭제는 알림 뒤로 미룬다.** 행이 바로 빠지고 `핀 #N 영구 삭제 · [되돌리기]`가 뜬다. 알림이 사라질 때 요청이 나간다(§알림(토스트)). 확인 대화상자는 없다.
- 휴지통은 모달 대화상자라 바깥이 비활성이 된다. 그래서 알림 상자(`#toasts`)가 열린 모달 대화상자 안으로 옮겨 가고, 닫히면 `<body>`로 돌아온다. 그러지 않으면 [되돌리기]를 누를 수 없었다.

## 상태와 표시

### 알림(토스트)

핀을 저장하면 뜨는 `핀 #N 저장됨 · 되돌리기`가 오른쪽 패널에서 너무 먼 곳에 떴다(저자 지적 2026-09-24). 데스크톱에서는 왼쪽 아래로 저장 버튼 중심에서 1,133px, 폴드에서는 본문 왼쪽 위로 810px 떨어져 있었다. 이제 방금 누른 자리 가까이 뜬다.

| 레이아웃 | 자리(`placeToasts()`가 재서 `--toast-r`·`--toast-w`·`--toast-b`로 넣는다) |
| --- | --- |
| `wide` | 패널 열 안 오른쪽 아래(열 폭 − 24px, 최대 380px). 작성 중이면 저장·취소 줄(`#c-actions`) 윗변 바로 위. 패널을 접었으면 PDF 영역 오른쪽 아래(스크롤바 안쪽), 떠 있는 상태 칩 위 |
| `mid` | 패널 쪽 오른쪽, 아래 동작 줄(`#bar1`) 윗변 바로 위. 작성 중이면 저장·취소 줄 위, 패널을 접었으면 떠 있는 상태 칩(`#bar2`·`#banner`) 위 |
| `narrow` | 시트 윗변 바로 위, 화면 폭 − 16px. 시트가 화면의 70% 넘게 덮으면(시트 위에 자리가 없다) 시트 안 아래쪽 — 저장·취소 줄이 보이면 그 위. 화면 위로 올리면 시트의 도구 줄([더보기])을 가렸다 |

- 터치 기기에서는 알림 몸통이 누름을 뒤로 흘려보내고 버튼만 받는다. 시트 바로 위에 뜬 알림이 PDF 길게 누르기를 가로채지 않게 하려는 것이다.
- 떠 있는 동안 250ms마다 자리를 다시 잰다(`watchToasts`). 작성 패널이 뜨거나 패널을 여닫아도 저장·취소 버튼과 아래 도구 줄을 가리지 않는다.
- 새 알림이 맨 위에 쌓이고, 3개가 넘으면 나머지는 접힌다. 마우스를 올리거나 초점이 들어가면 펼친다. 쌓인 알림 밑에는 `알림 N건 더 보기` 버튼(`#toasts-more`)이 붙고, 누르면 펼친다. 터치에서는 알림 몸통이 탭을 흘려보내 hover가 없으므로 이 버튼이 펼치는 길이다(예전에는 터치로 펼칠 수 없었다). 3개 이하로 줄면 다시 접는다.
- 6초 뒤 사라지고, 마우스를 올린 동안은 멈춘다. 들어오는 움직임(0.16초)은 `prefers-reduced-motion`에서 꺼진다.

**보내기를 미루는 되돌리기(0.2.2).** 페이지가 숨겨져 먼저 보낸 경우에는 알림도 함께 없앤다. 취소할 수 없게 된 [되돌리기]가 남아 있으면 취소된 줄 안다. 답글과 휴지통의 영구 삭제는 [보내기]를 눌러도 곧바로 서버로 가지 않는다(`deferred()`). 알림이 화면에서 사라질 때 보낸다. 6초가 지나거나, [x]를 누르거나, 새 알림에 밀려나거나(6개 초과), 페이지가 숨겨질 때(`visibilitychange`·`pagehide`, `fetch` `keepalive`)다. [되돌리기]를 누르면 아무것도 보내지 않고 글을 입력 칸에 되돌린다. 알림이 떠 있는 동안에는 에이전트도 다른 사람도 그 변경을 보지 못하므로, 되돌리기가 "보낸 뒤 지우기"가 아니라 "보내지 않기"다. 구현은 알림의 `_gone` 고리다. 알림이 자기 동작 버튼이 아닌 이유로 사라지면 한 번 부른다.

모양은 sonner를 따른다.

- 떠 있는 면 하나: `--popover` 바탕, 가는 `--border` 테두리, `--radius-lg`, `--shadow`. 그림자는 떠 있는 면에만 쓴다.
- 앞머리 상태 아이콘: 완료 `circle-check` 초록 · 경고 `triangle-alert` 호박 · 오류 `circle-x` 빨강.
- 제목 한 줄(굵게)과 흐린 설명 한 줄. 글은 첫 ` — `(없으면 첫 ` · `)에서 제목과 설명으로 가른다(`toastSplit`). 예를 들어 알림의 제목은 `핀 #10 · 본문`이다.
- 작은 outline 동작 버튼([되돌리기]·[열기])과 닫기 `x`.
- 색 띠는 없다.

### 상태 표현

왼쪽 세로 색 띠는 없앴다. 저자가 촌스럽고 'AI slop' 같다고 지적했다(2026-09-24). 지금은 이렇게 가른다.

- 열린 카드: **머리 맨 앞의 작은 점(8px) 색**과 **같은 뜻의 배지**(글자·아이콘).
- 닫힌·삭제한 핀: 흐린 보관함 행의 **앞머리 아이콘**.

> **핵심**
>
> 어느 상태도 색만으로 가르지 않는다. 점도 `aria-label`과 설명 `상태: …`를 가진다.

배지 문구는 뜻이 드러나는 말로 쓴다. 저자 지적(2026-09-23)의 예로, `⏳ 처리 중 · ~04:02`·`#20 안`·`일치 100%`는 뜻을 알 수 없었다.

| 상태 | 점·아이콘 | 글자(배지) | 모양 |
| --- | --- | --- | --- |
| 열림 | 초록 점 `--status-open` | 없음(기본) | 카드 |
| 처리 중(claim) | 호박 점 `--status-claimed`(다크 `#f0b43c`, 라이트 `#b86e00`) | `clock` `처리 중 · …` | 카드 |
| 검토 대기 | 보라 점 `--status-review`(다크 `#b197fc`, 라이트 `#6d28d9`) | `eye` `<작성자>님 확인 필요` | 카드(§스레드와 검토), 검토 대기 구획 |
| 다시 열림 | 초록 점(열림) | `rotate-ccw` `다시 열림`(경고색, 설명에 누가·언제·이유) | 카드 — 스레드의 마지막 닫기·다시 열기 기록이 다시 열기일 때 |
| 위치 잃음 | 경고색 점 `--status-warning` | `triangle-alert` `위치 잃음` | 카드, 테두리도 경고색 |
| 질문 | (열림과 같은 점) | `circle-question-mark` `질문`(주 색) | 카드 — 상태가 아니라 종류다 |
| 완료 | `check` 초록 `--status-closed` | 닫은 시각·답 한 줄 | 보관함 행(§보관함) |
| 삭제 | `trash-2` 회색 `--status-dropped` | 메모 한 줄, 남은 날 | 휴지통의 행(§휴지통), 글자가 더 흐리다(`--subtle-foreground`). 글 속 `#N`은 흐린 `#N 삭제된 핀` |

점·아이콘 색은 두 테마 모두 카드·패널 바탕 대비 3:1(비텍스트) 이상이다(3.7–10.0). 흐린 글자는 4.5:1 이상이다(`--subtle-foreground` 다크 5.3 / 라이트 4.8).

배지:

| 배지 | 뜻 | 보일 때 |
| --- | --- | --- |
| `처리 중 · 약 15분 · 20:40쯤` | 에이전트가 견적(`eta_min`)을 넣고 잡았다. 남은 분·시각 모두 5분 단위로 올림 | 견적 안 |
| `예상보다 늦어짐 (+5분)` | 견적을 넘겼다(초과 분, 5분 단위). 경고 색 | 견적 초과 |
| `처리 중 · 20:02부터 (23분째)` | 견적 없이 잡은 claim | 옛 claim |
| `#20 범위 안` · `#20과 같은 범위` · `#20과 일부 겹침` | 다른 열린 핀과 겹침. 같은 범위 > 범위 안(가장 좁은 바깥 핀) > 일부 겹침 순으로 하나. 조사는 숫자 읽기로 가린다(`#2와`, `#20과`) | 겹칠 때. pins.md 번호 칸도 같은 말 |
| `위치 불확실` | 드래그한 글자가 찾은 줄 범위에 90%보다 적게 있다. 30% 미만은 경고 색. 설명에 '좌표로 찾음/글자로 찾음 · 일치 N%'와 확인할 것 | 90% 미만일 때만(작성 패널의 위치 줄도 같다) |
| `줄 +3 이동` · `위치 잃음` · `수정됨` | 줄 맞춤이 옮김 · 앵커를 잃음 · 저장 뒤 고침 | 그대로 |

처리 중 배지의 시각은 보는 기기의 현지 시각이고 30초마다 다시 센다. 잠금 자동 해제 시각(`claim_until`)은 배지에 쓰지 않고 설명에만 둔다. 배지에 쓰면 그것이 예상 완료 시각으로 읽혔다. 잠금은 안전장치일 뿐이다([api.md](api.md) §처리 중 표시).

### 뜻과 모양

모든 시각적 구분은 뜻이 있어야 하고, 뜻 있는 것은 모두 눈에 갈려야 한다(저자 지적 2026-09-24). 이 원칙으로 점검한 규칙은 다음과 같다.

| 무엇 | 모양 |
| --- | --- |
| 누르는 참조(`#번호`·줄 범위·`N쪽`·글 속 `#12`·보관함 행의 줄 범위·[원래 요청]·[변경 보기]·[스레드 N]) | 링크 한 벌: 주 색 글자, 쉴 때 밑줄 없음, hover·초점에 실선 밑줄. 예전의 굵은 점선 · 파랑 · 회색 점선 세 모양을 하나로 모았다(QA 2026-09-24). 흐린 보관함 행에서도 누르는 말만 주 색이다. 회색 글자(작성자·시각·배지 속 `#20과 같은 범위`)는 누를 수 없다. 점선 밑줄은 이제 풀리지 않은 '@말'(`.mention-bad`)만 쓴다 |
| 복사하는 글자(줄 범위 `.loc`) | 같은 링크 모양에 고정폭 글자 + `cursor:copy`, 설명 '누르면 복사' |
| 동작 | 맥락마다 강조 하나(작성 패널 [핀 저장] = default, 카드 [완료] = soft). 위험 동작은 가장 눈에 띄지 않는다(카드 [삭제] = 바탕 없는 위험 색 글자). 끈 버튼은 금지 커서(not-allowed), [핀 저장]의 '저장 대기'는 옅은 주 색 + 진행 커서 |
| 마우스로 누르는 넓이 | 작은 컨트롤은 그린 크기 그대로 `::after`로 24×24px 이상을 받는다(WCAG 2.5.8, `@media (pointer:fine)`). 카드 머리의 `3쪽` 17×19, 답글 수 23×17, 마크 배지 22×22, 카드 버튼 53×23, 구획 머리 22px, 검토 대기 칩 20px이었다(입력 점검 2026-09-26, `s13_targets`). 터치는 전부터 44px다. 글 속 `#12`와 메모 줄 같은 글 안의 링크는 예외다 |
| PDF 쪽 위 마우스 커서 | 십자(`crosshair`) — 끌어서 영역을 고르는 곳이라는 표시. 첫 방문한 마우스 사용자에게는 한 번 'PDF를 끌어서 고칠 곳을 고르세요' 안내가 뜬다(`pinPrefs.coach.mouse`). 터치는 전부터 길게 누르기 안내가 있었다 |
| 사람 | 사진 또는 머리글자 원(주 색). 나는 이름 뒤 `(나)`(카드 작성자·스레드 글쓴이) |
| 에이전트 | `bot` 아이콘의 흐린 원 — 사람의 원과 가른다 |
| 시각 | 스레드·보관함은 상대 시각(`방금`·`N분 전`·`N시간 전`·`N일 전`, 일주일 넘으면 `M-D`), 절대 시각은 설명에. 60초마다 다시 센다(`tickRel`). 보관함의 시각은 줄이지 않는다(예전 `09-24 1…`) |
| 긴 글 | 스레드 글은 6줄에서 접고 [더 보기] 버튼을 둔다 — 1,000자 답글 하나가 카드를 1,390px로 늘렸다(→ 약 310px) |
| 검토 대기·완료 카드 | 겹침·위치 확실도 배지(`#N과 같은 범위`·`위치 불확실`)를 숨긴다 — 닫힌 핀은 줄 맞춤을 하지 않아 뜻이 없다 |
| 답글 수(`.th-n`) | 누르면 카드를 펴고 답글 칸을 한 번에 연다(접힌 compact 카드) |
| 검토 대기 수 | 상태 칩은 모든 문서를 센다 — 이 문서와 다르면 `검토 대기 2 (이 문서 1)` |
| 나를 부른 핀 거르기 | 목록 머리에서 `@` 아이콘 + 수(이름은 `aria-label`·설명) — 360px 패널에서 머리가 두 줄로 꺾였다 |
| 포커스 | 모든 조작 요소가 같은 `:focus-visible` 링(2px `--ring`). 설명(툴팁)은 뜻이 글자로 다 드러나지 않는 곳에만 — 알림 닫기 `x`는 `aria-label`만 |

**같은 사건의 알림은 한 번만 뜬다.** 알림이 오는 길은 둘이다. 하나는 브라우저 알림 경로이고, 탭에 포커스가 있으면 토스트로 뜬다. 다른 하나는 목록 비교 알림(`검토 대기로 넘어왔습니다`·`다시 열림`)이다. 두 길이 같은 핀의 같은 전환을 8초 안에 알리면 브라우저 알림 쪽이 이긴다(`toastDup`, 열쇠 `<이벤트>:<핀>`).

**[변경 보기]의 안내 줄.** 글이 길면 글이 줄바꿈되고 [원고로] 버튼은 잘리지 않는다. 예전에는 842px에서 버튼이 화면 밖이었다. [변경 보기]를 누를 때 보던 문서를 기억해(`REV_BACK`) 그 문서로 돌아간다. 다른 문서면 버튼이 `<문서 이름>(으)로`라고 말한다. 소스 diff에는 [줄바꿈] 토글이 있고, 터치 기기에서는 기본으로 켠다(`pinPrefs.diffWrap`). 문단 하나가 원고의 한 줄이라, 폰에서 diff가 6,273px 폭이었기 때문이다.

## 협업 UI

### 스레드와 검토

질문 핀(24%)과, 에이전트가 닫은 뒤 다시 열린 핀(#28·#42)이 계기다(2026-09-24). 데이터와 전환은 [api.md](api.md) §스레드와 §검토 대기가 맡는다.

**작성 패널.** 메모 위에 두 칸 분절 컨트롤 `[수정 요청 | 질문]`(`#c-kind`)이 있다. 기본은 수정 요청이고, 저장하거나 취소하면 되돌아간다. 편집 패널에도 같은 컨트롤이 있다. 질문 카드는 `질문` 배지(주 색 테두리)를 단다.

**종류 권하기.** 수정 요청인데 메모가 질문처럼 읽히면, 메모 칸 바로 밑에 `질문처럼 보입니다 — [질문으로 보내기]` 한 줄(`.q-hint`)이 뜬다. 판정은 `looksQuestion`이 한다.

- 질문으로 보는 끝: `?`·`？`, 또는 한국어 물음 어미 는가·나요·까요·인가·건가·니·냐·까.
- 끝의 마침표·말줄임·괄호와 끝에 붙은 @태그는 보지 않는다.
- 누르면 종류가 질문으로 바뀌고 줄이 사라진다. 스스로 바꾸지는 않는다.
- 누른 뒤 초점은 메모 칸 끝으로 돌아간다. 줄이 사라지며 초점이 `<body>`로 빠지면 Ctrl+Enter가 먹지 않았기 때문이다(0.2.0 E2E QA). 작성 패널 안이면 초점이 [수정 요청 | 질문] 같은 버튼에 있어도 Ctrl+Enter로 저장한다.
- 질문이 되거나 글이 질문처럼 읽히지 않게 되면 사라진다.
- 작성·편집 패널 둘 다 적용된다.

- @태그 미리보기(`알림 Bob Park`)는 그 위 한 줄에 예전처럼 남는다.

**수.** compact는 `[핀 N]` 안의 보라 알약(`#side-rv`), wide는 상태 칩 줄의 `검토 대기 N`(`#rv-chip`, 누르면 구획으로)이다. 문서를 가로질러 센다. 탭 제목에는 `· 검토 M`이 붙는다.

### 변경 보기

검토 대기 카드와 완료 행의 [변경 보기]가 변경사항 탭(#81/#82)을 그 핀에 맞춰 연다. 커밋은 최근 12개 안에서 아래 순서로 고른다.

| 단계 | 고르는 커밋(최근 12개 안) |
| --- | --- |
| 1 | 닫을 때 남긴 참조(`close_ref`)의 7–40자리 해시 앞부분(`PR #235 (f47c6bf)`) |
| 2 | 참조의 PR 번호가 제목에 든 커밋 — 스쿼시 `(#236)`, 머지 `Merge pull request #236` |
| 3 | 핀 파일의 핀 줄 ±5줄을 바꾼 가장 최근 커밋(커밋마다 소스 diff를 받아 hunk로 판정) |
| 4 | 가장 최근 커밋 |

- 줄 대응은 **소스 diff에만** 있다. 그래서 바로 [소스 diff]로 열고, 핀 파일(경로 끝 일치)을 고른다. 새 쪽 줄 번호가 핀 범위에 드는 줄을 보라로 강조해 가운데로 스크롤한다. 머리 아래 안내 줄(`#revision-pin`)이 어느 규칙으로 골랐는지와 [원고로]를 보인다. Esc도 [원고로]와 같다(겹친 패널이 열려 있으면 패널을 먼저 접는다).
- 비교 PDF(latexdiff)에는 SyncTeX 대응이 없다. 그 탭을 누르면 그때 만든다. 예전에는 소스를 볼 때도 늘 만들었다. 핀의 쪽 근처로만 옮기며 '대략'이라고 적는다.
- 접은 폴드(narrow)에서도 열린다. 예전에는 변경사항 보기가 없었다. 탐색 줄이 없으니 안내 줄의 [원고로]가 돌아가는 길이다.

**핀의 변경만 (0.3).** 한 커밋이 핀 여럿을 고쳤으면 [변경 보기]는 그 핀의 hunk만 보인다. 어느 hunk가 그 핀의 것인지는 서버가 정한다([api.md](api.md) §핀 단위 변경 보기, [ADR-0005](../adr/0005-pin-scoped-changes.md)). 결정 단계를 늘리지 않는다. 새 대화상자는 없고, 컨트롤은 아래 두 개뿐이다.

- **소스 diff.** 핀의 hunk만 보이고 그 아래에 `이 커밋의 다른 변경 N곳 ▸`(`#revision-other-toggle`, `aria-expanded`)가 접혀 있다. 누르면 같은 자리에서 나머지 hunk(`#revision-other`)가 펼쳐지고, 다시 누르면 접힌다. 다른 핀으로 [변경 보기]를 다시 열면 접힌 채 시작한다. 펼친 diff도 같은 줄바꿈·색 규칙을 따른다. 줄 번호는 커밋의 실제 번호라 핀 범위 강조가 그대로 맞는다. 안내 줄에 `이 핀의 변경 N곳만 보입니다(에이전트가 기록한 줄 | 핀 자리로 추정)` 가 붙는다.
- **비교 PDF.** 옛 판에 핀의 hunk만 넣은 합성 판과 비교한다. 상태 줄이 `핀 #N의 변경만 · 첫 부모 …` 로 시작하고, 컨트롤 줄에 토글 `[커밋 전체 비교]`(`#revision-whole`, `aria-pressed`)가 생긴다. 켜면 0.2.2의 커밋 전체 비교, 끄면 다시 핀의 것만이다. 두 비교는 각각 캐시되어 다시 누를 때는 빌드하지 않는다. 쪽 근처로만 옮긴다는 '대략' 안내는 그대로다.
- 핀의 hunk만으로 컴파일이 안 되면 커밋 전체 비교로 넘어가고 상태 줄에 `이 핀의 변경만으로는 비교 PDF를 만들지 못해 커밋 전체를 비교합니다` 를 붙인다. 이때 토글은 숨긴다.
- 핀 단위 보기는 [변경 보기]가 그 핀에 골라 준 커밋에서만이다. 목록(`#revision-select`)에서 다른 커밋을 고르면 그 커밋을 통째로 보이고(`pin` 없이 요청), 두 컨트롤도 없다. 핀의 커밋으로 돌아오면 다시 핀 단위다(`revisionPinFor`, PR #13 리뷰).
- 커밋 전체가 그 핀의 것이거나(핀별 커밋), 핀의 것을 하나도 고르지 못했으면 0.2.2와 똑같이 보인다. 두 컨트롤도 없다.
- 터치에서 두 컨트롤은 다른 버튼처럼 44px다. 폰(384px)에서는 [커밋 전체 비교]가 들어오면 컨트롤 줄이 두 줄로 꺾인다(QA 2026-09-25, 스크린숏 데스크톱·폴드·폰 × 한국어·영어).

할 수 없는 것도 있다.

- 닫힌 핀은 줄 맞춤을 하지 않는다. 그래서 닫은 뒤 원고가 크게 바뀌면 강조가 빗나갈 수 있다. 못 찾으면 그렇게 적는다.
- 최근 12개 밖의 커밋, 아직 머지 안 된 PR 브랜치의 커밋, 미커밋 수정은 볼 수 없다.

### @태그

**사람 목록.** 메모·편집·답글 칸에서 `@`를 치면 사람 목록(`#mention-pop`)이 뜬다. 최대 6명이고 나는 뺀다. 자리는 그 칸의 동작 줄을 가리지 않게 고른다(`mentionTop`). 동작 줄은 답글·다시 열기의 [취소][보내기], 편집의 [저장], 작성 패널의 [핀 저장]이다. 고르는 순서는 다음과 같다.

1. 입력 칸 바로 아래에 동작 줄 전까지 들어가면 아래.
2. 아니면 입력 칸 위.
3. 위에도 자리가 없으면 동작 줄 아래.
4. 어디에도 안 들어가면 입력 칸 아래를 화면 안으로 당긴다.

답글 칸은 두 버튼이 입력 칸 바로 밑이라 위로 뜬다. 예전에는 아래로 떠, 고르는 동안 [취소][보내기]를 덮었다(QA 2026-09-25, 세 폭 모두).

- 고른 줄은 목록 폭 전체의 납작한 띠(`--accent`, 모서리 없음 — shadcn Command 모양)다. 틀 안에 또 둥근 상자를 두지 않는다(§한 겹 담기).
- ↑/↓로 움직이고 Enter/Tab으로 고르고 Esc로 닫는다. Esc는 선택 취소보다 먼저 받는다(window capture).
- 목록을 눌러도 입력 칸 포커스를 뺏지 않는다. 고르면 `@이름 `을 넣는다.

**태그 토큰.** 글 속의 풀린 `@이름`(그 글의 `mentions`에 든 사람)은 **태그 토큰**이다. Slack·GitHub처럼 주 색 글자에 옅은 주 색 틴트 알약(`.mention`)을 입히고, 설명은 `@태그 — <이름>에게 알림이 갑니다`다. 지금 신원을 부른 태그는 한 단계 진한 틴트(`.mention.me`, 설명 `나를 부름`)다. 메모, 스레드 글, 접힌 카드 요약(`.sum`), 보관함의 답 한 줄, 원래 요청, 삭제한 핀 메모에 똑같이 적용한다. 풀리지 않은 `@말`은 평문 그대로다. 부른 것처럼 보이면 안 되기 때문이다. 저자가 제대로 불린 건지 평문인지 구분이 안 된다고 지적했다(2026-09-24).

**찾는 규칙.** 서버 `resolve_mentions()`와 같다.

- 이름 전체, 로그인, 로그인의 `@` 앞, 이름 첫 단어를 본다.
- 긴 것부터, 대소문자 없이 찾는다.
- `@` 앞이 글자·숫자면(메일 주소) 건너뛴다.
- 영문으로 끝나는 이름 뒤에 영문이 이어지면 다른 말로 본다.

글은 먼저 `esc()`를 거치고, 토큰은 이스케이프된 글에서 감싼다. 자리표로 바꿔 겹쳐 감싸지 않는다. 그래서 사람이 쓴 글이 HTML로 새지 않는다.

**입력 중 미리 보기.** textarea 안은 색을 칠할 수 없다. 그래서 메모·편집·답글 칸 바로 아래 한 줄(`.m-preview`, `#note-mentions`)에 두 가지를 보인다. 저장하면 알림이 갈 사람(`@ 알림  Bob Park`)과, 풀리지 않을 `@말`(점선 밑줄, `등록된 사람이 아님`)이다. 저장 전에 부른 것이 실제로 알림이 되는지 알 수 있다.

- 쓰는 중인 `@말`(커서가 그 끝에 있다)은 아직 알리지 않는다. 커서가 떠나거나(방향키·누르기) 칸을 벗어나면 알린다(`mentionBadSettled`). 예전에는 `@Sa`를 치며 목록에서 고르는 동안 경고가 먼저 떴다(QA 2026-09-25).
- 나를 쓴 태그는 `(나 — 알림 없음)`이다.

**`#번호` 링크.** 글 속 `#12`는 그 핀이 있으면(열림·검토 대기·완료·삭제) 링크(`.pin-ref`, 링크 한 벌)다. 누르면 그 카드나 보관함 행을 펴고 스크롤해 반짝인다. 다른 문서면 '모든 문서'를 켠다. 없는 번호와 `&#39;` 같은 이스케이프는 건드리지 않는다.

**부름 배지.** 사람을 부른 카드에는 `나를 부름`·`@이름` 배지가 붙는다. 담당이 적히지 않은 옛 핀에 쓴다.

### 담당

글에서 짐작하던 '누가 처리하나'를 명시 값 `assignee`로 둔다([api.md](api.md) §@태그·사람·이벤트). 계기는 초기 시범 핀 #43이다. `이거 콜링 제대로 작동하나 @Bob Park 확인 부탁합니다`라는 수정 요청으로, Bob Park에게 맡긴 것이었다. 그런데 `참고 @Bob Park`로 떠, 에이전트가 자기 일로 읽을 뻔했다.

**작성 패널.** 메모에 풀린 @태그가 하나라도 있으면 알림 줄 아래에 `담당  [에이전트 | @Bob Park | …]` 분절 컨트롤(`#c-assign`)이 뜬다. 태그된 사람마다 한 칸이고, 나는 빠진다. @태그가 없으면 컨트롤이 없다(에이전트).

- 기본값(`defaultAssignee`): 메모가 풀린 @태그로 **시작**하면 그 사람, 아니면 질문 핀의 첫 @태그, 아니면 에이전트.
- 고르기 전에는 메모가 바뀔 때마다 기본값을 다시 고른다.
- 고른 뒤에는 그 사람이 메모에서 빠질 때만 기본값으로 돌아간다.

**카드.** 담당이 사람이면 머리에 `담당 @이름` 칩이 붙는다. 나면 `담당 나`이고 한 단계 진한 틴트다. 에이전트는 기본이라 칩이 없다. 작성자(또는 신원 없는 로컬 화면)는 칩을 눌러 [수정]을 열고 같은 컨트롤로 바꾼다. 바뀌면 스레드에 `담당 바꿈` 한 줄이 남는다.

**에이전트와 알림.** 담당이 사람이면 에이전트가 건너뛰고(`→ @이름`) 그 사람에게 `assigned` 알림이 간다. 알림 순위는 담당 > 부름 > 다시 엶 > 검토 대기 > 답글이다. 담당이 에이전트면 @태그는 참고(`참고 @이름`)다. 어느 쪽이든 태그된 사람에게 부름 알림은 간다.

**나를 부른 핀.** 목록 머리의 [나를 부른 핀 N] 토글(`#mention-filter`)은 지금 신원을 부른 열린·검토 대기 핀만 모든 문서에서 보인다. 없으면 숨는다. 로컬 신원에는 뜨지 않는다.

### 브라우저 알림

탭이 살아 있는 동안만 쓰는 1단계 알림이다. 웹 푸시, 바깥 서비스, 새 의존성은 없다.

**켜기(기기마다).** 데스크톱 도구 줄의 벨(`#btn-notify`)과 [더보기]의 [알림 켜기] 버튼(`#m-notify`)으로 켠다. `Notification.requestPermission()`은 이 클릭에서만 부른다. 켠 여부는 `pinPrefs.notify`(localStorage)에 둔다. 상태 표시는 다섯 가지다.

- `켜짐`
- `꺼짐`
- `브라우저에서 차단됨`: 주소창 자물쇠 → 알림 → 허용을 안내한다.
- `이 주소에서는 안 됨`
- `테일넷 주소에서만`: 로컬 신원일 때다(아래).

**로컬 신원은 켤 수 없다.** 테일넷 로그인 없이(`127.0.0.1` 직접 접속 등) 연 탭에는 서버가 이벤트를 아예 싣지 않는다([api.md](api.md) §@태그·사람·이벤트, `events_since`). 그래서 알림이 영영 오지 않는다. 버튼과 메뉴 항목을 비활성(`disabled`)으로 두고 '테일넷 주소로 열면 켤 수 있습니다'를 알린다. 브라우저 권한을 얻어도 소용없는 상태를 숨기지 않으려는 것이다.

**보안 컨텍스트.** 서비스 워커와 알림은 https(테일넷 `*.ts.net` 주소)와 `http://127.0.0.1`·`localhost`에서만 된다. 다른 호스트의 plain http(예: LAN IP)는 브라우저가 막는다.

**흐름.** 5초 폴링(`pollLight`)이 `ev=<커서>`를 붙여 나에게 온 이벤트를 받는다([api.md](api.md) §브라우저 알림 커서). 커서(`pinNotifyCursor`)는 브라우저의 localStorage에 있다. 그래서 새로고침하거나 탭을 두 개 열어도 같은 이벤트를 다시 알리지 않는다. 처음 켜면 지금 `ev_seq`부터 센다. 지난 일을 몰아 알리지 않기 위해서다.

**무엇을 알리나.**

- 나를 부름(`mention`)
- 내 핀이 검토 대기로 옴(`review_requested`)
- 내가 쓰거나 불린 핀의 답글(`replied`)
- 내 핀이 다시 열림(`reopened`)
- 누가 내 핀을 지움(`dropped`, 0.2.2). 탭이 보이면 [되살리기]를 단 경고 알림이다. 브라우저 알림에도 [되살리기] 동작이 붙어(서비스 워커가 탭에 넘긴다), 본문을 누르면 휴지통의 그 행이 열린다. `viewer` 역할이면 [되살리기] 대신 [열기]다

내가 한 일은 알리지 않는다. 서버의 `to`와 뷰어가 둘 다 거른다. 한 번 받은 묶음 안에서는 핀마다 하나만 알린다(삭제 > 담당 > 부름 > 다시 엶 > 검토 대기 > 답글).

**보이기.** 늘 서비스 워커의 `registration.showNotification()`을 쓴다. 안드로이드 크롬은 페이지의 `new Notification()`을 막기 때문이다.

- `tag` = `pin-<번호>`라 같은 핀의 알림은 한 칸으로 겹친다. 에이전트가 답글과 닫기를 5초 틈을 두고 하면 두 번 오지만, 화면에는 나중 것(`검토 대기`)만 남는다.
- 제목은 `핀 #N · <문서 이름>`이다.
- 본문은 `Bob Park님이 불렀습니다: <80자>`(부른 사람의 `name` 그대로 + '님') 또는 `검토 대기: <답 첫 줄>`이다.
- 아이콘은 180px 마크 PNG(`apple-touch-icon`)다. 없으면 첫 파비콘이다. 안드로이드 알림은 SVG 아이콘을 그리지 않는다.
- 탭이 보이고 포커스가 있으면 알림 대신 토스트([열기])를 띄운다.
- 탭이 **숨어** 있어도 알림이 켜져 있으면 느린(20초) 이벤트 전용 폴링이 계속 돈다. 이 폴링은 목록을 다시 그리지 않는다.

**누르면.** 서비스 워커가 열린 뷰어 탭을 앞으로 가져와 `postMessage`로 그 핀을 연다. 탭이 없으면 `/#doc=<키>&pin=<번호>`로 새로 연다. `dropped` 알림의 [되살리기]를 눌렀는데 탭이 없으면 `&act=restore`가 붙는다. 부팅은 해시의 `doc=`·`pin=`·`act=`를 **맨 먼저** 읽고 곧바로 주소에서 `pin=`·`act=`를 지운다(새로고침해도 되풀이하지 않는다 — 예전에는 `act=restore` 링크를 새로고침하면 그사이 다시 지운 핀을 또 되살렸다). 그다음 그 문서로 바꿔 핀을 되살린 뒤(`act=restore`, `viewer` 역할 제외) 카드를 펴서 보인다. 해시는 그다음 `#doc=<키>`로 줄어든다. 0.2.1까지는 문서가 여럿인 인스턴스에서 부팅이 해시를 먼저 `#doc=<키>`로 고쳐 써 `pin=`을 잃었고, 탭 없이 누른 알림이 핀을 열지 못했다(0.2.2 E2E에서 발견).

**검증.** Playwright 새 헤드리스(`channel="chromium"`)로 했다. 예전 헤드리스 셸은 권한을 주어도 `Notification.permission`이 `denied`다. 실기기 안드로이드·iOS에서는 재지 못했다. iOS는 홈 화면에 추가한 웹앱에서만 알림을 준다.

## 여러 문서 전환

논문 저장소 하나에는 본문·답변서·커버레터·하이라이트처럼 문서가 여럿 있다. 저자 결정(2026-09-23)은 **논문 저장소마다 뷰어 하나·주소 하나**를 두고 그 안에서 문서를 전환하는 것이다(A안). 이 결정의 근거와 서버 쪽 규칙(핀 저장소, 문서별 빌드 폴더, 보기 전용 PDF)은 [domain.md](domain.md) §여러 문서가 맡는다. 여기서는 뷰어가 문서를 어떻게 전환해 보이는지만 다룬다.

| 화면 | 전환 수단 |
| --- | --- |
| 데스크톱·펼친 폴드(`wide`·`mid`) | PDF 영역 위의 낮은 줄에서 인라인 문서 링크와 `원고`/`변경사항` 보기를 고른다. `목차`는 PDF.js에 실제 outline이 있을 때 왼쪽에 펼쳐 쪽으로 이동한다. 쪽·확대·재빌드 도구는 기존 오른쪽 패널에 둔다 |
| 접은 폴드(`narrow`) | 기존 도구 줄의 `[문서 이름 ▾]` → 아래 시트 목록(이름·경로·핀 수·보기 전용). 바깥을 누르거나, 아래로 목록 높이의 35% 넘게 끌거나 튕기면 닫힌다. 데스크톱 탐색 줄은 숨겨 기존 모바일 PDF·시트 흐름을 유지한다 |
| 문서 하나 | 문서 선택기·문서 버튼·'모든 문서' 토글이 숨는다. 데스크톱의 보기 전환과 목차는 쓸 수 있다 |

**전환이 즉각적이어야 한다.** meta를 문서별로 캐시해, 기다리지 않고 바로 그린다. 뒤에서 최신 meta를 받아 빌드가 바뀌었으면 쪽만 바꾼다. PDF.js 문서 객체는 `문서|빌드`로 최근 3개만 들고 있다. 넘치면 오래 안 쓴 것부터 닫는다(워커 메모리). 실측(1440×900, 43·111쪽 원고) 결과는 다음과 같다.

- 캐시 없는 첫 전환 63ms.
- 되돌아오기 67ms. PDF를 다시 받지 않는다.
- 그 뒤 보이는 쪽만 벡터로 다시 그린다.

**문서마다 보던 자리와 확대를 기억한다.** 기억하는 것은 위쪽 기준 쪽·비율, 쪽 폭, compact의 손 확대 여부, 가로 스크롤이다. 같은 레이아웃에서 본 폭만 되살린다. 접은 화면에서 맞춘 폭이 데스크톱에 가지 않게 하려는 것이다. 새로고침에도 남게 `sessionStorage`에 둔다.

**주소.** `#doc=<키>`로 링크를 공유하고 새로고침한다. 처음 볼 문서는 해시 → 이 기기의 마지막 문서(localStorage) → 첫 문서 순으로 정한다.

**키보드.** Ctrl+PgUp/PgDn은 이전·다음 문서, Alt+1…9는 번호로 고르기다. Alt+숫자는 `e.code`로 읽는다. 맥의 Option+숫자는 다른 글자를 내기 때문이다. 문서 선택기는 기본 키보드 조작을 쓴다. 입력 칸에서는 전역 단축키가 동작하지 않는다.

**사이드바.** 기본은 지금 문서의 핀이다. '모든 문서' 토글을 켜면 전부 보이고 카드에 문서 칩이 붙는다. 다른 문서 카드의 `#번호`·[보기]·[수정]은 그 문서로 바꾼 뒤 그 자리로 간다. `jumpPin`·`openEdit`이 맨 앞에서 `viaDoc`을 거친다. 마크·겹침 배너·편집은 지금 문서의 핀(`PINS`)만 본다. 쪽 좌표는 그 문서의 PDF에서만 뜻이 있기 때문이다.

**빌드.** [PDF 재빌드]는 지금 문서만 빌드하고, 보기 전용 문서면 숨긴다. 다른 문서가 낡았거나 빌드 중이면 선택기에 표시한다. 뒤에서 빌드가 끝나면 알림에 [열기]를 붙인다(`build_seq`를 문서별로 센다).

**변경사항.** 선택한 메인 `.tex`가 있는 폴더 아래의 `.tex`·`.bib`·`.sty`·`.cls`·`.bst` 파일에 손댄 최근 Git 커밋 12개를 보여 준다.

- 빌드 루트가 같은 문서라도 메인 파일 폴더가 다르면 이력이 섞이지 않는다.
- 첫 화면은 가장 최근 커밋의 실제 patch다. 커밋과 파일을 고를 수 있다.
- API는 현재 목록에 나온 40자리 커밋 ID만 받고, diff는 256 KiB에서 자른다.
- 별도 작업 트리의 미커밋 수정과 보기 전용 PDF의 바이너리 변경은 표시하지 않는다.

**전환할 때 거두는 것.** 쓰던 선택과 위치 다시 잡기는 거둔다. 메모 글은 남긴다. 저장 안 한 편집은 닫지 않고 그 카드를 목록에 남긴다.

## 디자인 토큰과 컴포넌트

예전에는 색 리터럴이 49–54가지, radius가 14가지(2·4·5·6·7·8·9·10·12·14px, 50%, 0과 그 조합), 글자 크기가 13가지였고 토큰은 32개뿐이었다. 그래서 같은 역할의 버튼과 배지가 곳마다 조금씩 달랐다(2026-09-23). 이를 [shadcn/ui](https://ui.shadcn.com)의 **체계(토큰 이름·역할·변형 이름)만** 빌려 한 벌로 모았다. React·Tailwind·빌드 단계·CDN은 없다. CSS는 여전히 `src/limn/server.py` 안의 `<style>` 하나이고, 배포는 패키지 설치뿐이다. 동작·API·레이아웃 규칙은 그대로다.

### 토큰

색 리터럴은 **두 토큰 블록**(`:root` = 다크, `:root[data-theme=light]` = 라이트) 안의 변수 정의에만 있다. 규칙은 모두 `var(--…)`를 쓴다. 옅은 채움(선택 상자·마크·위험 버튼 바탕 등)은 `color-mix(in srgb, var(--토큰) N%, transparent)`로 만든다. 중립색은 zinc 계열이다.

| 묶음 | 토큰 | 쓰임 |
| --- | --- | --- |

### 한 겹 담기

테두리 상자 안에 또 테두리 상자를 그리는 방식이 촌스러웠다(저자 지적 2026-09-24). 예로는 카드 안의 테두리 배지·버튼, 테두리 있는 분절 컨트롤 안의 테두리 칸, 테두리 원문 상자, 테두리 겹침 안내, 보관함 행 안의 테두리 스레드 상자가 있었다. 그래서 담는 층은 하나만 둔다.

| 층 | 모양 |
| --- | --- |
| 패널·구획 | 테두리 없음. 구획 머리 + 구분선(`.arc-head` 윗줄) |
| 카드(`.card`) | 가는 `--border` 테두리 하나. 그림자 없음 |
| 카드 안 | 배지 = 옅은 채움(뜻 있는 배지는 그 색 14% 틴트) · 버튼 = 채운 secondary(완료 soft, 삭제 바탕 없는 위험 색) · 스레드 = 구분선 하나 뒤 목록 · 편집 = 간격만 |
| 작성 패널 | 상자 없음. 범위 사다리·종류 = shadcn Tabs(채운 틀 + 떠 있는 고른 칸) · 스테퍼 = 채운 묶음(안쪽 선 없음) · 원문 = `--code` 채움(테두리 없음) · 겹침 안내 = 글 + 버튼 · 테두리는 메모 입력 칸 하나 |
| 보관함 행 | 상자 없음. 행 사이 구분선 하나, 스레드·원래 요청은 들여쓰기만 |
| 떠 있는 면(대화상자·알림·@목록) | 가는 `--border` + `--shadow-lg`/`--shadow` — 그림자는 여기에만. 안의 버튼은 채운 secondary |

가드는 둘이다. `FrontendNoNestedOutlines`는 안쪽 컴포넌트 CSS에 테두리 상자가 없는지 본다. 스크린샷 하네스의 DOM 검사는 네 변 테두리를 가진 요소가 네 변 테두리를 가진 조상 안에 있는지 본다(입력 칸 제외). 고치기 전에는 목록 72개, 더보기 13개가 걸렸고 고친 뒤 0이다.

### 아이콘

이모지와 기본 문자 아이콘(⏳ ▾ ▸ ☾ ◐ ✓ ✎ ⚠ ⧉ ⋯ ＋ ×)은 기기·글꼴마다 모양이 달라 보기 흉했다(저자 지적 2026-09-23). 전부 없애고, 꼭 필요한 곳에만 [Lucide](https://github.com/lucide-icons/lucide)(ISC) 아이콘을 쓴다. 출처·버전·아이콘 목록은 [`src/limn/vendor/lucide/README.md`](../../src/limn/vendor/lucide/README.md)에 있다.

- `lucide-static` npm 원본의 `<svg>` 안 요소만 `src/limn/viewer/assemble.py`의 `LUCIDE`에 인라인으로 넣는다. 외부 CDN은 없다.
- `stroke="currentColor"`·`stroke-width="2"`(24 격자)·16px이라 글자색을 따른다. 배지·행 안에서는 12–14px이다.
- 서버가 `{{ic:이름}}` 자리를 채우고, JS는 `ic(이름)`으로 같은 모양을 그린다.
- 아이콘 없이 뜻이 분명한 버튼은 글자만 둔다. 카드의 [보기]·[수정]·[풀기]·[삭제]·[완료], 보관함 [답글]·[되살리기], 휴지통 [영구 삭제], [원문 펼치기], [더보기] 안의 [축소]·[확대]·[폭 맞춤]·[테마] 등이다.
- 아이콘만 두는 버튼(축소·확대·테마·도움말·더보기·위치 복사·알림 닫기)은 `aria-label`로 이름을 준다.
- 산문 속 화살표(→)와 키 이름(⌘ Enter)은 글자로 남긴다. 아이콘이 아니다.

### 마크와 파비콘

0.3.4 전에는 브랜드가 탭 제목 `Limn · <이름표>` 하나였다. 파비콘과 탐색 줄의 작은 네모는 이름표 첫 글자였다. 이제 Limn 마크 하나를 쓴다.

**모양.** 작은 점(핀)에서 시작한 한 획이 아래로 내려가 한 번 꺾이고, 오른쪽으로 줄(원고의 소스 줄)이 되어 뻗는다. PDF의 한 점을 `.tex` 줄로 되돌린다는 Limn의 일을 그대로 그린 것이다. Lucide와 같은 24 격자에 둥근 끝, 한 굵기(2.4)이고, 점 지름(5.2)은 획의 두 배가 조금 넘어 16px에서도 점으로 읽힌다. 그라데이션·그림자·마스코트·글자는 없다.

| 요소 | 값(24 격자) |
| --- | --- |
| 타일 | 24×24, 모서리 5.5 |
| 점 | 중심 (8, 8), 반지름 2.6 |
| 획 | `M8 8V13.5a3.75 3.75 0 0 0 3.75 3.75H17.2`, 굵기 2.4, 둥근 끝 |

기하는 [`src/limn/mark.py`](../../src/limn/mark.py) 한 곳에 있고 세 모양을 그 값에서 만든다. 뷰어 인라인 SVG(`inline_svg`), 파비콘 SVG(`favicon_svg`), PNG(`png`)다. 빌드 단계도, 저장소에 넣은 그림 파일도 없다.

**쓰는 곳과 색.** 인라인 SVG는 클래스만 달고(`limn-mark`·`limn-mark-tile`·`limn-mark-dot`·`limn-mark-line`) 색은 CSS 토큰으로 칠한다. 그냥 `.mark` 는 PDF 위 핀 상자라 `marks()` 가 지우고 다시 그린다. 처음에 같은 이름을 썼더니 핀을 그리는 순간 마크가 모두 사라졌다(가드 `MarkMarkup.test_mark_classes_are_its_own`, 브라우저 `EnglishChrome.test_the_limn_mark_survives_boot_and_pin_marks`). 장식이라 `aria-hidden`이고, 이름은 옆 글자가 말한다.

| 자리 | 크기 | 타일 | 점·획 |
| --- | --- | --- | --- |
| 탐색 줄의 이름표 앞(`#paper-identity-mark`, 데스크톱·펼친 폴드) | 16px | 인스턴스 색 `--brand` | `--brand-foreground`(흰색) |
| [더보기] 첫 줄의 이름표 칩(`#more-label`, compact) | 14px | `--brand`(칩과 같은 색이라 획만 보인다) | 흰색 |
| 도움말 머리(`#help-h`) | 20px | `--popover-foreground`(흑백) | `--popover` |
| 파비콘 SVG(data URL) | — | `--accent` 값 | 흰색 |
| `/favicon-32.png`, `/apple-touch-icon.png` | 32·180px | `--accent` 값(터치 아이콘은 네모, iOS가 깎는다) | 흰색 |

- 타일 색은 두 테마에서 같다. 이름표 색이 테마와 무관하기 때문이다(§토큰의 `--brand`). 흑백 도움말 마크만 테마를 따라 뒤집힌다.
- 파비콘은 이름표 첫 글자를 버렸다. 탭 사이의 구분은 타일 색과 탭 제목의 이름표가 맡는다. 첫 글자가 있을 때도 16px에서는 색이 먼저 보였다.
- `<head>`는 PNG(`sizes="32x32"`) → SVG(`type="image/svg+xml"`) → `apple-touch-icon` 순으로 잇는다. SVG를 아는 브라우저는 SVG를, 모르는 브라우저·홈 화면은 PNG를 고른다. PNG 주소의 `?c=<색>`은 색이 바뀌었을 때 옛 그림이 캐시에서 나오지 않게 한다.
- PNG는 부호 있는 거리로 그린다. 픽셀마다 한 번, 타일과 글리프 가장자리까지의 거리로 덮인 비율을 정하고 zlib으로 쓴다. 표준 라이브러리만 쓴다는 불변식([architecture.md](architecture.md) §불변식 2)을 지키려는 것이다. 180px 한 장이 수십 ms이고 크기·색마다 한 번만 그린다(메모리 캐시).

실측(2026-09-26, 헤드리스 Chromium): 16px에서 점과 줄이 따로 읽힌다(가드 `MarkRaster.test_glyph_reads_at_16px`). 스크린샷은 데스크톱(1400×850)·폴드(842×758)·폰(384×832) × 밝게·어둡게로 PR에 적은 경로에 있다.

## 렌더링과 확대

### 벡터 렌더링

저자 질문(2026-09-23): "PDF 빌드한 화면이 흐릿한 거는 어쩔 수 없는 거냐? 글자가 벡터로 살아있지는 않던데."

그전에는 쪽을 `pdftoppm -r 150` PNG로 그려 `<img>`로 보였다. A4 한 쪽이 1241×1754px이라, 데스크톱 폭 맞춤(954 CSS px)·DPR 2에서 이미 화면 픽셀의 0.65배였다. 확대할수록 더 흐려져 4배에서는 0.16배였다. 지금은 뷰어가 같은 빌드의 PDF를 PDF.js로 캔버스에 직접 그린다. 서버 API·핀 형식은 그대로이고, 경로 두 개(`GET /pdf`·`GET /vendor/pdfjs/…`, [api.md](api.md))만 덧붙였다. `vendor` 경로는 `.mjs` 이름 하나만 받고 폴더 밖(심볼릭 링크 포함)을 가리키지 않는다(`limn.files.vendor_file`).

| 항목 | 규칙 |
| --- | --- |
| 라이브러리 | `pdfjs-dist` 6.3.289 `legacy` 빌드를 `src/limn/vendor/pdfjs/`에 담는다(외부 CDN 없음). 출처·sha256·뺀 파일의 근거는 [`src/limn/vendor/pdfjs/README.md`](../../src/limn/vendor/pdfjs/README.md) |
| 문서 | `GET /pdf?build=<META.pages_build>` — 쪽 이미지와 같은 빌드의 PDF. 쪽 수가 화면과 다르면 쓰지 않는다 |
| 백킹 크기 | 쪽 CSS 크기 × `devicePixelRatio` × (브라우저 핀치 배율, 1 이상). 앱 확대는 쪽 CSS 폭(`W`)에 이미 들어 있다 |
| 가로·세로 | 따로 맞춘다(렌더 `transform`의 세로 배율). 쪽 상자 비율은 PNG 픽셀 수에서 왔고 PDF 쪽 비율과 0.1% 안쪽으로 다르다. PNG도 쪽을 그 상자에 꽉 채워 그렸으므로, 이렇게 해야 글자가 PNG 때와 같은 % 자리에 온다 |
| 가시 영역 | `IntersectionObserver`(root `#left`, 위아래 150%) 안의 쪽만 그린다. 밖으로 나간 쪽의 캔버스는 크기를 0으로 줄여 떼어 낸다(사파리도 메모리를 바로 돌려준다) |
| 순서 | 화면 안의 쪽을 가운데에서 가까운 순으로, 한 번에 한 장. 쪽 캔버스 → 상세 캔버스 순 |
| 픽셀 상한 | 캔버스 한 장 16,777,216 픽셀(iOS 캔버스 한계, 모바일 메모리). 넘으면 쪽 캔버스를 상한까지 낮추고, 화면에 보이는 부분(+화면 크기의 25% 여유)만 원래 해상도로 그린 **상세 캔버스**(`.dt`)를 쪽 안 % 좌표로 겹친다. 스크롤해 상세 영역을 벗어나면 다시 그린다 |
| 다시 그리기 | 확대·창 크기·DPR이 바뀌면 그리던 것을 취소하고 150ms 뒤 다시 그린다. 그동안에는 옛 캔버스가 CSS로 늘어나 보인다(깜빡임 없음). 끝나면 새 캔버스로 바꿔 끼운다 |
| 재빌드 | 캔버스를 걷어 새 PNG를 먼저 보이고(옛 PDF 그림이 새 좌표 위에 남지 않게), 새 빌드의 PDF를 열어 다시 그린다. 옛 문서는 `loadingTask.destroy()`로 닫는다 |
| 폴백 | pdf.js를 못 불러오거나(`vendor` 404·네트워크), PDF를 못 열거나, 쪽 수가 다르거나, 그리다 실패하면 캔버스를 모두 걷는다. 밑에 늘 있는 PNG `<img>`가 그대로 보이고, 상태 칩 'PNG 보기'(`#vec-chip`)가 사유를 설명에 싣는다. 서버의 `pdftoppm` 렌더는 그대로 둔다(첫 화면·폴백) |
| 텍스트 레이어 | 넣지 않는다. 드래그가 글자 선택이 아니라 영역 선택이라, 글자 선택 레이어가 있으면 끌기와 다툰다. 복사는 원문 스니펫(작성 패널)으로 한다 |

**좌표 체계는 바뀌지 않는다.** 캔버스는 `pointer-events:none`이라 드래그와 길게 누르기는 예전처럼 쪽 상자(`.pg`)가 받는다. `frac`은 쪽 상자 대비 비율이다. 쪽 상자의 크기·비율은 PNG 때와 같다. `pt_w`·`pt_h`는 여전히 PNG에서 온다(서버의 `limn.build.page_list`가 PNG 머리의 픽셀 크기와 dpi로 계산한다).

### PDF 영역 전용 확대

저자 질문(2026-09-23): "브라우저 확대 축소(pdf) 시 사이드바까지 같이 움직이는데, 이것도 기술적으로 어쩔 수 없는 건가?"

확대 입력을 가로채지 않으면 브라우저 페이지 확대가 되어 사이드바와 도구 줄까지 커진다. 지금은 PDF 영역의 확대 입력을 가로채 쪽 폭(`W`)만 바꾼다.

| 입력 | 처리 |
| --- | --- |
| Ctrl(⌘)+휠(`#left` 위) | `wheel`을 `passive:false`로 받아 `preventDefault`. 마우스 휠 한 칸(\|dy\|≥50 또는 줄 단위)은 버튼 한 번과 같은 1.2배, 트랙패드 핀치(크롬·파이어폭스는 ctrlKey가 붙은 잘게 나뉜 wheel)는 `exp(−dy/100)`(크롬이 핀치 배율을 휠로 바꾸는 식의 역, 한 이벤트 ±18로 자름). 한 프레임에 모아 한 번 적용한다 |
| 사파리 트랙패드 핀치 | `gesturestart`/`gesturechange`의 `e.scale`(시작 폭 × scale) |
| Ctrl(⌘) + `=`·`+` / `−` / `0` | 확대 / 축소 / 폭 맞춤. 입력 칸에 포커스가 있으면 가로채지 않는다 |
| 두 손가락(터치) | `#left`에 `touch-action: pan-x pan-y` — 브라우저 핀치·두 번 탭 확대를 막고 스크롤만 넘긴다. `touchstart`/`touchmove`(`passive:false`)에서 두 손가락 거리 비율로 `W`를 바꾸고, 두 손가락 가운데 점 밑의 자리가 손가락을 따라가게 스크롤한다. 선택 모드의 쪽은 `touch-action:none`(한 손가락 = 선택, 두 손가락 = 같은 앱 확대). 두 번째 손가락이 닿으면 그리던 선택 상자와 길게 누르기를 버린다 |
| 버튼 [＋]·[−]·[↔ 폭 맞춤] | 같은 1.2배 단계와 폭 맞춤(PDF 영역 가운데 기준) |

**기준점을 지킨다.** 확대할 때 포인터 밑의 쪽과 그 쪽 안 비율을 잡아 둔다. 키보드·버튼이면 PDF 영역 가운데가 기준이다. 폭을 바꾼 뒤, 그 비율 자리가 같은 화면 좌표에 오게 `#left`를 스크롤한다. 폭 맞춤은 보던 쪽의 위쪽 자리를 지키고 가로 스크롤을 처음으로 되돌린다.

**한계.** 폭 맞춤 폭의 0.5–5배이고 최소 160px이다. 예전 절대 상한 2200px는 없앴다. 쪽이 넘치면 `#left` 안에서만 가로로 스크롤되고 `body`는 넘치지 않는다.

**패널은 영향이 없다.** 사이드바·시트·도구 줄은 `#left` 밖이라 영향을 받지 않는다. 패널 위의 Ctrl+휠은 PDF 영역이 아니므로 가로채지 않는다.

**뷰포트 메타는 그대로다.** `maximum-scale`·`user-scalable=no`를 넣지 않는다. 패널 쪽 핀치는 여전히 브라우저 확대라, 접근성 확대를 빼앗지 않는다.

## 역할에 따른 화면

서버는 `/api/meta`의 `me.role`로 역할을 알려 준다. `viewer` 역할이면 `body.role-viewer`가 붙고, 서버가 어차피 `403`으로 거절할 상태 변경 컨트롤을 숨긴다(0.2.1). 카드의 수정·답글·삭제·완료·확인·되살리기·영구 삭제·처리 중 풀기, 재빌드, 작성 패널의 메모·종류·담당·[핀 저장]이 그 대상이다. 읽기는 그대로다. 보기·쪽 이동, 스레드, 닫힌 핀, 그리고 작성 패널의 위치와 원문 줄은 보인다. 작성 패널에는 `#c-viewer` 안내(`보기 권한만 있습니다 — …`)가 뜨고, Ctrl+Enter 같은 키 입력으로 저장·답글·수정을 보내려 하면 요청을 보내지 않고 토스트로 알린다(`viewerBlocked`). 휴지통의 [되살리기]는 0.3부터 viewer에게 아예 그리지 않는다(`droppedCard`, [영구 삭제]는 전부터 소유자에게만 그렸다). 숨김 규칙만으로도 보이지는 않았지만 버튼이 문서에 남아 있었다(E2E 재실행에서 지적, 테스트 `test_v03.ViewerTrashControls`).

**거부된 첫 화면.** 뷰어를 여는 `GET /`가 거부되면(`--members-only` 밖의 사람, `--allow` 밖의 사람, 테일넷의 헤더 없는 요청) 브라우저(`Accept: text/html`)는 JSON 대신 짧은 HTML 안내를 받는다(`limn/web/errors.py`의 `error_page_html`). 언어는 `?lang=`, 없으면 `Accept-Language`의 첫 태그(`ko*`면 한국어, 아니면 영어)로 정하고, 문구는 뷰어와 같은 메시지 표(`ui_en.json`)를 거친다. API 경로와 브라우저가 아닌 요청은 그대로 JSON이다.

## 알려진 제약

뷰어 화면·입력·렌더링·측정의 한계만 적는다. 좌표 역변환, 앵커, 여러 문서 서버 쪽 한계는 [domain.md](domain.md)가 맡는다.

**실기기에서 재지 못한 것.**

- 밀어서 닫기, 시트 끌기, 두 번 탭, 유령 클릭 삼키기는 헤드리스 크롬의 CDP 터치로만 쟀다. CDP 이동은 약 30ms 간격으로 도착해, 튕김 판정(0.5px/ms)을 그 간격에서 확인했다. 실기기는 입력 빈도가 높아 더 매끄럽다.
- 안드로이드의 시스템 뒤로 가기는 흉내 낼 수 없다. `CloseWatcher` 경로는 데스크톱의 닫기 요청(Esc)으로, history 경로는 `CloseWatcher`를 지운 채 `go_back()`으로 확인했다.

- 벡터 렌더링과 PDF 영역 전용 확대는 헤드리스 크롬(Playwright)으로만 쟀다. 사파리의 `gesturechange` 경로, 실기기 핀치(가속·관성), 실제 GPU의 렌더 시간은 재지 못했다.
- 모바일 레이아웃과 패널 폭·시트 높이 손잡이는 헤드리스 크롬 에뮬레이션(Playwright, `isMobile`·`hasTouch`)으로만 쟀다. 끌기는 CDP 터치 이벤트로 흉내 냈다. 실기기의 가상 키보드는 visualViewport 높이를 줄이는 흉내로, 핀치 확대는 두 손가락 CDP 터치로 대신했다. 실제 갤럭시 Z 폴드 7에서 한 번 더 봐야 한다.
- 여러 문서의 탭 전환은 헤드리스 크롬(1440×900·880×790·412×915 터치 에뮬레이션)으로만 쟀다. Ctrl+PgUp/PgDn은 실제 크롬에서 브라우저 탭 전환이 먼저 가져갈 수 있다. 헤드리스에서는 페이지가 받았다.

**일부러 가로채지 않는 입력.** 입력 칸에 포커스가 있을 때의 Ctrl/⌘ + `=`·`−`·`0`, 그리고 패널 위의 Ctrl+휠·핀치는 가로채지 않는다. 그래서 이때는 브라우저 확대가 된다. 입력 칸의 브라우저 단축키를 빼앗지 않으려는 것이고, 사이드바는 PDF 영역이 아니기 때문이다. 이미 브라우저로 확대해 둔 페이지는 입력 칸 밖에서 Ctrl+0으로 되돌릴 수 없다. 그 키는 PDF 폭 맞춤이 된다. 브라우저 메뉴나 입력 칸 안에서 되돌린다.

**`GET /pdf`는 `Range`를 받지 않는다.** 그래서 PDF를 통째로 받은 뒤 연다. 시험 원고는 5.5 MB로, PNG 28장 합계보다 작다. 아주 큰 원고에서는 첫 캔버스가 늦을 수 있고, 그동안은 PNG가 보인다.

**빠른 선택의 마크는 작다.** 빠른 선택의 상자가 작아서, 저장된 핀의 마크도 작은 상자로 그려진다. 문단 전체를 칠하지 않는다. 서버가 문단의 PDF 좌표를 돌려주지 않기 때문이다.

**`mid`의 적용 범위.** 예전 설계 문서에는 "`mid`는 터치 화면에만 쓴다. 마우스로 1100px보다 좁은 창을 쓰면 700px까지는 예전 사이드바 그대로다"라는 제약이 있었다. 지금 코드에서는 이 제약이 없다.

> **주의**
>
> `layoutFor`는 `innerWidth`만 보므로, 마우스 창도 701–1099px이면 `mid`다. `FrontendMobileLogic.test_layout_for_breakpoints`가 마우스 880px → `mid`를 확인한다. §모바일 레이아웃 표의 "입력 장치와 무관"이 현재값이다.
