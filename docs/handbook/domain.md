# 핀 도메인 — 개념·상태·위치 규칙

Limn이 다루는 대상은 핀 하나다. 사람이 PDF에서 영역을 고르면 서버가 그 자리를 `.tex` 파일과 줄 범위로 되찾는다. 그 위치에 요청 메모를 붙여 저장한 것이 핀이다. 이 문서는 핀이 무엇인지, 위치를 어떻게 찾고 원고가 바뀐 뒤에도 어떻게 맞게 유지하는지, 서버가 핀에 대해 어떤 규칙을 지키는지를 설명한다.

역변환·범위 계산·줄 맞춤·핀 저장소·상태 전이를 고치기 전에 읽는다. 그런 동작을 바꿨다면 같은 변경에서 이 문서도 고친다. 필드와 엔드포인트의 세부는 [api.md](api.md)가 정본이다.

> **한눈에**
>
> - 용어: 핀, 상태 이름, stale, anchor, 범위 사다리, 문서, 보기 전용 PDF, 그림 문서, 요소 지도, 요소의 뜻
> - 핀의 상태와 전이: 열림 → 처리 중 → 검토 대기 → 완료, 다시 열기, 삭제와 되살리기, 에이전트·사람·역할별로 누가 무엇을 할 수 있는가
> - 위치 찾기: 역변환이 두 경로인 이유, 범위 사다리, 그림 문서의 요소 pick
> - 위치 유지: 줄 번호 재동기화(`anchor`), 그림 핀의 요소 위치
> - 서버 규칙: 저장소 안전성, 작성자 귀속(신원 방식·토큰·역할·입장), 여러 문서의 서버 결정, 보기 전용 PDF와 그림 문서
> - 알려진 제약: 위치 대응과 핀 상태에서 아직 남은 한계

## 용어

아래 용어는 이 문서에서 한 번 정의하고 같은 뜻으로만 쓴다. 에이전트용 용어표는 [SKILL.ko.md](../../skill/SKILL.ko.md) §용어에 있다.

| 용어 | 뜻 |
| --- | --- |
| **핀** | 출력물의 한 자리 + 요청이나 질문 + 그 대화다. 자리는 PDF에서 고른 영역을 `.tex` 파일과 줄 범위로 옮긴 것이고, 요청은 메모, 대화는 스레드다. 위치가 붙은 TODO라고 생각하면 된다. 뷰어 도움말도 같은 한 줄로 정의한다. |
| **핀 번호(id)** | 핀마다 붙는 정수다. 인스턴스 안에서 문서를 가로질러 유일하고, 삭제된 뒤에도 다시 쓰지 않는다. 채팅에서 `#12`라고 부르는 번호가 이것이다. |
| **역변환** | PDF 위의 좌표를 원고의 파일·줄로 되돌리는 일이다. SyncTeX 경로와 글자 경로 두 가지가 있다(§역변환이 두 경로인 이유). |
| **pick** | 사람이 드래그한 영역에 대해 서버가 역변환을 하고 후보 범위를 돌려주는 요청(`POST /api/pick`)이다. pick 결과를 메모와 함께 저장하면 핀이 된다. |
| **범위 사다리** | pick이 돌려주는 줄 범위 단계 목록(`levels`)이다. 드래그한 줄, 감싸는 문단, 감싸는 환경처럼 넓이가 다른 범위를 한꺼번에 준다. 그림 문서에서는 고른 요소와 그 조상 요소가 단계가 된다(§범위 사다리). |
| **anchor** | 핀을 저장할 때 떠 두는 범위의 머리·꼬리 줄 텍스트다. 원고가 바뀌어 줄 번호가 밀려도 이 텍스트를 다시 찾아 범위를 맞춘다(§줄 번호 재동기화). |
| **stale(위치 잃음)** | anchor의 머리 줄을 원문에서 더 찾지 못한 핀의 표시(`stale: true`)다. 상태 전이와는 별개의 표시다. 줄 맞춤은 열린 핀에만 하므로 열린 핀에서 판정된다. |
| **열린 핀** | 닫히지도 삭제되지도 않은 핀이다. `pins.md` 본 표와 `GET /api/pins`에는 열린 핀만 나온다. |
| **처리 중(claim)** | 누군가 그 핀을 지금 고치고 있다는 표시다. 잠금이 아니라 유효 시간(TTL)이 있는 표시라서 서버가 다른 쪽의 닫기를 막지 않는다. `처리 중(<이름>, 약 N분)`으로 보인다. |
| **검토 대기** | 에이전트가 닫았지만 아직 사람이 결과를 확인하지 않은 핀이다. 레코드로는 `done: true`와 `review: true`가 함께 있는 모양이다. |
| **완료** | 닫혔고 검토도 끝난 핀이다. 사람이 직접 닫았거나, 검토 대기 핀을 사람이 확인(confirm)한 경우다. |
| **다시 열림** | 닫혔던 핀을 다시 연 것이다. 보통 검토에서 되돌아온 핀이며, 다시 연 이유가 스레드에 남는다. 뷰어에서는 사람이 닫힌 핀에 단 [답글]이 규칙에 따라 다시 연다(§전이와 할 수 있는 쪽). |
| **삭제(drop)와 되살리기(restore)** | 삭제는 핀을 `pins.jsonl`에서 빼 `pins.dropped.jsonl`로 옮기는 일이다. 되살리기는 같은 번호로 그 핀을 되돌리는 일이다. |
| **휴지통** | 삭제한 핀이 머무는 곳, 곧 `pins.dropped.jsonl`이다. 30일(`TRASH_DAYS`)이 지나면 저절로 지워지고, 소유자는 바로 영구 삭제(purge)할 수 있다. 뷰어에서는 목록이 아니라 [⋯] → 휴지통에서 본다. |
| **질문 핀** | 고칠 곳이 아니라 물음을 담은 핀이다. 레코드의 `kind_req`가 `question`이다. 없으면 수정 요청(`fix`)으로 본다. |
| **담당** | 핀을 맡은 쪽이다. 기본은 `agent`이고 사람의 로그인일 수도 있다. 담당이 사람인 핀은 에이전트가 건너뛴다. |
| **문서(doc)** | 논문 저장소 하나 안의 원고 하나다. 본문·답변서·커버레터처럼 따로 빌드되는 단위이고, `--doc`로 준 키(예: `ms`, `rr`)로 구분한다. 단일 문서 인스턴스의 키는 `main`이다. |
| **보기 전용 PDF** | LaTeX 소스 없이 PDF만 서빙하는 문서다. 리뷰어 코멘트나 받은 PDF가 해당한다. 이 문서의 핀에는 쪽과 영역은 있지만 줄 번호는 없다. |
| **그림 문서** | 그림 저장소가 렌더한 PDF와 요소 지도를 가져와 띄우는 문서다(`kind:"figure"`). 문서 목록에는 지도 파일(`.limnmap.json`)을 적는다. 핀은 그 그림을 그린 코드의 줄 핀이다(§그림 문서). |
| **요소 지도** | 그림 PDF의 쪽마다 요소의 나무를 적은 JSON이다. 요소마다 쪽 위 영역과, 그 요소를 그린 코드의 파일·줄이 있다. 빌드마다 쪽 폴더에 사본이 있다. 형식은 [api.md](api.md) §그림 요소 지도 (`limn-figure-map/1`)에 있다. |
| **요소(`el`)** | 그림 핀이 가리키는 지도의 요소다. 핀 레코드의 선택 필드 `el`에 id·경로·이름·공통 부품·영역을 적는다([api.md](api.md) §그림 문서의 pick·핀). |
| **`pins.jsonl`** | 핀 저장소다. 한 줄이 핀 하나의 레코드이고, 파일 전체가 곧 현재 상태다. |
| **`pins.md`** | 에이전트가 읽는 작업 목록이다. 핀이 바뀔 때마다 서버가 `pins.jsonl`에서 다시 만든다. |
| **`rev`** | 레코드 내용이 바뀔 때마다 1씩 오르는 판 번호다. 옛 화면에서 보낸 수정을 `409`로 거르는 데 쓴다. |
| **신원 방식** | 요청이 누구인지 정하는 방법이다. 인스턴스마다 하나를 고른다(`--auth`). `tailscale`(기본), `local`, `trusted-proxy`가 있다(§작성자 귀속). |
| **토큰** | 사용자가 `limn token create`로 만들어 에이전트에게 주는 API 토큰이다. 요청마다 `Authorization: Bearer <토큰>`으로 보낸다. 서버 머신의 에이전트는 `--save`로 둔 토큰 파일 `~/.config/limn/<인스턴스>.token`에서 읽는다. 토큰을 단 요청은 에이전트 `agent:<토큰 이름>`이다. |
| **에이전트** | 사람이 아닌 요청자다. 토큰으로 온 요청, 헤더 없는 루프백 요청(폐지 예정), `agent` 역할인 사람이 여기에 든다. 닫으면 검토 대기로 가고 확인은 못 한다. |
| **역할** | 사람이 이 인스턴스에서 바꿀 수 있는 범위다. `people.json`의 `role`로 정하고 `owner`, `editor`, `viewer`, `agent`가 있다. 없으면 `editor`다. |

## 핀의 상태와 전이

핀은 세 상태 중 하나에 있다. **열림**, **검토 대기**, **완료**다. 서버는 이 상태를 따로 저장하지 않고 레코드에서 계산해 응답의 `state` 필드(`open`|`review`|`done`)로 돌려준다. 계산 규칙은 [`limn/pins/model.py`](../../src/limn/pins/model.py)의 `state_of` 하나다. 전이가 레코드를 상태 타입으로 파싱할 때(`parse_pin`)도, API가 `state`를 낼 때도 이 규칙을 쓰고, `state` 값은 그 타입의 이름이다([`limn/pins/listing/projection.py`](../../src/limn/pins/listing/projection.py)의 `pin_state`). `GET /api/pins`의 다른 계산 필드(`rel`·`est`·`doc`·`addressed`·`fyi`, 옛 claim의 `claim_ts`, 그림 핀의 `mark`·`mark_page`·`el_sync`)를 붙이는 것도 같은 파일의 순수 함수 `pins_payload`이고, 레코드를 이 머신의 경로로 보이는 법·핀의 문서·문서의 빌드 이력·그림 문서의 지도·겹침·시계는 조립 지점이 인자로 넘긴다.

| 상태 | 레코드 모양 | 어디에 보이나 |
| --- | --- | --- |
| 열림 (`open`) | `done`이 없거나 `false` | `GET /api/pins`, `pins.md` 본 표 |
| 검토 대기 (`review`) | `done: true`이고 `review: true` | `pins.md` 맨 아래 `## 검토 대기` 소절, 뷰어 |
| 완료 (`done`) | `done: true`이고 `review`가 없음 | 뷰어의 닫힌 핀 |

이 세 상태 밖에 두 가지 표시가 더 있다. **처리 중(claim)** 은 열린 핀 위에 얹는 표시이지 별도 상태가 아니다. **삭제(drop)** 된 핀은 `pins.jsonl`에서 빠져 휴지통(`pins.dropped.jsonl`)으로 옮겨 가므로 상태 계산 대상이 아니다.

상태마다 가진 필드가 다르다. 처리 중 표시(`claimed_by`·`claimed_at`·`claim_ts`·`claim_until`·`eta_ts`)는 열린 핀에만, 닫은 기록(`done_at`·`closed_by`·`close_reply`·`close_ref`·`changes`·`changes_at`)은 닫힌 핀에만, 확인(`confirmed_by`·`confirmed_at`)은 완료 핀에만, 삭제 기록(`dropped_at`·`dropped_by`)은 휴지통 사본에만 있다. 실행 정본은 [`limn/pins/model.py`](../../src/limn/pins/model.py)의 상태 타입이고, 규칙은 이 속성만 읽는다. 다른 상태의 필드가 레코드에 남아 있어도 저장된 그대로 둘 뿐 그 상태의 것으로 치지 않는다. 다시 연 핀에 남는 지난 닫기의 `done_at`·`closed_by`가 그렇고, 손으로 고친 닫힌 핀의 claim 필드도 그렇다(`unclaim`은 아무것도 쓰지 않는다).

모든 상태가 함께 가진 필드는 상태 타입의 `core`(`PinCore`)에 타입으로 있다. `id`, 문서(`doc`), 위치(`place`), `note`, 만든 때와 사람(`at`·`author`), `rev`, `kind_req`, `assignee`, `mentions`, `thread`, 그리고 줄 맞춤 상태(`anchor`·`synced_at`·`stale`·`sync`)다. 위치는 줄 핀이면 `LineSpan(file, lo, hi)`, 영역 핀(보기 전용 PDF의 핀, 코드 없이 그린 그림 요소의 핀)이면 `Region(pdf, page, frac)`이다. 스레드 항목은 `ThreadEntry(id, by, at, text, ev, ref, mentions)`이고, `ev`는 `ThreadEv`(`close`·`reopen`·`confirm`·`assign`) 중 하나다. 전이와 편집 규칙은 레코드 사전이 아니라 이 속성을 읽는다. `rev`가 없으면 0으로, `kind_req`가 없으면 `fix`로 읽는다.

값이 없거나 저장된 종류가 틀린 필드는 속성으로 올리지 않는다. 위치는 세 필드가 모두 맞을 때만 올린다. 올리지 않은 필드와 나머지 필드는 레코드에 저장된 그대로 남는다. 줄 핀의 `name`·`page`·`frac`·`kind`·`scope`·`quote`, 그림 핀의 `el`, `pdf_build`, `file_rel`, 편집·다시 열기·복원 기록, 이 버전이 모르는 필드가 그렇다. 핀을 다시 쓸 때는 필드 순서까지 읽은 그대로 쓴다.

### 전이와 할 수 있는 쪽

"누가"는 요청의 신원과 역할로 가른다(§작성자 귀속). **에이전트**는 토큰으로 온 요청, 헤더 없는 루프백 요청, `agent` 역할인 사람이다. **사람**은 그 밖에 신원이 확인된 사람이고, 역할이 없으면 `editor`다. `viewer` 역할인 사람은 아래 전이를 하나도 할 수 없다(`403`).

에이전트와 사람의 구분은 대부분 기본값을 고르는 데 쓴다. 닫기가 검토 대기로 가는지 완료로 가는지, 답글이 닫힌 핀을 다시 여는지가 그렇다. 권한으로 막는 것은 에이전트의 확인, `viewer`의 모든 변경, 그리고 소유자만 하는 두 가지(`/api/clear`, 휴지통의 영구 삭제)다.

| 전이 | 출발 | 도착 | 할 수 있는 쪽 | 규칙 |
| --- | --- | --- | --- | --- |
| 처리 중 표시 (`claim`) | 열림 | 열림 + 처리 중 | 에이전트 | 뷰어에는 claim을 거는 버튼이 없다. 닫힌 핀은 `409 done`, 다른 신원이 유효한 claim을 쥐었으면 `409 claimed`다. 같은 신원이 다시 claim하면 연장이다. 토큰은 이름마다 다른 신원이다. |
| 처리 중 풀기 (`unclaim`) | 열림 + 처리 중 | 열림 | `viewer`를 뺀 누구나 | claim을 건 신원과 무관하게 지운다. 뷰어에는 [처리 중 풀기] 버튼이 있다. |
| 닫기 (`close`) | 열림 | 검토 대기 | 에이전트 | 에이전트가 본문에 `review` 없이 닫으면 `review: true`가 붙는다. |
| 닫기 (`close`) | 열림 | 완료 | 사람 | `editor`·`owner` 역할인 사람이 닫으면 그 사람이 검토자이므로 바로 완료다. |
| 닫기 (`close`, `review` 지정) | 열림 | 본문 값대로 | `viewer`를 뺀 누구나 | 본문에 `"review": true`/`false`가 있으면 그 값을 따른다. 토큰 없이 테일넷 주소로 닫는 원격 에이전트는 그 기기 사람의 신원을 달고 가므로 `true`를 넣는다. 사람 신원이 없는 태그 장치는 토큰 없이 닫을 수 없다(`403`). |
| 확인 (`confirm`) | 검토 대기 | 완료 | **사람만** | 에이전트의 요청은 `403 {"error":"확인은 사람이 합니다 — …"}`다. 토큰은 늘 에이전트라 토큰으로는 확인할 수 없다. `confirmed_by`·`confirmed_at`을 남긴다. |
| 다시 열기 (`reopen`) | 검토 대기 또는 완료 | 열림(다시 열림) | `viewer`를 뺀 누구나 | API 경로다. 이유(`reason`, 1000자 이하)를 줄 수 있고 스레드에 남는다. 뷰어에는 [다시 열기] 버튼이 없고 [완료]의 되돌리기에만 쓴다. |
| 답글로 다시 열기 (`reply`) | 검토 대기 또는 완료 | 열림(다시 열림) | 사람(규칙), 누구나(`reopen: true`) | 사람이 사람을 @태그하지 않은 답글을 달면 다시 연다. 답글이 다시 연 이유가 되고 기록은 `reopen`과 같다. 사람을 @태그한 답글, 질문 핀의 답글, 에이전트의 답글은 상태를 바꾸지 않는다. 본문 `reopen`(`true`/`false`)이 규칙보다 앞선다. 규칙표는 [api.md](api.md) §답글이 핀을 다시 여는 규칙 (0.2.2). |
| 삭제 (`drop`) | 어느 상태든 | 휴지통(`pins.dropped.jsonl`) | `viewer`를 뺀 누구나 | 핀을 저장소에서 빼 휴지통으로 옮긴다. `dropped_at`·`dropped_by`를 붙인다. 작성자가 아닌 쪽이 지우면 작성자에게 `dropped` 이벤트가 간다. |
| 되살리기 (`restore`) | 휴지통 | 삭제 전 상태 | `viewer`를 뺀 누구나 | 같은 번호로 되돌린다. 휴지통에 없으면(30일이 지난 항목 포함) `404`, 이미 같은 번호가 있으면 `409`다. |
| 영구 삭제 (`purge`) | 휴지통 | 없음 | **소유자만** | 휴지통에서 지운다. 번호는 다시 쓰지 않는다. `purged` 감사 이벤트와 `audit.jsonl` 한 줄을 남긴다. |
| 저절로 지우기 | 휴지통, 30일 지남 | 없음 | 서버 | 읽을 때는 숨기고, 기동 때·삭제·되살리기 때, 핀 목록 읽기에서 한 시간에 한 번 파일에서 뺀다. |

> **핵심**
>
> 에이전트는 확인(confirm)하지 않는다. 검토 대기는 에이전트가 닫은 핀을 사람이 실제로 봤다는 기록이다. 에이전트가 스스로 확인하면 그 기록의 뜻이 사라진다. 그래서 서버가 에이전트의 확인 요청을 `403`으로 막는다. 토큰, 헤더 없는 루프백 요청, `agent` 역할인 사람이 모두 여기에 든다. 뷰어는 작성자를 검토자로 제안할 뿐이고, `editor`나 `owner` 역할인 사람이면 누구든 [확인]을 누를 수 있다.

에이전트가 닫은 핀을 작성자가 나중에 다시 여는 일은 실제로 생긴다. 검토 대기가 없으면 그 핀을 사람이 봤는지가 어디에도 남지 않는다.

### 전이에 딸린 규칙

- **다시 닫아도 바뀌지 않는다.** 이미 닫힌 핀을 또 닫으면 `done_at`·`closed_by`·`rev`·`close_reply`·`close_ref`·`changes`가 모두 첫 닫기의 값으로 남는다. 두 번째 요청의 `reply`·`ref`·`changes`는 버려진다. 검토 대기 핀을 에이전트가 다시 닫아도 그대로다. 두 번째 닫기가 덮어쓰면 처음 닫은 사람이 지워지기 때문이다. 이때의 응답은 [api.md](api.md) §핀 만들기와 상태 바꾸기의 `close` 행에 있다.
- **닫는 사유를 고치려면 다시 열고 닫는다.** `reopen`이 옛 `close_reply`/`close_ref`/`changes`를 지우므로 다음 닫기가 새 사유를 채운다. 사유의 형식과 길이 제한은 [api.md](api.md) §닫을 때 사유 남기기에 있다.
- **다시 열기는 검토 흔적을 지운다.** `review`·`confirmed_by`·`confirmed_at`·`close_reply`·`close_ref`·`changes`를 지우고 `reopened_at`·`reopened_by`를 남긴다. 닫혀 있던 핀이면 스레드에 `ev: reopen` 한 줄을 더한다. `pins.md`의 번호 칸에는 `다시 열림`이 붙는다.
- **상태 전이는 스레드에 한 줄씩 남는다.** 닫기는 `ev: close`(사유와 `ref`), 다시 열기는 `ev: reopen`(이유), 확인은 `ev: confirm`이다. 다시 여는 답글은 `ev: reopen` 한 줄이 되고 따로 답글로 남지 않는다. 그 밖의 답글은 상태를 바꾸지 않는다. 질문 핀은 답글을 단 뒤 따로 닫는다.
- **닫기와 삭제는 처리 중 표시를 지운다.** 닫히거나 삭제된 핀에는 처리 중 표시가 남지 않는다. 다른 쪽이 claim을 쥔 핀을 닫는 것 자체는 막지 않는다. 그래서 에이전트는 처리를 포기하거나 넘길 때만 `unclaim`을 부른다.
- **claim은 잠금이 아니다.** claim은 유효 시간(TTL)이 있는 표시다. 서버는 다른 사람이 유효한 claim을 쥔 핀을 닫거나 강제로 다시 claim하는 것을 막지 않고, `unclaim`은 claim을 건 신원과 무관하게 지운다. 협업은 관례에 기댄다. 고치기 직전에 그 핀만 claim하고, `처리 중(…)`인 핀은 건너뛴다([SKILL.ko.md](../../skill/SKILL.ko.md) §핀 처리). 여러 핀을 한꺼번에 잡으면 손대지 않은 핀까지 막히고, 뷰어의 처리 중 시각이 전부의 완료 예상처럼 읽힌다. 요청 본문(`eta_min`·`ttl_min`)과 충돌 응답은 [api.md](api.md) §처리 중 표시에 있다.
- **검토 대기도 `done: true`다.** 그래서 검토 대기 핀은 `GET /api/pins`(열린 핀만)에 없고, claim은 `409 done`이며, 줄 맞춤과 겹침 계산에서 빠진다. `review`를 모르는 클라이언트와 이전 버전 서버는 이 핀을 완료로 본다. `review` 필드가 없는 `done: true` 레코드는 완료다. 읽기가 이관 쓰기를 일으키지 않는다.
- **`viewer` 역할은 핀을 바꾸지 못한다.** 핀 만들기, 수정, 답글, 닫기, 확인, 다시 열기, claim, 삭제가 모두 `403`이고 아무것도 바뀌지 않는다. 읽기와, 상태를 바꾸지 않는 계산(`/api/pick`, 비교 PDF 빌드)만 된다. 역할 검사는 모든 POST에서 처리 직전에 한 번 한다([api.md](api.md) §인증).
- **`/api/clear`는 소유자만 부른다.** 모든 핀을 `.bak`으로 옮기고 비운다. `pins.seq`는 건드리지 않으므로 번호는 계속 오른다. 처리하지 않은 핀까지 날아가므로 `owner` 역할만, 본문 `{"confirm": "clear all pins"}`와 함께 부를 수 있다. 편집자와 모든 에이전트는 `403`이다. 누가 지웠는지는 `cleared` 이벤트와 서버 로그, 잘리지 않는 `audit.jsonl`([api.md](api.md) §감사 기록 (`audit.jsonl`))에 남는다. 에이전트는 하나씩 닫는다([SKILL.ko.md](../../skill/SKILL.ko.md) §규칙).

stale은 이 전이와 별개다. 줄 맞춤이 머리 줄을 잃으면 열린 핀에 `stale: true`가 붙는다. 상태는 열림 그대로다. stale 핀을 어떻게 다룰지는 §줄 번호 재동기화 (`anchor`)에 있다.

닫기·다시 열기·확인·답글의 순수 판단은 [`lifecycle/rules.py`](../../src/limn/pins/lifecycle/rules.py)에 있다. 처리 중 표시의 변경은 [`claims/rules.py`](../../src/limn/pins/claims/rules.py), 삭제·복원은 [`trash/rules.py`](../../src/limn/pins/trash/rules.py)가 소유한다. 목록과 렌더도 쓰는 claim 유효 시간 판정은 공통 핀 도메인에 남는다. 각 기능의 입력·응답·쓰기는 아래 기능별 세로 슬라이스가 맡는다.

닫기·다시 열기·답글의 본문 파서는 [`pins/lifecycle/input.py`](../../src/limn/pins/lifecycle/input.py), 네 경로의 응답은 [`pins/lifecycle/http.py`](../../src/limn/pins/lifecycle/http.py)가 소유한다. 잠금 아래 저장하고 알림을 내는 `PinLifecycle`은 같은 기능의 [`service.py`](../../src/limn/pins/lifecycle/service.py)에 있다. 핀의 조립 모듈 [`runtime.py`](../../src/limn/pins/runtime.py)가 실행별 `pin_context()` 생성 함수를 이 서비스에 묶는다. 답글을 다시 여는 순수 규칙 `reopens_on_reply`는 [`lifecycle/rules.py`](../../src/limn/pins/lifecycle/rules.py)에 있다.

처리 중 표시의 입력·응답·셸은 [`pins/claims/service.py`](../../src/limn/pins/claims/service.py)의 `input.py`·`http.py`·`PinClaims`가 소유한다. 휴지통의 입력·응답·셸과 만료 정리는 [`pins/trash/service.py`](../../src/limn/pins/trash/service.py)의 `input.py`·`http.py`·`PinTrash`가 소유하고, 휴지통 조회와 정리가 함께 쓰는 만료·그림자 항목 판정은 순수 [`pins/retention.py`](../../src/limn/pins/retention.py)에 있다. 편집 규칙은 [`editing/rules.py`](../../src/limn/pins/editing/rules.py)의 `decide_edit`·`evolve_edit`와 `new_line_pin`·`new_region_pin`이고, 입력·위치 검사·응답·셸은 [`pins/editing/service.py`](../../src/limn/pins/editing/service.py)의 `input.py`·`location.py`·`http.py`·`PinEditing`이 소유한다. 모든 핀 셸은 `server.py`를 모르고 저장소·시계·알림·감사·@태그 조회·파일 위치·설정 값을 호출마다 만들어지는 `PinContext`로 받는다. 요청·응답 필드는 [api.md](api.md) §검토 대기, §처리 중 표시, §닫을 때 사유 남기기, §핀 레코드 스키마를 본다.

## 역변환이 두 경로인 이유

`synctex edit`만으로는 부족하다. `minipage`·`tabular` 안은 SyncTeX 노드가 희박하다. 전형적인 예가 Nomenclature 기호표다. 그 영역을 골라도 **조용히 엉뚱한 본문 줄이 잡힌다.**

그래서 두 번째 경로를 둔다. 선택 사각형에 실제로 찍힌 글자를 `pdftotext`로 뽑아 원문에서 되찾는 경로다. 한글 어절은 마크업을 거의 타지 않아서 원문에 그대로 남는다. 예를 들어 `타겟--소스 $i$ 간 코사인 거리`에서 `코사인`, `거리` 같은 어절은 PDF 글자와 원문이 같다.

두 경로는 **조건부 폴백이 아니라 같은 척도로 경쟁한다.** 어느 한쪽을 1차로 고정하면, 그쪽이 조용히 틀렸을 때 걸러낼 방법이 없다.

- **채점**: 영역 텍스트의 어절이 후보 줄 범위에 얼마나 들어 있는지로 점수를 매긴다.
- **희귀도 가중**: 어절마다 희귀할수록 큰 가중을 준다. 가중이 없으면 `데이터`·`학습` 같은 흔한 말이 점수를 지배한다. 그러면 본문 문단이 기호표만큼 잘 맞는다고 나온다.
- **동점 처리**: 동점이면 SyncTeX 결과를 남긴다. 글자가 없는 영역(그림)에서는 SyncTeX 쪽만 맞기 때문이다.

응답의 `via`(`synctex`/`text`, 그림 문서는 `map`)는 어느 경로를 택했는지, `score`(0~1)는 얼마나 확신하는지 알려 준다. `score`가 낮으면 서버가 경고 문구를 함께 돌려준다.

그림 문서에는 SyncTeX도 되짚을 원문 글자도 없다. 대신 그림을 그린 코드가 요소마다 쪽 위 영역과 호출 줄을 요소 지도에 적어 둔다. 그래서 그림 문서의 pick은 두 경로를 경쟁시키지 않고 지도로 되짚으며, 이때 `via`는 `map`이다(§그림 문서의 요소 pick). 지도로 되짚는 길은 `pdftotext`도 SyncTeX도 돌리지 않는다.

UI는 일치율이 90% 이상이면 아무것도 붙이지 않는다. 낮을 때만 위치 옆에 '위치 불확실' 배지를 달고, 30% 미만이면 경고 색을 쓴다. 찾은 방법(좌표/글자)·일치율·무엇을 확인할지는 배지 설명에 둔다. 배지 표현의 규칙은 [viewer.md](viewer.md) §상태 표현에 있다.

실행 정본은 [`pins/location/resolve.py`](../../src/limn/pins/location/resolve.py)의 `pick`과 [`source.py`](../../src/limn/pins/location/source.py)의 SyncTeX·pdftotext 호출 및 `TokenCache.weights`, [`src/limn/pins/location/mapping.py`](../../src/limn/pins/location/mapping.py)의 `synctex_range`·`trace_range`·`score_range`·`by_text`(순수 계산: SyncTeX 표본의 후보 선택, 두 경로의 경쟁, 약한 일치와 두 경로가 갈린 경우의 판정)다. 원고 루트·`--float-envs`·캐시·겹침 조회는 조립 지점이 `PickContext`로 넘긴다. `pick`은 결과를 값으로 돌려준다 — 찾은 범위(`Picked`), 그림 문서에서 요소의 줄(`PickedElement`), 영역 핀을 받는 문서의 영역이나 줄을 주지 못한 그림 문서의 영역(`PickedRegion`), 되짚지 못한 이유 하나(`PickRefusal`: 생성 파일·원고 밖 파일·읽지 못한 파일·되짚을 곳 없음). 선택 본문 검사는 [`pins/location/input.py`](../../src/limn/pins/location/input.py), 응답 본문과 경고·거절 문장은 같은 기능의 [`http.py`](../../src/limn/pins/location/http.py)가 만든다. 실행별 `PinLocationService`는 조립 지점에서 `PickContext` 생성 함수를 받아 `resolve.pick`을 호출한다. 같은 기능의 원문 구간 조회(`GET /api/snippet`)와 겹침 조회(`GET /api/overlaps`)는 `input.py`가 파일·줄 범위를 검사하고 `range.py`가 원문·범위 사다리 또는 열린 핀의 겹침을 만든다. 원고 트리 파일 검사는 핀 편집도 쓰므로 공통 `web.parse.source_file`을 공유한다.

## 범위 사다리

`POST /api/pick`은 줄 범위 하나가 아니라 단계 목록(`levels`)을 준다. 클라이언트는 서버에 다시 묻지 않고 단계를 바꾼다.

| `level` | 뜻 |
| --- | --- |
| `raw` | 드래그 영역이 직접 가리킨 줄 |
| `para` | 그 줄을 감싸는 문단. 경계 규칙은 아래 설명을 본다 |
| `env`, `env2`, `env3` | 감싸는 `\begin{X}…\end{X}`를 안쪽부터 최대 3단까지. 환경 이름은 가리지 않고 `document`만 뺀다 |
| `lines` | 사용자가 한 줄 버튼(위·아래 +/−)으로 줄을 직접 조정한 범위 |
| `el`, `el2` … `el8` | 그림 문서에서 고른 요소와 그 조상 요소를 안쪽부터 최대 8단까지(`LADDER_MAX`). 뿌리는 세지 않는다 |
| `fig` | 그림 문서의 뿌리 요소, 곧 그림 전체 |

`para` 단계는 네 가지 경계를 지킨다.

1. 앞뒤의 순수 `%` 주석 줄은 뺀다. 한 줄이 한 문단인 원고에서 TODO 주석이 범위와 앵커 꼬리가 되던 것을 막으려는 규칙이다.
2. 절 제목 줄을 넘지 않는다.
3. 감싸는 가장 안쪽 환경 밖으로 나가지 않는다. 환경 안쪽이면 `\begin`/`\end` 줄도 뺀다.
4. 드래그 밖 환경에 반쯤 걸치지 않는다.

`env` 단계에서 바깥 환경이 안쪽 환경을 앞뒤 한 줄로만 감싸면 둘을 같은 블록으로 보고 합친다.

범위가 같은 단계는 하나로 합치고 `merged`로 표시한다. 기본 단계(`default_level`)는 `--float-envs` 환경 안이면 그 `env` 단계이고, 아니면 `para`다. 응답의 `lo`/`hi`/`kind`는 기본 단계의 값이다.

section 단계는 두지 않는다. 절 전체를 범위로 잡으면 수백 줄 범위가 쉽게 생긴다.

그림 문서의 사다리는 고른 요소에서 뿌리까지 올라간다. 단계 하나가 요소 하나이고, 줄 범위는 그 요소의 `src`다. 이름(`label`)은 요소의 `label`, 없으면 `part`, 없으면 id다. 한 사다리의 단계는 모두 고른 요소의 `src`와 같은 파일에 있다. 단계를 바꿔도 파일이 바뀌지 않게 하려는 것이다. 그래서 `src`가 없는 조상, 다른 파일에서 그린 조상, 줄 범위가 지금 파일 길이를 넘는 조상은 단계에서 빠진다. 줄 범위가 같은 단계는 하나로 합친다. 합칠 때 안쪽 단계가 남고 바깥 단계의 이름이 `merged`에 들어간다. 안쪽 요소가 사람이 드래그한 자리에 더 가깝기 때문이다. 기본 단계(`default_level`)는 고른 요소의 단계 `el`이고, 그림 전체를 골랐으면 `fig`다. 단계마다 그 요소의 `el`이 붙어 있어서, 단계를 바꾸면 핀이 가리키는 요소도 함께 바뀐다. 실행 정본은 [`src/limn/pins/location/figure.py`](../../src/limn/pins/location/figure.py)의 `element_rungs`와 [`src/limn/builds/figure_map.py`](../../src/limn/builds/figure_map.py)의 `ladder_scopes`다.

실행 정본은 [`src/limn/pins/location/mapping.py`](../../src/limn/pins/location/mapping.py)의 `compute_levels`다. 어느 환경까지 넓힐지는 `--float-envs` 값을 인자로 받는다.

## 그림 문서의 요소 pick

그림 문서의 `POST /api/pick`은 드래그한 빌드(`pdf_build`)의 쪽 폴더에 있는 지도 사본으로 되짚는다. 그 사이 다시 렌더해 요소가 옮겼어도 사람이 화면에서 본 요소가 잡힌다.

요소 `E`마다 드래그 영역 `D`에 대해 두 비율을 잰다.

| 비율 | 뜻 |
| --- | --- |
| `cover = \|E∩D\| / \|D\|` | 드래그가 요소 안에 든 몫이다. 넓이가 없는 드래그(클릭)는 그 가운데 점으로 보고, 그 점을 품은 요소(가장자리 포함)면 1, 아니면 0이다 |
| `fill = \|E∩D\| / \|E\|` | 요소가 드래그에 덮인 몫이다 |

고르는 순서는 다음과 같다. 1·2단계에는 쪽의 뿌리 요소가 끼지 않는다. 뿌리는 쪽 전체라서 늘 드래그를 품기 때문이다.

1. `cover ≥ 0.6`(`COVER_MIN`)인 요소 가운데 가장 깊은 것을 고른다. 깊이가 같으면 영역이 작은 것, 그다음 지도 순서가 앞선 것이다. 그래서 작은 드래그와 클릭은 잎 요소로 간다.
2. 그런 요소가 없으면 드래그가 여러 요소에 걸친 경우다. `fill ≥ 0.5`(`FILL_MIN`)인 요소들의 가장 가까운 공통 조상을 고른다. 넓이가 없는 드래그는 아무것도 덮지 못한다.
3. 그것도 없으면 뿌리, 곧 그림 전체다.

`score`는 고른 요소의 `cover`다. 답의 `score`는 소수 둘째 자리로 줄여 주고, 줄이기 전 값이 0.3(`WEAK_SCORE`) 미만이면 원고 pick처럼 약한 일치 경고를 붙인다. 판단은 파일을 모르는 [`builds/figure_map.py`](../../src/limn/builds/figure_map.py)의 `pick_element`가 한다. 지도 사본을 받고 코드 줄을 읽는 쪽은 [`pins/location/figure.py`](../../src/limn/pins/location/figure.py)다. 줄은 원고 트리 안이면서 문서 폴더 안인 파일에서만 읽는다(`file_in_tree`, `tree_part`). 지도 사본은 같은 사본이 바뀌지 않는 동안 한 번만 파싱한다([`builds/artifacts.py`](../../src/limn/builds/artifacts.py)의 `BuildMapCache`, 실행마다 하나, 사본은 문서의 상태 폴더(`docs/<키>/`)·빌드 이름·수정 시각·크기로 구별하며 16개까지 둔다).

**줄을 줄 수 없으면 영역으로 떨어진다.** 두 경우가 있다.

| 이유 | 언제 |
| --- | --- |
| `figure_map_unavailable` | 그 빌드에 지도 사본이 없거나, 검사를 어겼거나, 그 쪽이 지도에 없다 |
| `element_without_source` | 고른 요소에 `src`가 없거나(코드 없이 그린 벡터 그래픽), 그 파일을 문서 폴더 안에서 읽지 못하거나, 줄 범위가 지금 파일 길이를 넘는다 |

두 경우 모두 보기 전용 PDF와 같은 영역 답을 돌려주고, `warn` 앞에 이유 문장을 놓는다. 이유는 그 한국어 문장으로만 드러난다. 답에 이유 코드 필드는 없다. 요소를 골랐으면(`element_without_source`) 영역 답에도 `el`을 싣는다. 영역 답의 글자(`quote`)는 보기 전용 PDF처럼 그 빌드의 PDF 사본에서 `pdftotext`로 뽑는다. 줄 범위가 파일을 넘는 것은 그림을 렌더한 뒤 스크립트가 바뀐 경우다. 그림을 다시 렌더하면 풀린다.

## 줄 번호 재동기화 (`anchor`)

> **핵심**
>
> Limn을 쓰는 이유가 "에이전트가 원고를 고친다"인데, 고치면 핀이 죽는 구조는 쓸 수 없다. 핀 하나를 처리해 세 줄을 넣는 순간 그 아래 핀이 전부 어긋난다.

그래서 핀을 저장할 때 블록의 **머리·꼬리 줄 텍스트**를 함께 떠 둔다. 이것이 `anchor`다. 순수 주석 줄은 건너뛰고 뜬다. 주석 줄은 파일의 종류로 가린다. 파이썬 스크립트(`.py`, 대소문자 무관, 그림을 그린 코드)는 `#`으로 시작하는 줄이고, 그 밖의 파일은 LaTeX처럼 `%`로 시작하는 줄이다(`mapping.comment_marker`). 건너뛴 주석 줄 수는 `head_off`·`tail_off`로 남긴다. 그래서 앞뒤에 주석 줄을 일부러 넣은 핀도 줄 맞춤 뒤 범위가 줄지 않는다. `*_off`가 없는 옛 anchor는 0으로 본다.

핀을 읽거나 쓰는 모든 요청은 먼저 줄 맞춤을 한다. 대상 파일의 mtime이 핀의 `synced_at`보다 새로우면 anchor 텍스트를 다시 찾아 `lo`/`hi`를 갱신한다. 줄이 움직이면 `rev`가 오른다. 그래서 옛 화면에서 보낸 수정은 `409`로 걸러진다.

| 결과 | `sync` | 표시 |
| --- | --- | --- |
| 그대로 | `ok` | — |
| 밀림 | `moved +3` | 새 줄 번호로 갱신('줄 +3 이동') |
| 머리 줄이 원문에서 사라짐 | `lost` | `stale: true`. UI에 '위치 잃음', `<state_dir>/pins.md`에 경고 |

줄 맞춤은 열린 줄 핀(LaTeX 핀과 그림 핀)에만 한다. 닫힌 핀과 영역 핀(보기 전용 PDF의 핀, 코드 없이 그린 그림 요소의 핀)은 건너뛴다. anchor 없이 저장된 옛 핀은 처음 한 번 anchor를 채운다.

> **주의**
>
> `stale` 핀은 추측해서 닫지 않는다. 사용자에게 보고한다. 사용자는 뷰어의 [수정] → 위치 다시 잡기로 고칠 수 있다.
>
> 예외는 그 범위가 방금 자신이 고친 곳일 때다. 앞선 핀을 처리하면서 그 문장 자체를 갈아엎은 경우가 그렇다. 이때는 원문을 확인하고 닫아도 된다([SKILL.ko.md](../../skill/SKILL.ko.md) §규칙).

실행 정본은 [`src/limn/pins/location/mapping.py`](../../src/limn/pins/location/mapping.py)의 `anchor_of`·`find_line`·`anchor_holds`와 [`src/limn/pins/location/position.py`](../../src/limn/pins/location/position.py)의 `follow_anchor`·`resync`(순수 계산: 열린 핀 하나를 지금 줄과 맞춰 바뀐 핀을 돌려준다), 그리고 [`src/limn/pins/location/lookup.py`](../../src/limn/pins/location/lookup.py)의 `sync_all`(핀 파일을 찾아 읽고 바뀐 핀으로 바꾸는 쪽)이다. 저장소는 `server.pin_store()`가 넘긴 `sync_all`을 트랜잭션마다 부른다.

### 그림 핀의 요소 위치 — 읽을 때 계산한다

그림 핀의 줄은 위의 anchor로 따라간다. 다시 렌더해 요소가 쪽 위에서 자리를 옮기는 것은 따로 따라가며, 이것은 저장하지 않고 읽을 때 계산한다. `GET /api/pins`는 `el`이 있는 핀마다 그 문서의 지금 화면 빌드의 지도에서 `el.id`를 찾아(`follow_element`) 필드를 붙인다.

| 결과 | `el_sync` | 붙는 필드 |
| --- | --- | --- |
| 핀의 쪽과 같은 쪽, 찍은 때와 같은 영역(네 값 모두 차이 `1e-4` 이하) | `ok` | `mark`, `mark_page` |
| 다른 영역이나 다른 쪽 | `moved` | `mark`, `mark_page`(새 자리) |
| 지도에 그 id가 없다 | `lost` | 없음 |

찍은 때의 영역은 `el.frac`, 곧 찍을 때 그 요소의 영역이다. `el.frac` 없이 저장된 핀은 핀의 `frac`과 비교한다. 둘 다 없거나 유한수 넷이 아니면 쪽 밖의 영역(`NO_FRAC`, 원점이 쪽 밖인 `(-1, -1, 0, 0)`)과 비교한다. 어떤 요소의 영역도 그 값에서 `1e-4` 안에 들 수 없으므로, 요소를 찾아도 이런 핀은 `ok`가 되지 않고 `moved`다. 지도를 읽지 못하면(지도가 없거나 검사를 어겼거나 문서가 그림 문서가 아니면) 세 필드가 모두 없다. 계산은 순수 함수 [`pins/listing/projection.py`](../../src/limn/pins/listing/projection.py)의 `element_marks`이고 `follow_element`([`builds/figure_map.py`](../../src/limn/builds/figure_map.py))를 부른다. 지도는 조립 지점이 문서마다 한 번 넘긴다.

저장하지 않는 이유는 둘이다. 트랜잭션 안에서 `frac`·`page`를 고쳐 쓰면 `rev`가 올라, 편집 중인 사람의 저장이 `409`로 거절된다. 또 옛 서버로 되돌려도 레코드는 찍은 때의 값 그대로 남는다. 그래서 다시 렌더해도 핀 파일은 쓰이지 않고 `rev`도 오르지 않는다.

## 저장소 안전성

핀 저장소(`pins.jsonl`)는 사람 여럿과 에이전트가 동시에 쓴다. 아래 규칙은 그때 핀이 사라지거나 번호가 꼬이지 않게 하는 서버 쪽 약속이다.

**모든 쓰기는 잠금 하나 아래에서 같은 순서를 지킨다.** 핀 파일을 만지는 모든 경로는 다음 순서를 따른다.

```text
읽기 → 줄 맞춤(sync) → 요청 변경 → 임시 파일에 쓰고 os.replace → <state_dir>/pins.md 재생성
```

잠금 없이 핀 30건을 동시에 저장하면 2건만 남는다.

**`pins.jsonl`은 append-only가 아니라 전체를 다시 쓴다.** 상태 갱신 레코드를 덧붙이는 방식이면 읽는 쪽이 매번 이벤트를 접어야 한다. 파일 하나가 곧 현재 상태인 편이 단순하고 틀릴 여지가 적다.

**핀 번호는 다시 쓰지 않는다.** id는 `pins.seq`로 발급하며, 삭제나 `clear` 뒤에도 같은 번호를 다시 내주지 않는다. 채팅 속 '#2'가 다른 핀을 가리키면 안 되기 때문이다. `pins.seq` 파일이 없으면 기동 때 한 번 기존 최대 id로 채운다.

**레코드 하나가 전체를 깨뜨리지 않는다.** 다음 줄은 건너뛰고 경고한다.

- 파싱할 수 없는 줄
- JSON이지만 필수 필드가 틀린 레코드: `id`(정수), `file`(문자열), `lo`/`hi`(정수, `1 ≤ lo ≤ hi`), `page`(있으면 정수), `el`(있으면 요소 모양, [api.md](api.md) §핀 레코드 스키마)

그 상태에서 처음 쓰기 전에 원본을 `pins.jsonl.corrupt-<시각>.bak`으로 보존한다. 레코드 하나 때문에 GET이 `500`이 되지 않는다. 보기 전용 PDF 핀처럼 모양이 다른 레코드의 검증은 §여러 문서에서 다룬다.

**첫 파일 교체 전에 바이트를 준비한다.** `<state_dir>/pins.md` 렌더와 `pins.jsonl` 직렬화를 잠금 아래 메모리에서 마친 뒤 `pins.jsonl` → `<state_dir>/pins.md` 순으로 쓴다. 삭제는 이 준비 뒤 휴지통을 먼저 쓴다. 렌더·직렬화가 실패하면 세 파일을 모두 그대로 둔다. 커밋한 뒤 `500`을 주면 클라이언트의 재시도가 중복 핀을 만들 수 있으므로, 준비 중의 실패를 교체 뒤로 미루지 않는다.

각 파일의 교체는 같은 폴더의 임시 파일에 쓰고 동기화한 뒤 `os.replace`로 끝낸다. 쓰기·권한 설정·교체가 실패하면 기존 파일을 유지하고 임시 파일과 열린 파일 기술자를 정리한다. 토큰 파일처럼 권한을 지정한 쓰기는 임시 파일부터 그 권한을 적용한다.

**핀의 파일은 원고를 옮겨도 따라온다.** 핀은 파일을 이 머신의 절대 경로 `file` 로 저장하고, 서버가 그 핀을 쓸 때 원고 폴더 기준 상대 경로 `file_rel` 을 함께 적는다. 읽을 때는 저장된 `file` 이 지금 원고 폴더 안이면 그것, 아니면 `file` 과 맞는 `file_rel`, 아니면 `file` 의 꼬리 가운데 핀의 문서 폴더 안에 있는 가장 긴 것으로 찾는다. 옛 레코드에 `file_rel` 을 채우려고 다시 쓰지 않는다. 옮긴 레코드의 줄을 다시 맞추면 그 파일을 `file` 에 적는다. 응답은 찾은 경로를 `file`·`rel_path` 로 싣는다. 규칙은 [api.md](api.md) §핀 파일의 위치에 있다.

**삭제·되살리기는 두 파일 사이에서 핀을 잃지 않는다.** 삭제는 준비된 바이트를 만든 뒤 `pins.dropped.jsonl`에 사본을 쓰고 `pins.jsonl`에서 핀을 빼며, 되살리기는 `pins.jsonl`과 `pins.md`에 먼저 쓰고 휴지통 사본을 뺀다. 중간에 죽으면 같은 번호가 양쪽에 남을 수 있다. 그때 살아 있는 핀이 정본이다. 휴지통 응답은 겹친 사본을 숨기고, 영구 삭제는 그 번호를 `not_in_trash`로 거절한다. 기동과 기존 주기적 정리는 같은 잠금 아래 겹친 사본을 지우며, 실패한 정리는 성공 시각을 갱신하지 않아 다음 쓰기 동반 읽기에서 다시 시도한다. 로그는 만료 항목과 겹친 사본의 제거 건수를 구분한다. 읽을 수 없는 휴지통 줄이 있으면 쓰기 전에 원본을 백업한다. 휴지통 조회는 잠금 아래 양쪽 파일을 함께 읽되 파일을 쓰지 않는다. 삭제 재시도는 같은 번호의 낡은 사본을 교체하고, 되살리기 재시도는 기존 `already_live` 거절을 유지하면서 사본을 정리한다. 전체 지우기는 살아 있는 번호의 휴지통 사본을 같은 잠금 아래 먼저 정리하고, 실패하면 원본 보관과 알림·감사를 시작하지 않는다.

`pins.jsonl` 쓰기 뒤 `pins.md` 쓰기가 실패하면 살아 있는 상태만 먼저 바뀌고 `pins.md`는 오래된 내용일 수 있다. 기동할 때 살아 있는 파일로 다시 렌더한다. 이 구간에서 실패한 요청의 알림은 남지 않을 수 있다. 파일 셋과 알림의 원자적 완료까지는 현재 저장 형식의 보장이 아니다.

쓰기의 잠금·순서는 [`pins/store.py`](../../src/limn/pins/store.py)의 `PinStore.transact()`가 정하고, 원자적 교체는 [`platform/files.py`](../../src/limn/platform/files.py)의 `atomic_write()`가 맡는다. 핀의 조립 모듈 [`runtime.py`](../../src/limn/pins/runtime.py)가 실행별 잠금과 레코드 검사·렌더 협력자를 저장소에 넘긴다. 휴지통 변경과 그림자 정리는 [`pins/trash/service.py`](../../src/limn/pins/trash/service.py), 잠근 조회는 [`pins/listing/service.py`](../../src/limn/pins/listing/service.py)가 맡는다. `pins.md`의 순수 렌더는 [`pins/listing/render.py`](../../src/limn/pins/listing/render.py), 조회 사실의 수집은 [`pins/listing/markdown.py`](../../src/limn/pins/listing/markdown.py)가 맡는다. 보존 규칙은 [`test_store.py`](../../src/limn/pins/tests/test_store.py)와 [`test_trash.py`](../../src/limn/pins/tests/test_trash.py)가 확인한다. 파일 배치는 [operations.md](operations.md) §상태 파일 배치에 있다.

## 작성자 귀속

공저자는 자기 컴퓨터에서 같은 주소로 들어와 핀을 남긴다. 서버는 요청마다 누가 보냈는지 정해 핀에 적는다. 작성자, 수정한 사람, 닫은 사람, 확인한 사람이 모두 이 신원이다. 기본은 테일넷 구성원을 신뢰하는 동료로 보아 **접근은 막지 않고 누가 무엇을 했는지만 구분한다.**

설정하면 같은 신원으로 들어올 수 있는 사람과 바꿀 수 있는 일도 가른다. 이 절은 그 모델의 뜻을 설명한다. 헤더 이름, 응답 코드, 검사 순서 같은 요청 세부는 [api.md](api.md) §인증이 정본이다.

> **핵심**
>
> 신원 방식을 정하지 않은 인스턴스(인스턴스 설정에 `AUTH` 없음, 곧 `tailscale`)에서는 테일넷에서 닿는 사람은 누구나 들어와 첫 방문 때 역할 없이 기록된다. 역할이 없으면 `editor`라서 핀, 답글, 닫기, 확인을 다 할 수 있다. 헤더 없는 루프백 요청은 에이전트다. 역할, 허용 목록, 토큰 전용 운영은 모두 켜야만 적용된다.

### 신원은 어디서 오나

서버는 요청마다 세 단계로 신원을 정한다.

1. **토큰이 가장 먼저다.** `Authorization: Bearer <토큰>`이 붙은 요청은 에이전트 `{"login": "agent:<토큰 이름>", "name": "<토큰 이름>"}`이다. 신원 헤더가 함께 와도 토큰이 이긴다. 틀리거나 폐기된 토큰은 `401`이고 다른 신원으로 물러서지 않는다.
2. **그다음은 인스턴스의 신원 방식이다.** 인스턴스마다 하나를 고른다(`--auth`). 아래 표를 본다.
3. **`tailscale` 방식에서만, 헤더도 토큰도 없는 루프백 요청은 에이전트다.** `{"login": "local", "name": "로컬/에이전트"}`로 기록된다. 폐지 예정인 규칙이고, `--no-agent-loopback`으로 끄면 `401`이 된다. `Host`가 루프백 이름인(또는 없는) 요청에만 해당한다. `tailscale serve`를 거쳐 `Host`가 `*.ts.net`인 헤더 없는 요청(태그 장치)은 `403`이다. `--tailnet-agent`를 켜면 그런 요청도 에이전트로 받는다.

| 신원 방식 | 누구로 보나 | 쓰는 곳 |
| --- | --- | --- |
| `tailscale`(기본) | `tailscale serve`가 붙이는 `Tailscale-User-Login`·`Tailscale-User-Name`·`Tailscale-User-Profile-Pic` 헤더의 사람. 루프백 피어에서 온 헤더만 믿는다 | 연구실 테일넷 |
| `local` | 루프백 요청은 모두 소유자(역할 `owner`)다. Tailscale 헤더는 무시한다 | 내 컴퓨터에서 혼자 쓸 때. 에이전트는 토큰을 쓴다 |
| `trusted-proxy` | 인증 프록시가 붙인 사용자 헤더의 사람. `--trusted-proxies`에 있는 주소에서 온 헤더만 믿는다 | oauth2-proxy 같은 인증 프록시 뒤에 둘 때 |

`Tailscale-User-Name` 같은 비 ASCII 이름은 RFC 2047로 인코딩되어 오므로 서버가 풀어 저장한다. 헤더로 온 로그인이 `local`이거나 `agent:`로 시작하면 `401`이다. 에이전트 신원은 토큰과 루프백 규칙으로만 생기고, 사람이 헤더로 흉내 낼 수 없다.

서버는 기본으로 `127.0.0.1`에만 바인딩한다. 루프백이 아닌 `--bind`는 `trusted-proxy` 방식일 때만 허용한다. `--i-know-this-is-insecure`로 강행할 수는 있지만 서버가 큰 경고를 남긴다. 그래서 `tailscale` 방식에서 신원 헤더는 `tailscale serve`나 같은 머신의 프로세스에서만 온다. 규칙은 [operations.md](operations.md) §보안 제약에 있다.

### 에이전트 신원

에이전트 신원은 두 가지다. 토큰으로 온 `agent:<토큰 이름>`과, 헤더 없는 루프백 요청의 `local`이다. 둘은 같은 규칙을 따른다.

- 본문에 `review` 없이 닫으면 검토 대기로 간다(§핀의 상태와 전이).
- 확인(confirm)은 `403`이다.
- `people.json`에 기록되지 않고 알림을 받지 않는다.

토큰은 이름마다 다른 신원이다. 작성자 쪽과 공저자 쪽 에이전트에게 토큰을 따로 주면 핀 기록과 처리 중 표시에서 둘이 구분된다. 헤더 없는 루프백 요청은 모두 같은 `로컬/에이전트`라서 구분되지 않는다.

`people.json`에서 역할이 `agent`인 사람도 같은 제약을 받는다. 닫으면 검토 대기로 가고 확인은 못 한다. 다만 사람이므로 명단에는 남는다.

### 역할 — 들어온 사람이 무엇을 바꿀 수 있나

사람마다 `people.json`의 선택 필드 `role`이 바꿀 수 있는 범위를 정한다. 역할은 소유자가 `limn member add`·`limn member role`로 정하고, 재시작 없이 다음 요청부터 적용된다.

| 역할 | 할 수 있는 일 |
| --- | --- |
| `owner` | 전부. 모든 핀을 지우는 `/api/clear`와 휴지통의 영구 삭제는 소유자만 한다. 멤버·토큰·설정 관리는 CLI와 파일 수준이다 |
| `editor` | 전체 지우기와 영구 삭제를 뺀 모두. 핀, 답글, 수정, 닫기, 확인, 다시 열기, 재빌드다. **역할이 없는 사람은 `editor`다** |
| `viewer` | 읽기만 한다. 영역 고르기(`/api/pick`)와 비교 PDF 빌드는 상태를 바꾸지 않으므로 된다. 그 밖의 변경은 모두 `403`이다 |
| `agent` | 에이전트 계약만 한다. claim, 답글, 닫아서 검토 대기로 보내기다. 확인과 전체 지우기는 못 한다. 토큰은 늘 이 역할이다 |

`role` 값을 알 수 없으면 `viewer`로 본다. 오타 난 역할이 전권이 되지 않게 가장 좁은 쪽으로 닫는 것이다.

`people.json`이 있는데 쓸 수 없으면(읽을 수 없거나 사람 목록 파일이 아니면) 같은 이유로 닫는다. 헤더로 들어온 사람은 명단의 역할과 관계없이 모두 `viewer`이고, `--members-only`는 그 파일로는 아무도 들이지 않으며(`--allow`는 파일과 무관하므로 그대로), 서버는 그 파일을 다시 쓰지 않는다. 고치면 다음 요청부터 원래 역할이 돌아온다. 파일이 없는 것(아무도 적히지 않은 새 인스턴스)은 이 경우가 아니다([api.md](api.md) §역할).

### 입장 — 누가 들어오나

역할은 들어온 사람이 무엇을 바꿀지 정한다. 들어올 수 있는지는 따로 정한다. 이 검사는 헤더로 신원이 정해진 사람에게만 한다.

- **아무것도 없으면** 신원 방식이 확인한 모든 사람이 들어온다. 첫 방문 때 `people.json`에 역할 없이 기록된다.
- **`--allow`만 있으면** 그 로그인 목록만 들어온다.
- **`--members-only`면** `people.json`에 있거나 `--allow`에 있는 로그인만 들어온다. 멤버는 소유자가 `limn member add`로 더한다.

거부된 사람은 `403`이고 `people.json`에 기록되지 않는다. 토큰과 `local` 방식의 소유자는 늘 들어온다. 태그 장치처럼 신원 헤더 없이 테일넷으로 온 요청은 허용 목록이 없어도 거부된다(`403`, [operations.md](operations.md) §실행 인자). 뷰어를 연 브라우저가 거부되면 JSON 대신 짧은 한국어·영어 안내 페이지를 받는다([viewer.md](viewer.md)).

### 신원이 보이는 곳

**뷰어 카드에 작성자가 보인다.** 핀 카드에 작성자 이름과 22px 원형 아바타가 붙는다. 사진이 없거나 못 불러오면 이름 첫 글자를 쓴다. 작성자 이름·아바타의 설명에는 '작성: 이름 · 시각 / 수정: 이름 · 시각'이 뜬다.

- 카드 전체에는 설명을 달지 않는다. 메모를 읽는 동안 설명이 떠 가리거나, 폰에서 탭한 뒤 목록 위에 설명이 남지 않게 하려는 것이다.
- 호버가 없는 기기(`(hover:none)`)는 호버·포커스 설명을 아예 띄우지 않고 길게 누르기로만 본다.
- 기록이 생기기 전의 옛 핀은 '기록 전'으로 보인다.

**`pins.md`에는 작성자 열이 없다**([api.md](api.md) §pins.md 형식). 누가 남겼는지는 `GET /api/pins`의 `author`/`edited_by` 필드나 뷰어 카드에서 본다.

**처리 분담도 작성자로 나누지 않는다.** 부탁받은 쪽이 그 시점의 열린 핀 전부를 처리한다([SKILL.ko.md](../../skill/SKILL.ko.md) §핀 처리).

> **주의**
>
> `tailscale` 방식에서 같은 머신의 로컬 프로세스는 헤더를 붙여 사람을, 헤더를 빼서 에이전트를 흉내 낼 수 있다. 헤더는 루프백 피어에서 오면 믿기 때문이다. 여러 사람이 쓰는 머신이면 에이전트에게 토큰을 주고, `--no-agent-loopback`으로 헤더 없는 에이전트를 끄고, `--members-only`나 역할로 좁힌다.

실행 정본은 [`src/limn/security/access.py`](../../src/limn/security/access.py)의 `identify`, `admit`, `check_role`, `actor_of`, `LOCAL_ACTOR`, `is_agent_actor`, 처리기가 묻는 두 역할 질문 `Principal.is_human`(답글이 사람의 것인가)·`Principal.review_on_close`(`review` 없는 닫기가 검토 대기로 가는가)와 [`limn/pins/context.py`](../../src/limn/pins/context.py)의 `is_agent`·`typed_actor`·`who`, [`collaboration/directory.py`](../../src/limn/collaboration/directory.py)의 `record`다.

## 여러 문서

논문 저장소 하나에는 문서가 여럿 있다. 본문·답변서·커버레터·하이라이트가 그렇고, 폴더와 빌드 방식이 서로 다르다.

**논문 저장소마다 뷰어 하나·주소 하나**를 두고, 그 안에서 문서를 전환한다. 문서마다 뷰어를 따로 띄우면 포트·테일넷 주소·브라우저 탭이 문서 수만큼 늘어난다. 또 "#12 처리해줘"가 어느 뷰어의 12번인지 모호해진다.

`--doc` 인자의 형식은 [operations.md](operations.md) §여러 문서 (`--doc`)에, 뷰어의 문서 전환은 [viewer.md](viewer.md)에 있다.

### 문서 종류와 능력

문서 종류(`Doc.kind`)는 `tex`(LaTeX 원고), `pdf`(보기 전용 PDF), `figure`(그림 문서) 셋이다. 종류는 기동할 때 `--doc` 경로에서 한 번 정한다(`parse_doc_arg`). 이름이 `.limnmap.json`으로 끝나면(소문자 그대로) 그림 문서, `.tex`면 LaTeX, `.pdf`면 보기 전용이다. `.tex`와 `.pdf`는 대소문자를 가리지 않는다. 그 뒤로는 닫힌 타입 `DocKind`로 다닌다. `--doc` 없이 띄운 단일 문서는 `tex`다.

분기는 종류 이름을 묻지 않고 **능력**을 묻는다. 능력은 `Doc`의 속성이고, 종류에서 능력을 정하는 규칙은 [`limn/documents.py`](../../src/limn/runtime/documents.py) 한 곳에 있다. 그래서 종류가 늘어도 분기마다 종류 목록을 고치지 않는다.

| 능력 | 뜻 | `tex` | `pdf` | `figure` |
| --- | --- | --- | --- | --- |
| `builds_from_source` | 원고에서 빌드한다. latexmk, `--git-pull` 뒤 재빌드, `POST /api/rebuild`, 원고가 더 새롭다는 `stale_build`, `.aux` 목차, 원고 트리의 지문과 `src_mtime`이 여기에 걸린다 | 예 | 아니요 | 아니요 |
| `watches_files` | 감시 스레드가 파일이 바뀌면 쪽을 다시 그린다. 기동 때도 파일이 바뀌었거나 지금 dpi의 쪽 이미지가 없으면 `--no-build`와 상관없이 그린다 | 아니요 | 예 | 예 |
| `takes_line_pins` | 줄 핀(`file`·`lo`·`hi`)과 anchor 재동기화를 받는다. 파일만 준 요청은 이 능력이 있는 문서 가운데서 찾는다(`doc_for_file`, §그림 문서) | 예 | 아니요 | 예 |
| `shows_revisions` | 변경 보기가 있다. 원고 Git 이력과 latexdiff 비교다 | 예 | 아니요 | 아니요 |
| `view_only` | 핀이 쪽·영역뿐이다. 늘 `takes_line_pins`의 반대이며, API의 `view_only`가 이 값이다 | 아니요 | 예 | 아니요 |
| `has_element_map` | 요소 지도를 가진다. 감시가 지도와 그 PDF를 함께 가져오고 쪽 폴더마다 지도를 보관한다 | 아니요 | 아니요 | 예 |

기동 때 `--doc` 값을 파싱한 뒤, 아직 `Doc`을 만들기 전에 두 가지를 정한다. 키가 `main`인 문서가 상태 폴더 루트를 쓰는지와 실행의 메인 파일이 무엇인지다. 둘 다 같은 규칙(`kind_builds_from_source`)을 쓴다.

종류 자체를 알리는 곳만 `kind`를 읽는다. API의 `kind`, 권한 대상의 문서 신원, 기동 로그의 문서 줄(`doc_start_line`)이 그렇다. 기동 로그는 종류마다 이름을 고르는 `match`라서, 종류가 늘면 타입 검사가 빠진 이름을 잡는다. 종류를 더할 때는 [`test_meta.py`](../../src/limn/documents/tests/test_meta.py)의 능력 표에 그 종류의 행을 먼저 적는다. 행이 없으면 테스트가 실패한다.

### 서버

| 결정 | 이유 |
| --- | --- |
| 핀 저장소는 하나(`pins.jsonl`·`pins.seq`)다 | 번호가 문서를 가로질러 유일해야 채팅의 `#12`가 모호하지 않다. 레코드에 `doc`을 더한다. `doc`이 없는 레코드는 첫 문서로 **읽을 때만** 본다. 이관 쓰기가 없으므로 이전 버전으로 되돌려도 상태 폴더가 그대로 동작한다 |
| 레코드 검증은 모양으로 한다 | `file`이 있으면 줄 핀(LaTeX 핀, 그림 핀)이고 줄 핀의 검증(§저장소 안전성)을 받는다. `pdf`만 있으면 영역 핀(보기 전용 핀, 코드 없이 그린 그림 요소의 핀)이다. `el`이 있으면 그 모양도 본다. 지금 설정에 없는 문서 키여도 깨진 줄로 보지 않는다. 깨진 줄로 치면 다음 쓰기가 그 핀을 지우고 백업만 남는다. pins.md는 그런 핀을 `## 설정에 없는 문서` 소절로 드러낸다 |
| 빌드·쪽·이력은 문서별 폴더(`docs/<키>/`)에 둔다 | 쪽 이미지 버전(`pages.cur`), 빌드 이력(`builds.json`, 위치 추정의 원천), `built_at`이 문서마다 다르다. 키가 `main`인 LaTeX 문서만 상태 폴더 루트를 쓴다. 그래서 단일 문서 인스턴스에 `--doc main=…`으로 문서를 더해도 본문의 빌드 이력이 이어지고, 옛 핀이 전부 점선(추정)으로 바뀌지 않는다 |
| 문서는 언제나 인자로 넘긴다 | 처리기가 요청의 문서를 찾아 서비스마다 넘긴다. 빌드 스레드가 '지금 문서'를 잃어 다른 문서의 빌드 폴더를 건드릴 길이 없다. 단일 문서는 시작할 때 고정한 실행 경로(`C.paths`)로 만든 문서(`limn.runtime.documents.Doc`, `legacy`)라서 옛 상태 폴더 배치가 그대로 돈다 |
| 빌드 잠금은 문서마다 둔다 | 빌드 폴더가 문서마다 따로다. 그래서 서로 다른 문서는 동시에 빌드해도 `.aux`를 밟지 않는다. 같은 문서는 한 번에 하나만 빌드한다(`409`) |
| `--git-pull`은 저장소 단위다 | 여러 문서면 잠금 하나로 줄 세운다. 20초 안에 다른 문서가 당긴 결과는 같이 쓴다(`pull.shared`). 동시에 fetch·merge하면 `.git/index.lock`이 부딪히고, 한 문서가 복사하는 중에 트리가 바뀐다 |
| LaTeX 문서는 메인 `.tex`가 있는 폴더에서 빌드한다 | 평소 `cd <그 폴더> && latexmk` 하던 그대로다. `<빌드 루트>::<메인>`의 빌드 루트는 사본으로 복사할 범위일 뿐이다. 본문이 `\graphicspath{{../1st/images/}}`로 옆 폴더 그림을 읽으면, 메인 폴더 하나만 복사해서는 그림이 빠진다 |
| 여러 문서면 기동 빌드를 백그라운드로 돌린다 | 문서 N개 × 수십 초를 기다리지 않고 서버가 바로 뜬다. 빌드가 실패해도 기동을 막지 않고, 그 탭이 오류 패널을 연다. 단일 문서는 동기로 빌드하고 실패하면 종료한다 |

### 보기 전용 PDF

LaTeX 소스가 없는 PDF도 같은 문서 목록에 둔다. 리뷰어 코멘트, 받은 PDF, 커밋된 제출본이 여기에 해당한다.

줄 번호를 되찾을 수 없으므로 이런 핀의 위치는 **쪽·영역(`frac`)** 이다. `pick`은 SyncTeX 없이 영역 글자를 돌려준다. 이 글자는 `pdftotext`로 뽑고 160자까지 담는다. 줄이 없으니 이 글자가 에이전트가 가진 유일한 원문 단서다. 그래서 pins.md에는 60자·긴 한 줄 같은 조건 없이 이 글자를 늘 `«…»`로 싣는다.

재빌드는 없다. 대신 감시 스레드가 3초마다 PDF의 `mtime:크기`를 본다. 바뀌었으면 같은 빌드 경로(`BuildRequests.tracked` → 이력·`build_seq`)로 쪽을 다시 그린다. 그러면 뷰어는 LaTeX 재빌드 때와 똑같이 화면을 바꾼다. 지문(PDF 내용 해시)이 달라진 옛 핀은 점선(추정)이 된다. 위치 추정 규칙은 [build-sync.md](build-sync.md) §위치 추정에 있다.

보기 전용 핀의 pick·저장·수정 요청 형식은 [api.md](api.md) §보기 전용 PDF 문서의 pick·핀에 있다.

### 그림 문서

코드로 그린 그림은 PDF로 받아 같은 문서 목록에 둔다. 그림 저장소는 PDF(그림 한 장이 한 쪽)와 요소 지도(`.limnmap.json`)를 내고, 문서 목록에는 지도 파일을 적는다. 지도는 쪽마다 요소의 나무다. 요소마다 쪽 위 영역(`frac`)과, 그 요소를 그린 코드의 파일·줄(`src`)이 있다. 형식과 검사 규칙은 [api.md](api.md) §그림 요소 지도 (`limn-figure-map/1`)에 있다.

문서 폴더는 `<폴더>::<지도>` 의 앞 폴더이고, `::` 가 없으면 지도가 있는 폴더다. 지도 속 `src`·`impl` 경로는 이 폴더 기준이고, `pdf` 는 지도가 있는 폴더 기준이다. `pdf` 는 가져올 때 문서 폴더 안이고 점으로 시작하는 이름 아래가 아니어야 한다. 심볼릭 링크는 푼 뒤에 본다. `src.file` 은 지도를 받을 때 모양만 보고, pick이 그 스크립트를 읽을 때 같은 규칙(문서 폴더 안, 점 이름 아래 아님, 심볼릭 링크는 푼 뒤)으로 본다. 그래서 문서 폴더 밖으로 이어지는 스크립트는 그것이 그린 요소만 줄을 주지 못하고, 그림의 나머지 요소는 그대로 쓰인다. 캐시가 따뜻하든 차갑든 답은 같다. `impl.file` 은 데이터다. 핀에 저장되고 pins.md에 글자로 적힐 뿐 열리지 않으므로 모양만 본다.

그림 문서는 빌드하지 않고 가져온다([build-sync.md](build-sync.md) §그림 문서). 가져올 때마다 지도를 쪽 폴더에 함께 보관하므로, 핀을 찍은 빌드의 지도를 다시 읽을 수 있다.

그림 문서의 pick은 지도로 되짚어 그 요소를 그린 코드 줄을 돌려준다(§그림 문서의 요소 pick). 핀은 그 스크립트의 줄 핀(`file`·`lo`·`hi`)이고, 선택 필드 `el`이 어느 요소인지 적는다. 줄 검증과 anchor 재동기화는 LaTeX 핀과 같다. 그래서 그림을 모르는 에이전트도 줄 핀으로 처리할 수 있다. 코드 없이 그린 요소를 골랐거나 줄을 줄 수 없으면 영역 핀(`pdf`·`page`·`frac`)에 `el`을 더한다. 영역 핀이 적는 PDF는 화면 빌드의 지도가 가리키는 PDF다([api.md](api.md) §그림 문서의 pick·핀). `/api/docs`·`/api/meta`의 `kind`는 `figure`이고 `view_only`는 `false`다. 줄 핀을 받기 때문이다.

파일만 준 요청(에이전트의 `curl`)은 줄 핀을 받는 문서, 곧 LaTeX 문서와 그림 문서 가운데서 문서를 고른다(`doc_for_file`).

- 그 파일을 가장 깊게 감싸는 문서 폴더의 문서가 먼저다. 그림 폴더가 LaTeX 문서의 빌드 루트 안에 있으면, 그 폴더의 파일은 더 깊은 그림 문서로 간다. 같은 소유가 그 LaTeX 문서의 `src_mtime` 에도 적용된다(§알려진 제약).
- 깊이가 같으면 파일 종류로 가른다. `.tex`·`.bib`·`.sty`·`.cls`·`.bst`(대소문자 무관)는 원고에서 빌드하는 문서로, 그 밖의 파일(그림 스크립트, 데이터)은 그림 문서로 간다.
- 그래도 가려지지 않으면(같은 종류 문서 둘이 한 폴더를 쓰는 경우) 문서 목록에서 앞선 문서다. 어느 문서 폴더도 그 파일을 품지 않으면 첫 문서다.

## 알려진 제약

위치 대응과 핀 상태에 남아 있는 한계다. 뷰어 화면·입력·렌더링의 제약은 [viewer.md](viewer.md)에 있다.

### 낡은 PDF와 원고의 어긋남

**화면의 PDF가 원고보다 낡으면 좌표와 원문이 어긋난다.** 에이전트가 원고를 고치고 아직 재빌드하지 않은 동안이 그렇다. 텍스트 경로는 그래도 비슷한 문단을 찾아 경고선(점수 0.3)을 아슬하게 넘기기도 한다. 기호표를 골랐는데 서론의 비슷한 목록이 `0.32`로 경고 없이 돌아오는 식이다.

그래서 서버는 원고 파일의 최대 수정 시각과 화면 빌드를 시작할 때 잰 값을 비교해 `meta.stale_build`로 알린다. `pick`의 `warn`에도 점수와 무관하게 이 사실을 앞세운다. 화면 위쪽에는 "원고가 더 새롭습니다" 배지가 뜬다. 이 상태에서 찍은 핀은 줄 범위를 확인해야 한다.

같은 이유로, 원고를 고친 뒤 PDF를 재빌드하지 않으면 화면(옛 PDF)과 원문 줄 번호가 어긋난 채로 pick이 된다. 에이전트가 원고를 고쳤으면 먼저 PDF를 재빌드한다.

### 역변환의 한계

- **SyncTeX이 선택 영역 바로 바깥의 float를 물 수 있다.** SyncTeX 좌표 조회는 가장 가까운 노드를 기준으로 한다. 그래서 밀집 클러스터링과 범위 사다리로 보정한다. 완전히 안전하지는 않다. 결과의 `kind`가 `float`·`env:*`인데 사용자가 기대한 대상과 다르면, `raw_lo`/`raw_hi`(보정 전 원시 범위)를 참고해 다시 시도한다.
- **`\input`/`\include` 경로 매핑이 깨질 수 있다.** 여러 `.tex` 파일이 `\input`/`\include`로 쪼개져 있으면 SyncTeX은 빌드 사본 안의 개별 파일 경로를 돌려준다. 서버가 이를 `<manuscript_dir>` 기준 원본 경로로 되돌린다([architecture.md](architecture.md)). 빌드 사본과 원본의 디렉토리 구조가 다른 경우처럼 이 매핑이 깨지면 경로가 어긋난다.
- **참고문헌 영역은 고를 수 없다.** 참고문헌을 고르면 SyncTeX이 생성 파일인 `.bbl`을 가리킨다. 서버가 이를 감지해 편집하지 말라고 안내하고 선택을 거부한다.
- **래스터 글자는 텍스트 경로가 못 읽는다.** 렌더 텍스트 경로는 `pdftotext`가 글자를 뽑을 수 있어야 한다. 그림 안에 래스터로 박힌 글자는 잡히지 않으므로, 그 영역은 SyncTeX 경로에만 의존한다.

### 줄 맞춤의 한계

- **머리 줄이 원문에 남아 있을 때만 따라간다.** 그 문장 자체를 갈아엎으면 `stale`로 떨어진다. 목적은 자동 복구가 아니라 표시다.
- **빈 줄만 고른 핀은 따라가지 않는다.** 앵커가 없기 때문이다.
- **같은 문장이 여러 번 나오면 틀릴 수 있다.** 원래 줄 번호에 가장 가까운 것을 고른다. 반복 구조가 많은 원고에서는 틀릴 수 있다.
- **영역 핀(보기 전용 PDF의 핀, 코드 없이 그린 그림 요소의 핀)에는 줄 맞춤(앵커)이 없다.** PDF가 바뀌면 영역 좌표는 그대로 남고 점선(추정)으로만 알린다. 어디로 옮겨졌는지는 찾지 않는다.
- **옮긴 원고에서 옛 핀의 파일은 꼬리로 짐작한다.** `file_rel` 이 없는 핀은 저장된 경로의 꼬리 가운데 핀의 문서 폴더 안에 있는 가장 긴 것으로 찾는다. 원고를 옮기면서 그 하위 폴더도 없앴는데 같은 문서 안에 이름이 같은 파일이 있으면 그 파일로 풀린다. anchor가 맞지 않으면 `위치 잃음` 으로 드러난다. 다른 문서의 파일로는 풀리지 않는다. 닫을 때 보낸 `changes` 의 경로도 같은 규칙으로 찾으므로 옮긴 뒤에도 [변경 보기]가 에이전트가 기록한 줄을 쓴다([api.md](api.md) §핀 파일의 위치).
- **꼬리 짐작이 틀려도 `file` 에 적힌다.** 옮긴 레코드의 줄을 다시 맞추다 anchor 머리를 못 찾아 `위치 잃음` 이 되어도, 줄 맞춤이 찾은 파일을 `file` 에 적는다. 그 뒤로는 그 경로가 1번 규칙으로 이긴다. 사람이 위치를 다시 잡으면 풀린다.

### 그림 핀의 한계

- **요소 id가 렌더마다 같아야 따라간다.** 생산자가 같은 요소에 다른 id를 주면 그 핀은 `요소 잃음`이 된다.
- **디스크의 `pins.md`는 화면의 지도를 따라가되, 다시 쓰는 때가 정해져 있다.** 핀을 쓸 때, 서버를 띄울 때, 그림 가져오기가 새 빌드를 화면에 올릴 때 다시 쓴다. 그래서 디스크의 `요소 잃음`은 지금 화면의 지도 기준이다. `GET /pins.md`는 요청마다 렌더한다. 이때 쓰는 것은 `pins.md` 하나뿐이고 `pins.jsonl`과 `rev`는 그대로다. 다시 쓰기가 실패하면 옛 파일이 남고 가져오기는 그대로 끝난다. LaTeX 빌드는 `pins.md`를 다시 쓰지 않는다.
- **그림 핀은 위치 다시 잡기로 영역 핀과 줄 핀 사이를 오가지 않는다.** 영역 핀의 `loc`은 영역만, 줄 핀의 `loc`은 줄만 받는다. 코드가 생기거나 사라졌으면 새로 찍는다. 같은 모양 안에서 `loc`에 `el`이 없으면 핀의 `el`은 지워진다.
- **그림 문서의 `/api/snippet?levels=1` 사다리는 `raw` 단계 하나다.** 문단·환경 단계는 LaTeX 규칙이라 코드에 뜻이 없고, 요소 사다리는 pick 답에만 있다. 편집 카드에서 줄을 조정해도 핀의 `el`은 `loc`이 바꾸기 전까지 그대로다.
- **옛 서버로 되돌린 동안 그림 핀의 위치를 다시 잡으면 `el`이 옛 요소 그대로 남는다.** 옛 서버는 `el`을 모르는 필드로 그대로 두기 때문이다. 다시 올리면 `mark`가 옛 요소를 따라간다. 사람이 위치를 다시 잡으면 풀린다.

### 상태와 운영 규칙의 한계

- **`claim`은 잠금이 아니라 TTL 있는 표시다.** 서버가 충돌을 막지 않으므로 협업은 관례에 기댄다(§전이에 딸린 규칙).
- **`--git-pull`은 `--ff-only`만 한다.** 서버 체크아웃에 로컬 커밋이 있어 분기했으면 pull을 건너뛰고(`skipped:diverged`) 지금 체크아웃으로 빌드한다. 리베이스나 머지 커밋을 대신 만들지 않는다.
- **허용 Host 집합은 고정 목록과 `--public-host`뿐이다.** 루프백 이름과 `*.ts.net`은 코드에 고정돼 있고, 다른 이름은 `--public-host`로만 더한다. [operations.md](operations.md) §Host·Origin 검사를 본다.
- **소유자 전용 HTTP 경로는 `/api/clear`와 `/api/pins/{id}/purge` 둘이다.** 멤버·토큰 관리는 서버 머신의 `limn member`·`limn token` 명령으로만 한다. 뷰어에서 사람을 초대하거나 역할을 바꿀 수 없다.
- **휴지통의 30일은 배경 작업이 아니다.** 지난 항목은 읽을 때 숨기고, 파일에서는 기동·삭제·되살리기 때와, 핀 목록 읽기(`GET /api/pins`·`/pins.md`)에서 한 시간에 한 번 뺀다. 그래서 오래 떠 있는 서버에서도 한 시간 남짓 안에 파일에서 빠진다.
- **헤더 없는 루프백 에이전트는 폐지 예정이다.** `tailscale` 방식에서는 아직 기본으로 켜져 있다. 에이전트가 토큰을 쓰게 되면 `--no-agent-loopback`으로 끈다.
- **여러 문서의 `src_mtime`은 빌드 루트 전체를 훑는다.** 문서마다 빌드 루트 전체를 2초 캐시로 훑는다. 빌드 루트가 크면 빌드와 무관한 PDF가 바뀌어도 그 문서가 '원고 수정됨'으로 보일 수 있다. 예를 들어 `manuscript/`에 1차 원고 PDF와 그림이 같이 있는 경우다. 빌드 루트를 좁게 잡는 편이 낫다.
  - 같은 빌드 루트 안의 다른 문서는 이 한계에서 빠진다. 그림 문서의 폴더에 있는 그림 확장자 파일과 보기 전용 PDF 문서의 PDF 한 개는 그 LaTeX 문서의 `src_mtime` 에서 빠진다. 단 그 빌드가 읽은 파일은 센다([build-sync.md](build-sync.md) §원고 변화 감지).
  - 그림 문서의 폴더가 지도가 있는 폴더 하나뿐이면(`x/figures.limnmap.json`) 그 밖의 그림 출력 폴더는 빠지지 않는다. 폴더를 넓히려면 `root::sub/figures.limnmap.json` 으로 쓴다.
  - 설정에 없는 PDF(옛 1차 원고 PDF 등)와 다른 LaTeX 문서의 폴더는 그대로 센다.
