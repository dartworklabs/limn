# 변경 흐름 — 설계에서 릴리스까지

이 topic은 Limn에 변경이 들어오는 순서를 설명한다. 설계와 승인, 구현, 검수, 문서 동기화, 릴리스가 어떤 순서로 이어지는지, 그리고 경로가 달라지는 경우(설계 이탈, 탐색, 긴급 수정)를 적는다. 작업을 시작하기 전과 PR을 올리기 전에 읽는다. 절차나 기여 조건이 바뀌면 이 파일과 [CONTRIBUTING.md](../../CONTRIBUTING.md)를 같이 고친다.

## 기본 경로

변경은 다음 순서로 흐른다. 작은 변경은 단계를 짧게 거치지만 순서를 건너뛰지는 않는다.

1. **관련 규칙 읽기.** [index.md](index.md) 목록에서 작업과 관련된 topic만 골라 읽는다. 구조를 건드리면 [architecture.md](architecture.md), 핀 규칙이면 [domain.md](domain.md), 화면이면 [viewer.md](viewer.md)다.
2. **설계.** 새 기능이나 동작 변경이면 요구사항·범위·비범위를 먼저 정리한다. 무엇을 만들지 소유자와 합의되기 전에는 구현하지 않는다. 설계 문서는 `docs/superpowers/specs/`에 둔다.
3. **계획.** 설계가 승인되면 검증 지점이 붙은 작업 단위로 나눈다. 계획은 `docs/superpowers/plans/`에 둔다.
4. **구현.** 팀 코딩 스킬(`code-implement`, 테스트는 `code-testing`, 신뢰 경계는 `code-security`)을 따른다. 기존 코드의 관례와 스킬이 부딪히면 **스킬이 우선**이다. Limn의 적용 경계와 검증 범위는 [code-style-roadmap.md](code-style-roadmap.md)에 있다.
5. **위반 검사.** 구현 중이나 직후에 diff가 [architecture.md](architecture.md) §멈춤 신호에 걸리는지 본다. 걸리면 멈추고 설계 판단을 받는다.
6. **검수.** [verification.md](verification.md)의 해당 게이트를 돌리고, 설계와 계획의 의도대로 됐는지 대조한다. 테스트 녹색만으로 합격이 아니다.
7. **문서 동기화.** 시스템의 현재 상태가 바뀌었으면 해당 Handbook topic을 같은 PR에서 고친다(§문서 동기화).
8. **머지와 릴리스.** CI가 녹색이고 리뷰가 끝나면 `main`에 머지한다. 릴리스는 §릴리스를 따른다.

> **핵심**
>
> 행동 계약을 바꾸는 변경은 **설계 승인 뒤에만** 구현한다(HARD-GATE). 여기서 행동 계약은 에이전트 계약(`pins.md`, HTTP API), 보안 경계(바인드 주소, Host·Origin 검사, 신원 신뢰, 역할 권한), 저장 형식(상태 디렉터리 파일과 레코드 필드)이다. 이 세 가지는 한번 퍼지면 되돌리기 어렵다.
>
> 승인은 소유자가 설계 문서·이슈·PR 가운데 하나에서 그 설계를 명시적으로 승인한 기록이다. 논의나 브레인스토밍이 끝났다는 것만으로는 승인이 아니다. 그 밖의 동작 변경은 2단계의 합의로 구현을 시작한다.

## 경로가 달라지는 경우

| 상황 | 경로 |
| --- | --- |
| 기본 청사진이나 채택한 설계 축에서 벗어나야 한다 | 멈추고 설계를 다시 검토한다. 승인되면 ADR을 쓰고(§결정 기록) [architecture.md](architecture.md)의 채택값을 같은 변경에서 고친다 |
| 해 보기 전에는 설계를 정할 수 없다 (탐색) | 시작 전에 알아낼 질문, 범위, 멈출 조건(시간·결과)을 적고 버릴 수 있는 브랜치에서 시도한다. 결과는 설계 문서로, 되돌리기 어려운 결정이면 ADR(§결정 기록)로 사후에 적고 승인받은 뒤 정식으로 구현한다. 탐색 코드를 그대로 머지하지 않는다 |
| 운영 중인 인스턴스가 망가졌다 (긴급) | 먼저 `limn update --ref <이전 태그>`로 되돌린다 ([instances.md](instances.md) §업데이트와 되돌리기). 원인을 고치는 변경은 기본 경로로 들어온다 |
| 화면의 모양이나 조작을 바꾼다 | 크기와 무관하게, `main`에 넣기 전에 네 기기군 PoC를 소유자에게 보인다(§화면 변경은 PoC를 먼저 보인다) |
| 문서만 고친다 (뜻이 같다) | 오탈자, 문장 다듬기, 의미와 권위를 그대로 둔 topic 이동·분할에는 설계 단계가 없다. [verification.md](verification.md) §1을 돌린다. 일부 테스트가 문서 문장을 확인하기 때문이다 |
| 문서만 고친다 (규칙이 바뀐다) | [api.md](api.md)의 계약, 검증 기준, 불변식, topic의 책임 범위처럼 정본 문서의 규칙을 바꾸면 코드를 고치지 않아도 기본 경로를 따른다 |

## 화면 변경은 PoC를 먼저 보인다

뷰어의 모양이나 조작을 바꾸는 변경은 크기와 무관하게, `main`에 넣기 전에 PoC를 소유자에게 보인다. 여백 몇 px, 문구 한 줄, 아이콘 하나도 해당한다. 화면은 글로 설명해서는 판단할 수 없고, 한 대역에서 맞춘 크기와 정렬이 다른 대역에서 어긋나는 일이 잦기 때문이다.

- **PoC는 실제로 렌더한 화면이다.** 바꾸기 전과 후를 같은 배율로 나란히 놓고, 달라진 곳이 작으면 확대 컷을 붙인다. 글 설명과 도식은 PoC가 아니다.
- **네 기기군에서 보인다.** 아래 표의 화면 크기를 쓴다. 변경이 닿지 않는 대역도 달라지지 않았음을 같은 표로 확인한다.
- **고를 것이 있으면 후보마다 화면을 만든다.** 추천안을 첫째에 두고 근거를 한 줄 적는다.
- **크기와 정렬은 잰 값으로 보인다.** 간격 토큰, 같은 줄에 놓인 것들의 잉크 중심, 누름 영역, 넘침과 잘림을 [viewer.md](viewer.md) §컴포넌트 규격에 대어 잰다. 눈으로 본 인상은 근거가 아니다.
- **에뮬레이션은 실기기 증거가 아니다.** 폭과 포인터를 바꾼 브라우저 화면과 실제 터치 기기에서 본 것을 구별해 적는다.
- **PoC 이미지는 저장소에 넣지 않는다.** PR 본문에는 어느 기기군에서 무엇을 보였고 소유자가 무엇을 골랐는지 적는다. PoC 서버는 `127.0.0.1`에만 묶고, 확인이 끝나면 내린다.

| 기기군 | 화면 크기(CSS px) | 포인터 |
| --- | --- | --- |
| 데스크톱 | 1440×900 | 마우스 |
| 휴대폰 | 390×844, 320×720 | 터치 |
| 태블릿 | 768×1024, 1024×768 | 터치 |
| 폴더블 | 바깥 344×882, 안쪽 673×841·841×673 | 터치 |

소유자가 PoC를 본 뒤에 머지한다. 해 보기 전에는 정할 수 없어 만든 PoC 코드는 §경로가 달라지는 경우의 탐색 규칙을 따르고, 그대로 머지하지 않는다.

## 문서 동기화

시스템의 현재 상태를 바꾼 변경은 해당 Handbook topic을 같은 PR에서 고친다. 무엇을 고칠지는 [index.md](index.md)의 "read or update when" 열이 알려 준다. 경로의 책임이 바뀌었으면 [index.md](index.md) §파일 지도의 행도 함께 고친다.

> **핵심**
>
> topic은 **지금의 상태와 규칙을 현재형으로** 쓴다. 날짜, 옮기기 전후의 수치, PR마다의 진행 기록, 모듈별 줄 수는 topic에 넣지 않는다. 그런 기록이 필요하면 성격에 맞는 곳에 둔다.
>
> - 이번 변경의 범위와 시공 순서: 설계 문서와 계획(`docs/superpowers/specs/`, `docs/superpowers/plans/`)
> - 이번 변경의 측정값·차등 비교 결과: PR 설명
> - 사용자에게 보이는 변경: [CHANGELOG.md](../../CHANGELOG.md)
> - 되돌리기 어려운 결정과 그 이유: [`docs/adr/`](../adr/index.md)의 결정 기록(§결정 기록)
> - 그 밖의 경위: git 이력

결함을 막는 현재 규칙은 실패 조건과 이유로 설명한다(예: "핀 쓰기는 잠금 아래에서 한다. 동시 요청이 서로의 변경을 덮어쓰지 않게 하기 위해서다"). 사건의 경위와 수치는 PR·커밋 기록에 둔다. [`tests/architecture/test_handbook_refs.py`](../../tests/architecture/test_handbook_refs.py)는 topic 산문의 ISO 날짜와 깨진 `§절 제목` 참조를 잡는다.

## 결정 기록

되돌리기 어렵거나 대안과 trade-off가 있던 결정은 [`docs/adr/`](../adr/index.md)에 번호 기록(ADR)으로 남긴다. 에이전트 계약·보안 경계·저장 형식의 변경, 외부 의존성 추가, [architecture.md](architecture.md)의 채택 설계 축에서 벗어나는 선택, 멈춤 신호에 걸려 설계 판단을 받은 경우가 해당한다. 명백하고 되돌리기 쉬운 작은 결정에는 쓰지 않으며, 애매하면 쓰는 쪽을 고른다. ADR의 필요 여부와 내용은 소유자와 함께 정하고 에이전트가 임의로 채우지 않는다.

- **번호와 이름.** `docs/adr/NNNN-<kebab-case-제목>.md`로 쓰고, 번호는 기존 번호 기록 중 가장 큰 번호의 다음이다. 본문은 맥락·결정·Trade-off·대안·결과로 쓴다.
- **상태.** 새 ADR은 `제안`으로 시작한다. 리뷰 지적을 반영할 수 있게 하기 위해서다. 결정이 확정되어 머지할 때 `승인됨`으로 올린다.
- **동결.** `승인됨`이거나 `main`에 이미 있는 ADR은 고치지 않는다. 오타·용어·링크 정리도 마찬가지이며, 저장소 전체 일괄 수정에서도 번호 ADR은 뺀다. 허용되는 수정은 `제안 → 승인됨` 전이와, 후속 ADR이 전체를 대체했을 때 `상태` 행을 `슈퍼시드됨 — ADR-NNNN`으로 바꾸는 한 줄뿐이다. 과거 기록이 바뀌면 결정의 경위를 다시 읽을 수 없기 때문이다. 고치기 전 `git diff --name-status main...HEAD -- ':(glob)docs/adr/[0-9][0-9][0-9][0-9]-*.md'`에서 `A`가 아닌 줄이 있으면 동결 대상을 건드린 것이다.
- **결정 바꾸기.** 기존 결정을 바꾸려면 새 ADR을 쓰고, 헤더에 `슈퍼시드`(전체), `부분 대체`(일부 조항), `명료화`(해석 확정), `과거 운영 조항 대체` 중 맞는 행으로 대상과 범위를 적는다. 대체 관계는 새 ADR의 헤더만 소유하며 과거 ADR에 후속 결정 문장을 덧붙이지 않는다.
- **같은 변경에서 함께 고칠 것.** 결정의 현재 결론·핵심 이유·감수한 비용·제약을 해당 Handbook topic 본문에 풀어 쓰고, 그 문단에 ADR 파일과 결정 절 또는 조항 범위를 짧게 인용한다. 인용을 지워도 본문만으로 규칙이 완결되어야 한다. [`docs/adr/index.md`](../adr/index.md)의 행도 원문에 맞춰 더하거나 고친다. 승인은 목표를 확정할 뿐 구현 완료의 증거가 아니므로, 구현 전에는 Handbook에 현재 실재와 채택한 목표를 나눠 적는다.

일상 작업은 Handbook과 코드에서 현재 규칙을 읽고 끝낸다. ADR은 결정을 바꾸거나 출처·경위를 확인할 때 index에서 찾아 필요한 기록만 읽는다.

## PR과 기여 조건

- 변경은 작게 유지하고, 동작이 바뀌면 테스트를 더하거나 고친다.
- PR 템플릿의 체크 항목을 채운다. 테스트 통과, 에이전트 계약 불변(또는 이슈에서 먼저 논의), CLA 동의다.
- 기여는 [CLA.md](../../CLA.md) 조건에서만 받는다. 커밋마다 `git commit -s`로 서명하고, CLA 동의 줄을 덧붙인다. 정확한 문구는 [CONTRIBUTING.md](../../CONTRIBUTING.md)에 있다.
- 코드·주석·docstring·테스트 이름·커밋 메시지·CLI 도움말·로그는 영어로 쓴다. Handbook과 [README.ko.md](../../README.ko.md)는 한국어, [README.md](../../README.md)와 [SKILL.md](../../skill/SKILL.md)는 영어다. SKILL은 영어·한국어 두 벌을 함께 고친다.

## 릴리스

버전의 정본은 [`src/limn/__init__.py`](../../src/limn/__init__.py)의 `__version__`이다. `pyproject.toml`은 hatch로 이 값을 읽는다.

1. `__version__`을 올리고 [CHANGELOG.md](../../CHANGELOG.md)에 날짜와 변경 요약을 적는다. 에이전트 계약이 바뀌지 않았다면 그 사실도 적는다.
2. `main`에 머지한 뒤 `vX.Y.Z` 태그를 단다. 태그 푸시에서도 CI가 돈다.
3. 각 머신의 운영자는 `limn update`로 최신 태그를 설치하고 실행 중인 인스턴스를 재시작한다. `--dry-run`으로 계획을 먼저 볼 수 있다. 상세는 [instances.md](instances.md)다.

> **참고**
>
> 배포 상태의 정본은 머신마다 `uv tool`로 설치된 패키지 버전이다. 인스턴스가 실제로 돌리는 버전은 `limn version` 또는 `GET /api/version`으로 확인한다.
