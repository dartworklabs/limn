# [확인]은 사람이 본 닫기에만 묶인다 — `POST /api/pins/{id}/confirm`의 선택 필드 `done_at` (설계 제안)

> **상태: 승인됨(소유자, 세션 승인). 아래 §승인 받을 것의 세 항목을 모두 승인했다.** 에이전트 계약(HTTP API)에 선택 필드 하나와 기존 `409` 응답 하나를 더하는 변경이라 [workflow.md](../../handbook/workflow.md) §기본 경로의 HARD-GATE 대상이다. 출발점은 [code-style-roadmap.md](../../handbook/code-style-roadmap.md) §R10의 "보여준 것을 승인한다 (WYSIWYS)" 부채다.

## 문제

사람의 [확인]은 "에이전트가 닫은 결과를 사람이 봤다"는 기록이다([api.md](../../handbook/api.md) §검토 대기). 그런데 `POST /api/pins/{id}/confirm`은 무엇을 봤는지 받지 않는다. 그래서 요청이 닿는 순간 그 핀에 있는 닫기를 완료로 바꾼다.

다음 순서면 사람이 보지 않은 결과가 확인된다.

1. 사람이 검토 대기 카드(답글·`changes`·변경 보기)를 연다.
2. 그 사이 에이전트가 핀을 다시 열고(`/reopen`) 다른 `reply`·`changes`로 다시 닫는다. 핀은 다시 검토 대기다.
3. 사람이 1에서 본 카드의 [확인]을 누른다. 뷰어의 [확인]은 되돌리기 알림이 끝난 뒤 보내는 지연 전송이라 이 창이 몇 초 더 열린다.
4. 서버는 2의 닫기를 완료로 바꾼다. `confirmed_by`에는 그 사람이 남는다.

에이전트는 [확인]을 부를 수 없지만 2를 할 수 있다. 악의가 없어도 에이전트가 고쳐 다시 닫는 일은 흔하다.

## 결정 (제안)

`POST /api/pins/{id}/confirm`이 선택 본문 `{"done_at": "<보여준 닫기의 done_at>"}`을 받는다.

| 요청 | 핀의 지금 상태 | 응답 |
| --- | --- | --- |
| `done_at` 없음 | 무엇이든 | 지금과 같다(하위 호환) |
| `done_at`이 지금 닫기의 `done_at`과 같음 | 검토 대기 | 지금과 같다. 완료로 바꾼다 |
| `done_at`이 다름 | 검토 대기·완료 | `409 {"error": "conflict", "reason": "conflict", "pin": <최신 핀>}`. 아무것도 바꾸지 않는다 |
| `done_at`이 있음 | 열림 | 지금과 같은 `409 {"error": "open"}` |
| `done_at`이 문자열이 아님 | — | `400`, 새 코드 `bad_done_at` |

- 뷰어는 [확인]을 그린 카드의 `done_at`을 함께 보낸다. `409 conflict`면 "핀 #N은 다시 닫혔습니다 — 새 결과를 보고 확인하세요" 알림을 띄우고 목록을 다시 읽는다. 카드는 검토 대기에 새 결과로 돌아온다.
- `409 conflict`의 모양은 `edit`의 `base_rev` 충돌과 같다. 에이전트와 뷰어가 이미 아는 응답이다.
- 이미 완료인 핀에 같은 `done_at`을 보내면 지금처럼 멱등 `{ok:true}`다.

## 왜 `rev`가 아니라 `done_at`인가

| 묶을 값 | 장점 | 단점 |
| --- | --- | --- |
| **`done_at`(제안)** | 닫기 한 번마다 정해지고 다시 열고 닫으면 바뀐다. 줄 맞춤·답글로는 바뀌지 않는다. 이미 저장·응답에 있는 필드라 저장 형식이 그대로다 | 초 단위라, 같은 초 안에 다시 열고 다시 닫으면 구별하지 못한다 |
| `rev` (`base_rev`처럼) | 모든 변경을 잡는다 | 원고를 고쳐 줄 번호를 자동으로 맞출 때도 오른다(`pins/location/position.py`). 그래서 사람이 본 결과가 그대로여도 [확인]이 거절된다. 에이전트가 작업하는 동안 재빌드는 흔하다 |
| 새 저장 필드(닫기 회차 번호) | 정확하다 | 저장 형식 변경이다(불변식 3·6, 멈춤 신호). 옛 레코드 해석과 되돌리기 호환을 따로 설계해야 한다 |

같은 초 안의 재닫기는 사람의 지연 전송 창(몇 초)보다 좁은 경우이고, 에이전트가 사람의 화면을 보고 일부러 맞추지 않는 한 일어나기 어렵다. 이 한계는 [api.md](../../handbook/api.md)에 남는 한계로 적는다.

## 범위

- 서버: `pins/lifecycle/input.py`(본문 파싱), `rules.py`의 `confirm()` 판단(보여준 닫기와 다르면 새 거절 값), `http.py`의 `409` 응답. 판단은 순수 함수에 두고 반환 값으로 거절한다([code-style-roadmap.md](../../handbook/code-style-roadmap.md) §R1).
- 뷰어: `actions.js`의 `confirmPin`이 카드의 `done_at`을 보내고 `conflict`를 알린다. `ui_en.json`에 영어 문장과 `reason:bad_done_at`.
- 문서: [api.md](../../handbook/api.md) §엔드포인트·§검토 대기·§오류 응답의 코드 표, [domain.md](../../handbook/domain.md)의 전이 표, [code-style-roadmap.md](../../handbook/code-style-roadmap.md) §R10의 부채 문장을 지운다. SKILL은 에이전트가 [확인]을 부르지 않으므로 바꾸지 않는다.

## 비범위

- `done_at`을 필수로 만드는 것. 옛 뷰어 탭과 사람이 직접 부르는 스크립트가 깨진다. 필수화는 버전이 붙은 이전 계획이 있을 때만 한다(불변식 3).
- 답글처럼 닫기 회차를 바꾸지 않는 변경까지 묶는 것.
- 새 저장 필드.

## 시험 계획

1. 순수 판단: 같은 `done_at` → 완료, 다른 `done_at` → 새 거절 값, `done_at` 없음 → 지금과 같음. 성질 테스트로 "다른 `done_at`이면 레코드가 바뀌지 않는다"를 확인한다.
2. HTTP: 사람이 본 뒤 에이전트가 다시 열고 다시 닫으면 옛 `done_at`의 [확인]이 `409 conflict`이고 핀 파일 바이트가 그대로다. 같은 `done_at`이면 정확히 한 번 완료된다.
3. 계약 스냅샷: 새 필드 없는 요청의 응답 바이트가 그대로다.
4. 뷰어: 브라우저 테스트로 [확인]의 지연 전송 중 다시 닫힌 핀이 알림과 함께 검토 대기에 새 결과로 돌아온다.

각 테스트는 먼저 실패를 본다.
