# 핀 닫기·다시 열기·확인 VSA 첫 슬라이스 설계

> **상태: 구현·검증 완료.** [백엔드 VSA 점진 이행 설계](2026-09-28-backend-vsa-migration-design.md)의 첫 구현 묶음이다. 나머지 백엔드 슬라이스는 별도 설계·계획으로 진행한다.

## 의도와 범위

한 핀의 닫기·다시 열기·확인을 읽거나 고칠 때 해당 경로의 입력, 판단, 저장·알림, HTTP 답을 `features/pins/lifecycle/`에서 찾게 한다. 이 세 경로를 옮기면서 `ServerApplication`의 `close_pin`·`reopen_pin`·`confirm_pin` 전달 메서드와 평면 `App` 계약의 세 메서드를 제거한다. `ServerApplication`은 실행별 협력자를 구성하고 처리기에 묶는 책임만 갖는다.

관찰 가능한 행동은 바꾸지 않는다. `POST /api/pins/{id}/close`, `/reopen`, `/confirm`의 경로, 입력 해석 순서, 상태 코드·오류 문장·`reason`·본문, 핀 레코드의 필드 순서와 `pins.md` 바이트, 알림 발생과 저장 순서를 보존한다. 답글·claim·만들기·편집·휴지통, 뷰어와 CLI 동작은 이번 묶음의 범위 밖이다. `PinStore.transact()`·공통 요청 보안 가드·실행별 `Runtime`은 그대로 공통 경계다.

## 현재 경로와 변경 근거

| 관심사 | 현재 코드 | 이 묶음의 목표 소유자 |
| --- | --- | --- |
| 경로와 입력 | `web/handler.py`의 `_pin_action`, `web/parse.py`의 `parse_close`·`parse_reopen` | `features/pins/lifecycle/http.py` |
| 응답 | `web/answers.py`의 `state_answer`·`confirm_answer` | 같은 슬라이스의 HTTP 코드 |
| 실행별 연결 | `ServerApplication.close_pin`·`reopen_pin`·`confirm_pin`, `pin_context()` | `ServerApplication`이 구성한 좁은 수명 주기 협력자. 기존 세 전달 메서드는 삭제 |
| 저장·알림 | `service/transitions.py`의 세 동작 | `features/pins/lifecycle/service.py` |
| 순수 판단 | `pins/lifecycle.py`의 닫기·다시 열기·확인 규칙 | 답글·claim 등도 쓰는 순수 파일의 공통 헬퍼와 얽혀 있으므로 현재는 한 소유자(`pins/lifecycle.py`)에 유지. 후속 핀 슬라이스에서 규칙까지 함께 옮김 |
| 핀 상태·저장 | `pins/model.py`·`store.py` | 여러 핀 슬라이스가 쓰는 공통 핵심으로 유지 |

`web/handler.py`가 먼저 본문을 끝까지 읽고 Host/Origin·신원·입장·역할을 확인하는 순서는 동일하다. 그 뒤 이 세 동작의 HTTP 입구를 호출한다. 그 입구는 이미 검사된 요청자와 파싱에 필요한 원고·상태 경로, 핀 번호와 본문을 받는다. 내부 판단·저장 실패는 현재와 같은 성공 값 또는 거절 값으로 돌려주며, HTTP 입구가 기존 응답 모양으로 바꾼다. `HTTPError`는 현재처럼 HTTP 표현과 접근 제어에서만 사용한다.

슬라이스의 서비스 객체는 자기 실행의 `PinContext` 생성 함수를 명시적으로 받는다. 한 요청에서 문맥을 만들고 잠금·트랜잭션·알림 순서를 직접 소유하며, 옛 `transitions` 함수로 한 번 더 전달하지 않는다. 다른 핀 동작도 쓰는 `PinContext` 자체는 이번 묶음에서 전면 재설계하지 않는다. 일부 순수 규칙을 아직 옮기지 않은 답글이 호출해야 한다면 기존 한 함수만 공유하고 복제하지 않는다. 답글 이행에서 이 임시 공유를 닫는다.

같은 서버 모듈 사본에서 두 실행을 만들어도 각 서비스 객체는 자기 `PinContext` 생성 함수와 잠금을 붙잡는다. 슬라이스는 `server.py`를 가져오거나 전역 앱을 조회하지 않는다. 처리기는 현재의 실행별 앱 바인딩을 통해 이 서비스에 도달한다. 범용 서비스 조회기나 문자열 기반 메서드 위임은 추가하지 않는다.

## 첫 변경의 절단면

1. 현재 세 경로의 허용·거절·옛 레코드·알림 경우를 차등 비교 입력으로 고정한다. 핀 번호 없음, 재닫기, 열린 핀 확인, 에이전트 확인 거절, `review` 기본값과 명시값, 다시 열기의 멘션을 포함한다.
2. 닫기를 먼저 수직으로 옮긴다. 완료된 닫기 경로는 새 HTTP 입구와 서비스가 단일 소유자이며, 옛 `ServerApplication.close_pin`과 해당 `App` 메서드·옛 전이 함수는 제거한다. 아직 옮기지 않은 다시 열기·확인은 현재 경로가 계속 소유한다.
3. 같은 경계를 다시 열기와 확인에 적용한다. 답글이 호출하는 재열림 순수 함수는 복제하지 않는다. 세 경로가 끝나면 핀 수명 주기의 HTTP 코드와 서비스 코드에서 해당 옛 코드가 사라진다.
4. 각 단계가 끝날 때 기능별 소유권 표와 실제 import를 확인한다. 같은 동작의 옛·새 구현을 병합하지 않는다. 마지막 단계의 현재 구조를 `architecture.md`·`index.md`와 관련 topic에 반영한다.

세 단계는 필요하면 별도 PR로 제출하지만, 각 PR은 하나의 완전한 HTTP 경로와 테스트를 포함하고 독립적으로 되돌릴 수 있다. 다른 슬라이스의 경로를 이 묶음과 함께 옮기지 않는다.

## 오류·데이터·검증 계약

- `parse_close`의 필드 확인 순서와 파일 경계 검사, `Principal.review_on_close`의 기본값, `parse_reopen`의 이유·멘션 검사 결과를 보존한다. 거절은 현재의 상태 코드·본문·문장을 그대로 낸다.
- 닫기는 이미 닫힌 핀을 다시 쓰지 않는다. 다시 열기는 이미 열린 핀에도 현재처럼 기록을 쓴다. 확인은 에이전트를 저장소 접근 전에 거절하고, 검토 대기에서 완료로 갈 때만 저장한다. 이 순서는 슬라이스 서비스의 계약이다.
- 저장은 `PinStore.transact()`만 사용한다. `pins.jsonl`과 `pins.md`의 모든 바이트, 옛 레코드의 알 수 없는 필드·필드 순서, 재동기화 결과, 알림·감사 순서는 기준 코드와 같다.
- `tests/test_contract_snapshot.py`, 핀 수명 주기·서비스·HTTP·보안 경로 테스트, 서버 두 실행 격리 테스트를 실행한다. `verification.md`의 별도 프로세스 차등 비교로 세 경로의 응답·상태 파일을 비교하고, 고의 변경을 한 번 주입해 비교가 실패하는지 확인한다. 전체 pytest, 적용 가능한 셸 테스트, Ruff, mypy를 통과한다. TeX 도구가 없어 건너뛴 경우는 별도 기록한다.

## 이 묶음의 완료 판정

`close`·`reopen`·`confirm`의 HTTP·서비스 소유자가 한 기능 패키지에 있고, 세 평면 앱 메서드와 옛 서비스 구현이 제거되어야 한다. 공통 가드·잠금·실행 격리와 기존 계약의 관찰 결과가 같아야 한다. 단순한 파일 이동, 메서드 이름 변경, 새 서비스 뒤에 옛 전달 메서드를 남기는 결과는 완료가 아니다. 답글·claim 등 나머지 핀 수명 주기는 전체 이행 설계의 다음 묶음으로 남는다.
