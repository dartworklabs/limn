## 문제

Markdown 문서의 변경 보기는 소스 diff 하나다. 표 행 하나, 목록 항목 하나, 그림 하나가 바뀐 커밋도 원문 기호로만 보이므로, 읽는 사람이 머릿속에서 문서를 다시 그려야 한다. 한 문단에서 낱말 몇 개를 고치면 그 문단 줄 전체가 지운 줄과 더한 줄로 나와, 무엇이 바뀌었는지 낱말을 직접 맞대야 한다. 절 하나를 옮기면 지운 줄 수십 개와 더한 줄 수십 개로 보여 옮긴 것인지 고친 것인지 알 수 없다.

LaTeX 문서는 latexdiff 비교 PDF로 이 일을 한다. [HTML 문서 화면 설계](2026-10-24-html-document-surface.md) §이후 단계의 2번이 Markdown의 같은 화면이다.

## 설계

변경 보기에 [그린 비교] 탭을 더하고, Markdown 문서는 이 탭으로 연다. 서버는 소스 diff와 같은 두 쪽의 원문을 새 읽기 경로 하나로 준다. 뷰어는 두 판을 Markdown 화면과 같은 렌더러로 그려 블록 단위로 맞대고, 바뀐 블록과 그 안의 낱말을 표시한다. [소스 diff]는 지금 그대로 옆 탭에 남는다. 핀의 [변경 보기]는 핀 단위 합성 판(§정한 결정 6의 B)이 들어오기 전까지 소스 diff로 열고, 옆의 [그린 비교]가 커밋 전체 비교에서 그 핀이 바꾼 블록에 보라 테두리를 두른다.

### 결정 1. 두 쪽과 원문 읽기

**추천.** 두 쪽은 소스 diff가 비교하는 그 둘이다. 커밋 하나는 첫 부모 → 커밋이고(첫 커밋은 옛 쪽이 없다), 범위는 옛 쪽 → 커밋이며 곁가지에서 고른 옛 쪽은 병합 기준이다([api.md](../../handbook/api.md) §두 커밋 사이의 규칙 그대로). 원문은 새 읽기 경로로 받는다.

`GET /api/revision-source?doc=<키>&commit=<40자리>[&base=<40자리>]` → `{id, base, merge_base?, path, old, new}`

- `base` 는 실제로 쓴 옛 쪽(첫 커밋이면 `null`), `path` 는 저장소 기준 파일 경로다. 그 경로는 문서를 등록한 경로(시작할 때 심볼릭 링크를 푼 경로)이고 이력 창이 커밋을 고른 경로와 같다. 요청마다 다시 풀지 않으므로, 시작한 뒤 문서 폴더가 링크(점으로 시작하는 폴더, 다른 폴더, 다른 저장소)로 바뀌어도 다른 파일을 읽지 않는다. 그 커밋에서 경로의 폴더가 링크면 그 쪽에 파일이 없다(`null`).
- `old`·`new` 는 `{lines, git_line_starts?}` 이고, 줄은 `GET /api/source` 와 같은 규칙(`str.splitlines()`)으로 센다. git은 LF만 줄 끝으로 세므로 폼 피드·외톨이 CR·U+2028 뒤에서는 hunk 머리의 줄 번호(git)와 블록의 줄 번호(화면)가 어긋난다. 그런 쪽에만 `git_line_starts` 가 붙는다. `[git 줄, 화면 줄]` 쌍의 목록이고(첫 쌍은 늘 `[1, 1]`), 쌍 `[g0, s0]` 부터 다음 쌍까지 git 줄 `g` 는 화면 줄 `s0 + (g − g0)` 에서 시작한다. git 줄 하나는 다음 git 줄이 시작하기 앞 화면 줄에서 끝난다. 마지막 git 줄이 화면 줄 여럿을 품으면(끝의 폼 피드·U+2028, 마지막 줄바꿈이 있든 없든) 끝 쌍 `[git 줄 수 + 1, 화면 줄 수 + 1]` 이 붙어, 마지막 git 줄도 마지막 화면 줄까지로 옮겨진다. 뷰어는 핀의 hunk를 이 값으로 화면 줄로 옮겨 블록에 맞춘다. 그 쪽에 파일이 없으면(그 커밋이 만들었거나 지웠다) `null` 이다. 그릴 수 없는 쪽은 줄 없이 `{reason}` 이다(API의 거절 이름과 같은 칸): `source_too_large`(`bytes`·`limit` 함께), `source_not_utf8`, `not_a_file`(심링크·하위 저장소), `source_unreadable`.
- 브라우저가 그리는 문서(Markdown·텍스트)만 받는다. 다른 문서와 이력 창 밖 커밋은 비교 PDF 경로가 그림 문서에 답하듯 `404 commit_not_recent` 다. 범위의 거절은 [api.md](../../handbook/api.md) §두 커밋 사이의 것 그대로다.
- 경로 매개변수는 없다. 읽는 파일은 문서의 이력 파일 하나로 서버가 정한다. 그래서 이 경로로 다른 파일이나 다른 객체를 이름 붙일 수 없다.

PoC는 핀만의 판(비교 PDF처럼 옛 판에 핀의 hunk만 넣은 합성 판)을 만들지 않고, 커밋 전체를 그린 뒤 그 핀의 블록에 테두리를 두른다. 그러나 표시 단위가 블록이라, 한 문단에 핀 여럿의 수정이 들어 있으면 어느 낱말이 어느 핀의 것인지 가르지 못한다. 그래서 핀의 [변경 보기]는 그 합성 판이 들어오기 전까지 [ADR-0005](../../adr/0005-pin-scoped-changes.md) §4의 소스 diff로 연다(§정한 결정 6).

**대안.**

- **`/api/revision-diff` 에 필드를 더한다.** 응답 하나가 256 KiB diff와 1 MiB 두 쪽을 함께 싣는다. 소스 diff만 볼 때도 두 쪽을 읽는다. 경로를 하나 아끼는 대신 무거운 응답이 생겨 추천하지 않는다.
- **뷰어가 지금 원문에 diff를 거꾸로 적용해 옛 판을 만든다.** 새 경로가 없다. 그러나 고른 커밋이 HEAD가 아니거나 미커밋 수정이 있으면 틀린 판이 나오고, 256 KiB에서 잘린 diff로는 만들 수 없으며, git은 `\n` 만 줄 끝으로 세어 `GET /api/source` 의 줄과 어긋난다. 기각한다.
- **핀만의 합성 판.** 위의 까닭으로 필요 없다.

### 결정 2. 한도와 시간

**추천.**

| 어디 | 한도 | 넘으면 |
| --- | --- | --- |
| 한 쪽의 원문 | 1 MiB(`GET /api/source` 와 같다). git이 알려 준 크기로 먼저 거르고, 그 아래면 그만큼만 읽는다 | 그 쪽은 `{reason: source_too_large, bytes, limit}`. 비교 자리에 `새 판이 1.2 MiB라 그려 비교하지 않습니다(한도 1 MiB)` 와 [소스 diff 보기] |
| git 호출 | 하나에 30초(`GIT_TIMEOUT`). 쪽마다 셋(`ls-tree`·`cat-file -s`·`cat-file blob`)과 옛 쪽을 정하는 확인 | `source_unreadable` |
| 커밋 | 문서의 이력 창(500) 안, 옛 쪽은 범위 규칙 안 | `404 commit_not_recent`·`base_too_old` 등 |
| 파싱·그리기 | 쪽마다 Markdown 화면의 한도(파싱 2초, 블록 30,000, 인라인 150,000, 요소 60,000, 중첩 20). 파서는 화면의 worker와 따로 띄운다 | 비교 자리에 그 한도의 말과 [소스 diff 보기] |
| 블록·낱말 대응 | 표 하나에 400만 칸. 같은 앞뒤는 먼저 떼고 잰다 | 남은 가운데를 모두 빼고 더한 것으로 본다. 틀린 짝은 만들지 않는다 |
| 비교 한 번의 일 | 대응 표의 칸과 고침 짝을 재는 낱말을 모두 합쳐 800만 걸음(`MDC_WORK`). 대응 표 하나가 한도나 남은 걸음을 넘으면 걸음을 다 쓴 것으로 본다 | 더는 짝짓지 않고 낱말도 표시하지 않는다. 남은 블록은 더함과 뺌으로 바로 그리고, 비교 머리에 `바뀐 곳이 많아 블록을 짝짓지 않고 더한 블록과 뺀 블록으로만 표시합니다` 를 적는다. 블록 8,000개씩의 비교가 0.2초 안이다(짝짓기에 한도가 없으면 13초) |

아무것도 쓰지 않는다. 캐시도 없다([ADR-0027](../../adr/0027-get-write-guard.md) 결정 1). 부분 클론에서 없는 blob은 받아 오지 않고 `source_unreadable` 이다(HTTP 읽기의 git 환경).

**잰 값.** `docs/handbook/viewer.md`(700 KB, 2,048줄)의 두 판(40줄마다 고침, 열 줄 지움, 서른 줄 옮김)을 Chromium에서 비교하면 두 쪽 파싱·짓기가 156 ms, 블록 1,442개를 뽑는 데 45 ms, 대응이 13 ms다. `api.md`(244 KB)는 각각 129·29·13 ms다.

### 결정 3. 비교 방식

**추천.** 블록 단위로 맞대고, 고친 블록은 낱말 단위로 표시한다.

1. **블록.** 문단, 제목, 목록 항목의 제 글(하위 목록은 제 블록), 표 행, 코드 블록, 구분선, 원시 HTML 자리표시(이어진 묶음은 하나)다. 블록의 열쇠는 그 블록이 보이는 모든 것이다. 보이는 글(공백을 접는다)과 그 글의 인라인 구조(굵게·기울임·취소선·코드·링크, 그림과 그 대체 글), 블록이 놓인 상자(인용·목록, 번호 목록은 시작 번호와 함께), 그림 경로, 링크 대상이다. 코드 블록은 펜스의 언어와 줄을 공백까지 그대로 담는다. 그래서 같은 낱말이 굵게 바뀌거나, 인용 밖으로 나오거나, 목록 번호가 1에서 5로 바뀌거나, 그림의 대체 글이나 링크 대상만 바뀌어도 그 블록은 바뀐 것이다. 낱말이 그대로인 고친 블록은 무엇이 바뀌었는지(`글자 모양(굵게·기울임·코드·링크)이 바뀜`·`인용·목록 안팎으로 자리가 바뀜`·`목록 번호가 바뀜`·`그림 대체 글이 바뀜`, 코드 블록은 `코드 언어가 바뀜`·`코드의 공백·들여쓰기가 바뀜`) 팁과 화면 낭독기의 말로 적는다. 낱말 비교도 낱말이 놓인 인라인 요소까지 보므로 굵게 바뀐 낱말은 뺀 낱말과 더한 낱말로 표시된다.
2. **대응.** 두 쪽 블록 열의 가장 긴 공통 부분열이다. 같은 블록은 그대로 둔다.
3. **고침.** 대응 사이의 같은 틈에서, 뺀 블록과 더한 블록이 종류가 같고 그림이 같으며 낱말이 40% 넘게 겹치면 한 블록을 고친 것으로 짝짓는다(차례를 지킨다). 그 안은 낱말(글자·숫자 묶음과 문장 부호 하나씩)의 공통 부분열로 뺀 낱말과 더한 낱말을 표시한다. 코드 블록은 줄 단위다. 한 단에서는 뺀 줄을 제 줄로 되돌려 넣는다. 링크 대상이 바뀐 링크는 그 링크를 표시하고 팁이 새 대상을 말한다.
4. **옮김.** 짝을 찾지 못한 뺀 블록과 똑같은 블록이 다른 곳에 더해졌으면 옮긴 것이다. 제목은 길이와 상관없이, 다른 블록은 6자 이상일 때만이다(빈 항목·`끝` 같은 짧은 블록이 엉뚱하게 짝지어지지 않게).
5. 나머지는 뺀 블록과 더한 블록이다.

**한계.** 낱말은 글자·숫자의 이어진 묶음이다. 띄어쓰기 없이 이어 쓴 글은 한 낱말이 된다. 중국어·일본어 문단이나 `부하예측모델` 같은 붙여 쓴 한국어는 글자 하나를 고쳐도 묶음 전체가 뺀 낱말과 더한 낱말로 표시되고, 띄어쓰기 없는 문단은 낱말이 거의 겹치지 않아 40% 문턱을 넘지 못해 고친 블록이 아니라 뺀 블록과 더한 블록으로 보일 수 있다. 정확한 글자는 [소스 diff]에 있다. 구현에서 그런 묶음을 글자 단위로 나눌지는 쓰는 문서를 보고 정한다.

**대안.**

- **원문 줄 diff를 그린 블록에 비춘다**(git hunk의 줄을 블록의 `data-lo..hi` 에 겹친다). 경로가 필요 없지만, 줄 하나를 고쳐도 블록 전체가 바뀐 것으로 보이고, 낱말 표시도 옮김도 없다. 소스 diff를 그린 모양으로 바꿨을 뿐이라 추천하지 않는다.
- **글자 단위 diff.** 한국어 어절 안까지 잘게 나뉘어(`확인할지` → `확인할 것을` 이 글자 조각 넷) 읽기 어렵다.

### 결정 4. 그림과 링크

**추천.**

- **그림은 두 쪽 모두 지금 원고 트리의 파일이다.** Markdown 화면과 같은 `GET /api/asset` 으로 받는다. 그림 경로가 바뀐 문단은 고침으로 짝짓지 않고, 옛 그림(뺌)과 새 그림(더함)을 함께 보인다. 경로가 같고 대체 글만 바뀐 문단은 같은 그림이 둘 보이지 않게 고친 블록 하나이고 `그림 대체 글이 바뀜` 이라고 적는다. 어느 쪽에든 트리 그림이 있으면 비교 위에 `그림은 두 판 모두 지금 원고 트리의 파일입니다 — 옛 판의 그림 파일은 읽지 않습니다.` 를 화면 낭독기도 읽는 줄로 적는다(숨긴 범례 안에 두지 않는다). 그림 파일의 이력은 원래 이 문서의 이력 밖이다([ADR-0030](../../adr/0030-markdown-tree-images-and-document-links.md) Trade-off의 "그림만 바꾼 커밋은 변경 보기에 나오지 않는다"). 옛 판에만 있고 지금 트리에 없는 그림은 Markdown 화면처럼 `그림: <대체 글>` 과 `그림을 불러오지 못했습니다` 다.
- **링크.** 다른 출처의 웹 링크와 `mailto` 는 지금처럼 새 탭이다. 트리 파일로 가는 링크도 Markdown 화면처럼 새 탭에서 그 파일을 열지만, 그림과 같은 까닭으로 지금 트리의 파일이다. 문서 안 `#제목` 과 다른 등록 문서로 가는 링크는 글자로 둔다(팁 `비교 화면에서는 문서 안 링크를 따라가지 않습니다`). 따라가면 변경 보기를 떠나 원고로 가고 보던 비교를 잃는다.

**대안.**

- **옛 판의 그림을 그 커밋에서 읽는다**(`GET /api/revision-asset?doc=&commit=&path=`, `/api/asset` 과 같은 형식·크기 검사). 정확하지만 읽기 경로가 하나 더 늘고, 이력 창의 모든 커밋에 걸친 트리 그림을 읽게 되어 보안 시험의 면이 넓다. 그림 파일만 바꾼 커밋은 여전히 보이지 않는다. 다음 단계로 둔다.
- **그림 대신 대체 글 칩만.** 그림을 바꾼 커밋이 무엇을 바꿨는지 보이지 않는다.

### 결정 5. 배치

**추천: 한 단.** 새 판을 그리고, 뺀 블록을 그 자리에 줄을 그어 끼우고(목록 항목은 목록 안에, 표 행은 표 안에), 옮긴 블록의 옛 자리에는 `여기 있던 블록 2개를 L5–L7로 옮김` 한 줄을 둔다. 고친 블록 안에서는 뺀 낱말을 제자리에 줄 그어 넣고 더한 낱말을 칠한다. 모든 기기군에서 같은 모양이고 옆으로 넘기지 않는다. 표시는 블록 바탕의 옅은 색과 단 왼쪽 여백의 말 칩(`더함`·`뺌`·`고침`·`옮김`)이다. 상자 가장자리의 색 띠는 쓰지 않는다. 색만으로 가르지 않게 뺀 글은 취소선이고, 화면 낭독기는 블록 앞에서 `더한 블록:` 처럼 읽는다. 머리에 네 칩의 범례가 선다.

**후보 B: 두 단(PoC에서 `?cmp=split`).** 옛 판이 왼쪽, 새 판이 오른쪽이고, 두 쪽이 함께 가진 블록은 같은 높이에 선다(뒤처진 쪽에 틈을 넣는다. 표 행은 맞추지 않고 표 다음 블록에서 다시 맞춘다). 비교 칸이 880px보다 좁으면 옆으로 넘기지 않고 한 단으로 쌓으며 그렇게 적는다.

**근거.** 1440×900 데스크톱에서 목차와 핀 패널을 편 채 비교 칸은 536px다(잰 값). 두 단은 두 패널을 접어야 선다. 태블릿 가로(1024×768)와 폴더블 안쪽에서도 서지 못한다. 그래서 두 단은 데스크톱의 한 경우에만 쓰이는데, 그 경우에도 한 단이 뺀 것과 더한 것을 한자리에서 보인다. 두 단은 긴 문단의 낱말 비교에서 눈이 좌우를 오가야 한다.

### 결정 6. 핀·읽던 자리·키

- **핀 배지는 그리지 않는다.** 핀의 줄은 지금 원문의 번호라 고른 커밋의 판과 맞지 않을 수 있다.
- **[변경 보기]로 연 핀만 표시한다.** 그 핀의 커밋을 볼 때, 서버가 가른 그 핀의 hunk(`/api/revision-diff?pin=` 의 `scope`, 핀이 커밋 전체를 가지면 커밋의 모든 hunk, 가르지 못했으면 핀의 줄)에 걸친 새 판 블록에 보라 테두리와 `핀 #N` 칩을 두르고 그 바뀐 곳으로 간다. hunk의 줄 번호는 git의 것이라 새 쪽의 `git_line_starts` 로 화면 줄로 옮긴 뒤 블록에 맞춘다(폼 피드나 U+2028 뒤의 문단도 제 블록이 표시된다). 이것은 PoC의 표시(아래 §정한 결정 6의 A)이고, 핀의 [변경 보기]에서 [그린 비교] 탭을 누르면 보인다(C). 안내 줄이 `핀 #2 자리의 바뀐 블록 2곳을 보라 테두리로 표시했습니다 (에이전트가 기록한 줄)` 처럼 말한다. 다른 커밋이나 범위로 넓히면 `핀 #2의 커밋을 볼 때만 핀 자리를 표시합니다` 다. [확인]·[원고로]는 지금 그대로다.
- **기본 탭.** Markdown 문서의 변경 보기는 [그린 비교]로 연다. 핀의 [변경 보기]는 [소스 diff]로 열고 [그린 비교]는 옆 탭이다(§정한 결정 6의 C). 목록에서 커밋이나 범위를 고르면 보던 탭(그린 비교나 소스 diff)을 지킨다. 그린 비교는 아무것도 빌드하지 않으므로 범위도 그린 비교로 연다. 범위의 목록 칠하기와 `[마지막으로 본 뒤 N]` 의 N은 지금처럼 소스 diff의 답에서 오므로, 그린 비교 옆에서 그 답을 함께 읽는다.
- **바뀐 곳 이동.** 도구 줄 오른쪽 `[▲] 바뀐 곳 2/7 [▼]` 가 이어진 바뀐 블록 묶음을 차례로 화면의 1/3 높이로 옮기고 테두리로 짚는다. 처음에는 `바뀐 곳 7곳` 이다. 단일 글자 단축키는 더하지 않는다. 뷰어의 단일 글자 키는 `?` 하나뿐이다. Esc는 지금처럼 [원고로]다.
- **읽던 자리.** 원고의 읽던 자리는 건드리지 않는다. 변경 보기는 문서 칸을 숨길 뿐이다. 비교 화면 안의 스크롤은 커밋을 바꾸면 처음부터다.

## 구현에서 바꾼 것

- **렌더러의 문맥.** PoC의 `mdcBuild` 는 렌더러가 읽는 `MD.lines`·`MD.els`·`MD.heads` 를 잠깐 바꿔 끼우고 그 사이 쉬지 않고 한 번에 지었다. 이제 렌더러(`mdRender` 와 그 아래)는 그리기 문맥(`MdRx`: 줄, 요소 수, 상자에 넣은 문자 수, BOM, 제목)을 받는다. 문서 화면의 문맥은 `MD` 자신이라 문서 화면의 시험이 그대로 통과하고, 비교는 쪽마다 제 문맥으로 지으며 문서 화면처럼 일 2,000개마다 차례를 넘긴다.
- **핀의 [변경 보기]는 소스 diff로 연다(정한 결정 6의 C).** [그린 비교]는 옆 탭이고, 누르면 PoC의 A(커밋 전체 비교와 핀의 블록 테두리)를 보이며 핀이 커밋의 일부만 가지면 그렇다고 적는다.
- **한 단만.** 두 단 후보와 그 높이 맞추기·틈·단 이름을 뺐다. 그래서 회전·패널 접기로 한 단 ↔ 두 단을 다시 고를 일도 없다.
- **그린 블록 그대로.** 숨은 문자 상자는 블록의 열쇠에 들고 낱말 하나다(바뀐 문자는 바뀐 낱말이고, 되돌려 넣은 글도 상자다). 머리 정보와 따로 선 수식은 제 종류의 줄 블록이고, 줄 안의 수식과 인라인 HTML은 코드와 다른 종류다. 렌더러의 줄 span은 구조가 아니라 다시 감싼 문단은 같은 블록이다. NUL이 있는 쪽은 문서 화면처럼 파싱하지 않는다.
- **범위의 상태 줄**이 소스 diff의 답에서 `커밋 N개 · 파일 N개` 를 함께 적는다.

### 정한 결정 6. 핀의 [변경 보기]가 보이는 것

[ADR-0005](../../adr/0005-pin-scoped-changes.md)는 핀의 [변경 보기]를 핀 단위로 정했다. 소스 diff는 그 핀의 hunk만 보이고 나머지를 `이 커밋의 다른 변경 N곳 ▸` 로 접으며(§4), 비교 PDF는 옛 판에 그 핀의 hunk만 넣은 합성 판과 견준다(§5). 에이전트가 핀 10여 건을 스쿼시 커밋 하나로 고치는 일이 흔하기 때문이다. PoC의 그린 비교는 Markdown 문서의 기본 보기를 커밋 전체 비교와 테두리로 바꿨다.

| 안 | 보이는 것 | 잃는 것·드는 것 |
| --- | --- | --- |
| **A. 커밋 전체 비교 + 핀의 블록 테두리**(PoC) | 커밋 전체를 그리고 핀의 hunk에 걸친 블록에 보라 테두리 | 다른 핀의 수정이 같은 화면에 함께 표시되고, ADR-0005 §4의 접기가 없다. 핀 여럿의 수정이 든 한 문단은 블록 전체가 테두리이고 그 안의 표시 낱말도 다른 핀의 것을 섞는다. ADR-0005를 Markdown 문서에서 고쳐 써야 한다 |
| **B. 핀 단위 합성 판** | 옛 판에 그 핀의 hunk만 적용한 판을 새 쪽으로 그려 견준다. 핀이 커밋의 일부만 가질 때(`scope.mode` 가 `pin`)만이고, `[커밋 전체 비교]` 토글로 A의 보기와 오간다 | 서버가 비교 PDF의 합성(블록 적용)을 파일 하나의 글에 쓰고, `GET /api/revision-source` 가 선택 `pin` 을 받는다(에이전트 계약에 더하기, `revision-build` 의 `pin` 과 같은 규칙: 핀의 커밋에서만, `changes` 가 먼저). 합성 판의 줄은 커밋의 줄과 다르므로 테두리는 합성 판의 블록에 둔다 |
| **C. 소스 diff를 핀의 기본으로** | 핀의 [변경 보기]는 ADR-0005 §4의 소스 diff로 열고, [그린 비교]는 옆 탭(A의 보기) | 핀을 볼 때 그린 문서가 한 번 더 눌러야 나온다. 새 계약은 없다 |

**정한 것: B가 목표이고, 구현 전까지 C.** 핀 단위로 가르는 것이 [변경 보기]의 까닭이고, 그린 비교에서 그것을 지키는 길은 비교 PDF가 이미 쓰는 합성뿐이다. B는 ADR-0005 §5의 합성을 넓힐 뿐이라 ADR-0005를 고쳐 쓰지 않는다(그 ADR에 "그린 비교도 같은 합성을 쓴다"는 덧붙임 하나). A는 ADR-0005의 핀 단위 약속을 Markdown 문서에서 거두므로 ADR-0005를 고쳐 써야 하고, C는 ADR-0005를 그대로 둔다. 커밋이나 범위를 목록에서 고를 때의 기본 탭(그린 비교)은 이 결정과 따로다.
