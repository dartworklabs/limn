# 서버의 명시적 App 소유 설계

> **상태: 구현됨.** 아래 "현재"는 설계 작성 당시의 `main`을 기록한다. 실행 중 구조의 정본은 `src/limn/server.py`와 System Handbook이다.

## 목적과 범위

`server.py`의 `_ModuleApp(globals())`는 HTTP 처리기가 요청할 때마다 서버 모듈의 이름을 찾아 준다. 서비스의 실제 의존성이 `C`·`RT`·`DOCS`와 다른 전역 함수에 흩어져 있어, 함수의 입력만으로 동작을 이해하거나 같은 모듈 사본 안에서 두 실행을 독립적으로 구성하기 어렵다. 목표는 **한 번의 서버 실행에 속한 설정, 자원, 문서 목록과 HTTP 서비스 연결의 소유자를 명시적인 값 하나로 만드는 것**이다. HTTP 처리기는 계속 `web/app.py`의 `App` 계약만 알고, 서버는 파일 경로 실행과 패키지 실행 모두에서 동작해야 한다.

이 설계는 내부 조립 방식을 바꾼다. 경로·응답·오류 문구·`reason`·`pins.md`·저장 파일, 빌드 결과, 인증·인가 판단, 뷰어 화면 동작은 바꾸지 않는다. 새 런타임 의존성을 들이지 않고, 표준 라이브러리로 구현한다. 설계 승인 전에는 생산 코드와 행동 계약을 변경하지 않는다.

현재 `main` 코드에서는 `web/app.py`의 `App`이 55개 메서드와 `C`·`APP_NAME`·`DEFAULT_ROLE`을 요구한다. `server.Handler.app`은 `_ModuleApp(globals())`이고, `start()`가 전역 `C`·`RT`를 묶은 다음 `prepare()`가 `DOCS`를 채운다. `Runtime`이 잠금·캐시·작업 목록·감시 스레드를 갖고, `main()`과 실패한 `start()`가 `RT.stop()`을 호출한다. `Runtime.start_thread()`는 시작에 성공한 스레드만 등록하며, 둘째 감시 스레드의 시작 실패 뒤 첫째 스레드를 끝내는 테스트가 있다. `start()`는 `Server`만 돌려주고 `main()`은 전역 `RT`를 종료한다. `main()`은 서빙이 끝나면 HTTP 서버 소켓과 런타임을 모두 닫고, 두 정리를 모두 시도하며 서빙 예외를 우선 보존한다. `tests/helpers.py`는 `server.py`를 `sys.modules`에 등록하지 않은 파일 사본으로 로드하고 매 테스트마다 전역을 다시 묶는다. `tests/test_web.py`는 두 파일 로드 사본의 설정·잠금·문서와 실제 GET `/`·`/api/docs` 응답이 분리됨을 확인한다. 같은 테스트는 한 사본의 전역 함수 재바인딩이 처리기에 즉시 보이는 동작도 검사한다. 이 재바인딩은 현재 테스트용 결합이지 공개 HTTP 계약은 아니다.

저장 핀 타입 경계의 검토는 PR #91의 작은 수정과 코딩 규칙 로드맵에 반영되었다. 이 문서는 서버 앱 소유권만 다룬다.

### 지켜야 할 현재 불변식

1. `web/`은 `server.py`를 import하지 않는다. 파일로 로드한 서버 사본끼리 설정·잠금·문서가 섞이지 않는다.
2. 서버 import에서는 뷰어 파일을 읽거나 런타임 자원을 만들지 않는다. 실행 설정은 시작 때 만든 얼린 값이고, 문서별 빌드 상태는 각 `Doc`가 갖는다.
3. 모든 요청의 가드 순서와 fail-closed 거절, 오류 응답, 저장 바이트, 오래된 상태 읽기 규칙을 유지한다. POST의 사람 기록은 역할 검사 뒤, 본문 JSON 파싱 앞에 있다.
4. 정상 종료와 시작 실패에서 시작된 감시 스레드가 끝난다. 요청을 받는 처리기는 살아 있는 자기 실행의 자원만 본다. 이미 열린 HTTP 서버 소켓도 실행 소유자가 닫는다.

### 결정 맥락

[ADR-0001](../../adr/0001-blueprint.md)은 확정된 청사진이며, 책임별 모듈과 실용적 함수형 구조를 채택한다. 이 설계는 그 방향 안에서 조립 지점의 전역 소유를 명시화한다. 새 배포 단위, 저장 형식, 외부 의존성은 제안하지 않는다. [ADR-0002](../../adr/0002-access-control.md)의 확정·구현된 접근 제어 범위와 [ADR-0007](../../adr/0007-agent-token-file.md)의 에이전트 토큰 파일 결정은 그대로 적용된다.

### 충돌·미확인

생산 코드가 `server.py`의 모듈 함수를 직접 부르는 테스트가 많아, 내부 호환을 어느 세로 절단면에서 끝낼지는 구현 계획에서 테스트 호출 목록으로 확정해야 한다. 동시에 둘 이상의 서버를 같은 모듈 사본에서 구동하는 용도는 확인되지 않았다. 설계는 그 경우에도 처리기별 앱 바인딩이 섞이지 않게 한다.

## 권장 설계

`server.py`의 조립 지점에 `RunApp` 같은 명시적 앱 값을 둔다. 필수 소유 값은 `config: RunConfig`, `runtime: Runtime`, `docs: tuple[Doc, ...]`이다. `RunConfig`와 문서 목록은 서버가 듣기 전에 확정한다. 현재 `App`의 `C`는 `config`를 돌려주는 읽기 전용 속성으로, `APP_NAME`·`DEFAULT_ROLE`은 타입이 드러나는 상수로 제공한다. `Runtime`은 지금처럼 잠금·캐시·감시 스레드를 소유하고 `stop()`을 담당한다. 앱은 HTTP 처리기가 필요로 하는 설정과 서비스 연결을 구현하며, 각 서비스가 받는 작은 설정·협력자 값(`PinContext`, `AccessSettings`, `RevisionContext` 등)을 자기 필드에서 만든다. 요청의 대상 문서는 계속 명시적 `Doc` 인자로 전달한다. 객체가 생겼다는 이유로 도메인 판단이나 파일·HTTP 처리를 앱 메서드 안으로 옮기지 않는다.

`App`은 HTTP 처리기의 좁은 포트로 유지한다. 완료 시 `RunApp` 자체를 `App`에 대입하는 정적 검사가 통과해야 하며, `Any`를 반환하는 동적 `__getattr__`, 모듈을 `App`으로 캐스팅하는 우회, 서비스 이름 문자열 목록을 통한 위임은 제거한다. 프로토콜이 요구하는 이름이 많다는 사실은 설계 중에 소유권을 묶을 근거다. 단지 줄 수를 줄이려고 55개 메서드를 한꺼번에 새 파일로 복사하지 않는다. 각 메서드가 실제로 쓰는 설정·런타임·문서·협력자가 명시적으로 드러나게 옮긴다.

`WebHandler.app`은 클래스 속성 계약을 유지한다. 조립 함수가 **실행별 처리기 하위 클래스**를 만들어 그 실행의 `RunApp`을 바인딩하고, `listen()`이 그 클래스를 HTTP 서버에 넘긴다. 따라서 한 모듈에서 다음 실행을 시작해도 앞선 HTTP 서버의 처리기 앱이 갈아 끼워지지 않는다. 파일로 로드한 사본 역시 자기 앱과 처리기 클래스를 가진다. 테스트의 `Recorder`는 생성된 처리기 클래스의 `app`을 감싸 가드 읽기 순서를 계속 기록할 수 있다.

시작 순서는 접근 옵션과 포트 검사 → `configure_run` → 뷰어 읽기·실행별 `Runtime` 생성 → 문서 목록 확정·앱 생성 → 저장소·빌드·감시 준비 → 요약·`listen(app)`이다. 성공 결과는 `StartedServer(server, app)`처럼 HTTP 서버와 그것이 사용하는 앱을 함께 담는다. `main()`은 이 결과의 `server.serve_forever()`를 실행하고, 종료 경로에서 **그 서버의** `server.server_close()`와 **그 앱의** `runtime.stop()`을 각각 수행한다. 하나의 종료가 실패해도 다른 자원을 닫으며, 원래의 서빙 예외를 가리지 않게 예외 처리·전파 순서를 정한다. 준비 또는 듣기 실패가 값을 돌려주거나 예외를 던지면 생성한 런타임을 중지하고, `listen()`이 소켓을 연 뒤 후속 단계에서 실패하면 그 소켓도 닫는다. 전역 `RT`로 종료 대상을 다시 찾지 않는다.

스레드 시작 실패, 소켓 종료, 서버 사본 격리의 선행 수정과 테스트는 `main`에 있다. `Runtime.start_thread()`는 시작 성공 뒤에만 등록하고, 앞선 감시 스레드가 시작된 뒤 다음 시작이 실패할 때도 `stop()`이 먼저 시작된 스레드만 기다리며 원래 시작 예외를 보존한다. `main()`은 소켓 종료와 런타임 정리를 모두 시도하고 서빙 오류를 우선 보존한다. 두 파일 로드 서버 사본의 독립성은 HTTP 응답으로 확인한다. 앱 이관에서는 이 성질들을 새 소유 경계에서도 유지한다.

`C`·`RT`·`DOCS`와 `RunApp`이 동시에 같은 실행의 권위가 되는 중간 상태는 병합하지 않는다. 내부 이행 절단면에서 임시 위임이 필요하더라도 한 HTTP 요청과 감시 작업의 설정·자원·문서는 한 소유자에서만 읽게 한다. 전역과 앱 필드를 함께 읽는 코드, 값을 양쪽에 복사해 동기화하는 코드는 완료된 절단면으로 취급하지 않는다. 최종 변경에서 요청과 감시 경로의 전역 조회를 없애고 나서 병합한다.

테스트에서는 `set_config`, `fresh_runtime`, `set_docs`가 서버 모듈을 다시 묶는 대신 **새 앱/처리기 구성 헬퍼**를 이용한다. 서비스별 실패 주입은 앱 인스턴스나 앱 생성 시 주입하는 명시적 협력자에 한다. `mock.patch.object(ps, "build_async")`처럼 서버 함수명을 바꾸는 테스트는 앱의 `build_async` 경계를 패치하도록 바꾸며, 함수 교체가 한 요청에만 필요한 경우에는 그 실행의 앱 인스턴스를 교체한다. 테스트를 위해 생산 코드에 범용 service locator나 전역 monkeypatch 통로를 추가하지 않는다. 직접 서비스 함수를 검증하는 테스트는 함수 호출을 유지할 수 있지만 HTTP 경로의 의존성 교체는 앱에서 한다.

## 대안과 대가

| 접근 | 얻는 점 | 비용과 선택 |
| --- | --- | --- |
| 실행별 `RunApp`과 처리기 클래스 | 설정·자원·문서의 소유가 드러나고 서버 사본·동시 실행이 격리된다. `App` 타입 검사가 실제 객체에 걸린다. | 기존 모듈 함수와 테스트 픽스처를 단계적으로 옮겨야 한다. **권장.** |
| `_ModuleApp`을 남기고 명시적 필드 일부만 추가 | 첫 diff가 작다. | 전역 조회와 객체 필드가 서로 다른 값을 볼 수 있고, `Any`가 타입 오류를 숨긴다. 최종 구조로 채택하지 않는다. |
| 55개 호출을 서비스별 객체 여러 개로 즉시 분할 | 관심사를 타입으로 더 세밀하게 표현한다. | HTTP 포트와 테스트가 동시에 크게 바뀌고, 별도 서비스 객체가 현재의 작은 서비스 함수 위에 의례를 만든다. 실제 공동 소유 경계가 확인된 뒤에만 검토한다. |
| 모듈 전역 `CURRENT_APP` 하나를 처리기에 제공 | 기존 처리기 형태를 거의 유지한다. | 같은 모듈 사본의 재시작·동시 서버에서 앱이 바뀐다. 채택하지 않는다. |

## 이행 절단면

1. **현재 계약과 수명 실패 고정:** HTTP·`pins.md` 계약 스냅숏, 파일 실행/패키지 실행, 모듈 import 무파일 읽기, 가드와 POST 기록 순서를 확인한다. 현재의 감시 스레드 시작 실패, 서빙 종료·소켓 닫힘·예외 우선순위, 두 파일 로드 서버 사본 격리 테스트를 회귀 기준으로 사용한다. 첫째·둘째 스레드 시작 실패, 듣기 실패, 서빙 예외와 정상 종료를 새 앱 소유 경계에서도 검증한다. 내부 구현에 고정된 테스트와 외부 행동 테스트를 구분한다.
2. **실행별 앱·처리기 조립:** 필드를 가진 앱 생성, 실행별 처리기 바인딩, `StartedServer` 결과를 도입한다. 먼저 읽기와 설정 연결 등 작은 서비스 묶음을 옮긴다. 임시 위임은 개발 중에만 한정하고, 모듈 전역 `C`·`RT`·`DOCS`를 읽는 요청·감시 경로가 남은 상태는 병합하지 않는다. 해당 절단면의 테스트부터 앱 교체 지점으로 바꾼다.
3. **상태 보유 서비스 이관:** 접근 캐시·잠금·핀 저장·빌드·리비전·동기화 순으로 `self.config`·`self.runtime`·`self.docs`와 문서 인자를 사용하게 한다. 감시 콜백도 자기 앱을 닫아 잡는다. 각 묶음에서 모듈 전역 재바인딩을 통한 HTTP 테스트를 없애고 관찰 가능한 결과를 비교한다.
4. **전역 대리자 제거:** 마지막 `App` 멤버가 명시적 객체에서 제공되면 `_ModuleApp`, `TYPE_CHECKING` 모듈 대입, 요청 경로의 전역 상태 조회를 지운다. `RunApp`의 프로토콜 적합성을 mypy로 검사한다. 직접 함수 호출용 래퍼가 남으면 소유권을 다시 숨기지 않는지 검토해 제거하거나 범위를 문서화한다.
5. **현재 상태 문서 반영:** 구현과 같은 변경에서 `architecture.md`의 조립·상태·의존 방향, `index.md`의 파일 지도, `verification.md`의 타입 검사 설명, `web/app.py`의 현재 계약 설명과 `code-style-roadmap.md`의 남은 일 목록을 실제 코드에 맞춘다.

각 절단면은 개발 중 리뷰 가능한 크기로 나누되, 전역과 앱이 이중 권위인 중간 상태는 머지하지 않는다. 임시 다리가 둘 이상의 진실 소스를 만들면 그 절단면은 완료로 보지 않는다. 내부 API가 바뀌어 테스트를 고칠 때는 옛 테스트의 실패 주입과 관찰 대상을 새 경계에서 보존한다.

## 합격 기준

- `RunApp` 인스턴스가 `App`을 정적 타입 검사에서 만족한다. HTTP 처리기가 `server.py`를 import하지 않고, import 시 뷰어 파일·런타임 자원을 만들지 않는다.
- 파일로 로드한 둘 이상의 서버 사본과 같은 모듈에서 만든 둘 이상의 앱이 서로 다른 설정·문서·잠금·뷰어를 보며, 한 실행의 종료나 테스트용 교체가 다른 실행에 영향을 주지 않는다.
- 시작 거절과 예외, 듣기 실패, 정상 종료 모두에서 시작된 감시 스레드가 종료되고 열린 HTTP 서버 소켓이 닫힌다. 스레드 시작 실패에서 미시작 스레드를 `join()`하지 않으며 원래 예외가 보존된다. 요청은 준비가 끝난 앱에만 닿는다.
- 모든 GET/POST 경로의 첫 동작이 본문 읽기 → Host/Origin → 신원 → 입장 → POST 역할 검사이고, 거절은 fail-closed다. POST는 역할 검사 뒤 사람 기록, 그다음 JSON 본문 파싱이라는 기존 순서를 유지한다. 이전의 상태 코드, 헤더, `error`·`reason`, 본문 읽기와 연결 종료 순서가 유지된다.
- 기존 상태 폴더와 `pins.md`의 바이트 왕복, HTTP 계약 스냅숏, 빌드·핀·뷰어의 관찰 결과가 같다. 새 런타임 의존성은 없다.
- `tests/test_web.py`, `test_server.py`, `test_access.py`, 계약 스냅숏, 전체 pytest, 셸 테스트, Ruff, mypy가 통과한다. 구조 이동의 차등 비교는 `verification.md`의 절차로 기록한다.

## 구현 결과

`ServerApplication`이 실행 설정·런타임·문서를 소유하고, `start()`는 실행별 처리기 하위 클래스를 만든다. `StartedServer`가 소켓과 앱을 함께 돌려줘 `main()`이 해당 실행의 자원만 종료한다. 같은 모듈에서 두 실행을 띄운 실제 HTTP 격리와 종료 수명은 `tests/test_server.py`가 확인한다. 행동 계약과 저장 형식은 유지한다.
