# 텍스트·코드 문서 — 원문 줄을 그대로 보이고 줄 핀을 받는다 (제안)

> **상태: 제안(2026-11-05).** [HTML 문서 화면 설계](2026-10-24-html-document-surface.md) §이후 단계의 1번이다. 소유자가 이 단계를 진행하라고 했다. 이 변경은 에이전트 계약(문서 `kind` 값, `scope` 값, `pins.md` 표시)을 넓히므로, 구현 전에 이 설계의 승인이 필요하다([workflow.md](../../handbook/workflow.md) §기본 경로). 결정 초안은 [ADR-0029](../../adr/0029-text-documents.md)(`제안`)다. 추천안대로 만든 PoC가 `poc/md-text-docs` 브랜치에 있고, 승인되면 시험을 더해 그대로 구현이 된다.

## 문제

Markdown이 들어온 뒤에도 일반 텍스트와 소스 코드 파일에는 화면이 없다. 그림 스크립트(`.py`), 참고문헌(`.bib`), 설정(`.yaml`·`.toml`), 메모(`.txt`)가 그렇다. 지금은 `--doc` 경로가 이런 확장자면 기동을 거절한다. 그래서 사람이 이 파일의 줄을 골라 핀을 남길 길이 없다. 에이전트가 `file`·`lo`·`hi` 로 직접 만들거나, 그림 문서의 요소를 거쳐 코드 줄에 닿을 뿐이다.

## 제안

새 종류 `text` 하나를 더한다. 화면은 Markdown 화면의 기계를 그대로 쓰되 파싱하지 않는다. 서버가 보낸 줄을 하나씩 줄 span(`data-line`)으로 짓고, 고정폭 글꼴과 줄 번호로 보인다. 서버는 등록과 `pins.md` 표시 둘만 바뀐다. 새 경로, 새 필드, 새 의존성은 없다.

## 결정 (추천안)

### 결정 1. 종류 값

**추천.** `/api/docs`·`/api/meta` 의 `kind` 에 `text` 하나를 더한다. 산문(`.txt`)과 코드(`.py`)를 가르지 않는다. 능력도 동작도 같기 때문이다. 기동 로그의 이름은 `text`, `pins.md` 문서 절의 꼬리말은 `— 텍스트(쪽 없음)` 이다. 능력은 Markdown과 같다. `takes_line_pins`·`shows_revisions`·`renders_in_browser`·`takes_suggestions` 가 참이고 나머지는 거짓이다. 뷰어만 `showsSourceLines(kind)` 한 곳에서 둘을 가른다. 꼬리말은 종류를 알리는 자리라 종류를 읽는다([domain.md](../../handbook/domain.md) §문서 종류와 능력).

**대안.** `text`·`code` 둘로 나누는 안은 행동 차이가 없어 기각한다. 언어마다 종류를 두는 안은 에이전트가 따라갈 값 목록만 늘린다.

### 결정 2. 어떤 파일이 텍스트 문서가 되나

**추천.** 닫힌 확장자 목록 `TEXT_SUFFIXES` 다. 대소문자는 가리지 않는다.

| 묶음 | 확장자 |
| --- | --- |
| 글과 데이터 | `.txt` `.text` `.rst` `.org` `.adoc` `.csv` `.tsv` |
| 설정 | `.json` `.toml` `.yaml` `.yml` `.ini` `.cfg` `.xml` |
| 코드 | `.py` `.pyi` `.r` `.jl` `.m` `.js` `.mjs` `.cjs` `.ts` `.tsx` `.jsx` `.css` `.scss` `.html` `.sh` `.bash` `.zsh` `.c` `.h` `.cc` `.cpp` `.hpp` `.java` `.kt` `.go` `.rs` `.swift` `.rb` `.lua` `.sql` |
| LaTeX의 다른 원천 | `.bib` `.sty` `.cls` `.bst` |

- 확장자의 종류는 한 번 정하면 바꾸지 않는다. 목록에 더하는 것은 거절하던 설정을 받아들이는 덧셈이라 계약을 깨지 않는다. 그래서 따로 화면이 생길 수 있는 `.typ`·`.ipynb` 와, 흔히 비밀을 담는 `.env`·`.pem`·`.key` 는 넣지 않는다.
- `.html` 은 글자로만 보인다. 그리지 않는다.
- 그림 지도 접미사를 대소문자만 틀리게 쓴 이름(`Figures.LIMNMAP.JSON`)은 `.json` 이어도 거절한다. 그림을 뜻한 설정이 조용히 텍스트가 되지 않게 하려는 것이다.
- 셸(`limn add`·`limn doc add`)은 같은 목록을 따로 들고, 시험 하나가 두 목록이 같은지 본다.
- 확장자 없는 파일(`Makefile`, `LICENSE`)은 1단계에서 받지 않는다.

**대안 A: 다른 종류가 차지하지 않은 확장자를 모두 텍스트로.** 가장 넓다. 그러나 오타(`.tex~`), 바이너리, 나중에 생길 종류(`.typ`)를 조용히 삼킨다. 나중에 그 확장자를 다른 종류로 옮기면 기존 인스턴스의 `kind` 가 바뀐다.

**대안 B: `--doc` 문법에 종류를 적는다**(`KEY=NAME:text:path`). 확장자 없는 파일까지 덮지만 등록 문법이라는 계약을 바꾼다.

### 결정 3. 범위 사다리

**추천.** 고른 줄 → 문단 → 들여쓰기 블록이다. 문단과 블록 가운데 짧은 쪽을 먼저 둔다. 같은 범위의 단은 앞의 단에 합친다(Markdown과 같다). 단은 뷰어가 서버의 줄만 보고 계산한다.

| 단 | `scope` | 핀 `kind` | 범위 |
| --- | --- | --- | --- |
| 고른 줄 | `raw` | `lines` | 누르거나 끈 줄 |
| 문단 | `para`(LaTeX와 같은 값) | `paragraph` | 빈 줄 사이의 덩어리. 고른 줄이 둘 이상에 걸치면 `문단 N개` 이고 줄(`lines`)로 저장한다 |
| 들여쓰기 블록 | `indent`(새 값) | `indent` | 고른 줄의 다음 비어 있지 않은 줄이 더 깊으면 고른 줄이 머리인 블록, 아니면 위쪽에서 처음 만나는 더 얕은 줄이 머리인 블록. 머리 줄부터, 머리보다 깊지 않은 다음 줄 앞까지다. 그 줄이 머리와 같은 깊이의 닫는 줄(`}`·`)`·`]`·`end`·`fi`·`done`·`esac`)이면 넣는다. 끝의 빈 줄은 뺀다 |

들여쓰기 블록은 언어를 가리지 않는다. 그래서 파이썬 함수, YAML 항목, 함수 호출의 인자 목록, `.bib` 항목 하나가 모두 한 번에 잡힌다. 탭은 4칸으로 센다.

**대안.**

- **파일 전체 단.** 한 핀이 문서 전체를 칠하고, 80줄을 넘으면 제안 수정을 둘 수 없다. 파일 전체에 대한 말은 1행 핀의 메모로 충분하다.
- **두 단만(고른 줄 → 문단).** 새 값이 없다. 대신 코드에서 "이 함수"를 고를 길이 없다.
- **언어별 구문 블록.** 파서가 필요하다(결정 5).

### 결정 4. 제안 수정과 판정

**추천.** 텍스트 문서의 줄 핀도 제안 수정을 받는다. 코드와 메모도 사람이 손으로 고치는 줄이기 때문이다. 편집 칸에는 원문이 그대로 보이고, 원문 대조와 `## 제안 문안` 은 그대로 쓴다. 그래서 [ADR-0020](../../adr/0020-suggested-edit-pins.md) D1(ADR-0025가 고친 "LaTeX·Markdown")에 텍스트를 더한다.

판정 핀은 그 줄이 대상이다. 서버의 배치가 이미 능력으로 가르므로 고칠 곳이 없다. 판정 낱말 파일은 지금 규칙(메인 파일의 `stem` + `.limnverdicts.json`)대로 `figs/plot.py` → `figs/plot.limnverdicts.json` 이다. 같은 폴더의 `plan.md` 와 `plan.txt` 는 낱말 파일 하나를 함께 쓴다. [api.md](../../handbook/api.md) §판정 낱말 파일 (`limn-verdicts/1`)의 자리 표에 이 경우를 적는다.

**대안.** 코드 문서에는 제안 수정을 끄는 안. 그림 문서는 그림 저장소가 다시 그리므로 끄지만, 텍스트 문서는 그 파일이 곧 결과물이라 끌 까닭이 없다. 낱말 파일을 `plan.txt.limnverdicts.json` 으로 두는 안은 자리 규칙에 예외를 하나 더 만든다.

### 결정 5. 그리기

**추천.**

- **파서도 구문 강조도 없다.** 모든 원문 줄이 그대로 글자다. 링크·그림·마크업이 되는 것이 없고, DOM은 `createElement`·`textContent` 로만 짓는다. `innerHTML` 싱크는 하나로 남는다.
- **고정폭 단 하나.** 줄 번호는 CSS가 그려서 고르거나 복사할 때 섞이지 않는다. 단 폭은 많아야 56rem이다(Markdown은 46rem). 80열 코드가 데스크톱에서 접히지 않는 폭이다.
- **긴 줄은 늘 접는다.** 쪽이 옆으로 넘어가는 일은 없다. 접힌 이어짐은 그 줄의 들여쓰기만큼 걸린다. 탭이 든 줄은 탭 칸(4칸)으로 내려 맞춘다. 그래야 탭이 편집기와 같은 칸에 선다. 걸림은 많아야 16칸이라 휴대폰에서도 글 자리가 남는다. 한국어 산문은 띄어쓰기에서 접는다(`keep-all`, Markdown과 같다).
- **글 순서를 바꾸거나 보이지 않는 문자는 이름으로 보인다.** 양방향 제어 문자(덮어쓰기·끼워 넣기·격리·LRM·RLM·ALM), 영폭 공백, 단어 결합자, 제어 문자가 대상이다. 원문 문자는 격리된(`unicode-bidi:isolate`) span 안에 남기고, 그 자리에 `U+202E` 같은 이름 상자를 보인다. 그래서 복사하면 원문 그대로이고, 화면의 줄은 원문과 다른 순서로 읽히지 않는다. 문서 머리에 "보이지 않거나 글 순서를 바꾸는 문자 N개를 이름으로 표시했습니다"를 한 줄 띄운다. 작성 패널의 원문 조각도 `⟨U+202E⟩` 로 보인다. 영폭 결합자(ZWJ·ZWNJ)는 이모지와 페르시아어·인도계 글자에 필요하고 순서를 바꾸지 않아 두며, 파일 맨 앞의 BOM도 둔다. 이렇게 하지 않으면 리뷰하는 사람에게 코드가 실제와 다르게 보인다(Trojan Source, CVE-2021-42574). PoC의 `check()` 줄은 그대로 그리면 `if role != "admin": # skip check` 로 보이지만, 실제로는 문자열 안에 주석처럼 보이는 글이 들었다.
- **한도.** 바이트는 서버의 1 MiB 그대로다. 줄은 Markdown 줄 보기와 같은 50,000줄이고, 넘으면 Markdown과 같은 알림을 띄운다. 2,000줄마다 브라우저에 양보하고, 새 원문이 오면 짓던 것을 버린다. UTF-8이 아닌 파일은 지금처럼 `원문을 읽지 못했습니다` 다.

**대안.**

- **구문 강조 번들(highlight.js, Prism 등).** 읽기는 낫지만 런타임 번들이 하나 늘고(멈춤 신호), 토큰을 DOM으로 짓는 보안 면이 생기며, 언어마다 크기가 붙는다. 1단계에서는 추천하지 않는다. 필요해지면 별도 ADR로 다룬다.
- **긴 줄을 코드 상자 안에서 옆으로 넘긴다.** 데스크톱에서는 익숙하다. 그러나 휴대폰과 폴더블 바깥 화면에서 줄 끝을 보려면 옆으로 끌어야 하고, 그 끌기가 글 고르기와 부딪힌다. 접기를 켜고 끄는 단추는 조작을 하나 더 늘린다.
- **숨은 문자를 그대로 둔다.** 브라우저가 순서를 바꿔 그린다(위 예). **지운다.** 복사한 글과 원문이 달라진다.

### 결정 6. 화면 동작

**추천(PoC 그대로).**

- **고르기.** 줄을 누르면(마우스·손가락) 그 줄, 끌면 그 줄들이다. 휴대폰에서는 길게 눌러 손잡이로 고르면 선택이 멈춘 뒤 0.5초에 고른다. 기본 단은 늘 "고른 줄"이다. Markdown의 누르기가 블록을 고르는 것과 다른데, 텍스트에서는 줄이 보이는 단위이기 때문이다. 처음 여는 사람의 안내도 그에 맞춘다(`누르면 그 줄을, 끌면 그 줄들을 고릅니다`).
- **표시.** 핀의 줄에 상태색 바탕을 깔고 왼쪽 여백에 번호 배지를 세운다. Markdown과 같은 코드다.
- **목차와 위치.** 제목이 없으므로 목차는 비어 있다(`이 문서에는 이동할 수 있는 제목이 없습니다.`). 단 띠에는 파일 이름이 서고, 휴대폰 위치 단추는 `L35/61` 이다. 찾기는 브라우저의 찾기다. 머리의 형식 칸은 `텍스트` 다.
- **변경 보기.** 그 파일 하나의 소스 diff다.

## 검증

**PoC에서 잰 것.**

- `uv run pytest -q -n 4 -m "not browser and not tex"`: 3,775 통과(1 건너뜀, 하위 사례 6,528). 종류를 나열하던 시험(능력 표, 확장자 거절, `scope` 거절 문구, 뷰어의 종류 비교 정규식)은 새 종류에 맞게 고쳤다.
- Markdown 브라우저 시험 `test_viewer_markdown.py`: 69 통과.
- 인스턴스 셸 시험: 224 통과(텍스트 문서 등록, 대소문자 다른 그림 지도 접미사 거절을 더했다).
- 새 순수 시험 `viewer/tests/test_text_surface.py` 5건(칸 수와 걸림, 문단, 들여쓰기 블록, `.bib` 항목, 숨은 문자), 새 구조 시험 `tests/architecture/test_text_suffixes.py`(셸·서버 목록 일치).
- Markdown 문서의 화면: 같은 두 문서로 `main`(770fa20c)과 이 브랜치를 네 기기군 11개 크기·테마에서 찍어 비교했다. 다른 픽셀이 0이다.

**본 구현이 더할 것.**

- **계약 시험.** `/api/docs`·`/api/meta` 의 `text`. 텍스트 줄 핀이 `page` 없이 왕복하고 `pins.md` 에 `—`·`indent`·`— 텍스트(쪽 없음)` 로 찍힌다. 보낸 `page`·`frac`·`pdf_build` 가 남지 않는다. 제안 수정을 받는다. 판정 핀의 `superseded_by`. 같은 폴더의 `.tex` 와 `.bib` 텍스트 문서에서 핀이 제 문서로 간다. 직전 릴리스(0.4.50)는 텍스트 문서가 든 설정으로 기동하지 않는다(Markdown과 같다. 되돌리려면 그 문서를 설정에서 먼저 뺀다). 상태 폴더의 핀은 그대로 읽힌다.
- **브라우저 시험.** 누르기·끌기·길게 누르기의 줄, 사다리 세 단과 합치기, 표시와 배지, 숨은 문자의 이름 상자와 복사한 글, 344px에서 가로 넘김 없음, 원문이 바뀌면 다시 그리기와 읽던 자리, 50,000줄 알림, UTF-8 아닌 파일.
- **네 기기군 PoC.** 이 문서의 PoC 캡처를 소유자가 보고, 고른 안으로 다시 찍는다.
