# 설계: HTTP로 읽는 pins.md 가 그 요청의 신원을 알린다

> **상태: 제안** — 소유자의 명시적 승인을 기다린다. 승인되면 이 줄에 승인한 사람·시점·승인한 문서 판(커밋)을 적는다. 이슈 [#540](https://github.com/dartworklabs/limn/issues/540). 결정 기록은 ADR(번호는 머지 시점의 가장 큰 번호 다음, §ADR)로 남긴다.

## 의도와 왜

토큰 없이 테일넷 주소로 요청하는 에이전트는 **그 기기에 로그인한 테일넷 계정의 사람**으로 기록된다. Tailscale은 기기 단위로 로그인하므로, 한 기기를 여러 사람이 쓰면 사용자 B의 에이전트가 잡고 닫고 답한 것이 기기 주인 A의 이름으로 남는다. 이슈 작성자는 v0.4.68에서 이것을 관찰했다. 토큰 없이 공용 기기에서 `GET /api/meta?light=1` 을 부르면 `me` 는 A의 로그인·이름이고 역할은 `editor` 였다. 같은 요청의 `GET /pins.md` 에는 요청자를 알리는 줄이 없었다.

신원을 정하는 규칙 자체는 [api.md](../../handbook/api.md) §인증대로이고 바꾸지 않는다. 문제는 두 가지다. 에이전트가 쓰기 전에 그 사실을 알 길이 없다. 그리고 에이전트 안내(`pins.md` 머리말, SKILL)는 토큰 없는 테일넷 쓰기를 정상 경로로 권한다. 이 설계는 에이전트가 첫 `GET /pins.md` 에서 "이 요청은 누구로 기록되는가"를 읽고, 내가 일하는 사용자가 아니면 멈추고 토큰을 요청하게 한다.

## 목표

1. `GET /pins.md` 응답의 머리말에 그 요청의 신원 한 줄(`요청자:`)이 있다. 이름, 로그인, 역할, 신원 출처를 적는다. 토큰 요청이면 로그인이 `agent:<이름>` 이다.
2. 신원 출처가 사람 신원(테일넷 헤더·프록시 헤더·로컬 소유자)이면, 그 줄은 "이 사람으로 기록된다, 내가 일하는 사용자가 아니면 쓰지 말고 토큰을 요청한다"를 말한다.
3. 디스크의 `<state_dir>/pins.md` 는 같은 자리에 요청자가 없다는 고정 줄을 두고, 신원을 확인하는 방법을 알려 준다. 요청자 정보는 디스크 사본에 들어가지 않는다.
4. 토큰 없는 테일넷 쓰기를 무조건 권하던 두 문장(닫기 안내 문단, 답글 안내 줄)이 "그 사람이 내가 일하는 사용자일 때만"으로 바뀐다.
5. `pins.md` 머리말, `skill/SKILL.md`·`skill/SKILL.ko.md`, [api.md](../../handbook/api.md), [domain.md](../../handbook/domain.md)의 안내가 서로 맞는다.

## 비목표

- **안 C(토큰 필수 설정).** 브라우저가 아닌 쓰기에 토큰을 요구하는 인스턴스 설정은 만들지 않는다. 소유자가 2026-11-23 방향을 고를 때 뺐다.
- **신원 판정 규칙.** `identify()`·`admit()`·`check_role()` 과 신원 방식 표는 그대로다. 어떤 요청이 누구로 기록되는지는 바뀌지 않는다.
- **새 API 필드·경로.** `/api/meta` 의 `me` 에 신원 출처를 더하지 않는다. 새 경로도 없다. 바뀌는 것은 `pins.md` 본문뿐이다.
- **외부 협업자의 진입 방식, 핀 담당 규칙, PR 대기 상태** — [#479](https://github.com/dartworklabs/limn/issues/479)의 범위다.
- **PR #543의 접근 관리**(뷰어의 멤버·역할·`--tailnet-agent` 관리). 같은 영역이지만 그 PR의 동작과 파일 내용은 건드리지 않는다. 이 변경은 #543이 `main` 에 머지된 뒤 그 위에서 시작한다.

## 안티목표 (이것이 되면 기술적으로 작동해도 실패다)

- 디스크 사본이나 다른 사람의 응답에 어느 요청자의 로그인·이름이 새어 들어간다. 디스크 사본은 그 기기의 모든 에이전트가 읽는 공용 파일이다.
- 요청자 줄이 에이전트에게 "통과"처럼 읽힌다. 예를 들어 사람 신원일 때 경고 꼬리 없이 이름만 있으면, 에이전트는 확인했다고 여기고 그대로 쓴다.
- 기존 안내 줄의 시작 부분이나 api.md가 정한 줄 순서(원고 → 논문, 안내 문단 → claim → 인증 → 답글)가 바뀌어, 줄 시작으로 맞춰 읽는 에이전트가 줄을 놓친다.

## 소유자가 고른 것

방향(2026-11-23, 다른 세션의 선택 창): 이슈의 **안 A + 안 B**, 안 C는 하지 않는다. 방향만 승인했고 세부는 이 설계에서 정한다.

### 지켜야 할 현재 불변식

- `pins.md` 형식과 HTTP API는 다른 저장소의 에이전트가 읽는 계약이다. 더하기만 하고, 바꾸려면 설계 승인을 받는다(CLAUDE.md, workflow.md). 이 설계가 그 승인 요청이다.
- 안내 줄은 시작 부분으로 찾는다. `TOKEN_GUIDANCE` 는 뒤에만 덧붙인다(`render.py` 주석, api.md §pins.md 안내 줄).
- 줄 순서: `원고:` 바로 다음 `논문:`(api.md §머리줄 1), 안내 문단 바로 뒤에 claim 줄과 인증 줄, 그 뒤에 답글 줄(§pins.md 안내 줄).
- 디스크의 `<state_dir>/pins.md` 는 요청과 무관하게 루프백 base로 쓴다(§원격 에이전트 진입점). 다른 세션이 그 파일을 읽어도 안내가 바뀌지 않는다.
- 핀 파일은 `transact()` 의 잠금·순서로만 쓴다. 이 변경은 핀 파일을 쓰지 않는다. 디스크 `pins.md` 는 지금처럼 쓰기 뒤 렌더에서만 쓴다.
- 서버 런타임은 표준 라이브러리만 쓴다(`dependencies = []`).
- 렌더러는 순수하다. 바깥에서 오는 것은 모두 `PinsMdInput` 값으로 들어온다(`render.py` 모듈 docstring).
- 응답은 따로 주지 않으면 `Cache-Control: no-store` 다(`web/handler.py`).

### 설계 이유와 제약

- 신원은 이미 요청마다 정해져 있으므로(`GetRequest.principal`), 새 판단이나 새 파일 읽기 없이 렌더러에 값 하나를 넘기면 된다.
- `Via` 의 `header` 는 `--auth tailscale` 이면 테일넷 헤더, `--auth trusted-proxy` 이면 프록시 헤더다. 출처 이름표를 정하려면 신원 방식(`AccessSettings.auth`)도 함께 봐야 한다.
- `--tailnet-agent` 로 받은 헤더 없는 테일넷 요청도 `via == "loopback-agent"` 이고 `LOCAL_ACTOR` 다(api.md §헤더 없는 루프백 에이전트). 서버가 그 요청을 일부러 루프백 에이전트와 같은 주체로 받으므로, 이 설계도 같은 이름표를 쓴다.

### 충돌·미확인

- PR #543이 api.md §인증(검사 순서 문단, §pins.md 안내 줄의 "실행 정본" 줄)과 SKILL의 인증 표 한 줄을 고친다. 이 설계가 고칠 문단과 겹치는 것은 "실행 정본" 줄 하나다. #543 머지 뒤 그 위에서 고친다.

## 설계

### 1. 요청자 줄 (HTTP, `GET /pins.md`)

**자리.** 머리말의 `갱신:` 줄 바로 다음, 그 뒤의 빈 줄 앞이다. 문서가 하나든 여럿이든(소절 머리말이든) 같은 자리다. 줄은 늘 정확히 한 번 나온다.

**모양.**

```text
요청자: <이름>(`<로그인>`) · 역할 <역할> · 신원 출처 <출처 이름표><꼬리>
```

- `<이름>` 은 그 요청의 `actor.name`, 비었으면 로그인이다. 표 칸과 같은 정리(`md_cell`)를 거쳐 줄바꿈과 `|` 를 막는다. 길이는 신원 쪽 상한(100자)을 그대로 따른다.
- `<로그인>` 은 `actor.login` 이다. 기록되는 값이 이것이고 이름은 겹칠 수 있어서 함께 적는다. 코드 스팬 안에 두며, 로그인에 백틱이 있으면 백틱을 더 길게 둘러 깨지지 않게 한다.
- `<역할>` 은 `Principal.role`(`owner`·`editor`·`viewer`·`agent`)을 영어 그대로 적는다. API·`people.json` 과 같은 낱말이다.

**출처 이름표** (`Via` 와 신원 방식으로 정한다):

| `Via` | 신원 방식 | 출처 이름표 | 사람 신원 |
| --- | --- | --- | --- |
| `header` | `tailscale` | `테일넷 헤더(이 기기에 로그인한 테일넷 계정)` | 예 |
| `header` | `trusted-proxy` | `프록시 헤더(인증 프록시가 보낸 사용자)` | 예 |
| `local-owner` | `local` | `로컬 소유자(--auth local 의 루프백 요청)` | 예 |
| `token` | 모두 | `토큰` | 아니요 |
| `loopback-agent` | `tailscale` | `헤더 없는 루프백(폐지 예정)` | 아니요 |

`people.json` 에서 역할이 `agent` 인 사람도 출처는 헤더이고 기록은 그 사람의 로그인이므로 사람 신원으로 본다.

**꼬리.**

- 사람 신원: ` — 이 요청으로 쓰면 이 사람으로 기록된다 · 내가 일하는 사용자가 아니면 쓰지 말고 사용자에게 토큰을 요청한다(`limn token create <인스턴스>`)`
- 에이전트(토큰, 헤더 없는 루프백): ` — 이 요청으로 쓰면 에이전트로 기록된다`

예:

```text
요청자: Alice Kim(`alice@example.com`) · 역할 editor · 신원 출처 테일넷 헤더(이 기기에 로그인한 테일넷 계정) — 이 요청으로 쓰면 이 사람으로 기록된다 · 내가 일하는 사용자가 아니면 쓰지 말고 사용자에게 토큰을 요청한다(`limn token create <인스턴스>`)
요청자: reviewer(`agent:reviewer`) · 역할 agent · 신원 출처 토큰 — 이 요청으로 쓰면 에이전트로 기록된다
요청자: 로컬/에이전트(`local`) · 역할 agent · 신원 출처 헤더 없는 루프백(폐지 예정) — 이 요청으로 쓰면 에이전트로 기록된다
```

역할이 `viewer` 인 사람도 같은 꼬리를 받는다. 쓰기는 어차피 `403` 이고, 역할 칸이 그것을 보여 준다.

### 2. 디스크 사본의 줄

디스크의 `<state_dir>/pins.md` 는 같은 자리에 다음 고정 줄을 둔다. `<port>` 는 디스크 사본이 이미 쓰는 루프백 base의 포트다.

```text
요청자: 없음(디스크 사본) — 쓰는 요청의 신원은 요청마다 정해진다 · 확인하려면 쓸 때와 같은 인증으로 `curl -s http://127.0.0.1:<port>/pins.md` 를 읽어 이 줄을 본다
```

이 줄은 어떤 요청자 값도 담지 않는다. 디스크 사본을 쓰는 렌더는 요청자 없이 호출한다. 마지막으로 쓴 사람이 누구든 바이트가 같다.

### 3. 안내 두 문장 (제자리 고쳐 쓰기)

두 줄의 시작 부분(`처리한 핀은 닫는다`, `답글(0.2.2):`)은 그대로다. 바뀌는 것은 가운데 구절 하나씩이다.

닫기 안내 문단:

```text
지금: … — 테일넷 주소로 닫는 에이전트는 요청이 사람 신원을 달고 가므로 본문에 `"review":true` 를 넣는다 · 검토 대기 핀은 다시 처리하지 않는다 · …
바꿈: … — 머리말 '요청자:' 줄의 신원 출처가 사람 신원(테일넷 헤더·프록시 헤더·로컬 소유자)이면 그 사람이 내가 일하는 사용자일 때만 닫고 본문에 `"review":true` 를 넣는다(아니면 닫지 말고 토큰을 요청한다) · 검토 대기 핀은 다시 처리하지 않는다 · …
```

답글 안내 줄(`REPLY_GUIDANCE`):

```text
지금: … — 토큰 없이 사람 신원을 달고 가는 에이전트(테일넷 주소로 닫을 때 `"review":true` 를 넣는 경우, `--auth local` 의 헤더 없는 curl)는 답글 본문에 `"reopen":false` 를 넣는다 · 토큰을 쓰는 에이전트의 답글은 상태를 바꾸지 않는다
바꿈: … — 토큰 없이 사람 신원을 달고 가는 에이전트('요청자:' 줄의 신원 출처가 테일넷 헤더·프록시 헤더·로컬 소유자)는 그 사람이 내가 일하는 사용자일 때만 답글을 달고 본문에 `"reopen":false` 를 넣는다 · 토큰을 쓰는 에이전트의 답글은 상태를 바꾸지 않는다
```

두 문장은 디스크 사본과 HTTP 응답에 똑같이 나온다. 디스크 사본을 읽는 에이전트는 §2의 줄이 가리키는 대로 HTTP로 신원을 확인한다. `TOKEN_GUIDANCE` 는 바꾸지 않는다.

### 5. 구조

- **렌더러(순수).** `render.py` 에 닫힌 값 `Requester`(이름·로그인·역할·출처)와 출처 `Literal` 하나를 둔다. `PinsMdInput` 에 `requester: Requester | None` 를 더하고, 기본값은 `None` 이다. `None` 이면 §2의 디스크 줄, 값이 있으면 §1의 줄을 낸다. 문구 상수(출처 이름표, 두 꼬리, 디스크 줄)는 다른 안내 상수처럼 이 파일에 둔다.
- **조립 지점.** `PinMarkdown.current_text(base, requester)` 가 값을 받아 `pins_md_input` 으로 넘긴다. 디스크를 쓰는 `pins_md_text(pins)` 경로는 요청자를 받지 않는다. 그래서 디스크 사본에 요청자를 넣을 호출 경로가 없다.
- **경로.** `pins/listing/routes.py` 의 `/pins.md` 분기가 `request.principal` 과 신원 방식으로 `Requester` 를 만든다. `Via` 와 신원 방식을 출처로 바꾸는 함수는 `security` 쪽에 둔다. 역할·신원 비교는 `security/access.py` 밖에 두지 않는다는 architecture.md 규칙 때문이다. 정확한 자리(`Principal` 의 메서드인지, `security` 의 작은 순수 함수인지)는 계획 단계에서 경계 검사(`tools/check_boundaries.py`)에 맞춰 정한다.
- **새 파일 읽기·쓰기 없음.** 신원은 이미 정해져 있다. `people.json` 을 다시 읽지 않는다.

### 6. 보안 (신뢰 경계)

- 요청자 줄은 **그 요청의 주체에게만** 나간다. 응답은 지금처럼 `no-store` 이고, 렌더 결과를 요청 사이에 기억하는 캐시를 두지 않는다. 나중에 `pins.md` 에 캐시나 ETag를 붙인다면 요청자별로 갈라야 한다는 것을 api.md 새 절에 적는다.
- 디스크 사본에는 요청자 값이 닿는 호출 경로가 없다(§5). 시험으로도 막는다(§검증).
- 줄은 요청자 자신의 신원만 보인다. 그 사람이 이미 `/api/meta` 의 `me` 로 볼 수 있는 값이다. 다른 사람의 로그인은 나오지 않는다.
- 이름은 신원 제공자(테일넷·프록시)가 준 표시 이름이라 신뢰하지 않는 글자로 다룬다. `md_cell` 정리와 길이 상한을 거친다. 로그인은 `_identity_login` 이 이미 공백·제어 문자를 거른 값이고, 코드 스팬으로 감싼다.
- 신원 판정·입장·역할 검사는 바뀌지 않는다. 이 줄은 안내일 뿐 권한을 만들지 않는다.

### 7. 오류 처리

렌더는 전부 정의된 함수다. `Via`·출처는 닫힌 `Literal` 이라 모르는 값이 없다. 이름이 비면 로그인을 쓴다. 신원이 정해지지 않은 요청은 이미 `401`·`403` 으로 거절돼 이 경로에 오지 않는다.

## 바뀌는 계약

- **더함:** HTTP `pins.md` 의 `요청자:` 줄, 디스크 `pins.md` 의 고정 `요청자: 없음(디스크 사본)` 줄.
- **바꿈(소유자 승인 대상):** 닫기 안내 문단의 한 구절, `REPLY_GUIDANCE` 의 한 구절(§3). 두 줄의 시작 부분은 그대로다.
- **그대로:** 표의 열·번호 칸 표시·상태 이름, `TOKEN_GUIDANCE`, claim 줄, HTTP API의 경로·필드, 신원 판정.

## 검증

1. **렌더러 단위 시험.** 출처 다섯(테일넷 헤더, 프록시 헤더, 로컬 소유자, 토큰, 헤더 없는 루프백) 각각의 줄을 문자열로 확인한다. 사람 신원에만 경고 꼬리가 있는지, 요청자 없음이면 디스크 줄인지, 줄이 `갱신:` 바로 다음에 정확히 한 번 나오는지(단일·다중 문서), 이름의 `|`·줄바꿈과 로그인의 백틱이 줄을 깨지 않는지 본다.
2. **HTTP 시험(이슈의 완료 기준).** 실제 처리기로 `GET /pins.md` 를 부른다. 테일넷 헤더 요청(`Tailscale-User-Login`·`-Name`), 토큰 요청(`agent:<이름>`), 헤더 없는 루프백 요청 각각의 신원 줄을 확인한다. `--auth local` 의 소유자와 `--auth trusted-proxy` 의 프록시 헤더도 확인한다.
3. **디스크 사본이 새지 않는다.** 테일넷 헤더 요청으로 쓰기(핀 만들기)를 한 뒤 디스크의 `pins.md` 를 읽어, 그 로그인·이름이 없고 고정 줄만 있는지 확인한다. 같은 요청의 `GET /pins.md` 는 그 신원을 보인다.
4. **계약 스냅샷·옛 판 대조.** `tests/data/contract_snapshot*.json` 을 다시 만들고, 바뀐 곳이 요청자 줄 두 종류와 두 구절뿐인지 diff로 확인한다. `test_access.py` 의 v0.1 대조는 더한 줄을 지우고 바꾼 두 구절을 `replace` 로 맞추는 기존 방식대로 고친다.
5. **문서 대조.** `pins.md` 문구, `skill/SKILL.md`·`SKILL.ko.md`, api.md, domain.md가 같은 조건을 말하는지 대조한다. 두 SKILL 사이의 뜻이 맞는지 본다.
6. **실서버 확인.** 체크아웃의 서버를 루프백에 띄우고 `curl` 로 세 경우(헤더, 토큰, 헤더 없음)의 `GET /pins.md` 머리말을 읽는다. 디스크 사본도 함께 읽는다.
7. **CLAUDE.md의 검증 목록 전체**(`pytest`, `ruff`, 경계·적합도·타입 검사, `npm` 검사, `strict_ratchet`).

## ADR

ADR을 쓴다(소유자 결정). 번호는 머지 시점의 가장 큰 번호 다음이다. 상태는 `제안` 으로 시작하고, 머지하는 마지막 커밋에서 `승인됨` 으로 올린다. 승인됨이 되면 동결되어 리뷰 문구 지적을 고칠 수 없기 때문이다. 내용은 다음과 같다.

- D1 HTTP `pins.md` 의 `요청자:` 줄 — 자리, 모양, 출처 이름표, 꼬리
- D2 디스크 사본의 고정 줄과, 요청자 값이 디스크에 닿지 않는 구조
- D3 사람 신원으로 쓰는 조건 — 안내 두 구절의 제자리 고쳐 쓰기, SKILL·api.md·domain.md의 같은 조건
- 버린 대안: 인증 줄 끝 구절, 디스크 줄 없음, 옛 문장에 조건만 덧붙이기, 안 C(토큰 필수 설정)

api.md의 새 절은 이 ADR의 결정 절을 짧게 인용하되, 인용을 지워도 본문만으로 규칙이 완결되게 쓴다. `docs/adr/index.md` 에 한 행을 더한다.
