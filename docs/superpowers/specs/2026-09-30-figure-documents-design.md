# 그림 문서 — 벡터 그래픽에 핀을 찍는다 (설계 제안·핸드오버)

> **상태: D1·D5 확정([ADR-0011](../../adr/0011-figure-documents.md)).** 소유자가 목적 범위를 "LaTeX 원고와 벡터 그래픽"으로 넓히고(D1), 계약 값 목록을 늘리는 A안을 골랐다(D5). D2–D4·D6·D7은 권장안을 계획의 전제로 삼았고, 소유자가 계획을 검토할 때 확인한다. 구현 계획은 [색인](../../superpowers/plans/2026-09-30-figure-documents.md)에서 시작한다. 이 문서는 구현을 이어받을 사람과 에이전트를 위한 핸드오버다. 승인 전에는 생산 코드, 에이전트 계약(`pins.md`·HTTP API), 저장 형식을 바꾸지 않는다. Limn의 목적 범위([purpose.md](../../handbook/purpose.md) §지원 범위)를 넓히고 에이전트 계약에 값을 더하므로 HARD-GATE에 걸린다([workflow.md](../../handbook/workflow.md) §기본 경로). 승인되면 결정을 ADR로 먼저 박고 그다음 구현 계획을 쓴다.

## 이 문서를 이어받는 법

1. §목적과 범위와 §사용 흐름을 읽고 무엇을 만드는지 잡는다.
2. §결정할 것의 D1–D7에 소유자 답을 받는다. 답이 권장안과 다르면 이 문서를 먼저 고친다.
3. D1을 ADR로 박는다(목적 범위 확장과 문서 종류 추가).
4. §이행 절단면의 P0부터 `docs/superpowers/plans/`에 계획을 쓰고 [workflow.md](../../handbook/workflow.md) §기본 경로를 따른다.

§현재 코드의 이음매의 파일·줄 인용은 `main` `5d1c4b6` 기준이다. 구현 전에 다시 확인한다.

## 목적과 범위

Limn은 원고에서 위치 찾기 비용을 줄인다. 사람이 PDF 위를 드래그하면 SyncTeX가 `.tex` 파일·줄을 돌려준다. 에이전트는 헤매지 않고 그 줄을 고친다.

논문 그림에도 같은 비용이 있다. 요즘 논문 그림은 코드가 그린다. 파이썬 스크립트가 SVG·PDF를 쓰고, 공통 부품(노드·범례·달력 칸 같은 컴포넌트)을 불러 조립한다. "B2 그림의 7월 칸 글자가 작다"는 요청을 받으면, 에이전트는 그 칸을 그린 호출이 어느 파일 몇째 줄인지 찾아야 한다. 지금은 두 방법뿐이다.

- **스크린샷에 박스를 그려 채팅에 붙인다.** 사람 손이 많이 가고, 요청이 수명 주기 없이 대화에 흩어진다.
- **디자인 도구(예: Figma)에 올린 사본에 댓글을 단다.** 댓글은 도구 안의 노드에 붙는다. 그런데 그 노드는 SVG를 가져온 이름 없는 벡터 조각이라 원본 코드로 돌아가는 길이 없다. 그림을 고쳐 다시 올리면 노드가 바뀌어 댓글이 떨어진다.

**목표.** 그림 한 장 위의 드래그를 **그 부분을 그린 코드의 파일·줄과 요소**로 되돌려 준다. 그 결과는 지금의 핀 수명 주기(담당·처리 중·닫기·답글·검토)로 처리한다. 원고의 SyncTeX 자리에는 **그림 생산자가 내는 요소 지도**가 들어간다.

**비범위.**

| 비범위 | 이유 |
| --- | --- |
| 디자인 도구 화면 위의 핀 | 그 화면은 다른 출처의 앱이라 Limn이 위에 핀을 그리거나 드래그 좌표를 읽을 수 없다. 보는 사람마다 로그인도 필요하다 |
| Limn이 그림을 렌더하는 것 | 파이썬·브라우저 렌더 도구를 서버에 들이지 않는다. 렌더는 그림 저장소의 일이다(D3) |
| 그림 편집기 | 서버는 원본을 고치지 않는다([architecture.md](../../handbook/architecture.md) §5. 원본 원고는 서버가 고치지 않는다) |
| 요소 지도가 없는 그림 | 사진이나 받은 래스터 그림이다. 지금의 보기 전용 PDF로 충분하다 |

## 핵심 결정 — 그림을 PDF로 받는다

그림을 새 매체로 받지 않는다. **그림 한 장을 PDF 한 쪽으로 받는다.** 그림 저장소는 파일 두 개를 낸다.

| 파일 | 내용 |
| --- | --- |
| `figures.pdf` | 그림 한 장 = 한 쪽. 책갈피(outline) 이름은 그림 번호와 제목 |
| `figures.limnmap.json` | 쪽마다 요소 목록. 요소 id, 쪽 위 영역(`frac`), 그 요소를 그린 코드의 파일·줄 |

PNG 한 장이 아니라 PDF인 이유는 뷰어다. 지금 뷰어는 `/pdf`를 받아 PDF.js로 벡터를 그리고 쪽 수를 맞춰 보고 목차를 만든다(`viewer/js/pdf-open.js:26-56`). PNG 문서를 들이면 이 경로를 끄고 오류 칩을 피하는 분기를 뷰어 곳곳에 넣어야 한다. PDF로 받으면 다음을 그대로 쓴다.

| 이미 있는 것 | 그림 문서에서의 쓰임 |
| --- | --- |
| PDF.js 벡터 렌더링, 확대, 쪽 이동, 목차 | 그림을 선명하게 확대한다. 책갈피가 곧 그림 목록이다 |
| 보기 전용 PDF의 감시와 다시 그리기(`features/builds/engine.py:307-354`) | 빌드 버튼이 없다. 그림 저장소가 새 PDF를 쓰면 화면이 바뀐다 |
| 쪽 폴더 버전(`pages-<ts>/`, `pages.cur`), 빌드 이력, 위치 추정(`est`) | 핀의 화면 위치와 빌드 신원 |
| 줄 핀의 anchor 재동기화(`pins/position.py:265-310`) | 핀이 가리키는 `.py` 줄이 에이전트 수정으로 밀려도 따라간다. anchor는 머리·꼬리 줄의 텍스트라 언어를 가리지 않는다 |
| 문서 전환, 핀 번호 유일성, 사람, 토큰, `pins.md` | 그림 핀도 같은 번호 공간과 같은 에이전트 진입점을 쓴다 |

새로 필요한 것은 다섯이다.

- 문서 종류 `figure`
- 지도를 빌드마다 보관하는 가져오기 빌드
- 지도로 되짚는 pick
- 읽을 때 계산하는 요소 위치
- 계약 값 추가

## 사용 흐름

한 논문 저장소의 인스턴스가 이미 떠 있고, 본문·하이라이트·커버레터 탭이 있다고 둔다.

**한 번만 하는 것.** 그림 저장소의 렌더 명령(예: `make figures`)이 `figures.pdf`와 `figures.limnmap.json`을 낸다. 인스턴스 설정의 문서 목록(`DOCS=`)에 지도 파일을 한 항목 더한다(`fig=그림:figures/out/figures.limnmap.json`). 확장자로 그림 문서임을 알아본다(D2). 새 앱·새 주소·새 포트는 없다.

1. **기동.** 평소대로 인스턴스를 연다. 문서 줄에 `그림` 탭이 생긴다.
2. **불러오기.** `그림` 탭을 누르면 첫 그림이 한 쪽으로 뜬다. 목차에서 그림 번호로 옮겨 간다. 그림 저장소가 다시 렌더하면 몇 초 안에 화면이 바뀐다.
3. **핀.** 고칠 곳을 드래그한다. 작성 패널에 되짚은 결과가 뜬다.
   - 요소 윤곽이 그림 위에 겹쳐 보인다.
   - 위치 줄은 `B2 › 달력 › 7월 칸 · src/B2_calendar.py:88–95` 형식이다.
   - 범위 사다리는 요소 → 부품 → 패널 → 그림 순서다. 단계를 바꿀 때 서버에 다시 묻지 않는다.
   - 메모를 쓰고 보낸다. 결정 단계는 원고 핀과 같다.
4. **수정.** 에이전트는 `pins.md`에서 핀을 읽는다. 그림 핀의 행에는 요소 경로와 파일·줄이 있다. 에이전트는 핀을 가져가(claim) 그 줄을 고치고, 그림을 다시 렌더해 커밋한 뒤 답글과 커밋을 남기고 닫는다.
5. **확인.** Limn이 새 PDF와 지도를 가져와 쪽을 다시 그린다. 핀 표시는 요소 id로 새 자리를 따라간다. 사람은 고친 그림을 보고 확인하거나, 답글로 다시 연다.

원고에 들어간 그림을 본문 탭에서 찍으면 지금처럼 `\includegraphics` 줄로 되짚는다. 그 핀을 그림 요소까지 이어 주는 일은 P3에서 다룬다.

## 생산자 계약 — 요소 지도 (`limn-figure-map/1`)

지도는 그림 저장소가 쓰고 Limn이 읽는다. Limn은 지도를 만든 도구를 모른다. 파이썬 SVG 도구든 matplotlib이든 같은 형식으로 내면 된다.

```json
{
  "format": "limn-figure-map/1",
  "pdf": "figures.pdf",
  "pdf_sha256": "9f2c…",
  "pages": [
    {
      "page": 1,
      "figure": "B2",
      "title": "Deployment calendar",
      "elements": [
        {"id": "B2", "frac": [0, 0, 1, 1],
         "src": {"file": "src/B2_calendar.py", "lo": 12, "hi": 140}},
        {"id": "B2/calendar", "parent": "B2", "part": "CalendarStrip", "label": "달력",
         "frac": [0.06, 0.18, 0.88, 0.12],
         "src": {"file": "src/B2_calendar.py", "lo": 80, "hi": 97}},
        {"id": "B2/calendar/m07", "parent": "B2/calendar", "part": "MonthCell", "label": "7월",
         "frac": [0.47, 0.18, 0.07, 0.12],
         "src": {"file": "src/B2_calendar.py", "lo": 88, "hi": 95},
         "impl": {"file": "lib/components.py", "lo": 410, "hi": 470}}
      ]
    }
  ]
}
```

| 필드 | 규칙 |
| --- | --- |
| `pdf` | 지도 파일 기준 상대 경로. 문서 폴더 안이어야 한다 |
| `pdf_sha256` | 지도가 설명하는 PDF 바이트의 해시다. 생산자는 PDF를 먼저 쓰고 지도를 나중에 쓴다. 그래서 지도가 아직 옛 PDF를 가리키는 순간이 생긴다. 지금 PDF와 해시가 다르면 Limn은 가져오기를 미룬다 |
| `page`, `figure` | 쪽 번호는 1부터 센다. `figure`는 그림 id이고, 쪽 순서가 바뀌어도 같다 |
| `id` | **렌더를 거듭해도 같아야 한다.** 그리는 순서나 카운터가 아니라 뜻에서 만든다(`B2/calendar/m07`). 지도 안에서 유일하다. 핀이 렌더를 건너 따라가는 열쇠다 |
| `parent` | 요소 나무를 이룬다. 쪽마다 뿌리 요소가 하나 있다. 뿌리의 `id`는 그림 id, `frac`은 쪽 전체다 |
| `frac` | `[x, y, w, h]`. 쪽 폭·높이에 대한 비율이고 원점은 왼쪽 위다. 핀의 `frac`과 같은 규약이다(`viewer/js/selection.js:74`) |
| `src` | 그 요소를 **부른 자리**다. 곧 그림 스크립트의 호출이며, 핀의 `file`·`lo`·`hi`가 된다. 경로는 문서 폴더 기준 상대 경로다. 코드로 그린 그림이면 필수다. 코드 줄이 없는 벡터 그래픽(디자인 도구에서 내보낸 그림)은 생략한다. 그 요소의 핀은 영역 모양(`pdf` + `el`)이 된다(D7) |
| `impl` | 선택 필드. 요소를 **구현한 자리**, 곧 공통 부품의 정의다. 요청이 한 그림이 아니라 공통 모양에 관한 것일 때 에이전트가 참고한다 |
| `part`, `label` | 선택 필드. 사람에게 보이는 이름이다. `label`은 원고 핀에서 인용 글자(`quote`)가 하던 역할을 한다 |

생산자가 지킬 것은 셋이다.

- **쓰는 순서.** PDF를 먼저 쓰고, 지도는 마지막에 원자적으로 교체한다(임시 파일에 쓰고 rename).
- **id 안정성.** 같은 뜻의 요소는 다음 렌더에서도 같은 id를 받는다. id가 바뀌면 핀 표시가 요소를 잃는다.
- **경로.** `pdf`·`src`·`impl`의 파일은 문서 폴더 안에 있어야 한다. 밖이면 Limn은 원고 밖 파일과 같이 거절한다.

## 서버

### 문서 종류

`Doc.kind`는 지금 `"tex"`와 `"pdf"` 둘이다(`documents.py:72,159-161`). 여기에 `"figure"`를 더한다. 그런데 두 번째 종류는 참·거짓 값 `is_pdf` 하나로 약 25곳에서 갈린다. 그림 문서는 이 값 하나에 맞지 않는다. 빌드는 보기 전용 PDF처럼 가져오기이고, 핀은 LaTeX처럼 줄 핀이기 때문이다. 그래서 먼저 `is_pdf`를 능력 값으로 바꾼다(P0).

| 능력 | tex | pdf | figure |
| --- | --- | --- | --- |
| 원본에서 빌드한다(latexmk, `--git-pull`, 재빌드 요청) | 예 | 아니요 | 아니요 |
| 감시로 가져온다(보기 전용 감시 스레드) | 아니요 | 예 | 예 |
| 줄 핀을 받는다(`file`·`lo`·`hi`, anchor 재동기화) | 예 | 아니요 | 예 |
| 변경 보기(`.tex` 이력, latexdiff) | 예 | 아니요 | P2 |

`is_pdf`는 없앤다. API의 `view_only`(`/api/docs`·`/api/meta`·보기 전용 pick 응답)는 `Doc.view_only`에서 나오고 바이트가 그대로다.

### 가져오기 빌드

보기 전용 PDF의 다시 그리기(`render_pdf_doc`, `engine.py:307-332`)를 본뜬다.

1. 감시 스레드가 지도와 그 지도가 가리키는 PDF의 `mtime:크기`를 본다.
2. 바뀌었으면 지도를 읽어 검사하고, `pdf_sha256`이 지금 PDF와 맞는지 본다. 맞지 않으면 이번 차례를 건너뛴다.
3. `pages-<ts>/`에 쪽 이미지를 그리고 PDF를 복사한다. **지도도 그 폴더에 복사한다.** 옛 빌드 화면에서 한 드래그는 그 빌드의 지도로 되짚어야 하기 때문이다(`build.py:176-186`의 PDF 복사와 같은 이유).
4. `pages.cur`를 바꾸고, 빌드 이력의 `src_hash`에 PDF와 지도의 해시를 적는다.

그러면 빌드 진행 표시, `build_seq`, `est`, 뷰어의 쪽 교체가 그대로 돈다. 재빌드 요청(`POST /api/rebuild`)은 보기 전용 PDF처럼 `400`이다. Limn은 그림 저장소의 코드를 실행하지 않는다.

### pick — 지도로 되짚기

`POST /api/pick`의 요청 형식은 그대로다(`{page, x0, y0, x1, y1, frac, pdf_build, doc}`). 그림 문서면 `pdf_build`의 쪽 폴더에 있는 지도로 되짚는다. 판단은 파일을 읽지 않는 순수 함수(`figmap.py`, `mapping.py` 옆)로 둔다. 입력은 쪽의 요소 목록과 드래그 영역 `D`이고, 출력은 줄 결과 값 또는 거절 값이다.

1. 요소 `E`마다 `cover = |E∩D| / |D|`를 잰다. 드래그가 요소 안에 든 몫이다.
2. 뿌리를 뺀 요소 가운데 `cover ≥ 0.6`인 것 중 가장 깊은 것을 고른다. 뿌리는 쪽 전체라 `cover`가 늘 1이므로 이 단계와 다음 단계에서 경쟁하지 않는다. 깊이가 같으면 넓이가 작은 것을 고른다. 작은 드래그나 클릭에 가까운 선택은 잎 요소로 간다.
3. 그런 요소가 없으면 드래그가 여러 요소에 걸친 경우다. 뿌리를 뺀 요소 가운데 `fill = |E∩D| / |E| ≥ 0.5`인 것들의 가장 가까운 공통 조상을 고른다.
4. 그것도 없으면 쪽의 뿌리 요소, 곧 그림 전체를 고른다.
5. 고른 요소에서 뿌리까지 올라가며 범위 사다리 `levels`를 만든다. `src`가 같은 단계는 지금처럼 하나로 합치고 `merged`로 표시한다.
6. `via`는 `map`, `score`는 고른 요소의 `cover`다. 점수가 낮으면 지금과 같은 경고 문구를 붙인다.

지도가 없거나 검사를 어기면 보기 전용 PDF처럼 영역만 돌려주고(`PickedRegion`), `warn`에 그 이유를 싣는다.

### 핀 저장

그림 핀은 **줄 핀**이다. `file`·`lo`·`hi`가 있고, 지금의 줄 핀 검증과 anchor 재동기화를 그대로 받는다. 더하는 필드는 하나다(D4).

| 필드 | 뜻 |
| --- | --- |
| `el` | `{id, path, label, part, impl, frac}`. `path`는 뿌리부터 이어지는 id 목록이고, `frac`은 찍은 빌드에서 그 요소의 영역이다. 읽을 때 계산하는 위치는 이 값과 비교한다. 정확한 모양은 [계획 색인](../plans/2026-09-30-figure-documents.md) §Pin record (P1b)다 |

`page`·`frac`·`pdf_build`는 지금처럼 **찍은 때**의 화면 위치와 빌드다. 어느 지도로 찍었는지는 `pdf_build`가 이미 말해 준다.

### 요소 위치는 읽을 때 계산한다

그림 핀의 위치는 두 가지 이유로 바뀔 수 있고, 각각 다른 방법으로 따라간다.

| 무엇이 바뀌나 | 어떻게 따라가나 |
| --- | --- |
| 에이전트가 스크립트를 고쳐 줄이 밀린다 | 지금의 anchor 재동기화가 트랜잭션 안에서 한다(`store.py:199-221`). 결과는 `ok`·`moved +n`·`lost` 그대로다 |
| 다시 렌더해 요소가 자리를 옮긴다 | **읽을 때 계산한다.** 지금 빌드의 지도에서 `el.id`를 찾아 `mark`(현재 영역)와 `el_sync`(`ok`·`moved`·`lost`)를 핀 응답에 붙인다. `est`를 계산하는 자리(`pins/view.py:76-101`)와 같은 곳이다 |

두 번째를 저장하지 않는 이유가 있다. 트랜잭션 안에서 `frac`·`page`를 고쳐 쓰면 `rev`가 오르고, 편집 중인 사람의 저장이 `409`로 거절된다(`features/pins/editing/rules.py:324`). 저장하지 않으면 되돌리기도 쉽다. 옛 서버로 되돌려도 레코드는 찍은 때의 값 그대로다.

요소를 찾은 핀은 점선(추정)이 되지 않는다. 뷰어는 `mark`가 있으면 그 영역에 핀을 그린다. `el_sync`가 `lost`인 핀은 `위치 잃음`처럼 드러내고, `pins.md`에 경고를 단다.

### 경계

원고 저장소를 믿는 코드로 보는 가정([build-sync.md](../../handbook/build-sync.md) §신뢰 가정 — 원고 저장소는 믿는 코드다)을 지도에도 쓴다. 그래도 서버는 지도를 파싱할 때 다음을 검사한다. 어긴 지도는 없는 것으로 보고 영역 핀으로 떨어지며, 핀을 망가뜨리지 않는다.

- 파일 크기와 쪽당 요소 수에 상한이 있다.
- `frac`은 0–1 범위의 유한수다. 판정은 `pins/shapes.py`의 `is_finite_num`으로 한다.
- `id`는 지도 안에서 유일하다.
- `parent`는 같은 쪽의 요소를 가리키고 순환이 없다.
- 모든 경로는 문서 폴더 안이다.

SVG는 서버가 내주지 않는다. SVG는 스크립트를 품을 수 있어서 화면에는 PDF만 그린다. 지도 읽기는 가장자리(빌드 가져오기)에서 하고, 판단 함수는 파일을 모른다([ADR-0009](../../adr/0009-backend-vertical-slices.md)).

## 뷰어

- **문서 탭.** 그림 문서는 보기 전용 PDF처럼 재빌드 버튼이 없다. 문서 목록에 `그림` 표시를 단다.
- **작성 패널.** 되짚은 요소의 윤곽을 쪽 위에 겹쳐 그린다. 위치 줄은 요소 경로와 `파일:줄`이다. 범위 사다리의 단계 이름은 요소의 `label`이고, 없으면 `part`다. 지금 작성 패널의 분기는 영역이냐 줄이냐 하나뿐이다(`isRegion`). 그림 핀은 줄 쪽에 요소 표시만 더한다.
- **핀 표시.** `mark`가 있으면 그 영역에, 없으면 `frac`에 그린다(`viewer/js/list.js:108-116`).
- **보내기.** `save.js:34-36`과 `repick.js:25-28`이 `el`을 함께 보낸다.
- **변경 보기(P2).** 지금은 `.tex` 이력만 본다(`features/revisions/core.py:295-322`). 그림 문서는 지도에 나오는 `src`·`impl` 파일의 이력을 본다. 비교는 latexdiff 대신 이전 빌드의 쪽과 지금 쪽을 겹쳐 보인다.

## 에이전트 계약

[api.md](../../handbook/api.md)의 필드 이름과 상태 이름은 바꾸지 않는다. 더하는 것은 두 종류다.

**순수한 추가.** 옛 에이전트와 옛 상태 폴더에 영향이 없다.

- `POST /api/pick` 응답: 그림 문서에서만 `el`이 붙는다. `levels`의 각 단계에도 그 단계 요소의 `el`이 붙는다.
- `POST /api/pin` 허용 필드: `el`이 는다(`features/pins/editing/input.py:17-33`).
- `GET /api/pins`: 계산 필드 `mark`·`el_sync`가 는다.
- `pins.md`: 그림 핀은 지금 열(위치·쪽·범위)에 그대로 실린다. 여기에 요소 `label`을 `«…»`로 늘 싣는다. `impl`이 있으면 "공통 부품: `파일:줄`"을 덧붙인다. 그림 핀이 있을 때만 안내 줄을 하나 더한다(`pins/render.py:466-470`과 같은 방식).
- SKILL(두 벌): 그림 핀 처리 규칙을 더한다.
  - `src` 줄을 고친다.
  - 여러 그림에 같은 문제가 있는 공통 모양의 요청이면, 한 그림만 덮어쓰는 편법을 쓰지 말고 사람에게 묻는다. `impl`을 고치면 모든 그림이 바뀐다.
  - 닫기 전에 다시 렌더한다. 그래야 사람이 고친 그림을 보고 확인한다.

**값 목록이 느는 것 (D5).** 필드를 더하는 것은 분명한 "더하기"다. 그런데 이미 있는 필드가 받는 **값 목록**에 값을 더하는 것은 경계에 있다. 모양은 그대로지만, 그 목록이 전부라고 믿고 짠 소비자는 새 값을 잘못 분류한다. 그래서 따로 결정한다.

그림 문서가 건드리는 값 목록은 넷이다.

| 값 목록 | 지금 | 그림이 필요로 하는 것 | 권장 |
| --- | --- | --- | --- |
| 문서 `kind`(`/api/docs`·`/api/meta`) | `tex`·`pdf`. 함께 오는 `view_only`는 `kind == "pdf"`와 같다(`api.md` §엔드포인트) | 그림 문서라는 표시 | `figure`를 더하고 `view_only:false`로 둔다 |
| 범위 단계 `scope`·`levels[].level` | `raw`·`para`·`env`·`env2`·`env3`·`lines`의 닫힌 목록. 입력은 `bad_scope`로 거절한다(`pins/edit.py:13`) | 요소 → 상위 요소 → 그림의 사다리 | `el`·`el2`·`el3`… 와 뿌리 `fig`를 더한다. `env`·`env2`·`env3`과 같은 짜임이다 |
| 핀 `kind`(범위 종류) | 이미 열린 목록이다. `env:<이름>`처럼 이름이 붙고, 모르는 값은 원문 그대로 둔다(`api.md` §핀 레코드 스키마) | 어떤 요소인지 | `el:<부품>`(`el:MonthCell`)과 `figure`. 지금 규칙 안에 든다 |
| `via` | `synctex`·`text`의 닫힌 목록. 입력은 `bad_via`로 거절한다(`web/parse.py:29`) | 지도로 되짚었다는 표시 | `map`을 더한다 |

**값을 늘려도 저장은 안전하다.** 확인한 사실은 셋이다.

- 레코드 검사(`pins/record.py`의 `fits_record`)는 `kind`·`via`·`scope`가 문자열인지만 본다. 옛 서버가 `el2`·`map`을 만나도 깨진 줄로 보지 않는다.
- 저장소는 모르는 필드를 바이트 그대로 되쓴다(`pins/model.py` 모듈 설명). 옛 서버로 되돌려도 `el`이 남는다.
- `pins.md`의 범위 칸(`pins/render.py`의 `range_label`)은 모르는 `scope`면 `kind`를 그대로 싣는다. 옛 서버도 `el:MonthCell`로 보인다.

**위험은 소비자 쪽에 있다.** 목록이 전부라고 가정한 에이전트나 스크립트다. 실제 예가 SKILL에 있다. SKILL은 "원고를 고쳤으면 그 문서의 PDF를 재빌드한다. 보기 전용 문서는 재빌드가 없다"고 가르친다. 그림 문서는 `view_only:false`이므로, 옛 SKILL을 따른 에이전트는 그림을 고친 뒤 `POST /api/rebuild`를 부르고 `400`을 받는다. 피해는 없지만 헛걸음이다. 그래서 SKILL 두 벌을 같은 변경에서 고친다. 새 규칙은 "그림 문서는 재빌드하지 않는다. 그림 저장소에서 다시 렌더한다"다.

**다른 길 — 값은 그대로 두고 필드만 더하기.** 예를 들어 문서는 `kind:"pdf"`에 `figure:true`를, 단계는 `env` 이름을 빌려 쓰는 방식이다. 목록이 안 늘어서 옛 소비자가 새 값을 볼 일이 없다. 대신 그림 문서가 "보기 전용 PDF인데 줄 핀이 있다"는 모순된 모양이 된다. 그림의 상위 요소가 `env:CalendarStrip`처럼 LaTeX 환경인 척 실린다. 이러면 뜻이 흐려져 새 에이전트까지 헷갈린다. 권하지 않는다.

**앞선 권장을 고친다.** 이 문서의 첫 판은 `via`를 싣지 말자고 했다. 목록을 늘리지 않으려는 이유였다. 위 확인으로 저장과 되돌리기가 안전하다는 것을 봤으므로, 어느 경로로 찾았는지를 드러내는 `map`을 더하는 쪽으로 바꾼다. 뷰어의 '위치 불확실' 배지도 찾은 방법으로 `지도`를 보인다.

그림 핀에는 `file`·`lo`·`hi`가 있으므로, 그림을 모르는 에이전트도 줄 핀으로 처리할 수 있다.

## 통합인가, 별도 앱인가

통합한다. 핀 저장소만 나눠 쓰는 별도 앱은 비용이 더 클 뿐 아니라 안전하지도 않다.

| 접근 | 얻는 점 | 비용과 선택 |
| --- | --- | --- |
| **Limn 안의 문서 종류 `figure`** | 주소·핀 번호·사람·토큰·`pins.md`·SKILL이 하나다. "#12 처리해줘"가 모호하지 않다. PDF.js 뷰어, 보기 전용 감시, 줄 anchor를 다시 쓴다. 원고 탭과 그림 탭을 오간다 | 목적 범위 확장(ADR), P0 능력 값 정리, pick 분기 하나, 읽을 때 계산하는 필드, 계약 값 추가. **권장** |
| 같은 핀 파일을 쓰는 별도 앱 | 릴리스가 독립적이고 Limn 목적을 건드리지 않는다 | 핀 잠금은 프로세스 안의 `threading.RLock`이다(`server.py:162`, `store.py:110-123`). 프로세스 사이 잠금(`files.py:64-74`)은 사람·토큰·감사 기록만 덮는다. 두 프로세스가 핀 파일을 쓰면 불변식 4가 깨져 쓰기가 사라진다. 번호 발급(`pins.seq`)과 `pins.md` 렌더도 쓰는 쪽이 하나라고 가정한다. **채택하지 않는다** |
| 핀 파일까지 따로 둔 별도 앱 | 안전하다 | 인증·토큰·사람·수명 주기·뷰어를 복제한다. 주소가 둘이고 번호 공간이 갈린다. "앱 이름은 Limn 하나"라는 불변식과 부딪힌다. **채택하지 않는다** |
| Limn 밖 갤러리에 좌표 댓글만 | 오늘 만들 수 있다 | 수명 주기와 에이전트 계약이 없다. 승인 전 임시로만 쓴다 |
| 디자인 도구 댓글 API로 연동 | 디자이너가 익숙한 곳에서 쓴다 | 서버에 외부 자격증명이 필요하다. 댓글이 원본 코드가 아니라 사본 노드에 붙는다. 비범위 |

**규모 추정.**

- 새 모듈 약 4개: `figmap.py`, `features/pins/location/figure.py`, `features/builds/figure.py`, `viewer/js/figure.js`. 테스트 파일도 약 4개다.
- 고치는 곳
  - 백엔드 약 25파일: 대부분 `is_pdf` 자리의 1–10줄 분기다.
  - 뷰어 약 12파일: 조각 목록, CSS, `ui_en.json`을 포함한다.
  - 문서 약 10개: Handbook topic, SKILL 두 벌, CHANGELOG다.

[ADR-0009](../../adr/0009-backend-vertical-slices.md)는 한 동작의 주인이 둘인 것을 금한다. 그래서 그림 pick은 `features/pins/location`에, 가져오기 빌드는 `features/builds`에 둔다.

**위험한 자리.**

1. **`is_pdf` 분기의 누락.** 하나라도 빠뜨리면 그림 문서를 LaTeX로 오인한다. 예를 들어 latexmk를 돌리고(`features/builds/service.py:54`), pull·재빌드하고(`features/sync/run.py:232`), `.tex` 이력에 latexdiff를 돌린다(`features/revisions/core.py:300`). 에이전트 요청의 파일이 엉뚱한 문서로 가기도 한다(`documents.py:209`). 그래서 P0에서 능력 값으로 먼저 바꾸고, 동작 불변을 테스트로 증명한다.
2. **레코드 유효성.** `pins/record.py:58-86`과 `features/pins/editing/rules.py`다. 버그가 데이터를 잃는 유일한 자리다.

4. **빌드별 지도 보관과 지문.** `build.py:58-60,548-604`다.
5. **작성 패널의 영역·줄 분기.** `viewer/js/composer.js`다.

## 이행 절단면

1. **P0 — 능력 값으로 바꾸기(구조 이동).** `is_pdf` 분기를 능력 값으로 바꾼다. 동작은 바꾸지 않으며, 계약 스냅숏과 전체 테스트로 증명한다([ADR-0001](../../adr/0001-blueprint.md) 구조 이동 우선).
2. **P1 — 그림 문서와 지도 pick.** 다음을 한 묶음으로 넣는다.
   - 등록, 가져오기 빌드, 지도 검사, pick 순수 함수
   - 핀 필드 `el`, 읽기 계산 필드 `mark`·`el_sync`
   - `pins.md` 그림 행, 뷰어의 요소 윤곽과 위치 줄, SKILL 두 벌
   - 계약 스냅숏에 그림 흐름 추가. 옛 상태 폴더의 바이트 왕복은 그대로여야 한다.
3. **P2 — 변경 보기.** 지도에 나오는 파일의 이력을 보이고, 이전 빌드 쪽과 지금 쪽을 겹쳐 비교한다.
4. **P3 — 원고 속 그림으로 잇기(탐색).** 본문 탭의 핀이 `\includegraphics`로 넣은 지도 달린 PDF 위에 있으면, 그 그림의 요소까지 되짚는다. 쪽 위에 그림이 놓인 상자를 SyncTeX 상자 기록에서 얻을 수 있는지 버릴 브랜치에서 먼저 확인한다.
5. **P4 — 디자인 도구 내보내기(보류).** D7.

P1은 새 문서 종류와 계약 추가를 묶으므로 마이너 버전으로 낸다. P0과 P2 이후의 작은 추가는 패치 버전이다.

## 합격 기준

- 지도 파일을 `DOCS=`에 더하면 그림 탭이 뜬다. 드래그하면 요소 경로와 `파일:줄`이 돌아온다. 점, 작은 상자, 여러 요소에 걸친 상자에서 모두 결정적인 결과가 나온다.
- 지도가 없거나 해시가 틀리거나 검사를 어기면 영역 핀으로 떨어지고 경고를 싣는다. 서버는 예외로 죽지 않는다.
- 그림 핀은 `pins.md`에 파일·줄·요소로 실린다. 그림을 모르는 에이전트도 줄 핀으로 처리한다.
- 스크립트 수정으로 줄이 밀리면 anchor가 따라간다. 다시 렌더해 요소가 옮기면 핀 표시가 새 영역으로 간다. id가 사라지면 `el_sync: lost`로 드러난다. 어느 경우에도 핀의 `rev`는 렌더 때문에 오르지 않는다.
- 옛 상태 폴더, 옛 핀, 계약 스냅숏이 그대로다. 그림 핀이 있는 상태 폴더를 옛 버전 서버로 열어도 레코드가 지워지지 않는다. 런타임 의존성은 늘지 않는다.
- [verification.md](../../handbook/verification.md)의 파이썬 테스트, 셸 테스트, Ruff, mypy가 녹색이다. 뷰어 변경은 실측으로 확인한다.
- 같은 변경에서 purpose·domain·build-sync·api·viewer·instances topic과 index 파일 지도를 현재형으로 고친다.

## 충돌·미확인

- **목적 문장.** [purpose.md](../../handbook/purpose.md)는 Limn을 "LaTeX 논문 원고와 PDF 뷰어 사이를 잇는" 도구로 적고 Typst를 범위 밖에 둔다. D1이 결정됐으므로 ADR을 박고, 구현하는 변경에서 이 문장과 §지원 범위를 "LaTeX 원고와 벡터 그래픽"으로 고친다.
- **옛 서버로 되돌릴 때.** 옛 서버는 `.limnmap.json` 문서 항목을 모른다. 되돌릴 때는 그 항목을 설정에서 뺀다. 그러면 그림 핀은 "설정에 없는 문서" 핀으로 남는다([domain.md](../../handbook/domain.md) §여러 문서). 옛 서버가 모르는 필드 `el`을 다시 쓸 때 보존하는지는 P1에서 테스트로 확인한다.
- **anchor의 주석 줄.** `anchor_of`는 `%`로 시작하는 줄을 건너뛴다. 파이썬 파일에서는 `#` 주석 줄을 건너뛰지 않아도 동작은 하지만, 주석을 머리 줄로 떠서 약해질 수 있다. 규칙을 문서 종류별로 둘지 정한다.
- **문서 폴더의 겹침.** 그림 폴더가 LaTeX 문서의 빌드 루트 안에 있으면, 파일에서 문서를 찾는 규칙(`documents.py:198-218`)이 두 문서를 모두 후보로 본다. 가장 깊은 폴더가 이기게 할지 확인한다.
- **P3의 그림 상자.** SyncTeX가 `\includegraphics` 상자의 쪽 위 위치를 충분히 정확하게 주는지는 확인하지 않았다.
- **첫 사용처.** 한 논문 저장소의 개념도 도구다(파이썬 → SVG → PDF, 공통 컴포넌트 층). 지도를 내는 일은 그 저장소의 몫이다. 컴포넌트는 이미 레이아웃으로 자기 영역을 알고 있어서, 호출 자리만 기록하면 지도가 나온다.
