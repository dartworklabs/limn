# 백엔드 VSA 점진 이행 설계

> **상태: 확정·점진 구현 중.** 이 문서는 목표 구조와 이행 경계를 정한다. 현재 실행 구조의 정본은 `src/limn/`과 System Handbook이다.

## 목적과 성공 기준

사용자가 줄이려는 비용은 파일의 행 수 자체보다 **논리적 불협화음과 인지부하**다. 지금은 핀 하나를 닫는 동작을 이해하려면 `web/handler.py` → `web/parse.py` → `server.py`의 전달 메서드와 `PinContext` → `service/transitions.py` → `pins/lifecycle.py` → `store.py` → `web/answers.py`를 따라가야 한다. `web/app.py`의 `App`은 55개 메서드를 요구하고 `ServerApplication`은 108개 메서드를 품는다. 책임별 모듈은 분리됐으나 사용자 동작의 소유자는 한눈에 드러나지 않는다.

목표는 **백엔드의 사용자 동작을 기능별 세로 슬라이스가 소유하는 구조로 끝까지 옮기는 것**이다. 한 번에 재작성하지 않고, 완료된 슬라이스마다 병합 가능한 작은 변경을 만든다. 완료 시 한 동작의 경로·입력·판단·부수효과·응답을 같은 기능 패키지에서 찾을 수 있고, 공통 보안 검사와 저장 순서는 한 곳에서만 집행된다. 단일 패키지 배포와 표준 라이브러리 전용 런타임은 유지한다.

행 수 감소만으로 성공을 판정하지 않는다. 기존 메서드를 새 객체에 복사하고 이전 전달 메서드를 남기거나, 같은 규칙을 여러 슬라이스에 복제하면 실패다. 각 완료된 슬라이스에는 단일 코드 소유자와 제거된 옛 진입점이 있어야 한다.

### 지켜야 할 현재 불변식

1. 모든 요청은 공통 본문 읽기 → Host/Origin → 신원 → 입장 → POST 역할 검사를 지나고, 거절은 닫힌 방향으로 실패한다. 슬라이스가 이 검사를 우회하는 경로를 등록하지 않는다.
2. 모든 핀 파일 쓰기는 `PinStore.transact()`의 잠금·재동기화·준비·원자적 쓰기 순서를 따른다. 알림·감사와 저장의 현재 순서도 유지한다.
3. HTTP API, `pins.md`, 저장 레코드와 옛 상태 디렉터리의 읽기, 원본 원고를 수정하지 않는 규칙은 바꾸지 않는다.
4. 실행마다 설정·잠금·캐시·스레드·문서와 처리기 바인딩이 분리된다. import만으로 자원을 만들지 않고, 정상 종료와 시작 실패 모두 자기 실행의 자원을 정리한다.
5. 런타임 외부 의존성을 더하지 않고, `web/`과 기능 슬라이스가 `server.py`를 가져오지 않는다. 순수 판단 코드는 파일·subprocess·HTTP를 가져오지 않는다.

### 결정 맥락

`ADR-0001`은 2026-09-25 작성, 2026-09-26 확정됐다. 1차 구조로 책임별 모듈을 채택하고 VSA를 명시적으로 제외했다. 이 문서는 그 결정을 조용히 재해석하지 않는다. 확정된 `ADR-0009`가 **축 1(1차 구조)만 부분 대체**하고, 코드가 옮겨진 범위부터 적용한다. `ADR-0001`의 단일 배포, 실용적 함수형 규칙, 검수와 시간축 호환 결정은 유지한다. 2026-09-27에 구현된 명시적 서버 앱 설계도 현재 실재다. 목표 VSA는 그 실행별 소유권을 보존하면서 앱의 기능별 전달 표면을 줄인다.

### 충돌·미확인

- 구조 선택의 기존 근거는 기능보다 핀 도메인·저장·빌드·HTTP의 변경 이유가 다르다는 것이었다. VSA에서도 이 경계는 사라지지 않고 **슬라이스 안의 순수 규칙·부수효과 셸·HTTP 입구**로 남는다. 실제 공동 소유가 필요한 코드만 공통 핵심으로 둔다.
- 로컬 전체 pytest는 설계 조사 시 1,827개 통과, 11개 건너뜀이다. TeX 도구와 실제 상태 디렉터리를 필요로 하는 건너뜀은 통과 증거가 아니다. 이행 PR은 CI의 해당 게이트로 확인한다.

## 목표 구조

백엔드의 기본 탐색 단위는 HTTP 층이나 순수 함수 층이 아니라 **사용자가 요청하는 동작 묶음**이다. 다음은 목표 소유권을 보여 주는 구조이며 파일명은 각 슬라이스의 첫 계획에서 확정한다.

```text
src/limn/
  server.py                 실행 설정·자원 생성, 기능 등록, 시작·종료
  web/                      공통 HTTP 프레이밍·보안 가드·디스패치·전송
  access.py                 공통 신원·입장·역할 검사
  store.py                  핀 파일의 단일 트랜잭션 경계
  files.py, documents.py    여러 기능이 실제로 함께 쓰는 파일·문서 기본 규칙
  pins/model.py             여러 핀 슬라이스가 함께 쓰는 상태 타입과 옛 레코드 왕복
  features/
    pins/lifecycle/         닫기·다시 열기·확인·답글·claim
    pins/editing/           만들기·편집·담당·메모
    pins/location/          PDF 역변환·위치 선택·anchor 재동기화
    pins/listing/           핀 조회·pins.md·겹침 표시
    pins/trash/             삭제·복원·영구 삭제·전체 비우기
    builds/                 LaTeX/PDF 빌드·페이지·목차·상태
    revisions/              Git 이력·핀 범위 diff·비교 PDF
    sync/                   git pull·원격 main 감시
    collaboration/          사람 목록·멘션·이벤트·감사
    administration/         serve 설정·인스턴스·토큰/멤버 CLI·이전
```

각 HTTP 슬라이스는 자기 경로의 요청 파싱, 동작, 성공·거절 응답을 소유한다. 순수 판단과 부수효과가 둘 다 필요하면 같은 슬라이스 안에서 파일을 나누고, 안쪽 판단은 HTTP와 파일을 모른다. 한 슬라이스의 코드가 다른 슬라이스의 내부 파일을 직접 가져오지 않는다. 실제 소비자가 둘 이상이고 같은 불변식을 집행해야 하는 타입·저장·보안·문서 규칙만 공통 핵심에 둔다. `viewer/` 정적 자산과 번들 vendor는 이 백엔드 이행의 대상이 아니다.

`server.py`는 실행별 `RunConfig`·`Runtime`·문서와 슬라이스의 좁은 협력자를 조립한다. HTTP 처리기는 본문과 요청 보안 가드를 **한 번** 적용한 뒤 해당 슬라이스에 위임한다. 기능 경로는 실행별 협력자를 등록 시점에 받으며, 모듈 전역 앱이나 동적 service locator를 조회하지 않는다. 이행 초반에는 현재 처리기의 경로 분기를 유지하고 해당 분기가 슬라이스의 HTTP 함수로 위임할 수 있다. 마지막 슬라이스가 옮겨진 뒤 공통 처리기를 전송·가드·디스패치만 하는 상태로 정리한다. 경로 등록 순서와 fallback은 현재 HTTP 응답과 동일해야 한다.

평평한 `App` 프로토콜과 `ServerApplication`의 기능별 전달 메서드는 슬라이스가 끝날 때마다 함께 줄인다. 새 슬라이스와 옛 메서드가 같은 동작의 두 권위가 된 중간 상태는 병합하지 않는다. 현재 테스트가 앱 메서드를 교체하는 경우에는 해당 슬라이스의 명시적 협력자 주입으로 옮기되, 실패 주입과 관찰 결과는 보존한다.

## 대표 흐름: 핀 닫기

현재 경로는 `Handler._pin_action` → `parse_close` → `ServerApplication.close_pin`/`pin_context` → `service.transitions.close_pin` → `pins.lifecycle` → `PinStore.transact` → `answers.state_answer`다.

목표 경로는 공통 HTTP 가드 → `features/pins/lifecycle`의 닫기 입구(파싱·응답) → 같은 슬라이스의 동작(실행별 자원으로 트랜잭션·알림) → 같은 슬라이스의 순수 상태 전이 → 공통 `PinStore.transact`다. 요청의 `review` 기본값은 현재 `Principal.review_on_close`가 결정하는 값을 그대로 쓴다. 닫힌 핀의 재닫기와 권한 거절은 같은 결과·상태 코드·바이트를 낸다. `ServerApplication.close_pin`과 `web/app.py`의 해당 평면 메서드는 슬라이스가 소유권을 얻은 변경에서 지운다.

## 이행 단위와 순서

이 문서는 **전체 백엔드의 목표와 이행 규칙**을 승인 대상으로 삼는다. 전체를 한 구현 계획이나 PR로 만들지 않는다. 첫 묶음의 구체 설계는 [핀 닫기·다시 열기·확인 VSA 첫 슬라이스](2026-09-28-pin-lifecycle-vsa-design.md)다. 각 묶음은 별도 spec → 계획 → 작은 시공·검수 흐름을 가지며, 앞 묶음의 실제 결과에 따라 세부 파일 배치를 조정한다.

| 순서 | 묶음 | 완료 조건 |
| --- | --- | --- |
| 1 | 핀 수명 주기의 닫기·다시 열기·확인 | 세 경로의 HTTP·판단·부수효과 소유자가 슬라이스에 있고, 기존 전달 메서드는 제거됐다. 계약과 저장 바이트가 같다. |
| 2 | 수명 주기의 답글·claim, 핀 만들기·편집, 휴지통 | 각 동작의 한 권위와 `transact()` 진입이 보이고, 멘션·알림 순서가 유지된다. |
| 3 | 위치 찾기·재동기화와 핀 조회·`pins.md` | SyncTeX/텍스트 후보와 옛 핀 경로 읽기, `pins.md` 바이트와 모든 조회 응답이 같다. |
| 4 | 빌드·원고 상태, Git 동기화, 이력·비교 PDF | 문서별 빌드 잠금과 감시 작업 수명, 비교 작업의 캐시·실패 결과가 유지된다. |
| 5 | 사람·멘션·이벤트·감사와 운영 CLI | 보안 검사와 감사 순서, CLI 출력·종료 코드가 유지된다. |
| 6 | 공통 처리기·조립 지점 정리 | 기능별 분기가 공통 `web/`과 `server.py`에서 없어지고, 모든 백엔드 동작에 슬라이스 소유자가 있다. |

첫 묶음 안에서도 PR을 나눌 수 있다. 먼저 닫기 경로의 소유권과 차등 비교를 확보하고, 같은 패턴으로 다시 열기와 확인을 옮긴다. 각 PR은 완전한 실행 경로 하나의 단일 소유자를 남기며, 옛 함수와 새 함수의 이중 권위를 병합하지 않는다. 이행 중 아직 옮기지 않은 동작이 옛 책임별 모듈을 쓰는 것은 허용한다. 이미 옮긴 동작이 옛 HTTP 파서·응답·전달 메서드에 의존하는 상태를 완료로 부르지 않는다.

## 검증과 문서 동기화

- 첫 시공 전에 옮길 경로의 허용·거절·낡은 레코드·저장·알림 경우를 적고, 기준 커밋과 변경을 **서로 다른 프로세스**에서 실행해 상태 코드·헤더(시계성 헤더 제외)·본문·상태 파일 바이트와 권한을 비교한다. 비교가 문구 또는 필드 순서의 고의 변경을 실제로 잡는지도 확인한다.
- 계약 스냅숏, 해당 기능 테스트, 공통 요청 가드 순서·두 실행 격리·저장 순서 테스트를 유지한다. 구조만 바뀐 PR에서는 출력 스냅숏을 재기록하지 않는다. 테스트가 내부 함수명에만 묶여 있다면 같은 실패 주입과 관찰 가능한 동작을 새 경계에서 지킨다.
- 모든 PR에서 적용 가능한 pytest, 셸 테스트, Ruff, mypy를 실행한다. TeX·비교 PDF 등 CI 전용 게이트와 로컬 건너뜀을 구분해 보고한다.
- 완료된 슬라이스마다 `architecture.md`의 현재 구조, `index.md`의 파일 지도, 관련 `domain.md`·`build-sync.md`·`api.md`·`verification.md`의 **현재 상태 설명**을 코드와 맞춘다. 계약 자체가 그대로라면 `api.md`의 계약 값은 바꾸지 않는다. 이행 경위·수치·차등 비교는 PR에 둔다.

## 전체 이행 완료 판정

1. 백엔드의 모든 HTTP·CLI 사용자 동작에 기능 슬라이스 하나가 소유자로 지정되어 있다. 공통 `web/`, `server.py`와 기본 모듈에는 전송·보안·저장·실행 수명 등 실제 공통 규칙만 남는다.
2. `ServerApplication`의 기능별 전달 메서드와 55개 메서드의 평면 `App` 계약이 사라지고, 실행별 자원 소유권과 처리기 격리는 유지된다. 단순 이름 변경이나 전달 객체의 증가는 완료로 세지 않는다.
3. 사용자와 에이전트가 관찰하는 계약·저장 바이트는 기준과 같고, 각 슬라이스의 차등 비교·회귀 테스트·정적 게이트가 통과한다. `ADR-0009`와 Handbook의 채택한 구조가 실행 코드와 일치한다.
