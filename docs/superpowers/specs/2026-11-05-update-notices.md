# 보고 있는 사람에게 새 소식 알리기 (제안)

> **상태: 제안(2026-11-05).** 소유자의 질문 "보고 있는 동안 새 업데이트가 들어오면 알려 줄 수 있나? 머지될 때만? 공저자가 표시할 때도?"에 답하는 설계와 PoC다. PoC 브랜치는 `poc/update-notices`(기준 `origin/main` ea798484, 0.4.51)이고 테일넷 PoC를 띄웠다. 에이전트 계약(HTTP API·`pins.md`)·저장 형식·보안 경계는 바꾸지 않는다(결정 1). 화면이 바뀌므로 `main` 에 넣기 전에 네 기기군 PoC를 보인다([workflow.md](../../handbook/workflow.md) §화면 변경은 PoC를 먼저 보인다).

## 문제

뷰어는 다른 사람과 에이전트, 저장소가 만든 변화를 대부분 조용히 화면에 반영한다. 쪽은 제자리에서 바뀌고 카드는 목록에 끼어든다. 알리는 것도 6초 뒤 사라지거나, 브라우저 알림 스위치를 켠 기기에만 온다. 그래서 원고를 읽는 사람은 무엇이 바뀌었는지, 누가 무엇을 남겼는지 모르고 지나간다. 가장 위험한 경우는 Limn 자체가 업데이트됐을 때다. 열린 탭은 옛 뷰어 코드로 새 서버와 말하는데, 그 사실을 아무도 말하지 않는다.

"머지될 때만?"에 대한 답부터 적는다. 인스턴스가 보여 주는 것은 서버 체크아웃의 `main` 이다(`--git-pull` 이 60초마다 fast-forward 한다, [build-sync.md](../../handbook/build-sync.md) §재빌드 전 원격 main 당겨오기 (`--git-pull`)). 그래서 문서가 바뀌는 사건은 머지만이 아니다. PR 없이 `main` 에 올린 커밋, 서버 작업 트리에서 직접 고친 파일, 다시 가져온 그림과 PDF도 같은 "문서가 바뀌었다"다. 반대로 아직 머지되지 않은 PR 브랜치는 인스턴스가 보여 주지 않으므로 알릴 것이 없다. "이 문서에 PR이 열렸다"는 GitHub 접근이 필요하고 서버에는 그 자격 증명이 없다(Limn은 바깥 서비스를 부르지 않는다). 이 설계의 범위 밖이다.

공저자가 표시하는 경우도 알린다. 새 핀, 답글, 닫기·확인·다시 열기·삭제가 모두 해당한다. 다만 나와 관계된 것과 아닌 것을 갈라 소음을 줄인다.

## 제안

**알리는 길은 기존 상태 줄 하나다.** 새 상자·패널·토스트를 만들지 않는다. 데스크톱은 상태 칩 아래 줄, 폴더블 펼친 화면은 동작 줄 가운데, 휴대폰·태블릿 시트는 시트 위 24px 줄이다. 좁은 줄은 제목만 보이므로 제목을 짧게 쓴다(`본문이 바뀌었습니다`, `새 핀 #14`). 나머지는 설명과 `+N` 목록이 맡는다.

**같은 일은 한 줄로 모은다.** 메시지마다 묶음 열쇠(`upd:<문서>`, `new:<문서>`, `ev:<이벤트 종류>`, `done`, `review` …)가 있다. 같은 열쇠의 메시지가 줄에 있으면 새 사건은 그 메시지에 합쳐지고, 메시지는 전체를 다시 말하며 가장 새것으로 선다. 에이전트가 핀 12개를 하나씩 닫으면 메시지가 12개 생기는 대신 한 줄이 자란다. 지나가는 메시지(6초)는 합쳐질 때 창이 다시 시작한다.

**줄의 차례를 지킨다.** 새 소식은 줄에 서 있는 되돌리기 뒤에 선다. 되돌리기는 6초 창 동안 누를 수 있는 자리에 있어야 한다(§알림 자리 원칙 2). 다른 문서의 소식은 이 문서의 것 뒤에 서고, 돌아왔을 때 모은 것은 이미 줄에 있는 메시지 뒤에 선다. 줄의 다섯 개 한도는 자리가 아니라 온 때로 가장 오래된 정보부터 내보낸다. PoC에서 공저자의 새 판정이 [되돌리기]를 `+N` 뒤로 밀어낸 것을 보고 정한 규칙이다.

**문서가 바뀌면 "봤다"까지 남는다.** 문서의 변경은 그 문서를 보는 모두에게 해당하지만 읽는 흐름을 끊을 정도는 아니다. 그래서 자리만 차지하고 기다린다. [x]나 동작을 누르면 그때 본 것으로 이 브라우저의 `localStorage`(`limnSeen`)에 적는다. 적지 않은 변경은 새로 고쳐도, 다른 문서로 갔다 와도, 며칠 뒤 열어도 다시 말한다. 무엇이 바뀌었는지는 본 커밋과 지금 커밋 사이의 `GET /api/revisions` 행에서 센다. squash 머지의 `(#12)` 와 머지 커밋의 `Merge pull request #12` 가 PR 번호다. [변경 보기]는 변경 보기를 그 범위의 소스 diff로 연다. Markdown·텍스트 문서는 뷰어가 앞뒤 원문을 다 가지고 있으므로 줄 단위로 비교해 바뀐 줄을 칠하고 [바뀐 곳]으로 간다.

**나와 관계된 것은 스위치와 무관하게 탭 안에서 말한다.** 사람의 탭은 늘 `ev=<커서>` 를 붙여 폴링한다. 브라우저 알림 스위치는 탭이 앞에 없을 때 시스템 알림을 띄울지만 정한다. 커서는 이 브라우저에 남으므로 다음 방문은 그사이 온 것(서버가 싣는 최근 20건)을 말한다. 로컬 신원은 지금처럼 이벤트가 없다.

**Limn 업데이트는 상태다.** 화면은 자기 버전을 안다([더보기] 아래의 `v0.4.51`). 연결이 끊겼다 돌아올 때, 탭에 돌아올 때, 그리고 1분마다 `GET /api/version` 을 묻는다. 다르면 상태 줄이 새로 고칠 때까지 말한다. 자동으로 새로 고치지 않는다. 쓰던 글을 잃을 수 있기 때문이다.

**돌아오면 한 줄로 말한다.** 마지막 답 뒤 2분이 지났으면(숨긴 탭, 잠든 기기, 끊긴 연결) 돌아온 첫 폴링과 그것이 시작한 빌드·문서 확인이 말하는 것을 잠깐(2.5초, 길어도 8초) 모아 한 줄로 말한다. 오류와 되돌리기는 모으지 않는다. 오류는 지금 보이는 곳에 나와야 하기 때문이다(§알림 자리 원칙 1).

## 결정

추천안을 첫째에 둔다.

1. **계약을 더하지 않는다.** 문서의 변경은 이미 있는 빌드·`sync`·`/api/revisions`·`/api/source` 로, 새 핀은 목록 비교로, 버전은 `/api/version` 으로 말한다. GET은 여전히 아무것도 쓰지 않는다([ADR-0027](../../adr/0027-get-write-guard.md)). 대안 A: 라이트 meta에 `version` 을 더한다. 요청이 하나 줄지만 계약이 바뀌고 승인이 필요하다. 대안 B: 이벤트에 `created`·`updated` 종류를 더한다. 탭이 닫힌 사람에게도 시스템 알림을 줄 수 있지만, 공저자의 모든 핀이 모든 사람에게 가는 이벤트가 되고 `events.jsonl` 의 5000건 창이 빨리 찬다. 결정 근거는 [ADR-0033](../../adr/0033-update-notices-from-existing-reads.md).
2. **"본 것"은 기기마다 둔다.** `limnSeen` 은 브라우저의 `localStorage` 에 문서별 마지막으로 본 판(`ver`: 화면 빌드 또는 원문 mtime)과 그때의 최신 커밋(`rev`), 그리고 알린 가장 큰 핀 번호(`pin`)를 둔다. 처음 온 기기는 지금 것을 본 것으로 하고 아무것도 말하지 않는다. 대안: 서버에 사람별로 둔다. 기기를 바꿔도 이어지지만 GET이 아닌 쓰기 경로와 저장 형식이 새로 필요하다.
3. **문서 변경은 [x]나 동작까지 남는다.** 대안 A: 6초(지금). 읽던 사람이 놓친다. 대안 B: 쪽 위에 띠를 띄운다. 토스트와 같은 문제(일어난 자리와 떨어져 떠 있다)가 있고 소유자가 띠를 원하지 않는다.
4. **내가 아닌 사람의 새 핀은 알리고, 남의 핀의 답글·수정은 알리지 않는다.** 새 핀은 원고의 새 지적이라 공저자 모두에게 뜻이 있다. 남의 핀의 답글은 대개 에이전트와 그 작성자의 대화다. 대안: 카드에 `새로` 배지를 단다(기기마다 본 기록 필요, 이후 단계).
5. **나와 관계된 이벤트는 스위치와 무관하게 탭 안에서 말한다.** 대안: 지금처럼 스위치를 켠 기기만. 스위치를 모르는 공저자는 자기를 부른 것을 끝내 모른다.
6. **같은 종류는 한 줄로 모은다**(묶음 열쇠). 대안: 한 번 읽은 목록 안에서만 묶는다(지금). 폴링을 가로지르는 연속 사건이 쌓인다.
7. **Limn 업데이트는 상태 줄의 상태 항목이고 자동으로 새로 고치지 않는다.** 대안: 새로 고침을 강제한다. 쓰던 답글·수정 카드를 잃는다(작성 패널의 초안과 읽던 자리는 `sessionStorage` 에 남지만 답글 초안은 메모리에만 있다).
8. **돌아오면 모아서 한 줄로 말한다**(2분). 대안: 하나씩 다시 말한다(지금). 다섯 개를 넘으면 앞의 것이 사라지고 화면 낭독기는 여러 번 읽는다.
9. **문서 변경은 시스템 알림을 띄우지 않는다.** 탭 밖의 사람은 돌아왔을 때 한 줄로 듣는다. 대안: 스위치와 별도로 "문서 변경도 알림" 설정을 둔다(기기마다).

화면 낭독기: 나와 관계된 것과 문서 변경, 모은 한 줄, Limn 업데이트는 정중하게(`#sr-news`, 상태 줄의 `.st-sr`) 읽는다. 합쳐질 때는 글이 바뀐 때만 다시 읽는다. 오류는 지금처럼 단언(`#sr-alert`)이다.

## 열린 결정

소유자가 정할 것만 적는다.

1. **계약을 더하지 않는다(결정 1).** 추천: 그대로. 지금 읽기만으로 모든 경우를 말할 수 있고 승인·호환 부담이 없다.
2. **문서 변경은 [x]까지 남고 "봤다"를 기기마다 적는다(결정 2·3).** 추천: 그대로. 읽던 사람이 놓치지 않고, 서버 쓰기가 없다.
3. **남의 새 핀은 알리고, 남의 핀 답글은 알리지 않는다(결정 4).** 추천: 그대로. 새 지적은 모두의 일이고 남의 대화는 소음이다.
4. **나와 관계된 이벤트는 스위치와 무관하게 탭 안에서 말한다(결정 5).** 추천: 그대로. 스위치를 모르는 공저자도 자기를 부른 것을 본다.
5. **브라우저(시스템) 알림의 범위는 지금 여섯 이벤트 그대로(결정 9).** 추천: 그대로. 문서 변경까지 시스템 알림으로 보내면 머지마다 모두에게 간다.
6. **돌아오면 모아 한 줄로(결정 8), 기준 2분.** 추천: 그대로. 다섯 개 한도에서 밀려나 사라지는 일이 없다.
7. **Limn 업데이트는 새로 고침을 권하기만 한다(결정 7).** 추천: 그대로. 쓰던 답글을 잃지 않는다.
8. **기기 설정을 더하지 않는다.** 추천: 지금은 없음. 묶음과 [x]로 소음이 충분히 줄고, 설정은 쓰임을 보고 더한다.
